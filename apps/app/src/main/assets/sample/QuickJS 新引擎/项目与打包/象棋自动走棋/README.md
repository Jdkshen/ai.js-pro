# 象棋自动走棋 · QuickJS 工程骨架

中国象棋自动走棋工程的**落点**：FEN / 棋盘几何 / 格线自动定位 / 格点分配 / 时序融合 / 棋规与合法着法 /
**识别链路（模型随包）** / **本机算棋** / **自动执行（票据 + 点击 + 落子确认）** 都是真代码。
界面上的状态文案与这里保持一致，不会把"还没做"写成"已经能用"。

## 现在有什么

- `project.json`：QuickJS 工程（`engine: quickjs`、`uiMode: true`、保留 OpenCV 模块）。
- `main.js`：界面 + 三个模式（① 只识别 / ② 着法建议 / ③ 自动走棋）+ 单次操作入口
  （「运行离线自检」「查看运行环境」「定位棋盘（真机）/（图片）」「识别棋盘 → FEN」「算棋」）。
  只有③会点棋盘，而且必须同时满足轮次/局面/几何/票据/着法条件。
- `src/automation/`（P4）：
  - `move-ticket.js`：动作票据 —— 会话/局面版本/方向/模型版本/几何版本/有效期全部绑在一张票上，
    出手前重新核对（思考中棋盘变了、换局、换模型、过期一律作废）。
  - `click-executor.js`：把格点换成当前几何下的屏幕坐标并按压；**只识别/建议模式用显式禁用的桩**
    （调用即计数报错，验收 A05 查的就是这个计数）；起点之后、终点之前再查一次取消。
  - `move-verifier.js`：用**新观测**判定落子：CONFIRMED / 对方已应手 / 仍没动 / 无法解释 / 看不清；
    「点击函数返回成功」与「棋子真的走了」分开统计。
  - `state-machine.js`：状态机 + 出手条件 + 两条看门狗（轮次未知超时、确认超时）。纯逻辑，
    离线自检里直接覆盖 S01–S04 / A01–A05。
  - `auto-driver.js`：把状态机的「动作清单」执行掉（定位/算棋/点击/确认），并按 `transition.infer` 推轮次。
- `tools/p4-scan.js`：真机识别调参（在真实棋局上试几组 confidence/cropMargin，打印未知格数）。
- `tools/p4-move-probe2.js`：**前台对照版点击探针**（等 dumpsys 确认游戏在前台再注入两步；
  通道/走法从 `/sdcard/xiangqi-p4/who.txt`、`move.txt` 读）。
- `tools/p4-shift-scan-file.js`：**离线**几何偏移扫描（只读一张已保存截图，扫 ±20px 看未知格怎么变）。
- `tools/p4-calibrate-check.js`：离线验收会话级几何校准（校准前/后的未知格与偏移）。
- `tools/p4-align-check.js`：离线对照「按残差自动对齐」的效果（结论：残差最小 ≠ 未知格最少）。
- `tools/p4-capture-wait.js`：截图会话就绪性探针（量「多少次/多少毫秒才出第一帧」）。
- `src/chess/fen.js`：FEN 生成 / 解析 / 静态校验（不设少子残局门槛，未知轮次不塞 side）。
- `src/chess/rules.js`：兵种走法（蹩马腿、塞象眼、炮架、九宫、过河、兵卒方向）与将帅照面/被将判断。
- `src/chess/legal-moves.js`：完整合法着法（过滤自将与照面）、着法比对、局面差异。
- `src/chess/transition.js`：由「上一局面 + 新观测」推断发生了什么（唯一着法 / 己方着法+对方应手 / 未知）。
- `src/vision/geometry.js`：规范交点 ↔ 屏幕坐标、180° 方向映射、稳健拟合（含离群点剔除）。
- `src/vision/board-locator.js`：亮度**支撑度**扫线（比暗线投影耐噪）+ 格点阵拟合（能补回被棋子压住的线、
  并按棋盘范围锚定序号）+ 1px 细扫精修；失败就明确要求手动校准（四点起），不给假几何。
- `src/vision/cell-assignment.js`：检测框 → 90 个交点，保留候选/冲突/残差，不硬猜。
- `src/vision/temporal-fusion.js`：有时间跨度的多帧融合，版本变化即作废历史。
- `src/vision/piece-side.js`：阵营判定 —— 模型只有 7 个兵种类别（无颜色），靠数「红笔画 / 黑笔画」补红黑。
- `src/vision/recognizer.js`：识别链路（裁剪 → 检测 → 落格 → 判色 → FEN 布局），裁剪/检测/取像素都是**注入**的，
  所以离线自检里能用桩跑完整条链路（含错误分支）。
- `src/runtime/aijs-adapter.js`：**唯一**直接调用宿主接口的地方（截图/裁剪/取像素/模型加载/路径解析），能力缺失如实上报。
- `tools/self-check.js` 离线自检；`tools/runtime-probe.js` P0 运行时探针；`tools/locate-board.js` 真机定位；
  `tools/recognize-board.js` 真机识别（定位 + 识别 → FEN）。
- `assets/models/`：**象棋模型已随包**（`chessai_160.onnx` 9.65MB + `chessai_160.txt`），见其中的 `README.md`。

## 自动走棋（P4）怎么跑、卡在哪

流程：先选模式（①/②/③）→ 选我方颜色 → 点「开始观察」→ **切到棋局画面**（脚本在后台继续跑）
→ 回到本页面会自动交回界面控制（按钮重新可用）。

- **轮次怎么来**：画面里没有「轮到谁」。第一次观察到的局面是**标准开局**就按红先；否则需要用户
  点「现在轮到我」声明一次，之后用 `transition.infer` 沿合法着法链推。推不出来就一直等/恢复，
  **轮次未知超时不会出手**。
- **循环写法**：用 `sleep` 分片的手动循环，**不要用 `setInterval`** —— 真机实测（K40）应用切到后台后
  定时器不再被派发，自动走棋会停在最后一帧（YOLO 持续识别 用的也是 sleep 循环）。
  代价：循环期间界面按钮不响应，回到本页面会自动退出循环交回控制。
- **点击的三个前提**：截图授权、**无障碍服务已开启**（`auto.service` 就绪，否则 `press/click` 一律失败）、
  悬浮窗权限（只在画计划框时需要，没有也能走棋）。
- **出手闸门**：稳定局面里还有未知格 / 有冲突 / 几何不可信 → 不算棋、不出手（这是设计，不是 bug）。

K40（cccc62c7）+ 腾讯天天象棋实测（2026-09-13，engine dev-568/569/570）：

| 项 | 结果 |
|---|---|
| 离线自检（PC 与真机 QuickJS） | `SELF_CHECK OK passed=105 failed=0`（含 30 条 P4 用例）|
| 棋盘定位（真实棋局） | ok：起点 (81,666) 格距 (115,114)，残差 0.016 格 |
| 单帧识别（同一局面） | 检测 32–38 框，**恒定有 6 个未知格**（第 0 行的相/士两对、第 9 行左侧车）|
| **几何校准后**（见下节） | 未知格 **6 → 1**（偏移 dx=-11, dy=-4）|
| 建议/自动模式 | 因未知格 > 0 → 正确拒绝算棋与出手；点击计数 0（禁用桩 0 次调用）|
| **真机点击（Shizuku 通道）** | ✅ **成功落子**：`shell("input tap x y",{shizuku:true})` 点炮二平五 → 棋盘实测 红炮 在 (第4列,第7行)、游戏「2步」、黑方已应着 |
| **真机点击（无障碍通道）** | ✅ **同样成功**：`press(x,y,120)` 走 馬二进三 → 馬 从 (1,9) 消失、出现在 (2,7) |
| 截图会话（MediaProjection） | ⚠️ 脆弱：会话在应用切前台/后台变化时会被 MIUI 移除（`removeMediaProjection`），之后连续 31s 都是 `Timed out waiting for the first screen capture frame` |
| **截图回退通道（Shizuku screencap）** | ✅ **实测可用**：`shell("screencap -p /sdcard/aijspro-capture-0.png",{shizuku:true})` + `images.read` → 真实全分辨率帧（1080×2400，棋盘色 `#f0d5ac`），不需要任何授权、不会被作废；代价约 **0.6–1.4s/帧** |

### 截图会话挂了怎么办：自动换通道（不用人工重新授权）

`aijs-adapter.capture()` 现在有**两条通道**，默认 `auto`：

1. `screen` = 宿主的 `captureScreen()`（MediaProjection）—— 快（几毫秒），但要授权、且会被系统移除；
2. `shell` = **用 Shizuku/root 跑 `screencap -p` 再 `images.read` 读回来** —— 慢（K40 实测 0.6–1.4s/帧），
   但**不需要授权、也不会被系统悄悄作废**（等同 `adb shell screencap`，只是身份换成 shell）。

`auto` 的行为：先用 `screen`，**失败（超时/被移除）自动改走 `shell`**；`requestCapture()` 在 shell 通道下直接返回
true（不弹授权框），授权被拒时 auto 也不会提前失败。没有 Shizuku/root 的设备只能靠人工重新授权，
错误信息里会写明这一点。界面加了「截图通道」按钮可强制指定（自动 / 系统截屏 / screencap）。

验收探针：`tools/p4-capture-fallback.js`（实测输出 `capture ok=true 实际通道=shizuku` + `recognize ok=true`）。
⚠️ 用 shell 通道时**每帧 1 秒起**，所以自动走棋的节奏会明显变慢（`tickMs` 要放宽），
且它与点击共用同一个 shell 通道（串行执行）。

### 点击通道的结论（之前搞错了，这里更正）

**「游戏会忽略无障碍注入」这个结论是错的**：之前的点击探针是在**我们自己的 RunIntentActivity 还在前台**
时注入的，触摸被我们自己的窗口吃掉，所以看起来「返回 true 但没反应」。
把游戏真正切到前台再注入（并且**用 dumpsys 判断前台，不能用 `currentPackage()`** ——
MIUI 游戏加速的悬浮侧栏会让 a11y 一直报 `com.miui.securitycenter`），两条通道都能落子：

- Shizuku：`shell("input tap x y", {shizuku:true})`，以 shell 身份注入，K40 上 `uid=2000`、含 `1004(input)` 组；
- 无障碍：`press(x, y, 120)`（前提是 `auto.service` 就绪）。

复现工具：`tools/p4-move-probe2.js`（前台对照版，走法/通道从 `/sdcard/xiangqi-p4/{who,move}.txt` 读）。

### 那 6 个未知格：一半是几何，不是模型

`tools/p4-shift-scan-file.js`（**离线**版本，只读一张已保存的截图，不碰屏幕截图）把定位原点
在 ±20px 内平移扫描，逐个统计未知格：

| 偏移 | 未知格 |
|---|---|
| (0,0)（定位原样） | 6 |
| (-7,-14) | **1** |

也就是说定位给出的原点有**约 10px 的系统性偏差**，边角格的裁剪框偏出去 → 模型看不见。
`recognize-board.calibrateGrid()` 把这个搜索做成**会话级校准**：按「**最终未知格数**」打分
（**不能**按几何残差 —— 残差最小的偏移是 (+3,+6)，未知格仍是 6），每个候选跑一次完整识别，
一局只做一次（十几次推理约 2 秒）。③ 模式的定位回调已经接上它（`main.js` 的 `locate`）。

剩下 1–2 格未知 + 少量错认（把「炮五」认成第 2 列的炮、漏一个士）仍然是**模型在皮肤上的能力**问题：
要彻底通 ③ 模式，仍需用这套皮肤的截图人工核对标签后微调（不能自标），或按构造器口径重训 320 档。

## 硬性约束

- **多文件工程必须从磁盘运行**：`require('./src/xx.js')` 的模块加载器只认磁盘路径（`files.read`）。
  所以：资源页的「运行」会把工程拷到临时目录再跑（保证是最新内置代码，且不动用户导入的副本）；
  要自己改代码就先「打开文件夹」导入到脚本目录，从文件页运行；
  打包成独立 APK 时运行端会把整棵工程拷到 `filesDir/project/` 再启动，所以工程里用 `require` **没问题**。
- **完全本地**：不做云库、远程推理、远程棋力；不添加 `INTERNET` 权限。资源随包提供，断网可用。
- **权限**：本工程在 `permissionConfig.manifestPermissions` 里明确声明 5 条
  （存储读写 / 悬浮窗 / WakeLock / 震动），**不含** `INTERNET`、`ACCESS_NETWORK_STATE`。
  打包页以工程声明为准；模板自带的那 16 条只在工程没写这段时才是默认值。
- **模型契约**：`yolo.load({ backend: 'dnn' })` 走 OpenCV DNN，当前只适配固定输入、六列输出
  （`[x1,y1,x2,y2,score,classId]`）的 YOLO26 类模型；非六列输出必须先按 `decoder` 显式解码，
  不能靠"总元素能除以 6"猜。
- **不要用 COCO 模型冒充象棋模型**：内置的 `yolo26_160/640.onnx` 是通用目标模型，能加载不等于能识别红车黑炮。
- **点击前置条件**：轮次未知、局面不可靠、票据过期时一律不许点击（详见任务书的状态机一节）。
- **棋盘范围（region）的契约**：**紧贴棋盘外沿，误差 ≤ 半个格距**。格线自动定位靠它给格点定序号
  （最外圈那条线经常被棋子压住而扫不到），范围给大了会选错序号、整盘错一整行；
  对不齐时宁可报失败并提示改人工校准。
