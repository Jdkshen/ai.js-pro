# AI.js Pro MCP 逆向能力优化建议

> **文档性质：开发建议与实战复盘，不代表下述功能已经实现。**
>
> 依据：本次 SonicTopography 交接补全与“影安加固-测试demo”定位过程中实际调用工具得到的反馈。
>
> 优先级：P0＝可靠性与正确性；P1＝定位效率与动态观测；P2＝高级辅助与工作流。

---

## 1. 核心结论

当前 MCP 已经具备较完整的逆向工具入口，下一阶段不应主要追求工具数量，而应优先做到：

1. 工具错误能够被正确解释，不把后端异常当成目标程序异常。
2. 分析状态能够持续保存，不必每次重新自动分析。
3. 静态推断、机器码证据、运行时命中、修改后验证能够明确分级。
4. 任务、工作区、文件访问和多客户端协作足够稳定。
5. 动态定位入口可用，并如实说明免 Root 的能力边界。

**建议路线：先修可靠性，再提升定位效率，最后扩展高级自动化。**

## 2. 现有能力与主要缺口

### 2.1 已提供的能力入口

- APK / ZIP / DEX / Smali / AXML / 资源表读取和编辑。
- APK 解包、回编译、签名、验签、对齐检查。
- DEX 成员搜索、交叉引用、调用图、继承关系。
- JADX、Apktool、AAPT2 可选组件。
- ELF 元数据、指令分析、Capstone、radare2、r2ghidra。
- Frida Gadget、YARA、Unicorn 可选组件。
- Node / QuickJS / Rhino 脚本执行与手机侧终端。
- 工作区、编辑会话、检查点、回退、后台任务。

以上是能力入口的盘点，**不表示所有接口和组件都在本次会话中完成了行为验收**。文档支持、组件安装、真实运行验证应分别记录。

### 2.2 现在最值得补的能力

- 有状态的 native 分析会话。
- 应用启动、目标日志与退出原因的关联采集。
- Frida Java Bridge 和有时限的持续会话。
- 可验证的离线二进制变换及分析覆盖层。
- 统一证据导出与回归测试。

## 3. P0：工作区生命周期与配额一致性

### 3.1 实测现象

创建 APK 工作区时报“最多保留 16 个 APK 工作区”，但工作区列表只返回一个保存工作区，无法通过公开列表定位占用配额的其它工作区。

目前不能仅凭这个现象断言内部一定发生泄漏，但公开查询和配额错误之间存在明显的信息缺口。

### 3.2 建议

扩展现有工作区列表，支持：

- 列出保存、临时、过期、异常、待清理工作区。
- 返回实际计数、占用字节数、配额和统计范围。
- 返回 owner / clientId / sessionId、创建时间、最后访问时间、活动引用数。
- 区分“关闭分析句柄”“释放临时快照”“永久删除工作区”。

增加受控清理能力：

- GC 默认只预览。
- 支持 protectedIds、最短保留时间、按所有者筛选。
- 不自动删除其它客户端的工作区、活动任务引用的快照或用户保存的工作区。
- 检查磁盘目录与注册记录不一致的情况，并提供可审计的修复结果。
- 可按源 APK SHA-256 复用不可变快照，避免重复复制。

### 3.3 验收标准

- 配额报满时，列表能够解释全部配额占用。
- 临时与保存工作区混合使用时，列表与配额统计一致。
- GC 预览不修改数据；受保护项和活动引用项不会被清理。
- 服务重启后，配额与磁盘状态能够重新核对。

## 4. P0：Manifest 解析与验签错误分层

### 4.1 Manifest 解析

本次遇到 `Can not decode without package`，而同一 APK 能被 Apktool 解出清单。

建议将基础信息解析与完整资源解码分开：

1. 优先独立解析二进制 AXML 的字符串池、标签与属性。
2. 包名、版本、SDK、组件、split 等基础字段不应被不必要的资源上下文依赖阻断。
3. 需要解析资源引用时，再使用 resources.arsc 的 package/configuration 上下文。
4. 可回退到 PackageManager 或另一个独立解码器，但必须说明结果来源。
5. 保留原始失败原因，不能把回退结果冒充主解析器成功。

返回结果应区分：

- 目标清单确实损坏。
- 格式或属性暂不支持。
- 资源上下文缺失。
- 后端解析异常。
- 基础字段已获取，但完整 XML 尚不可用。

### 4.2 apksig V1 解析

本次出现过如下类型的异常：

```text
ContentInfo is not annotated with Asn1Class
```

这是对验签后端反射注解的报错，**高度怀疑与 apksig 的打包、R8/混淆或注解保留有关**。需要用已知正常的 V1 测试包复核，不能直接据此判定原 APK 签名损坏。

建议：

- 检查运行时注解、注解定义及 ASN.1 反射相关类的保留规则。
- 为 V1、V2、V3 分别记录验证状态和错误。
- 区分密码学失败、输入格式失败、后端异常和未执行。
- Manifest 获取失败时，不应不加说明地把任意 SDK 范围作为完整验签范围。

建议状态模型：

```text
valid          检查已完成且通过
invalid        检查已完成，且发现明确不一致或密码学失败
backend_error  检查后端异常，无法得出目标有效性结论
unsupported    当前不支持
not_run        尚未执行
```

### 4.3 ABI 路径不匹配

某些加固包可能故意把 x86 桥接库放在 ARM 目录中。

应保留“路径 ABI 与 ELF machine 不一致”的证据，但需要区分：

- 普通 APK 的真实打包错误。
- 壳的桥接或辅助载荷。
- 尚未确定用途的异常条目。

不要未经分析就自动删除这些库，也不要直接把整个 APK 判定为不可运行。

## 5. P0：路径访问、文件发现和应用查询

### 5.1 Android/data 访问诊断

本次普通应用 UID 访问 MT 临时目录返回 `ENOENT`，但授权的 Shizuku shell 可以访问同一路径。

建议提供文件访问诊断，返回：

- 实际 UID / 后端。
- 原始 errno。
- 当前路径是否在允许范围内。
- 是否可能受到存储作用域限制。
- 授权后端是否可用，以及是否真实执行过访问检查。

若系统无法区分“不存在”和“不可见”，应返回不确定性，不能编造结论。

后端建议显式选择：

```text
backend = app | shizuku
```

不得静默切换权限身份；也不应为了“自动成功”扩大到用户未授权的目录。

### 5.2 APK 发现不要只依赖扩展名

本次目标实际叫：

```text
影安加固-测试demo.apk.1
```

建议增强现有文件发现或 artifact 打开流程：

- 扩展名仅作初筛。
- 支持按 ZIP 魔数和 APK 内部结构确认候选。
- 覆盖 `.apk.1`、`.bak`、临时缓存名和无扩展名文件。
- 控制扫描范围、深度和字节预算。
- 返回 truncated / skipped / stopReason，不能把部分搜索当作全部未找到。

### 5.3 应用查询一致性

本次按名称查询没有匹配，但按准确包名查询能读到已安装 Demo。

建议检查：

- 是否先截断列表，再执行 query 过滤。
- 应用可见性是否受限。
- label 与包名的查询行为是否一致。
- Unicode、大小写、空格归一化和分页是否正确。

结果应包含 `visibilityLimited` 或同等字段，明确“完整列表”还是“当前可见列表”。

## 6. P0：任务隔离、结果保留与嵌入式 Node 诊断

### 6.1 终端任务

本次发生过刚创建的任务随后无法读取的情况；同时存在其它客户端密集传输任务。任务淘汰是需要排查的可能原因，不能仅凭通用提示认定服务重启。

建议：

- 按 clientId / sessionId 隔离任务所有权。
- 未读结果有明确保留窗口；必要时持久化到文件或轻量数据库。
- 输出缓存与任务元数据分开管理。
- 超过配额时明确拒绝或通知淘汰，不静默丢失结果。
- 分别返回 JOB_EVICTED、SERVICE_RESTARTED、JOB_NOT_FOUND 等错误。
- 停止操作默认只作用于调用方拥有的任务。

### 6.2 明确各种 ID 的语义

建议统一文档与返回字段：

| 标识 | 语义 |
|---|---|
| artifactId | 输入制品身份或内容哈希关联 |
| workspaceId | 不可变快照/工作区 |
| editSessionId | 写时复制编辑会话 |
| analysisSessionId | 分析器状态，不是业务文件修改 |
| executionId | 脚本引擎执行 |
| jobId | 后台分析/构建任务 |
| traceSessionId | 运行时观测会话 |

### 6.3 嵌入式 Node

本次 `process.execPath` 指向 Android 的 `app_process64`，不能直接把它当独立 Node CLI 启动子脚本。

建议暴露：

```text
runtimeMode
hostExecutable
standaloneNodeExecutable
canSpawnStandaloneNode
supportedChildScriptRunner
```

不要伪造 `process.execPath`；应提供准确运行形态和正确执行入口。

## 7. P1：有状态 native 分析会话

### 7.1 为什么需要

当前多次 native 查询通常会重新打开文件、自动分析、查询后退出。

这样会丢失手工补充的：

- 函数起点与范围。
- 参数、返回值和结构体类型。
- noreturn 标记。
- 导入/重定位修正。
- 只供分析的解密覆盖层。

同一个库反复执行自动分析，既浪费时间，也容易产生前后不一致的结果。

### 7.2 建议接口（拟新增）

| 接口 | 作用 |
|---|---|
| native_analysis_open | 按文件哈希打开分析上下文 |
| native_analysis_define_function | 补函数起点、长度、名称 |
| native_analysis_set_type | 补参数、返回值和结构体 |
| native_analysis_set_noreturn | 标记终止函数 |
| native_analysis_overlay | 应用仅供分析的数据/重定位覆盖层 |
| native_analysis_save | 保存分析器状态 |
| native_analysis_close | 释放上下文 |

实现可选：

- 有时限的持久 radare2 进程。
- 保存分析数据库，按需恢复。

不必为了“持久”一直占用进程；重点是分析状态可恢复、输入哈希可核对、并发修改可串行化。

### 7.3 安全与正确性要求

- 分析覆盖层与 APK 编辑会话分开。
- 覆盖层明确标记 analysisOnly，不允许默认流入构建产物。
- 源文件变化后拒绝沿用旧地址和旧分析状态。
- 地址始终注明 virtual / file_offset / runtime_address 和 ABI。
- 有资源、时间、输出与会话数量限制。
- 如提供批处理，优先结构化动作；默认禁止任意 shell、文件写入和网络命令。

## 8. P1：精简反编译输出与增强交叉引用

### 8.1 反编译接口扩展

建议在现有接口上增加：

- analysisSessionId。
- forceFunction、functionSize。
- includeAnnotations，默认 false。
- 单独的 code、warnings、evidence、coverage 字段。

本次部分伪 C 只有几 KB，但携带高亮注解后返回超过百 KB。默认返回代码、警告和必要证据，注解按需读取，可以显著减少上下文开销。

### 8.2 函数边界与归属

需要区分：

- 实际属于函数 CFG。
- 仅落在某个符号声明的地址范围。
- 自动识别的候选函数。
- 用户明确指定的函数边界。

不要仅因为地址显示为 `JNI_OnLoad + 偏移`，就认定该指令属于 JNI 初始化函数。

### 8.3 ELF 与间接引用

建议增强：

- 无节表 ELF 的动态信息解析。
- DT_HASH / GNU_HASH 辅助确定符号范围。
- REL / RELA / JUMP_SLOT / RELATIVE 的显式解析。
- GOT/PLT、函数指针表、全局变量地址引用。
- BSS 地址与有文件字节地址的明确区分。

交叉引用结果应说明证据类型：

```text
直接 call/jump
重定位指针
静态可解析的数据引用
推测的间接引用
未覆盖的动态引用
```

“没有直接引用”不能被简化成“没有调用者”。

## 9. P1：应用启动、日志与退出原因关联采集

### 9.1 建议接口（拟新增）

- app_exit_info(packageName)。
- app_trace_start(packageName)。
- app_trace_read(traceSessionId)。
- app_trace_stop(traceSessionId)。
- app_launch_trace(...)。

### 9.2 工作流

```text
记录目标身份、设置状态和时间
→ 建立目标日志采集
→ 启动应用
→ 跟踪 PID/UID 与存活状态
→ 读取退出原因
→ 导出本轮证据
```

至少区分：

- Java 异常。
- native 崩溃。
- 主动 exit。
- SIGKILL。
- 系统回收。
- 启动失败。
- 因权限或日志覆盖而无法判断。

### 9.3 约束

- 默认只采集目标及与目标启动直接相关的系统记录。
- 不混入其它应用的大量日志。
- 保留 PID、UID、时间、采样窗口和日志是否完整。
- 启动目标属于执行操作，应由用户任务或显式参数授权。
- A/B 比较应记录实际配置；不能默认自动关闭开发者选项、ADB 或其它系统安全设置。
- SIGKILL 只解释结束方式，不能自动归因为某个检测分支。

## 10. P1：补强 Frida 动态观测

### 10.1 Java Bridge

将 frida-java-bridge 做成可选组件，提供明确版本、打包方式、加载状态与最小验证用例。

仅有 Frida native 客户端并不等于 `Java.perform` 已可用。

### 10.2 持续会话

建议增加有界持续会话：

```text
frida_session_open
frida_session_read
frida_session_close
```

要求：

- TTL、超时分离和显式停止。
- 消息序号、时间戳、分页与截断标记。
- 目标 PID/包名与 endpoint/token 绑定。
- 服务退出和取消后的真实清理结果。
- 不自动延长成无限后台驻留。

### 10.3 启动早期观测

明确支持哪些入口：

- Application.attachBaseContext。
- native constructor。
- 普通 Provider 初始化。
- app zygote 等特殊路径。

普通 Provider 注入可能晚于壳的检测，不应宣称覆盖全部启动阶段。

等待附加的模式需要超时自动恢复，避免诊断版一直卡住。

### 10.4 默认先观测，不默认屏蔽终止

优先采集调用栈、返回地址、模块偏移和检查输入。

不要默认把所有 kill/exit 置空；这可能只是掩盖失败，使应用停留在未完成解密或初始化的状态。

## 11. P2：可验证的二进制变换与 VM 辅助

### 11.1 二进制变换

建议提供统一变换流程，而不是为每种算法新增一堆碎片工具：

- XOR、字节序、索引排列恢复。
- 参数明确的 AES、SM4 等变换。
- 分段解压。
- 指针表、导入表与重定位恢复。

每次变换记录：

```text
输入身份和哈希
输入范围
变换及参数来源
输出哈希
验证断言
分析副本/运行时修改的分类
```

验证可以包含魔数、长度、指针范围、排列完整性、CRC 或与独立证据对照。

只出现可读字符串或只解出一小段，不应自动标成“全部解密成功”。

### 11.2 VM 辅助

可以优先实现：

- 聚类相同的解释器薄壳。
- 提取字节码地址、长度、引用表和参数布局。
- 为引用表索引建立可核对映射。
- 支持用户提供 opcode 规则与版本标识。
- 输出带覆盖范围和置信度的 CFG、调用关系。

不建议承诺“任意 VMP 一键还原源码”。不同 VM、密钥、动态状态和指令语义之间差异很大。

## 12. P2：统一证据导出与验收

复用现有工作区、检查点、diff、构建与验签能力，增加统一的证据导出流程：

```text
原件身份
+ 分析覆盖层/编辑差异
+ 工具版本与命令
+ 报告与复现脚本
+ 文件清单和哈希
+ 归档完整解压校验
```

建议证据分级：

| 等级 | 含义 |
|---|---|
| 文档/接口声明 | 仅表明存在入口或文档支持 |
| 静态推断 | 由结构、命名或模式推测 |
| 静态确认 | 字节码、机器码或重定位证据能够对上 |
| 运行时确认 | 在目标进程实际观测到命中 |
| 修改后验收 | 在明确环境中验证修改后的目标行为 |

以下结果必须独立记录：

- 签名通过。
- 可以安装。
- 可以启动。
- 目标功能正常。
- 某个检测被正确处理。

导出时默认排除生产私钥、连接令牌、ADB 授权资料和无关应用数据。调试密钥如需导出，应明确标注仅供测试。

## 13. 免 Root 能力边界

| 场景 | 边界 |
|---|---|
| 静态分析 APK/DEX/ELF | 主要受文件访问、格式与预算约束 |
| 查询应用与退出记录 | 受 Android 权限和可见性限制；Shizuku 可扩展部分查询 |
| 原版非 debuggable 应用的任意附加/内存读取 | 普通应用或 Shizuku shell 不能普遍做到，不能仅靠增加接口突破系统隔离 |
| 自有可调试应用 | 可在对应调试权限与工具条件下开展观测 |
| 集成 Gadget 的副本 | 需要重签和安装，可能触发签名/包名校验 |
| 修改系统设置做对照 | 必须明确授权并记录恢复，不能作为默认排障动作 |

增加工具不等于获得 Root、绕过 SELinux 或沿用原作者签名。能力返回必须说明实际身份、权限及本轮是否验证。

## 14. 建议实施顺序

### 第一阶段：可靠性与正确性

1. 工作区列表、配额与受控清理。
2. Manifest 基础解析和回退。
3. apksig V1 后端问题与错误分层。
4. 任务所有权、结果保留和准确错误码。
5. Android/data 访问诊断与非标准文件名发现。
6. 应用查询一致性和嵌入式 Node 运行形态说明。

### 第二阶段：定位效率

1. native 分析会话与持久状态。
2. 函数范围、类型和 noreturn 配置。
3. 反编译默认精简输出。
4. 应用启动/日志/退出原因关联采集。
5. Frida Java Bridge 与有时限持续会话。

### 第三阶段：高级辅助与工作流

1. 二进制变换及验证。
2. VM 薄壳、字节码与引用表辅助。
3. 统一证据导出。
4. 任务规划器按真实权限和组件状态选择路线。

不建议在第一阶段优先引入体积很大的新组件，或再增加多个功能重叠的公共入口。

## 15. 最低回归测试清单

| 类别 | 最低测试要求 |
|---|---|
| 工作区 | 临时/保存混合、满额、活动引用、重启核对、受保护项 GC |
| Manifest | 普通包、无资源包、纯 native 包、split、缺失资源上下文、损坏输入 |
| 签名 | 已知正确的 V1-only、V2、V3；改动字节的包；明确后端异常 |
| 应用列表 | 大量应用、多页、中文名称、包名、可见性受限 |
| 文件 | .apk.1、无扩展名、作用域不可见、确实不存在、授权 shell 可访问 |
| 任务 | 多客户端并发、未读结果保留、超额、取消、服务重启 |
| ELF | 无节表、动态哈希、REL/RELA、BSS、ARM Thumb、AArch64、x86/x86-64 |
| native 分析 | 强制函数边界、noreturn、覆盖层隔离、输入变化使旧状态失效 |
| Frida | Java Bridge 缺失/可用、早期检测、超时恢复、目标退出、取消清理 |
| 导出 | 原件不变、来源完整、哈希一致、归档完整解压复核、敏感材料排除 |

## 16. 效果评估指标

建议记录真实任务指标，而不只统计工具数量：

- 完成一次目标定位所需的工具调用数。
- 同一 ELF 重复自动分析次数。
- 总返回字节数、代码与注解比例。
- 需要手工补写脚本的数量。
- 后端异常被错误归因为目标损坏的次数。
- 任务结果丢失、工作区无法解释占用的次数。
- 静态结论中具有可复现证据的比例。
- 修改后完成真实验证的比例。

**最终目标：从“很多工具可以调用”，提升为“分析状态能延续、错误能解释、结论有证据、结果可复核”的逆向工作台。**
