# AI.js Pro MCP 使用体验反馈（用户侧实战复盘）

> 来源：声动地形图 1.1（云镜 VMP）逆向会话，**数百次 MCP 调用**后的实测记录。
> 与 `AI.js-Pro-MCP-逆向能力优化建议.md`（开发侧）互补：那份讲「应该做什么」，本篇讲「实际卡在哪」。
> 文档性质：实测反馈，不代表任何功能已实现。数字（次数/耗时）为会话内估计值。

---

## 0. 总评

```
★ 能用的部分非常好用  —— 靠它完成 29 处方法还原 + 几十轮编译/装机/界面验证
✗ 坑的部分很耗时间    —— 本会话至少 10 次因工具细节返工，累计约 1~2 小时
⇒ 与开发侧建议书判断完全一致：先修可靠性 → 再提效率 → 最后扩自动化
```

---

## 1. 强项（实际依赖最多的，建议保留并加强）

| 能力 | 实测用法 | 评价 |
|---|---|---|
| **terminal_exec 双后端** | 编译走 `app`，装机/日志/UI 走 `shizuku` | ★★★ 一台手机跑通完整工具链，**最有价值** |
| **get_ui_layout / capture_screen** | 界面文字回归 12/12 + bounds 逐像素比对 | ★★★ 无需 frida 即可精确验证界面 |

| 脚本目录 = MCP root | 分析产物直接落地 | ★★ 顺手 |
| 组件化 | radare2 / r2ghidra 可选安装 | ★★ 好设计 |
| probe_engine_api / list_engine_api | 探测三引擎 API 差异 | ★ 有创意 |

## 2. 痛点（按损失排序，含实测次数与耗时）

### 2.1 ★★★ 后端能力分界不明确（2 次，各 5+ 分钟）

```
现象  javac / java 只在 app UID 可达（位于应用私有目录）
      pm / am / logcat / uiautomator 只在 shell（shizuku/adb）可达
      用错后端时只报：javac: inaccessible or not found —— 不提示是后端问题
影响  需试错才发现；报错文本会误导为「工具没装」
建议  ① 自动路由；或 ② 报错文本里明确指出「该命令需 X 后端」
对应  开发侧 §6 任务隔离与 ID 语义
```

### 2.2 ★★★ 无「有状态 native 分析会话」（N 次，每次约 30 秒）

```
现象  每次 r2 调用都要重新加载 libliuyun.so（较大），无法复用会话
影响  213 个壳的批扫「完全不可行」，只能分批（每批 5~8 个）
      本应「几分钟」的工作变成「几十分钟以上」，实际被迫放弃全量扫描
建议  提供常驻 native 会话（一次加载，多次查询）
对应  开发侧 §7 有状态 native 分析会话
```

### 2.3 ★★ raw 反汇编看不到重定位（1 轮白跑，2~3 轮摸索）

```
现象  r2 的 pdf（raw 反汇编）看不到 adrp/add 算出的地址
      用 pdf 批扫 213 壳 => 0 命中（白跑一轮）
      必须用 pdg（Ghidra 反编译，会解析重定位）—— 但 pdg 很慢
根因  需开 bin.relocs.apply=true（我自行摸索得出）
建议  ① 工具/文档明确提示该参数；② pdg 与 pdf 的能力差异显式标注
对应  开发侧 §1 核心结论第 3 条（证据分级）
```

### 2.4 ★★ shell 环境能力未知（≥5 次）

```
实测结论（busybox 风格）：
  grep  不支持 \b / \s                  （改用 node 或等价写法）
  cat   不支持 -n / -A                  （改 sed -n / grep -n）
  zip / jar / 7z 均不可用，只有 tar      （自写 pack.js 打 APK）
  python 链接坏，只有 node 可用
建议  在工具描述里列出 shell 能力清单；或引导用 MCP 自身的 read_text / search_text
```

### 2.5 ★ node 内联脚本易被转义破坏（3 次；本次写本文档时又踩 1 次）

```
现象  node -e '...' 里含引号/中文引号/反斜杠时，shell 与 JS 双重转义易坏
      且 argv 语义：argv[0]=node，argv[1]=脚本，argv[2] 才是参数
影响  脚本报错却看起来像工具问题
建议  提供「写脚本文件 + 运行」的一体化入口（我现已一律手写 .js 或改用 heredoc 规避）
```

### 2.6 ★ 崩溃缓冲清理语义不明（1 次困惑）

```
现象  logcat -b crash -c 之后仍能读到 2 条旧崩溃
影响  一度误判「自己引入了崩溃」，白排查一轮
建议  明确清缓冲的语义与验证方法（或提供 MCP 层日志过滤）
```

### 2.7 ★ 路径一致性（外部改动导致脚本集体失效）

```
现象  工作目录被外部重组后（如 15_可编译源码树/ 被移走），旧脚本全部失效
建议  MCP root 共享时，最好能感知路径变化（或提供稳定的工作目录）
```

## 3. 最该优先改的 3 件事（用户侧排序）

```
① ★★★ 后端能力自动路由 / 明确报错           （开发侧 §6）
   => 所有做安卓脚本的人都会踩，收益面最大
② ★★★ 有状态 native 会话（r2 常驻）          （开发侧 §7）
   => 让「批扫」从不可行变可行
③ ★★  证据分级显式化（raw / pdg / 间接引用）  （开发侧 §1.3）
   => 避免「白跑一轮」这类损失
```

## 4. 本项目真实调用面（供优化时参考）

```
高频  terminal_exec（app/shizuku 双后端）· get_ui_layout · capture_screen ·
      read_script · list_scripts
中频  run_script（node 24）· get_mcp_log · list_overlays · workspace_open/read/write
低频  probe_engine_api · list_engine_api · check_syntax · apk_* · zip_* · artifact_*
未用  frida_*（Java 桥未打包）· yara_* · unicorn（native_emulate）· apk_inject_gadget
⇒ 结论：「终端 + 无障碍」是本次的两条生命线，其余多为一次性使用
   ⇒ 优化资源宜优先投在这两条
```

## 5. 一句话总结

```
能用、够用、且有独特价值（双后端 + 无障碍验证是杀手级）
但「错误解释」与「原生活动会话」若不补齐，每个用户都要重复踩同样的坑
=> 建议先把开发侧建议书的 P0（§3~§6）做完，体验会有台阶式提升
```
