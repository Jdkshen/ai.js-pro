# 象棋自动走棋：YOLO + OCR + 红黑分离视觉架构重构方案

> 目标平台：AI.js Pro QuickJS 新引擎、Redmi K40（1080×2400，Android 13/MIUI）  
> 运行方式：完全本地，不访问云端，不依赖网络  
> 文档用途：可直接作为 DeepSeek 或其他开发人员的实施任务书

## 1. 背景与当前问题

现有流程主要依赖 YOLO 同时完成棋子定位与棋子类别判断，再通过局部颜色采样推断红黑。该方案在棋盘皮肤、动画、阴影、选中效果或截图尚未稳定时容易发生连锁错误：

- 棋子框漏检或偏移后，棋子会映射到错误交点；
- 七类 YOLO 模型不区分红黑，同字异色容易读反；
- 单帧颜色判断被木纹、棋子阴影和高亮动画干扰；
- 错误局面进入算棋后可能产生非法或不属于当前局面的着法；
- 点击成功只代表输入命令发出，不代表游戏接受并完成了走子；
- 截图切换过程中可能出现大量未知格，状态机随后反复恢复；
- 悬浮窗覆盖棋盘或抢占前台焦点，会同时影响截图和点击。

重构只替换视觉识别层。规则引擎、搜索引擎、自动走棋状态机、点击确认、悬浮窗主体继续保留。

## 2. 新架构目标

新架构将“位置、文字、颜色、规则”彻底分开：

```text
屏幕截图
  ↓
画面稳定性检查
  ↓
YOLO：检测棋盘/棋子圆形区域
  ↓
棋盘几何：拟合 9×10 交点并缓存
  ↓
检测框映射到交点
  ↓
OCR/字形分类：识别车马炮等类别
  ↓
颜色分类：独立识别红方/黑方
  ↓
多帧融合 + 象棋规则校验
  ↓
可信局面快照
  ↓
本地引擎算棋
  ↓
前台确认 → 点击 → 再识别确认
```

核心原则：任何单一模块都不能直接决定最终局面；最终结果必须经过置信度、多帧和规则三层校验。

## 3. 模块职责

### 3.1 截图与稳定帧模块

建议文件：`src/vision/frame-gate.js`

职责：

- 获取完整分辨率截图；
- 确认当前前台包是目标游戏；
- 检查截图不是黑屏、授权弹窗、AI.js Pro 页面或切换动画；
- 连续采集两帧，在棋盘区域计算平均像素差；
- 只有稳定帧才进入识别。

建议条件：

| 项目 | 建议值 |
|---|---:|
| 前台切换后等待 | 350～500 ms |
| 两帧间隔 | 100～160 ms |
| 棋盘区域平均差阈值 | ≤ 6/255 |
| 最大重试 | 3 次 |
| 大量未知格触发重拍 | 未知格 > 6 |

切回游戏后第一帧只用于预热，不送入状态机。

### 3.2 YOLO检测模块

建议文件：`src/vision/piece-detector.js`

YOLO只负责回答：

- 棋盘大致在哪里；
- 哪些位置存在棋子；
- 每个棋子圆形区域的检测框与置信度。

YOLO不负责：

- 红黑阵营；
- 最终棋子名称；
- 轮到哪一方；
- 棋盘局面是否合法。

现有 `chessai_160x320_v5r.onnx` 可以先作为候选框检测器使用。后续训练时建议将标签简化为 `piece` 一类，减少分类任务对检测召回率的影响。

建议参数：

```js
{
  inputWidth: 160,
  inputHeight: 320,
  confidence: 0.22,
  nms: 0.45,
  maxDetections: 40
}
```

检测框必须保存：

```js
{
  x, y, width, height,
  centerX, centerY,
  score,
  source: "yolo"
}
```

### 3.3 棋盘几何与90交点

建议文件：继续使用 `src/vision/geometry.js`，新增 `grid-tracker.js`。

棋盘由9列、10行、90个交点组成。几何模块需要输出：

```js
{
  originX,
  originY,
  stepX,
  stepY,
  orientation: "RED_BOTTOM" | "RED_TOP",
  version,
  confidence,
  updatedAt
}
```

运行策略：

1. 第一次运行时完整定位棋盘；
2. 将YOLO棋子中心拟合到规则网格；
3. 正常对局复用几何，不重复完整定位；
4. 检测中心平均残差超过0.22格距时进行小范围微调；
5. 超过0.35格距或连续两帧异常时重新定位；
6. 每次几何变化递增 `version`，旧点击票据立即失效。

检测框映射到交点时：

- 每个检测框只能分配给一个交点；
- 每个交点只能接收一个检测框；
- 超过0.38格距的框拒绝分配；
- 冲突时优先选择距离更近且置信度更高的框。

### 3.4 棋子裁剪

建议文件：`src/vision/piece-cropper.js`

只裁剪YOLO确认有棋子的交点，通常不超过32个。不要对90格全部运行OCR。

每个裁剪块应包含完整棋子圆盘并保留少量边缘：

```js
cropSize = min(abs(stepX), abs(stepY)) * 0.82
```

预处理输出两份：

- OCR图：灰度/对比度增强，用于识别文字；
- 颜色图：保留RGB，用于红黑判定。

OCR图建议步骤：

1. 裁剪棋子区域；
2. 缩放到192×192；
3. 转灰度；
4. CLAHE或轻量对比度拉伸；
5. 去除圆盘外圈；
6. 保留中心约70%的文字区域。

### 3.5 OCR与字形分类

建议文件：`src/vision/piece-ocr.js`、`src/vision/ocr-runtime.js`

第一阶段使用AI.js Pro内置本地PP-OCR：

```js
const session = $ocr.create({ backend: "ppocr" });
const blocks = session.detect(pieceImage, { max: 1 });
```

需要将可能返回的文字归一化为七种逻辑类别：

| OCR文字 | 逻辑类别 |
|---|---|
| 车、俥、車 | R |
| 马、馬、傌 | N |
| 相、象 | B |
| 仕、士 | A |
| 帅、將、将 | K |
| 炮、砲 | C |
| 兵、卒 | P |

PP-OCR置信度低于0.70时不接受结果；低于0.55时直接记为未知。

第二阶段建议训练专用192×192七分类模型。专用模型仅识别字形，不区分红黑：

```text
输入：1×1×192×192 或 1×3×192×192
输出：R N B A K C P
```

专用分类模型的目标：

- 单块推理小于8 ms；
- K40整盘32子小于260 ms；
- 真实截图Top-1准确率不低于98.5%；
- 不同皮肤测试集每种至少100张棋子块。

### 3.6 红黑颜色分类

建议文件：`src/vision/piece-color.js`

颜色必须独立于OCR。不要让字形模型同时学习红黑，否则需要14类数据且容易过拟合皮肤。

推荐算法：

1. 对棋子中心区域生成文字笔画掩码；
2. 排除高亮、圆盘木色和阴影像素；
3. 将剩余像素转换到Lab或HSV；
4. 统计红色像素比例、平均色相和 `a*` 分量；
5. 输出 `RED / BLACK / UNKNOWN` 与置信度。

建议特征：

```js
{
  redRatio,
  darkRatio,
  meanHue,
  meanSaturation,
  meanLabA,
  sampleCount
}
```

建议判定：

- 红色比例高且Lab `a*` 明显偏正 → RED；
- 低饱和、低亮度文字像素占比高 → BLACK；
- 有效采样少于40像素 → UNKNOWN；
- 两种得分差小于0.18 → UNKNOWN。

颜色结果要经过连续两帧投票。同一个交点单帧读反时保留上一帧结果，并记录冲突，不直接更换阵营。

### 3.7 棋子结果融合

建议文件：`src/vision/piece-fusion.js`

每个棋子输出统一结构：

```js
{
  index,
  col,
  row,
  type: "R",
  side: "RED",
  fen: "R",
  detectionScore: 0.94,
  ocrScore: 0.88,
  colorScore: 0.91,
  finalScore: 0.90,
  box,
  evidence: {
    yolo: true,
    ocrText: "车",
    color: "RED"
  }
}
```

建议综合分数：

```text
finalScore = detectionScore×0.30 + ocrScore×0.45 + colorScore×0.25
```

最终接受条件：

- YOLO框已稳定映射到交点；
- OCR类别已确认；
- 红黑颜色已确认；
- 综合分数≥0.78；
- 与多帧历史或合法走法一致。

不满足时输出 `?`，绝不猜测。

### 3.8 多帧融合

建议文件：继续使用 `temporal-fusion.js`，修改为按证据融合。

建议保存最近3帧：

- 两帧结果相同即可确认；
- 三帧三种结果则未知；
- 棋子移动只允许出现“起点消失、终点出现”或合法吃子变化；
- 颜色单独投票，不能因字形一致就覆盖阵营；
- 点击后短暂动画帧不参与投票。

### 3.9 规则校验与安全门

建议文件：`src/vision/board-validator.js`

识别局面进入算棋前必须通过：

- 恰好一个红帅/将和一个黑将/帅；
- 每方棋子数量不超过16；
- 总棋子数量不超过32；
- 未知格为0，或未知格能够由合法单步补全；
- 相邻稳定局面之间能由0步、1步或“一步+应手”解释；
- 当前局面至少存在一个合法着法；
- 引擎返回着法必须存在于当前合法着法列表。

禁止把 `a0b0` 当作兜底着法。无合法着法时应返回：

```js
{ ok: false, reason: "当前识别局面没有合法着法" }
```

点击执行器必须再次校验着法，形成双重保护。

## 4. 绘制与调试显示

建议文件：`src/vision/overlay-draw.js`

调试绘制应支持开关，并显示：

- 棋盘外框；
- 90个交点；
- YOLO检测框；
- 检测框到交点的连线；
- OCR文字与分数；
- 红黑颜色及分数；
- 最终FEN字符；
- 未知格、冲突格和被规则拒绝的格子。

建议颜色：

| 内容 | 颜色 |
|---|---|
| 红棋 | `#FF4040` |
| 黑棋 | `#E0E0E0` |
| 未知 | `#FFD54F` |
| 冲突 | `#FF00FF` |
| 网格 | `#40C4FF` |
| YOLO框 | `#66BB6A` |

绘制层只读取识别结果，不参与任何识别或决策。

## 5. 点击与确认流程

自动点击前：

1. 确认模式为“自动走棋”；
2. 确认当前轮到我方；
3. 确认棋盘快照安全；
4. 确认着法存在于合法着法列表；
5. 确认几何版本与着法票据一致；
6. 将目标游戏切回前台；
7. 等待350～500 ms；
8. 检查触摸焦点确实属于目标游戏；
9. 执行起点和终点点击。

点击后：

1. 等待动画结束；
2. 获取两张稳定帧；
3. 重新执行完整识别；
4. 对比“点击前、预期后、实际后”三个局面；
5. 只有实际局面与预期一致才算成功；
6. `UNCHANGED`只允许重试一次；
7. 第二次仍无变化则暂停，要求重新校准或切换点击通道。

点击通道建议顺序：

```text
无障碍 press → Shizuku input swipe → 失败后暂停
```

不允许同一着法无限循环重试。

## 6. 悬浮窗要求

- 默认收起，避免遮挡棋盘；
- 仅显示模式、运行状态、未知格数、OCR状态和停止按钮；
- 展开后显示调试信息；
- 动态颜色统一传 `#RRGGBB` 字符串，禁止传Android有符号颜色整数；
- 切换游戏前台时悬浮窗不能关闭脚本；
- 截图时可临时隐藏悬浮窗，截图完成后恢复；
- 面板隐藏失败不能影响识别主流程。

## 7. 性能预算（K40）

| 阶段 | 目标耗时 |
|---|---:|
| 稳定帧检查 | 150～300 ms |
| YOLO检测 | ≤ 40 ms |
| 网格映射 | ≤ 10 ms |
| 32块专用OCR | ≤ 260 ms |
| PP-OCR临时方案 | ≤ 800 ms |
| 颜色判断 | ≤ 30 ms |
| 多帧融合与规则校验 | ≤ 20 ms |
| 单次完整识别 | 专用模型≤500 ms，PP-OCR≤1.2 s |

检测器与OCR会话必须复用，不能每一帧重新加载模型。

## 9. 迁移实施顺序

### 阶段A：稳定现有运行链路

- 修复悬浮窗颜色与显隐；
- 点击前确认游戏前台与触摸焦点；
- 禁止非法着法和无限重试；
- 大量未知格直接丢弃该帧。

### 阶段B：拆分视觉职责

- YOLO只输出候选框；
- 新增统一棋子裁剪；
- 接入PP-OCR；
- 新增独立颜色分类；
- 输出14类最终棋子。

### 阶段C：多帧与规则融合

- 最近3帧投票；
- 合法变化校验；
- 未知格与冲突可视化；
- 点击后使用预期局面确认。

### 阶段D：专用192×192模型

- 从真实截图自动裁剪棋子块；
- 人工复核标签；
- 训练七类字形模型；
- 导出ONNX；
- 在K40上做PP-OCR与专用模型A/B测试。

- 中局、残局；
- 红方在下和红方在上；
- 选中、将军、可走位置高亮；
- 棋子移动动画；
- 不同棋盘皮肤；

- 游戏暂停、菜单和结算界面；

每一帧保存：原始截图、棋盘几何、YOLO框、OCR结果、颜色结果、最终局面和规则校验原因。

## 11. 验收标准

### 识别

- 标准开局连续20次识别，32子全部正确率≥95%；
- 单个棋子字形准确率≥98.5%；
- 红黑判断准确率≥99.5%；
- 棋盘交点映射错误率≤0.2%；
- 稳定画面不得出现超过2个未知格；
- 切换动画帧必须被稳定帧模块拒绝。

### 自动走棋

- 非法着法点击次数必须为0；
- 只识别/建议模式点击次数必须为0；
- 同一着法最多尝试2次；
- 点击后局面不变必须暂停；
- 连续完整走棋20回合，无错点、无重复点、无轮次错判；
- 悬浮窗隐藏、展开、切前台后脚本仍保持运行。

### 性能

- K40完整识别平均耗时不超过1.2秒；
- 专用OCR接入后目标不超过500毫秒；
- 连续运行30分钟无明显内存增长、无检测器重复加载。

## 13. 最终原则

- YOLO负责位置；
- OCR负责字形；
- 颜色模块负责红黑；
- 规则模块负责否决不可信局面；
- 多帧模块负责稳定；
- 点击模块只执行已经验证的合法着法；
- 任何模块不确定时输出UNKNOWN，不能猜测。
