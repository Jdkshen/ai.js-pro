# MCP 截图：质量模式与快速模式（dev-1353/1354）

> 用户要求：MCP 截图「一个质量好、一个快速的」。做法：给 `capture_screen` 加 `mode` 预设，并把真实耗时/字节回传，让调用方自己权衡。

## 一、三种模式

| mode | 输出 | 适用 | 说明 |
|---|---|---|---|
| **`fast`** | 540 宽 + JPEG60，timeout 2s | 定位、轮询、先看一眼 | 最快最小；细节会糊，坐标按 `sourceWidth/scale` 换算 |
| **`balanced`**（默认） | 原图 PNG，timeout 3s | 兼容旧调用 | **与历史默认完全一致**，不改变老客户端拿到的东西 |
| **`quality`** | 原图 PNG，timeout 6s | 存档、取证、像素级比对 | 输出与 balanced 相同的无损原图，语义上更明确、超时更宽 |

调用方显式传的 `format`/`quality`/`maxWidth`/`timeoutMillis` **始终覆盖**预设；未知 `mode` 直接报错（不会静默降级）。

## 二、MI8（1080×2160 / Android 15）实测

| mode | 输出尺寸 | 字节 | 采集 | 编码 | 总计 |
|---|---|---|---|---|---|
| `fast` | 540×1080 JPEG | **36 KB** | 132 / 150 / 185 ms | ~20 ms | **222 / 244 / 271 ms** |
| `balanced` | 1080×2160 PNG | 216 KB | 65 / 76 / 217 ms | ~540 ms | 616 / 621 / 762 ms |
| `quality` | 1080×2160 PNG | 216 KB | 50 / 60 / 83 ms | ~545 ms | **599 / 613 / 633 ms** |
| `fast` + `maxWidth:180` + `quality:40` | 180×360 JPEG | **7 KB** | — | — | **104 ms** |

**结论**：耗时主因是 **PNG 编码约 540 ms**（采集本身只要 50~200 ms）。`fast` 通过「缩小 + JPEG」把编码成本压到 ~20 ms，于是**约 3 倍快、约 6 倍小**；要更极端可以显式覆盖参数（180 宽 + JPEG40 → **104 ms / 7 KB**）。

## 三、返回结构（新增字段）

```json
{ "success": true, "width": 540, "height": 1080, "sourceWidth": 1080, "scale": 0.5,
  "mimeType": "image/jpeg", "format": "jpg", "size": 36864, "method": "accessibility",
  "mode": "fast", "modeNote": "fast：540 宽 + JPEG60，最快最小……",
  "captureMs": 132, "encodeMs": 22, "totalMs": 222,
  "effective": { "format": "jpg", "quality": 60, "maxWidth": 540, "timeoutMillis": 2000 } }
```

`captureMs/encodeMs/totalMs` 是**实测值**（不是估算），`effective` 是最终生效参数——两者一起让调用方能自己判断「这次够不够快/够不够清」。

## 五、追加：`fastest` 档与 `region` 区域截图（dev-1355）

### 5.1 `mode=fastest`（360 宽 + JPEG40，最省）

| mode | 输出 | 字节 | 采集 | 编码 | 总计 |
|---|---|---|---|---|---|
| `fastest` | 360×720 JPEG | **18 KB** | 130 ms | 10 ms | **188 ms** |
| `fast` | 540×1080 JPEG | 36 KB | 161 ms | 18 ms | 238 ms |
| `quality` | 1080×2160 PNG | 215 KB | 233 ms | 542 ms | 782 ms |

只用来回答「有没有 / 大概在哪」；要读字请用 `fast` 或 `quality`。

### 5.2 `region`：只截一块 —— 又小又快，还更清楚

`region` 与 `ui_*` 的 `bounds` 同一套写法（屏幕坐标）：

```jsonc
{"region": [0,1000,1080,1400]}              // [left,top,right,bottom]
{"region": "[0,1000][1080,1400]"}           // 字符串同形
{"region": {"x":200,"y":800,"width":400,"height":300}}
{"region": {"left":0,"top":1000,"right":1080,"bottom":1400}}
```

实现顺序是**先裁后缩**：只截一小块时编码成本极低，而且保留 1:1 像素（比"整屏缩小"更清楚，不是用清晰度换速度）。实测：

| 调用 | 输出 | 字节 | 总计 |
|---|---|---|---|
| `quality` 整屏 | 1080×2160 PNG | 215 KB | 782 ms |
| `quality` + `region:[0,1000,1080,1400]` | 1080×400 PNG | **50 KB** | **175 ms**（≈4.5× 快，像素不缩） |
| `fast` + `region:{200,800,400,300}` | 400×300 JPEG | 11 KB | 203 ms |
| `fastest` + `region:"[0,0][540,540]"` | 360×360 JPEG | 7 KB | 317 ms |

> 注意：`region` 与 `maxWidth` 会叠加——上表最后一行的 540 宽区域被 `fastest` 的 `maxWidth=360` 又缩了一次（这是预期行为：预设只管"没传的参数"）。

返回新增：`cropped`、`region`（已按屏幕边界夹取后的实际区域）、`regionClamped`、`regionNote`（坐标换算口径），以及 `scale` 现在以**区域宽度**为基准。

坏输入给可读错误，例如 `region:"[10,20,30,40]"` → `region 字符串格式无效：[10,20,30,40]；应为 [left,top][right,bottom]`。

## 四、边界

1. `balanced` 与 `quality` 的**输出相同**（原图 PNG），差别只在超时语义与自我说明；真正拉开差距的是 `fast`。
2. `fast` 是缩小图：**坐标要按 `sourceWidth/scale` 换算**（`get_ui_layout` 的节点坐标不受影响）。
3. JPEG 有损，像素级比对/存档请用 `quality`；单张仍受 16 MiB 上限保护。
4. 需要 Android 11+ 且无障碍已连接——**重装 APK 后要重新开启无障碍**（本轮实测就踩到：更新后 a11y 未绑定，截图报「录屏兼容截图需要 Android 11+……请关闭再开启一次」，切换一次设置即恢复）。
5. 只在 MI8（1080×2160 / Android 15）测得上述数字，其它机型/分辨率可能不同。
