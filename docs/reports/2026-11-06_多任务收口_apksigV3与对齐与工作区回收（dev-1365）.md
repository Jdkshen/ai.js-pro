# 多任务收口：第 4 项（apksig V1+V2+V3）+ 对齐端到端 + 工作区回收（dev-1365）

> 用户要求：**开工、能补就补**，测试机默认 K40、MI8 退役。本轮多任务并行：队友 A 做 apksig 签名切换、队友 B 做工作区回收，Lead 做对齐端到端与全部接线/构建/真机验证。一轮构建收口三件事。

## 一、第 4 项完成：`apk_build(sign=true)` 现在产出 V1+V2+V3

**K40 实测（dev-1365，真 APK 138MB）**：

```json
{"signer":"apksig","schemesApplied":["V1","V2","V3"],"schemesVerified":["V2","V3"],
 "signerFallbackReason":null,"signature":{"verified":true,"certificateCount":1},
 "verification":{"signature":{"schemes":{"V1":"not_run","V2":"valid","V3":"valid"}}}}
```

### 路上挖出并修掉的两个坑（都不是队友写错，是这条件本身要求的知识）

1. **R8 把 apksig 签名 API 裁掉了**：实测 dev-1360 的 `classes.dex` 里 `ApkSigner$Builder` 整类消失、`ApkSigner` 只剩 `findCdRecord/getAndroidManifestFromApk` → 补 `proguard-rules.pro` keeps 后 `get_build_tools.signing.apksigAvailable` 由 **false → true**。
2. **预检规则写错，导致 apksig 路径永远回退**：队友的预检要求 `V1/V2/V3` 全部 `verified`，但 **apksig 的 `ApkVerifier` 在 minSdk≥24 时不会单独验 JAR 签名**（报告 `V1=not_run`）。实测第一次装 1363 就是 `signer=keystore-legacy`、`signerFallbackReason="apksig 输出 V1 未通过验证"`。
   修正为**诚实版**：`V2/V3` 必须 `verified`；`V1` 只要求「**真的产出了 META-INF 签名**（`hasV1Signature` 直接查 zip 条目）且未被判 `invalid`」。
3. **上报口径纠正**：`schemesApplied` 原来只列「验过的」，于是产出了 V1 却显示 `["V2","V3"]`；现在拆成 **`schemesApplied`（实际产出，V1 由 META-INF 存在性判定）** 与 **`schemesVerified`（verifier 真验过的）**。

### 回退链路（保留，未破坏可安装包产出）

回退条件：apksig 类缺失 / 签名抛异常 / ZIP 非 valid / V2 或 V3 未 verified / V1 判 invalid 或没有 META-INF / 复制失败 → 走旧 `KeyStoreApkSigner`，并报 `signer=keystore-legacy` + `signerFallbackReason`。`VirtualMachineError`、取消/中断**不吞**，直接抛出。

## 二、对齐（alignment）端到端 + 补齐两处返回体

| 场景 | 结果（K40 / dev-1365） |
|---|---|
| `apk_build` **未签名**（fixture） | `checked=true / misalignedEntries=0 / fixed=true / zipStatus=valid` |
| `apk_build` **已签名**（真 APK 138MB） | `checked=true / misalignedEntries=0 / storedEntriesChecked=1390 / storedEntriesMisaligned4Bytes=0 / zipStatus=valid` |
| `apk_build_project` / `apk_inject_gadget` | ✅ Lead 补上**同源顶层 `alignment`**：把 `alignmentDiagnostics` 下沉为顶层 `internal fun alignmentDiagnosticsJson(...)`，三处返回体共用同一份实现 |

另核实（队友 B 的结论）：`ToolkitArchiveAlignment.align()` **本来就在真重排/真补齐**（Stored 非目录 4B、Stored `.so` 16KiB，写 `0xd935` extra field），4 处调用链都会 align，最终 `ToolkitApkVerifier` 强制 `zip.status=valid` —— 不是「只检测」。

## 三、工作区自动回收（策略式，默认 dryRun）

**K40 实测**：

| 参数 | 结果 |
|---|---|
| `{dryRun:true, keepLatest:20, olderThanHours:24, protectApplied:true}` | `scanned=4, wouldDelete=0, protectedCount=4, protectedByReason={keep_latest:4}` |
| `{dryRun:true, keepLatest:0, protectApplied:true}` | `wouldDelete=0, protected={applied_protected:4}` ← **默认不会碰 APPLIED** |
| `{dryRun:true, keepLatest:0, protectApplied:false, keepAppliedHours:0}` | `wouldDelete=4, reclaimedBytes=3,341,776, deleted=0` ← **显式放开才动，且 dryRun 不删** |

安全边界：只删 `ROLLED_BACK` 与「无修改的 `OPEN`」；`APPLIED`（可回退）、`PENDING_APPROVAL`/`saved`、有修改的 `OPEN`、显式未知 owner、元数据坏掉的一律保护，并逐条给出 `protectedByReason`。旧 retention 自动过期逻辑也同步安全化。

## 五、边界（别当已完成）

1. `apk_build_project` / `apk_inject_gadget` 的顶层 `alignment` 只经过**编译与代码核对**，本轮**没有真跑**一次 apktool 回编（那需要真实 apktool 工程，见 ①）。
2. `schemesVerified` 只有 `V2/V3` 是**密码学验证**结论；`V1` 是**存在性**结论（`META-INF` 里有 `.SF/.RSA/.DSA/.EC`），我们的 verifier 不单独验 V1。
3. 工作区回收当前默认 `dryRun=true` 是**行为变化**（旧工具默认真删）；要真删必须显式 `dryRun:false`。
