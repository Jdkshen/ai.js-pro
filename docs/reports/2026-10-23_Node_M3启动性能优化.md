旧包 `defineClass` 虽声明 `async`，内部却直接同步 `javaCall` 编译 Classfile/Dex。在 Android 主线程发起的 UI 回调内执行时，原线程会等它完成。首轮异步化后，该编译工作通过现有 `asyncCall` 和独立完成结果队列执行，主线程回调可以先返回。V8 仍在 Node 线程，View 操作仍转交 Android UI 线程，未修改原生回调队列或伪造线程判定。

旧包重复运行时，六张图片请求约 149–230 ms 完成；图片来自外网，时延受网络影响。未修改图片地址、缓存或解码逻辑，也未把全部加载等待归因于网络。DP 只读检查确认资源包存在重复加载，但本轮测得资源加载约 60–100 ms，并非最大的初始化阻塞点；没有贸然增加跨配置 Resources 缓存。

## 生成器快速编译的补充核验

初始 dx 入口按 major <= 51 启用，但 Rhino ClassFileWriter 默认输出 52，因此 dev-1226 的这条快速分支实际上未启用。新增实际编译测试发现后，生成器针对其自身使用的普通构造器、装拆箱和虚调用输出 major 51；生成器 JVM 语义测试同步检查这一目标版本。用户提供的 JAR 不降级、不改写。

新增 `Node24GeneratedClassDexTest` 用真实生成字节码验证带接口、受保护父方法、宽参数与返回值的 dx 编译；原有 `Node24ClassGeneratorTest` 继续验证构造回调、虚调用、协变桥、super 转发和各返回类型。D8 的 Java 17 JAR 回归保留并通过。最终分支现有 MI8 ART 加载和回调验证；原 Android 16 设备与其他第三方生成类场景仍需分别验收。

## 2026-10-24 批量/懒加载第一轮（dev-1231，向 500ms 首帧推进）

本轮由多任务并行完成，目标是先砍 onContentViewSet 与列表 item 初始化：

- **底层批量 inflate**：新增 `ui.inflateBatch(layoutOrXml, count, parent)`；Java `NodeUiLocalSession.inflateLayoutBatch/inflateXmlBatch` 在主线程一次生成 N 个 View，返回真实 View[]；`ui.js` 转成普通 JS 数组。支持 layoutId（RecyclerView item）和 XML 字符串，count 1..256；批量 XML 暂不展开自定义 Widget（明确报错）。
- **M3 示例初始化拆批**：`MyViewHolder/MyAdapter` 的 `$java.defineClass` 提前到 `setMainActivity` 前并行编译；`onContentViewSet` 只留 fab 点击与 deferred 调度，ViewPager/Drawer/Grid/Console 按序在 `setTimeout(0)` 后初始化；grid_item 用一次 `ui.inflateBatch` 预生成 8 个 View，Adapter 优先消费、耗尽回退 LayoutInflater。

### 结论与下一步

- 方向 1（批处理）和 5（批量创建 API）已落地第一版，首帧内容回调已进入 **84ms**，但**整页从启动到列表 ready 仍约 1.5s**；`ui:show` 362ms + Activity onCreate 是新的上限。
- 要到「完整页面 500ms」还需：Node Activity 预热/复用（压缩 show）、原生 M3 组件替换自定义 Widget、ViewStub/懒加载（grid/console 已延迟，仍可把图片/后续页再后置）。
- 方向 2（解析/render 缓存）对冷启动首屏收益有限，主要用于重复切页；方向 4（原生 M3 组件）是下一阶段大头。
