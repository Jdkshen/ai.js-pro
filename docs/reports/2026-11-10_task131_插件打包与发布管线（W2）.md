## 二、清单格式（plugins.json v1）
与 update.json **同目录**发布、**同一 Release**（资产名 plugins.json），客户端 URL 与插件 APK 同源：
内置源 = 加速前缀 + releases/latest/download/plugins.json（PluginDownloads.pluginUrl 同一套前缀逻辑）。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| schema | int | 清单格式版本（当前 1）；客户端不认识就忽略整份清单（不猜） |
| generatedAt | string | 生成时间（ISO，仅诊断） |
| plugins[].id | string | 小写 kebab-case，稳定键（apkbuilder / xiangqi / ocr） |
| plugins[].displayName | string | 插件页显示名 |
| plugins[].package | string | 插件 APK 的 applicationId（安装/卸载/是否已装的唯一判据） |
| plugins[].version / versionCode | string / int | 与插件 APK 的 versionName/versionCode 一致（比较用 versionCode） |
| plugins[].minAppVersion | int | 主程序 versionCode 下限；低于它就只提示「请先升级主程序」 |
| plugins[].file | string | 下载文件名（与 Release 资产、更新源目录里的文件名一致） |
| plugins[].sizeBytes / sha256 | int / string | 下载后校验（pending 表示该 APK 尚未构建，客户端应视为「暂不可用」） |
| plugins[].requiresRestart | bool | 装完是否需要重启主程序（插件类进程内加载 ⇒ true） |
| plugins[].abis | string[] | 该插件 APK 里带的 ABI（用于设备不匹配时提前拒绝，不下白流量） |
| plugins[].notes | string | 插件页说明（一句话，别塞长文） |

## 三、快速更新策略（用户要的「像 C/C++ 那样更新快」）
1. **只先拉清单**：进入插件页/定时检查时只 GET plugins.json（几 KB）。带 **If-None-Match（ETag）/ If-Modified-Since**；**304 直接结束**（不下载任何 APK）。
2. **按需拉 APK**：对每个插件比 versionCode：
   - 未安装 ⇒ 「可安装」；已安装且清单更高 ⇒ 「可更新」；相同/更低 ⇒ 不动（不发请求）。
3. **下载前先判**：minAppVersion、abis 与设备匹配、sha256 已知（pending 不下载）；下载后按 sha256 + sizeBytes 校验，再交给安装器。
4. **失败不阻塞**：清单拉取失败 ⇒ 用上次缓存（带时间戳）并标注「离线」；单个 APK 失败不影响其它插件。
5. **不做的事**：不做全量探测、不轮询所有 APK 的 HEAD、不在后台静默下载（用户点了才下）。

## 四、发布步骤（与现有 dev-update.ps1 串起来）
1. 构建插件：:apkbuilder-plugin:assembleRelease / :xiangqi-plugin:assembleRelease（**需要 gradle，由 Lead 统一跑**）。
2. 校验产物：node tools/plugins-manifest.mjs --check <更新源/plugins.json> --apk-dir <放 APK 的目录>（sha256/大小对账）。
3. 生成清单：node tools/plugins-manifest.mjs --out <更新源>/plugins.json。
4. 把插件 APK 与 plugins.json 放进**同一个 Release**（资产名与 file 字段一致），同时复制到更新源目录（现有 dev-update.ps1 已在做插件 APK 那步——建议在其后**追加一行**生成 plugins.json，我没有改它，避免碰发布脚本）。
5. 客户端：304 命中即结束；有变化才下 APK；装完按 requiresRestart 提示重启。
