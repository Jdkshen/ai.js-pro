## 三、两个关键发现（都影响契约）

### 1. 既有协议层用 `errorCode`，不是 `reasonCode` ✗
- 实测：参数形状错时是 `errorCode=INVALID_ARGUMENT`；**没有 `reasonCode`**；
- ⇒ 若新契约只写 `reasonCode`，**既有消费方读不到码** ✗；
- **裁决**（已落地）：`ToolkitIo.fail(...)` **双写** `reasonCode`（权威）+ `errorCode`（既有兼容、**同值**）+ `error` 镜像 `message`，并加**三字段一致**钉子防漂移 ✓；
- **已知不对称（显式记录，不是遗漏）**：**协议层（JSON-RPC handler）今天仍只有 `errorCode`**，暂时不补 `reasonCode` 镜像 —— 动那是所有工具调用的公共失败路径 ✗，风险/收益不划算，排到第 2 批或长期 ✓。

### 2. 既有失败信封比契约文档写的**更丰富** ✓
- 实测失败侧带 `isError=true` + `error` **对象**（含 `type`）+ `details` + `baseline` ✓；
- ⇒ 契约文档必须**补全既有字段**，而不是只写「`reasonCode` + `message`」✗ —— 否则后人读文档会以为那些字段可以删 ✗；
- ⇒ 这也是「**先采基线再动手**」的直接价值 ✓：不采基线就会把已存在的字段写丢 ✗。

**比对判据**（三态都要能区分）：
1. **成功**：`ok=true` + `data` 有内容 ✓（且 `clamped` 若发生可出现 ✓）；
2. **空结果**：`ok=true` + **`empty=true`** ✓（**唯一判据** ✓ 不看 data 是否空集合 ✗）；
3. **失败**：`isError=true` + `ok=false` + **`reasonCode` == `errorCode`** + `message` 可读 ✓。

**注意** ✓：`file_stat` 的「缺失路径」**不是失败** ✓ —— 别把它当基线里的失败样本 ✗（要构造真失败请用**参数形状错**或**不可达权限路径** ✓）。
