> 此为 DP 首次交付记录；主助手的后续修正、实际构建和最终 MI8 验收以[五项优化任务与验收](2026-10-24_五项优化任务与验收.md)为准。

## 1. 本轮背景与目标

用户给出的 MI8/dev-1240 基线现象：

- `get_status.activeMcpRuns=0`、`overlayCount=0`，但前台仍有 `NodeUiLocalActivity$Slot1` 占用；
- Node 运行等待 8s 被拒绝；
- 按返回关闭 M3 页面后，35 条 common API/storage/MCP 用例通过。

本轮只处理两个具体问题和诊断，不重写数千个 API、不伪造兼容率：

1. `McpEngineApi.probe` 原实现沿路径读取 `value[key]`，会执行中间层/末端 getter，却宣传“不执行 getter”；缺失的末端成员只返回 `type: undefined`，没有明确的“不存在”结论。
2. `Node24JavaScriptEngine.init` 捕获所有异常后回退旧 `:node24`，容量满或取消也会走 legacy，绕过进程池容量。
3. 新增公共诊断快照，把 `:script` 池状态、已知 Node 进程 PID、运行时元数据、最近失败证据边界说清楚。

## 3. 探针契约

### 3.1 保持兼容的字段

仍返回：

- `name`
- `module`
- `type`
- `keys`
- `members[]`（每项仍有 `name` / `type` / `arity`）
- `arity`

`members[].type` 继续使用 `typeof` 的结果或 `accessor`；旧的 `accessor` 语义保留。

### 3.2 新增 shape 字段

顶层新增：

- `present`: `true` / `false` / `null`
- `presence`: `present` / `missing` / `accessor` / `unreadable` / `unverified`
- `evidence`: `descriptor` / `reflection` / `presence` / `shape` / `root` / `none`
- `failureAt`（路径中间失败时的前缀，如 `fixture.value`）
- `error`（有可读错误时）
- `probeMode: "shape"`

`members[]` 也补了 `present` / `presence` / `evidence`，不删旧字段。

关键语义：

- 末端数据属性：`presence=present`，`type=typeof value`；
- getter/accessor：`presence=accessor`，`present=true`，**不读取**；
- 证明不存在：`presence=missing`，`present=false`，`type="undefined"`；
- descriptor 读取抛错且无法证明：`presence=unreadable`，`present=null`；
- 代理/动态成员无法证明存在或不存在：`presence=unverified`，`present` 为 `null` 或 `true`（仅当 `in` 已经是形状证据），不伪造 `missing`。

### 3.3 Java/Rhino 代理

原实现用 `Object.getOwnPropertyNames(Object(o))` 枚举 Java 对象；Rhino 的 Java 包装对象在这里会抛异常，原实现还会在读取成员时触发 JavaBeans getter。

新探针：

- 先走自己/原型链的 `Object.getOwnPropertyDescriptor`；
- descriptor 不可用且对象是 Rhino Java 对象时，用 `in` 做存在性形状判断；
- 通过 `getClass().getMethods()/getFields()` 反射区分方法、字段和 JavaBean 属性；
- 方法/字段读取是反射形状而不是调用；JavaBean 属性（如 `getValue()` 对应的 `value`）直接报 `accessor`，不读取；
- 反射也确认不了的对象报 `unverified`，不把 `ownproperty` 失败当作全部 `missing`。
- `arity` 仍按原契约使用 JS `function.length`，没有改成 Java 参数个数。

`call_engine_api` 仍使用原来的真实取值/`value.apply(owner, args)`，不改成 shape-only。

### 3.4 一个真实 Rhino 输出示例

在 Rhino 1.7.15.1 下实际执行生成的探针（不是字符串匹配）：

```json
{"name":"fixture.value","module":"","present":true,"presence":"accessor","type":"accessor",
 "keys":[],"members":[],"arity":null,"evidence":"descriptor","probeMode":"shape",
 "failureAt":"fixture.value"}
```

同一轮 fixture 的 `calls` 保持 0；`fixture.missing` 返回：

```json
{"present":false,"presence":"missing","type":"undefined","evidence":"shape"}
```

Java `ArrayList` 的 `add`/`size` 仍可枚举，JavaBean 的 `value` 返回 `accessor` 且 getter 调用计数为 0。

## 4. Node24 池回退

### 4.1 可识别错误

`Node24Pool` 新增：

- `PoolBusyException`：3/3 槽占用，等待 8s 超时；
- `PoolInterruptedException`：等待前已取消，或等待中被中断。

`acquire()` 在入口检查线程中断，超时/中断分别抛上述异常，不再抛裸 `IllegalStateException`。

### 4.2 回退策略

`Node24Pool.shouldFallbackToLegacy(error, interrupted)`：

- 忙、取消、线程已中断 → `false`；
- 其它池启动错误 → `true`；
- 会检查 cause 链。

`Node24JavaScriptEngine.init()`：

- 忙/取消时记录日志并抛出原始运行时异常，**不创建 legacy `Node24Client`**；
- 真正的池启动故障仍回退旧 `:node24`；
- 显式 legacy 开关（`autojs.node24.legacy`、`AJS_NODE24_LEGACY`、SharedPreferences `node24.legacy`）不变，直接走旧通道。

这解决“容量满时被拒绝，却偷偷回退 legacy 并把任务当成已启动”的问题。

## 5. 诊断快照

### 5.1 入口

`McpEngineDiagnostics.snapshotJson(context: Context): String`，Kotlin `object` + `@JvmStatic`，主助手可通过反射接到 `PocIntegration.mcpState`/Dart。

`get_status` 增加对象字段：

```json
"engineDiagnostics": { ...snapshotJson 解析后的对象... }
```

`list_engines` 新增每项：

- `probeEvidence: "shape"`
- `behaviorStatus: "unverified"`

原有 `engine`/`available`/`run`/`apiQuery`/`apiCall`/`syntaxCheck` 未改。

### 5.2 schema

顶层：

- `schemaVersion: 1`
- `capturedAt`（epoch ms）
- `process`（当前进程名、pid）
- `engines[]`：`engine`、`available`、`behaviorStatus="unverified"`、`probeEvidence="shape"`、`surface`、`note`
- `nodePool`
- `runtime`
- `lastFailure`（无证据时为 JSON null）

`nodePool`：

- `capacity` 来自 `Node24Pool.capacity()`（当前 3）
- `busy: null`
- `busyKnown: false`
- `scope: "process-local"`
- `scopeDetail`：槽在 `:script` 分配，MCP 主进程看不到跨进程占用
- `knownProcesses`：`:node24`（legacy）与 `:node24_1..3`，能读到 `/proc/<pid>/cmdline` 时给 `pid` + `observed=alive`，否则 `pid=null` + `observed=not_visible`
- `pidSource`、`note`：明确 `busy=null` 不是“0 个空闲”，`not_visible` 可能是没启动或 `/proc` 受限

因此不会把主进程 `busyCount()` 的 0 冒充全局空闲；跨进程槽忙时 `busy` 仍是 `null`。

`runtime`：

- `nodeVersion: "24.22.0"`（源码元数据，注明不是本轮运行探测）
- `bundledMetadataPresent` / `runtimePins`：只打开很小的 `runtime.json`，不读 106MB 运行时、不校验哈希
- `hashRead: false`、`integrityVerified: false`、`scriptsStarted: false`
- `cache.statsLogTag: "C-NODE24"`、`statsHint` 指向 logcat
- `cache.speedMeasured: false`，不声称已测速
- `note` 明确未读取/校验运行时

`lastFailure`：

- 当前 MCP 主进程没有跨进程引擎失败记录，因此为 `null`；
- 有真实证据的调用方可在内部 builder 传入；不用 static counter 伪造“最近失败”。

## 7. 未验证/限制

1. **未做 Gradle 构建和真机测试**：`McpTools.kt` 只做了独立 Kotlin 类型检查，未运行 Android 打包；`McpEngineApi.kt` 与 `McpEngineDiagnostics.kt` 已用独立 Kotlin 编译器通过，`Node24Pool.java` 已用 `javac` + stubs 通过，`Node24JavaScriptEngine.java` 已用 `javac` + 最小 stubs 通过，但完整 Android 引擎生命周期仍需构建/真机确认。
2. **Node24JavaScriptEngine.init 未做单测**：行为策略由 `Node24Pool.shouldFallbackToLegacy` 单测覆盖，但完整 Android 引擎生命周期仍需构建/真机确认。
3. **跨进程 busy 仍是 null**：这是有意的诚实值；如需真实占用，应由 `:script` 或各 `:node24_N` 进程回报，而不是主进程 static counter。
4. **`lastFailure` 当前为 null**：主进程没有可信的跨进程引擎失败记录；真实失败仍需 logcat/设备证据。
5. **PID 观测依赖 `/proc`**：Android 高版本/厂商限制下可能只能看到 `not_visible`，诊断已明确说明，不推断空闲。
6. **cache 统计未测速**：只写明 logcat 标签 `C-NODE24`；未改 `Node24Libraries`/`Node24RuntimeFileCache`，也未声称缓存加速数值。
7. **PocIntegration/Dart/UI 未改**：主助手负责把 `engineDiagnostics` 接到页面；`get_status` 已提供对象字段。
8. 基线中“关闭 M3 后 35 条 common API/storage/MCP 通过”来自用户提供，本轮未复跑；本轮只保证探针、回退策略和诊断代码层面的契约。
9. 主助手若通过反射接 `PocIntegration`/Dart，需要在 release proguard 中保留 `McpEngineDiagnostics.snapshotJson`；proguard 由另一 worker 负责，本轮未改。
10. 没有 Java/Rhino/Node shape marker、且 `in` 也为 false 的第三方 Proxy 仍可能被报为 `missing`：ECMAScript 没有标准方法识别这种“靠 get trap 合成成员”的代理。已识别的 Java/Rhino 对象和 Node `__handle`/`__classRef` 等 marker 会走 `unverified`/`accessor`，不会假判全部 missing；这是当前安全探针的明确边界。
