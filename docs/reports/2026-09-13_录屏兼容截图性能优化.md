# 录屏兼容截图性能优化

## 修改

- 无障碍回调只转交 HardwareBuffer 所有权，不在回调线程复制整屏 Bitmap。
- QuickJS 原生层通过官方 AHardwareBuffer API 直接锁定 RGBA 像素，缩放/复制到既有 NativeFrame 复用池；消除整屏软件 Bitmap 和整屏 Java ByteBuffer 的两次中转。
- 非 RGBA 或无法 CPU 映射的设备保留原 Bitmap 转换回退；回退通道复用 ByteBuffer，脚本退出时释放引用。
- HardwareBuffer 生命周期由 AutoCloseable 管理；原生锁用 RAII 解除；超时/脚本中断的晚到资源仍回收。
- AHardwareBuffer 函数通过 dlsym 延迟加载，避免 API 21 旧机仅加载 QuickJS 库就失败。新链接依赖仅 libdl，不提升最低系统。
- 请求间隔从 350ms 收紧至 340ms，保留少量系统调度余量。Android 15 AOSP 的无障碍截图 API 要求间隔大于 333ms；不尝试绕过系统限频。
- 普通 MediaProjection 高速路径、YOLO 模型、输入尺寸、推理线程、图像坐标语义均未修改。

## 小米 8 实机取帧对比

同一 30 帧测试脚本，`captureScreen({mode:'fast',size:720,timeout:2000})`，实际画面尺寸 1080×2248：

| 指标 | dev575 原实现 | 优化本地测试包 |
|---|---:|---:|
| 成功帧/错误 | 30 / 0 | 30 / 0 |
| 总耗时 | 10254ms | 9921ms |
| 取帧 p50 | 354ms | 340ms |
| 取帧 p95 | 365ms | 354ms |

新版日志明确输出 `hardware-direct, no full Bitmap/ByteBuffer copy`，说明直读确实生效。新版测试时系统录屏会话属于 `com.android.systemui`，测试结束后仍在进行。

旧版本用户连续 YOLO 日志有每隔数秒回收 64–74MB 大对象的记录；新版 30 帧取帧测试期间没有同类 app 进程 GC 记录。此结果仅是短测，不代表长稳无 GC，也不能把 GC 总耗时当成 UI 停顿时长。

重要边界：本轮取帧延迟改善约 4%，而不是十倍提速。独立无障碍截图仍约 3 FPS；减少内存分配/回调线程中转不等于绕过系统的截图频率上限。两个版本测试期间录屏/画面负载未完全控制一致，不作为严格跨负载性能评测。

## 验证

- 三个 ABI 的原生库重新编译成功。
- 主应用构建成功，既有截图状态 7 项测试通过。
- 实机直读和连续 30 帧零错误已验证。
- 系统录屏开启时，YOLO 兼容示例完成 60 帧、累计 59 个检测结果；实际取帧约 3 FPS。结束后 `dumpsys media_projection` 仍显示 `com.android.systemui` 的录屏会话。
- 新版取帧及 60 帧 YOLO 短测期间没有 app 进程同类大对象 GC 日志，不能据此断言所有界面卡顿都已消失。
- 未测试非 RGBA 回退、API 21 实机、Android 16；未更新用户已有的 template.apk。

官方依据：[原生 HardwareBuffer API](https://developer.android.com/ndk/reference/group/a-hardware-buffer)、[Android 15 AOSP 截图间隔定义](https://github.com/aosp-mirror/platform_frameworks_base/blob/android15-release/core/java/android/accessibilityservice/AccessibilityService.java)。
