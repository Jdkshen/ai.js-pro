# A1-5 脚本侧 Aapt2 评估（W2，结论：不做）

- 任务：task-71 ①。范围：只出 1 页评估 + 回填方案 A1-5 终态。**不改主源**。

## 1. Pro 有没有脚本侧 aapt2？——有
证据（源码树 .artifacts/AutoJsPro源码树-2026-11-09）：
- com/stardust/autojs/core/ui/aapt/Aapt2.java：Kotlin 类，公开面是 compile(res, outPath) / link(res, manifest, pkg, args, outPath) / list / listAllFiles，返回内嵌的 CommandResult；
- com/stardust/autojs/core/ui/aapt/Aapt2Exception.java：aapt2 执行失败的具名异常；
- 内嵌类里有 **PluginNotLoadedException / PluginVersionNotSupportedException** → **Pro 的脚本侧 aapt2 是「插件门禁」能力**（没装/版本不符就直接不可用）；
- 被 org/autojs/autojspro/v8/api/global/V8AutoJsGlobal.java 引用 → **具备脚本可见性**（具体暴露名未逐字确认，记为边界）。

## 2. 我们这边现状：构建期有、脚本侧没有
- 构建期：MCP 工具链把 aapt2 当**组件**用 —— McpBuildTools.kt:17/21/38/116（组件表 java/javac/keytool/d8/smali/gradle/aapt2/zipalign/apksigner/app_process；requiredComponents 含 aapt2；appPrivateComponents 含 aapt2），AndroidReverseRuntime.kt:684 直接落一份 aapt2 二进制调 apk-resources。
- 脚本侧：**没有任何** aapt2/Aapt2 包装（全仓仅上述构建链路命中）。

## 3. 真实用途 vs MCP apk_build* 的重叠
| 脚本侧 aapt2 的潜在用途 | 今天用什么覆盖 | 结论 |
| --- | --- | --- |
| 把 res/ 编成 .flat、再 link 成 resources.arsc 打包 APK | MCP apk_build（完整链路：aapt2/d8/zipalign/签名）、apk_build_project（工程级）、chain_resume（checkpoint→回编→签名→验签） | **已覆盖**（脚本可通过工具桥调用，且比裸 aapt2 更安全） |
| 读回已编译资源（arsc/AXML 结构） | apk_decode_project、apk_verify 的清单/签名结果、apk_dex_* 家族 | **已覆盖** |
| 运行期做 Android 界面 | ui.layout / AndroidResources（XML 直接 inflate，**不需要 aapt2**） | **不需要 aapt2** |
| 在设备上增量改一个资源再重打包 | 目前要走 MCP 的 workspace/session 工具链（apk_workspace_open → apk_session_* → apk_build） | **部分覆盖**；若真有强需求，更该扩 apk_build 的参数（如 --extra-res）而不是放开裸 aapt2 |

## 4. 成本/风险
- **暴露面**：要么给脚本一个能跑任意 aapt2 命令的命令行包装（等于放开本机任意路径写 + 资源编译，路径穿越/资源炸弹/耗时无上限都要自己兜），要么按 Pro 那样做**插件门禁**（需要插件分发与版本协商，我们目前没有 aapt2 插件体系）；
- **收益**：真实用户场景（自建 APK/改资源）MCP 已经端到端覆盖，且我们的 MCP 还多了签名/验签/会话/回滚；脚本侧再开一份**只会形成第二套构建路径**（口径漂移、权限面扩大）；
- **判据**：没有「MCP 做不到而脚本侧 aapt2 能做」的具体用例 → 不满足「确缺才做」。

## 5. 结论与终态
**不做（A1-5 关闭）**。理由三句：① Pro 的脚本侧 aapt2 是插件门禁能力，不是核心脚本 API；② 我们的 MCP apk_build*/apk_decode_project/chain_resume 已覆盖其真实用途（且更安全、可审计）；③ 放开裸 aapt2 会新增任意路径写与资源编译的攻击面，收益为 0。
**将来要重开的条件**（写进方案）：出现「必须在脚本里做 MCP 做不到的增量资源编译」的具体用户案例，且我们愿意按插件门禁形态交付（而不是裸命令包装）。

## 附：工具链审计脚本用法（W3 交付，本次顺带写进小结）
tools/apk-native-lib-audit.mjs 用来核对一个产物的 lib/ 是否「每个 .so 都有来源」：
~~~
node tools/apk-native-lib-audit.mjs <apk> --expect-abi arm64-v8a [--expect-abi armeabi-v7a] --fail-on-leak
~~~
- 判据：**leaks=0**（对不上「模板必需/工程策略/内建 OCR」的 .so）、**unknown=0**（未识别项要显式归类，别留灰区）、**missingAbi=[]**（声明了却没产出）；
- 典型用法：① 打包策略改动后核对产物（与 task-63 的 NativeLibPolicy 同一套判据）；② 出 v7a 时确认两个 ABI 的条目齐全；③ 模板重建后回归（配合 K40 的 project copy excludes / abis / plugins 三条日志）；
- 配套：tools/verify-16kb-alignment.ps1（16KB 页对齐）、MCP 侧 apk_verify（逐方案签名结论）。
