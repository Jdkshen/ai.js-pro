# 象棋棋子检测：**速度与精度**权衡分析（供 GPT 分析）

> 背景：手机端「象棋自动走棋」脚本的视觉识别系统。目前识别质量已经不错，但仍有强化的空间：
> **推理要快（实时闭环），识别要准（错一个子就下错棋）**。请基于本文的数据与约束，给出优化方案排序。

2. 哪些方向**收益最大、风险最低、验证最快**？请排序并给出预估（延迟/精度/工程量）。
3. 是否有我们没列出的方向（架构/量化/时域/级联/数据）？

## 1. 系统全景

```
截屏(1080×2400 级) → 棋盘定位(90 交点网格) → 裁剪棋盘区域(外扩0.75格)
    → YOLO 棋子检测(7类, ONNX) → 检测框→格点分配 → 格心颜色采样判红黑
    → FEN → 象棋引擎 → 点击落子 → 等对手走子 → 重新截屏
```

**关键约束（不可轻易变更）：**

| 项 | 约束 |
|---|---|
| 推理后端 | OpenCV DNN（CPU），Android 手机 |
| 模型格式 | end2end ONNX，opset 12，**输出 [1,300,6] = x1,y1,x2,y2,score,classId**（图内含 TopK 选取，无 NMS 节点；App 侧按 score 过滤） |
| 输入几何 | 支持方形 `inputSize=N` 与竖屏矩形 `inputWidth×inputHeight`（如 160×320），矩形是 QuickJS 引擎能力，已可用 |
| 类别 | **7 类兵种**（车 马 相 仕 帅 炮 兵，红黑合并）；颜色由格心采样后处理补上 |
| 训练环境 | **无 GPU**（Ryzen 7 5800H，CPU 训练；160 方形 50 epoch ≈ 1.5 小时） |
| 目标设备 | 中低端 Android（K40 等） |
| 场景特征 | 棋盘 ~9×10 格、最多 32 子；棋子基本**静态**，只在落子/点击瞬间变化；同应用有 2 种以上视觉主题 |

**当前模型**：YOLO26n 微调版（2,376,201 参数，5.3 GFLOPs @160），已部署手机，单帧竖屏 160×320 推理 **10.6ms**（新机实测）。

## 2. 实测数据（核心依据）

### 2.1 延迟 vs 输入几何（K40 实测，同一模型家族）

| 输入几何 | 单帧推理 | 等效质量档 |
|---|---|---|
| 方形 160 | 7.4 ms | 低 |
| **竖屏 160×320** | **12.4 ms** | ≈方形 320 |
| 方形 320 | 21.3 ms | 中 |
| 竖屏 288×640 | 37 ms | ≈方形 640 |
| 方形 640 | 80 ms | 高 |

> 新机（2602BRT18C）实测竖屏 160×320 全链路 = 10.6ms（预处理 0.6ms + 推理 10.0ms）。
> 竖屏屏 1080×2400 套**方形**输入时左右各 ~40% 是灰边白算；换竖屏矩形后「内容不变、算量减半」。

### 2.2 精度 vs 几何/内容（QQ象棋真实截图，36 张 892 框，均 IoU≥0.5、conf 0.25）

| 识别链路 | 棋子像素高 | v2 | v3n | **v4（当前）** |
|---|---|---|---|---|
| 全屏 → 方形 160 | ~8 px | F1 0.683 | 0.707 | **0.820** |
| 全屏 → 竖屏 160×320 | ~16 px | F1 0.766 | 0.759 | **0.867** |
| 裁剪棋盘 → 方形 160（工程实际链路） | ~17 px | R 0.720 | 0.714 | **R 0.794** |
| 天天象棋 np26（成熟域）| — | R 0.95 | R 0.97 | ~R 0.95 |

**重要经验值：棋子输入像素高 6–9px 时分类崩（位置能学会、类别学不出）；13–18px 正常。**

### 2.3 失败案例特征（已定位）

- 某「浅色盘 + 细笔画棋子 + 低对比」主题的残局页：16px 下模型输出**低置信+类别混乱**（召回 0.17–0.6）；
- 用**竖屏 320×160 几何**微调 30 轮后该难点帧召回 **0 → 1.00**；但同权重导出回方形 160 只有 0.62
  → 结论：**训练几何必须匹配推理几何**；低对比样式对像素尺度更敏感。

### 2.4 已尝试过的方向与结果

| 方向 | 结果 |
|---|---|
| 调训练配方（cos_lr、aug scale、域数据×15 过采样） | 打平，无增益 |
| 新数据（×30 过采样）+ 双尺度(1280/1600)类别仲裁 | 全屏 F1 +0.10（离线） |
| 棋规后处理约束（非法位置/缺王/超量 → 自动修正） | 输出错误 50→0（离线） |
| 竖屏矩形输入替代方形 | 同延迟下精度提升（已落地） |
| 多帧时序融合（temporal fusion） | 工程已有基础，未做预算分配优化 |

## 3. 候选方向（请评估/补充/排序）

**A. 几何与级联**
1. 棋盘裁剪后**按格距自适应缩放**，让棋子恒定落在 14–16px 最优区间（不同机型/主题自适应）
2. **两级级联**：先低分辨率（方形 128/160）全盘跑；对低置信框只做局部 ROI 高分辨率复检（每帧 ≤3 个小 crop）

**B. 模型与部署**
3. 更小/更快架构（剪枝、轻 backbone、蒸馏），或 160×320 原生训练（目前多为方形训练再导出矩形）
4. **INT8 量化**：OpenCV DNN 对量化 ONNX 的支持度？ARM CPU 实测收益/精度损失？（请给出可行路径与坑）
5. 替代运行时（NCNN/MNN/ORT-mobile）：App 目前只走 OpenCV DNN —— 评估改造价值 vs 代价；或建议「双后端+回退」

**C. 运行时策略（时域）**
6. **事件驱动调度**：只在「点击后 / 对手走子动画结束后 / 画面差异超阈值」触发识别；静态期零推理
7. **增量检测**：画面差分只对变化区域重跑（涨落点有限）
8. 已有时间融合 → 如何做**每帧预算分配**（如 10ms/帧预算下怎么排 GPU… 不，CPU 核/线程/跳帧）

**D. 数据与训练**
9. 训练时**多尺度几何一致性**增强（避免「训 8px、考 16px」错配）
10. 难例挖掘：低对比主题专项；不同主题按「视觉域」管理采样权重

**E. 后处理**
11. 棋规/时序一致性继续吃错误（开销 ~0，可放大利用）

## 4. 现状与目标的差距（请按此给方案）

| 维度 | 现状 | 诉求 |
|---|---|---|
| 单帧推理 | 10–12ms（160×320） | ≤10ms（越低越好） |
| 全链路 | ~15-30ms（截屏+定位+推理+后处理） | 保持流畅闭环（每步棋内可多次采样） |
| 主场景精度 | 对局页 R≈0.9–1.0 | 全主题 ≥0.98（含低对比残局页） |
| 泛化 | 2 个 App/主题已覆盖 | 新主题零样本或少样本可用 |
