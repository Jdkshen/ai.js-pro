# 「悬浮窗关闭不了」定位与修复（dev-1352）

> 用户反馈：悬浮窗好像有 bug，关闭不了。以下把**两类悬浮窗**都实测了一遍，定位到真正的缺陷并修掉。

## 一、先分清两类窗口（都实测过）

| 类型 | 归属 | 实测关闭方式 | 结果 |
|---|---|---|---|
| 脚本悬浮窗（`floaty.window`，示例「悬浮窗/悬浮文字.js」） | `:script` 进程 | 真实 `input tap` 点右上角 ×（25dp） | ✅ 窗口消失、`exitOnClose` 生效、脚本结束 |
| 同上 | 同上 | `window.close()` / 同脚本 `floaty.closeAll()` | ✅ overlay 计数归 0 |
| 同上 | 同上 | MCP `close_overlays`（全部 / 按 executionId） | ✅ `dumpsys window` 里该窗口真的消失（不是只改计数） |
| 同上 | 同上 | 停止脚本 / `stop_all_scripts` | ✅ 计数归 0 |
| **应用自身悬浮球**（`CircularMenu`，48dp，主进程常驻） | 主进程 | **以前没有任何可靠入口** | ❌ 本次修复对象 |

结论：示例里的脚本悬浮窗**关闭是好的**；用户说的「关不掉」是**应用自己的悬浮球**（无脚本时也常驻在屏幕上）。

## 二、根因（两处，都在关闭路径上）

1. **`CircularMenuWindow.close()` 三步清理串在同一个 try 里**：

```java
try {
    ...保存位置...; mDragGesture.cancel(); mOrientationEventListener.disable();
    getWindowManager().removeView(mCircularActionMenu);   // ← 菜单没 inflate/attach 时这里抛异常
    getWindowManager().removeView(mCircularActionView);   // ← 永远不执行
    FloatyService.removeWindow(this);                     // ← 永远不执行
} catch (Exception e) { e.printStackTrace(); }            // ← 异常被吞，用户看到「点了没反应」
```

只要第一步失败（悬浮球只展开过/从没展开、菜单视图未 attach），**小球就留在屏幕上**，且没有任何提示。

2. **`FloatyWindowManger.hideCircularMenu()` 先 close 再清引用**：一旦 close 内部部分失败，`sCircularMenu` 仍非空 → `isCircularMenuShowing()` 从此恒为 true → `showCircularMenuIfNeeded()` 认为「已经在显示」不再重建，`hideCircularMenu()` 又因引用陈旧而无效（既关不掉也打不开）。

## 三、修复

1. `CircularMenuWindow.close()` 重写：状态保存/手势/监听各自 try；**三步移除彼此独立**，新增 `removeViewSafely()`（`null`/`getParent`/`isAttachedToWindow` 判断 + 失败时 `removeViewImmediate` 回退 + `Log.w` 记录），`FloatyService.removeWindow` 与 `onClose` 回调也各自兜底。
2. `FloatyWindowManger.hideCircularMenu()`：**先摘引用再关闭**，并对 `close()` 兜 `Throwable` + 日志。
3. 新增 MCP 工具 **`floating_menu {action: state|show|close}`**：主线程执行（WindowManager 要求），返回真实 `showing/suppressed/windowType`，让「关不掉」时有一个**确定可用**的关闭入口（也便于机器验证）。公开入口 **212**（203+9）。

## 四、真机验证（MI8 / dev-1352）

```text
floating_menu {action:"state"} -> showing=true, suppressed=false, windowType=2038
dumpsys window 中本包 APPLICATION_OVERLAY 窗口数 = 2
floating_menu {action:"close"} -> showing=false
dumpsys window 本包窗口数 = 0          ← 真的移除了，不是只改计数
floating_menu {action:"show"}  -> showing=true；窗口数回到 2
```

脚本悬浮窗侧的真实点击验证（修复前后一致）：

```text
浮窗窗口 frame=[0,77][374,202]；input tap 340,111（右上角 25dp × 的中心）
-> list_overlays: 1 → 0；窗口从 dumpsys window 消失；脚本 STOPPED（exitOnClose 生效）
```

## 五、边界

1. `floating_menu` 只管**应用自身悬浮球**；脚本悬浮窗仍由脚本自身、`close_overlays` 或停止脚本来关闭（三条路径均已实测可用）。
2. `showing` 来自主进程内存引用；**是否真的在屏幕上以窗口列表为准**（工具说明里已写明，避免又一次「看起来关了」）。
3. 本次未做多 ROM/多机型验证（只在 MI8 上）；未改悬浮球 UI 布局与位置持久化逻辑。
