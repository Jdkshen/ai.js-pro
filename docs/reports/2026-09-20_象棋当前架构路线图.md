这张图里最关键的一条闭环是：**识别 → 思考 → 落子前复核 → 点击 → 重新截图 → 落子确认 → 更新可靠基线**。点击成功本身不算走棋成功，只有新画面通过确认后才能进入下一回合。

## 2. 新视觉管线内部路线

```mermaid
flowchart LR
    INPUT["截图 + 已标定的 9×10 网格"] --> SESSION["长生命周期 DetectionSession"]
    SESSION --> DETECT_STAGE["detection-stage<br/>缩放、矩形输入、region/aspect、坐标还原"]
    DETECT_STAGE --> ADAPTER["aijs-adapter.detect"]
    ADAPTER --> YOLO["AI.js Pro 新引擎<br/>本地 YOLO ONNX"]
    YOLO --> BOXES["候选框 + 置信度"]
    BOXES --> PIECE_DETECTOR["piece-detector<br/>排序、截断、映射到 9×10 交点"]
    PIECE_DETECTOR --> CROPPER["piece-cropper<br/>按交点或检测中心裁棋子"]

    CROPPER --> OCR["PP-OCR Session<br/>识别字形：车马相仕帅等"]
    CROPPER --> COLOR["piece-color + ink-color<br/>从像素判断红方或黑方"]
    BOXES --> LABEL["YOLO 类别<br/>只作候选或兜底证据"]

    OCR --> FUSION["evidence-fusion<br/>位置、字形、颜色、置信度、多帧证据融合"]
    COLOR --> FUSION
    LABEL --> FUSION

    FUSION --> KING["inferKings + rescueKings<br/>结合九宫约束和 board-scan 补救将帅"]
    KING --> VALIDATOR["board-validator<br/>规则与安全校验"]
    VALIDATOR --> OUTPUT["chars：控制层使用的棋盘<br/>rawChars：未经最终修复的观测<br/>evidence / timing：诊断信息"]

    OCR_RUNTIME["vision/ocr-runtime.js<br/>已存在，但当前生产管线尚未统一从这里调用"]
    OCR_RUNTIME -.待接入.-> OCR
```

各算法的职责边界如下：

| 模块 | 唯一主要职责 | 不应承担的职责 |
|---|---|---|
| YOLO | 找到棋子在哪里、提供候选框 | 单独决定最终棋子身份和红黑方 |
| PP-OCR | 识别棋子上的汉字 | 仅凭文字颜色猜阵营 |
| 像素颜色算法 | 区分红字和黑字 | 推断棋子名称 |
| 多帧融合 | 合并连续帧证据、抑制偶发误识别 | 绕过棋盘规则直接改局面 |
| 规则校验 | 检查数量、将帅、阵营和局面合理性 | 生成搜索着法 |
| auto-driver | 管理轮次、可靠基线、点击闭环和恢复 | 直接实现视觉模型 |
| engine/search | 在可信局面上生成合法着法 | 决定识别结果是否可信 |

## 3. 自动走棋状态路线

```mermaid
stateDiagram-v2
    [*] --> STOPPED
    STOPPED --> INITIALIZING: 启动自动走棋
    INITIALIZING --> CALIBRATING: 基础能力就绪
    CALIBRATING --> WAIT_STABLE: 定位与几何校准成功
    WAIT_STABLE --> WAIT_STABLE: 帧不稳定、存在未知格或关键冲突
    WAIT_STABLE --> WAIT_TURN: 轮到对方或轮次暂时未知
    WAIT_STABLE --> THINKING: 稳定可信且轮到我方
    WAIT_TURN --> THINKING: 新观测确认轮到我方
    THINKING --> PRECHECK: 搜索得到合法着法
    THINKING --> SUGGESTED: 建议模式只输出着法
    SUGGESTED --> SUGGESTED: 同一局面继续等待
    SUGGESTED --> THINKING: 局面变化且需要重新计算
    PRECHECK --> CLICKING: 新观测与计划仍一致
    CLICKING --> VERIFYING: 起点和终点点击完成
    VERIFYING --> WAIT_STABLE: 新局面确认成功，清空旧稳定快照

    WAIT_STABLE --> RECOVERING: 棋盘几何不可信
    WAIT_TURN --> RECOVERING: 长时间无法确认轮次
    THINKING --> RECOVERING: 算棋失败或思考期间局面变化
    PRECHECK --> RECOVERING: 棋盘已变化或着法失效
    CLICKING --> RECOVERING: 点击异常
    VERIFYING --> RECOVERING: 局面未变化或验证超时
    RECOVERING --> WAIT_STABLE: RECOVERED，重新稳定观察

    INITIALIZING --> PAUSED: 用户暂停
    WAIT_STABLE --> PAUSED: 用户暂停
    WAIT_TURN --> PAUSED: 用户暂停
    THINKING --> PAUSED: 用户暂停
    PRECHECK --> PAUSED: 用户暂停
    PAUSED --> WAIT_STABLE: 恢复
    PAUSED --> STOPPED: 停止
    WAIT_TURN --> GAME_OVER: 检测到对局结束
    WAIT_STABLE --> GAME_OVER: 检测到对局结束
    INITIALIZING --> ERROR: 不可恢复错误
    CALIBRATING --> ERROR: 不可恢复错误
```

`THINKING` 是状态机状态，`COMPUTE` 是它发给驱动的算棋动作；驱动优先交给 `search-worker`，不可用时再走同步引擎。悬浮窗中的不稳定帧会被直接丢弃并等待下一帧，不会因此进入 `RECOVERING`。

恢复阶段当前还有一条专门的基线重建路线：

```mermaid
flowchart LR
    FAIL["点击后验证失败或观测冲突"] --> FLAG["needFreshBaseline = true<br/>清理旧的协同证据"]
    FLAG --> FRESH["重新截图并完整识别"]
    FRESH --> TRUST{"几何、稳定性、规则可信？"}
    TRUST -->|否| RELOCATE["重新定位或继续等待"] --> FRESH
    TRUST -->|是| UNKNOWN{"未知格是否在配置上限内<br/>且每格都能由已知事实补齐？"}
    UNKNOWN -->|否| FRESH
    UNKNOWN -->|是| REBUILD["重建可靠基线<br/>丢弃过期 known facts"]
    REBUILD --> LOOP["回到 WAIT_STABLE / WAIT_TURN"]
```

## 4. 当前架构与建议目标架构

当前两个入口仍各自装配依赖，主页面和悬浮窗实际走的识别路线不一致：

```mermaid
flowchart LR
    MAIN["main.js"] --> MA["自行装配 board-service"] --> LEGACY["旧识别"]
    FLOAT["悬浮窗运行与测试.js"] --> FA["自行装配 board-service"] --> NEW["新视觉管线"]
    NEW --> FALLBACK["旧识别兜底"]
    MA --> DRIVER1["auto-driver"]
    FA --> DRIVER2["auto-driver"]
    BOOTSTRAP["app/bootstrap.js"] -.已有框架，但尚未成为两个入口的统一生产装配点.-> MA
```

建议最终收敛为一条装配路线：

```mermaid
flowchart LR
    MAIN["主页面"] --> BOOT["统一 bootstrap / application controller"]
    FLOAT["悬浮窗"] --> BOOT
    BOOT --> SERVICE["唯一的 board-service 装配规则"]
    SERVICE --> PIPE["新视觉管线"]
    PIPE --> GATE{"可信？"}
    GATE -->|是| DRIVER["auto-driver"]
    GATE -->|否| LEGACY["受控旧识别兜底"] --> DRIVER
    DRIVER --> ENGINE["engine/search"]
    DRIVER --> EXEC["click-executor"]
    EXEC --> VERIFY["fresh frame + move-verifier"] --> DRIVER
```

## 5. 对当前架构的判断

当前路线的主体已经合理：YOLO 负责位置、OCR 负责字形、像素负责阵营，多帧证据经过规则校验后才进入控制层；点击以后还要重新观测和验证，符合自动走棋需要的安全闭环。模型和算法均在 AI.js Pro 本地运行，不依赖云端推理。

目前仍有五处需要继续收敛：

1. `main.js` 尚未接入新视觉管线，主页面与悬浮窗的识别结果可能不一致。
2. `vision/ocr-runtime.js` 尚未成为生产 OCR 的统一入口，当前管线直接使用 PP-OCR Session。
3. `app/bootstrap.js` 还没有成为两个 UI 入口的共同装配点。
4. `auto-driver.js` 同时承担观测、历史事实、轮次、恢复和点击编排，后续应拆出独立的观测仓库与恢复策略。
5. 视觉观测与 `known facts / reliable baseline` 之间仍可能冲突；正在修改的恢复逻辑必须坚持“新鲜可信观测优先、确认后再推进基线”。

## 6. 推荐实施顺序

```mermaid
flowchart LR
    A["1. 固定恢复和基线重建语义"] --> B["2. 用真机回放验证点击闭环"]
    B --> C["3. 将 ocr-runtime 接成统一接口"]
    C --> D["4. 主页面接入同一 board-service 视觉装配"]
    D --> E["5. 两个入口统一交给 bootstrap"]
    E --> F["6. 再拆分 auto-driver 的观测与恢复职责"]
```

先保证“能连续完整走棋”，再做入口和模块收敛。这样每一步都能用现有真机日志、截图、回放和自检工具验证，不会一次性重构后失去故障定位依据。
