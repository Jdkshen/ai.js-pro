# 全盘 OCR 补正的「写基准前闸门」 + 几何体检（2026-09-20，K40）

> 上一轮真机的拦路石不是颜色，而是**可靠基准被单帧 OCR 读数改漂**：
> 基准里出现重复黑炮 `(4,4)+(4,5)`、红帅 `(4,9)` 丢失、`(7,7)` 变 N，
> 于是确认阶段反复 `UNRELIABLE：起点/落点附近有 2 格对不上`、轮次推断永远解释不通。

## 1. 问题链（真机日志 09:51–09:52）

```
[driver] 全盘 OCR 改正 2 格：(2,3)空→C(OCR 炮)；(4,6)空→c(OCR 炮)     ← 单帧 OCR 直接写盘面 + 基准
[driver] 票据里的盘面已按当前基准重建：… 新 base=…/4c4/4c4/…            ← 基准里出现重复黑炮
[driver] 确认：UNRELIABLE：起点/落点附近有 2 格对不上 …                 ← 每帧都解释不通
```

原因：`applyOcrBoardFixes` 把**一帧**的 OCR 读数当成事实 —— 写进观测盘面、登记进 `knownPatches`、
并顺手改 `lastReliable`。而 OCR 本身会串（兵↔炮、士→H）、会被落子动画/高亮环挡住，单帧不足为凭。

## 2. 三道闸门（`src/automation/auto-driver.js`）

| 闸门 | 规则 | 配置 |
|---|---|---|
| ① 字符合法 | 只认 `rnbakcpRNBAKCP`；`?`、空串、垃圾字一律**不写** | 常量 `PIECE_CHAR_RE` |
| ② 分数 | 低于阈值的字形只记录、不采纳（面板过滤过一道，这是第二道） | `ocrPatchMinScore: 0.6` |
| ③ 连续帧共识 | 同一格要连续 N 帧给出**同一个字**才写盘面/`knownPatches`/基准 | `ocrPatchFrames: 2` |
| ③′ 翻色更严 | 补正会**翻颜色**时（模型说红、像素说黑）：N 帧 + **像素（找色）必须给出决定性结论**且与之相符 | `ocrPatchFlipFrames: 3` |

实现要点：

- **分两层写**（真机跑完一轮后加的）：
  · **本帧观测**（`chars`）**立即**用证据改 —— 它只活这一帧，专给同帧的验证/轮次推断用。
    只卡基准的话，模型把 (4,4) 炮读成卒这类格子会把整手确认拖成 UNEXPECTED（真机 10:14 现场）；
  · **可靠基准 / `knownPatches`** 才要连续 N 帧共识（那才是跨帧生效的账本）。
- 一帧 = **一次全盘 OCR 询问**（限频 `ocrBoardCooldownMs`，两帧至少隔 6 s）；面板把 `at`（帧标识）
  随结果一起给出来，命中缓存（1.2 s）时它不变 ⇒ **重复问同一帧不能凑帧数**。
- 找色结论来自 `board-scan` 的 `sides[i]`（`RED`/`BLACK`/`UNKNOWN`）：`UNKNOWN` 时**不许翻色**；
  与补正方向矛盾（像素说红却要写成黑）同样驳回。
- 待定/驳回都留痕：`全盘 OCR 待定 X 格／驳回 Y 格（连续 2 帧一致才写基准，翻色要 3 帧）：(8,9)R→c（第 1/3 帧）`，
  并计入 `stats().ocrBoardPending / ocrBoardBlocked`（体检输出里能看到）。
- 闸门账本在 `assertTurn` / `newSession` / `stop` / `setMySide` / 已知事实被作废时清空 —— 换基准就重新数帧。

## 3. 证据链

- `board-scan.js` 现在把**逐格 OCR 分数**（`scores`）一起返回；面板 `ocrBoard()` 把 `scores` 与 `at` 交给驱动。
- 自检（PC，`node tools/self-check.js`）189 → **193**，新增/改写的三条：
  1. 「全盘 OCR 改正：兵种取字形、颜色取像素，且**翻色要连续 3 帧**」——
     第 1、2 帧基准必须还是旧的（`R`），第 3 帧才变 `c`；
  2. 「像素没给结论 / 与像素矛盾 ⇒ 永不写基准」（连跑 5 帧验不变 + `blocked` 计数）；
  3. 「`?` 与低分字形永不进盘面与基准；合法高分要连续 2 帧」；
  4. 「几何体检：整行偏一格的假几何必须被认出来」。

## 4. 同一轮真机顺带抓到的两个几何坑（已修）

同一轮日志里还发现：定位/校准链路本身在不声不响地给错几何 —— 它同样会把基准弄脏。

### 4.1 线定位「成功」也可能整行偏 → `grid-sanity` 体检 + pickGrid 兜底

真机现场（中局帧）：`locateBoard` 返回 `origin.y = 590`，而棋盘第 0 行在 ~690（差 ≈0.87 格距），
精校准照样报「未知格 0」（偏移接近一整格时 90 个交点全落在格子上，只是全错一行）。
后果：黑方底线读到第 1 行、红方底线（真第 9 行）掉到网格外 ⇒ 布局、基准、票据全错。

- 新增 `src/vision/grid-sanity.js`：**极端行**（0/9）一个子证据都没有、相邻行（1/8）却 ≥6 个 ⇒ 判可疑。
- 面板 `locateAndCalibrate` 在「线定位成功」后跑一遍体检，不过就按「定位失败」走 `pickGrid` 缓存框搜索。
- 真机实测：`线定位几何体检不过（第 0 行一个子都没有、第 1 行却有 7 个）→ pickGrid 成功（800 候选）→
  校准完成：几何 v1 偏移(-22,-2) 未知格 0`，布局变成 `r1bakabn1/9/7c1/pCp1p1p1p/…/2BAKABNR`（与截图逐格核对一致）。

### 4.2 几何缺 `quality` ⇒ 状态机永远判「几何不可信」

`geometry.isTrustworthy` 要看 `grid.quality.inlierCount/maxResidual`，而 `pickGrid`/`calibrateGrid` 出来的 grid
不带这两个字段 ⇒ `信任=false` ⇒ `RECOVERING｜几何不可信：`（连原因都是空的）。

- 面板新增 `attachGridQuality`：用**检测框到交点**的归一化残差补上 `quality`（与 `piece-detector.mapToCells` 同一把尺），
  并在日志里打出「几何质量：样本 N｜鲁棒最大残差 0.xxx」。
- 驱动在 `GEOMETRY trusted:false` 时补上原因（`几何质量不足：{…}`），不再出现空原因。
- **两个细节**（真机 10:21 那轮调出来的）：
  · 残差取**鲁棒最大值**（丢最差 10%）：单个跑偏的检测框不该把整块几何否掉；
  · 可信阀值 `maxResidual` 从 0.35 放到 **0.40**（与 `piece-detector.maxCellDistance: 0.38` 对齐）。
    依据：pickGrid+校准落下来的网格与交点会固定偏 ~⅓ 格（实测 mean 0.335 / max 0.369），
    而**颜色与落点都是锚在检测框上的**（不是交点）—— 偏零点几格不影响判色与点击；
    真正致命的「整行/整列偏」已由 `grid-sanity` 体检拦住。
- 另外：`grid-search` 的「必须看到双方将帅」从**硬拒**改成默认**软惩罚**（cost +250）。
  真机后果：模型对帅/将召回差 ⇒ 每个候选都被否 ⇒ `pickGrid 也失败：最优候选不合用：将帅数量异常（1）`
  ⇒ 定位彻底做不出来。与“兵种超限默认软惩罚”同一道理（缺将帅是识别问题，不是几何问题）；
  需要严格求值时显式传 `requireKings: true`（契约测试 `tools/test-cells-contract.js` 新增一条守着）。

## 5. 帅/将抢救：不再因「红帅数量 0」把整帧退回旧路径（同日）

真机日志反复出现 `视觉流水线不可信 ⇒ 退回旧路径：局面不可信：红帅数量 0（应为 1）`，本轮观察直接作废。
根因：**帅那一格检测框没检出**（模型对帅/将召回差）⇒ 融合层里连证据都没有（不是 `?`）⇒
`inferKings`（只吃 `?` 格子）无从下手 ⇒ 规则门报缺帅。

修（用户指定：走 `board-scan` 的字形 + 找色证据，而不是整帧退回）：

- `board-scan.scan` 新增 `options.only`（只扫指定格子）与 `minScore` 覆盖；
- `vision-pipeline.rescueKings`：融合后若缺帅或缺将，就用 `board-scan` 只扫**它自己的九宫**
  （红 7–9 行 / 黑 0–2 行 × 3–5 列，共 9 格，≈0.4s），字形认兵种、**找色判颜色**；
  九宫里**恰好一个**候选才补（0 个=没找到、多个=有歧义，都不动），命中后重新过规则门；
- 新增配置 `kingRescue`(true) / `kingRescueMinScore`(0.45，真机 帅 实测就在 0.5 上下)，统计 `stats.kingRescued`，
  日志 `帅/将抢救：(4,9) = K（board-scan 字形 帅 + 找色颜色，整帧不必退回旧路径）`；
- 自检 193 → **194**：正例（帅被抢救 → 规则门通过）+ 反例（九宫也读不到 ⇒ 不许猜）。

## 6. 抢救改成「YOLO 定位优先」（同日，用户要求）

用户口径：**yolo 定位放前面**。本帧的检测框 + 类别标签在抢救之前就已经算出来了 ⇒ 拿它当第一证据是**零额外开销**；
字形路要扫九宫 9 格（≈0.4s）甚至认不出帅 ⇒ 退第二路。

`rescueKings` 现在的顺序（都不猜：九宫里必须**恰好一个**候选）：

1. **YOLO 定位路（先）**：`label` 的类别为 K + `inkColor.judgeFor(该格检测框)` 的颜色与该方一致 ⇒ 用它。
   兵种仍**不取框的类别**（用户口径不变）：标签只决定「哪一格值得查」，落地靠
   「九宫 + 该方恰好缺一个 + 找色颜色对得上 + 宫中唯一候选」。
2. **字形路（①没找到才跑）**：`board-scan.scan(..., {only: 九宫 9 格, minScore})`，字形认兵种 + 找色判颜色，
   **命中必须恰好 1 个**（多个=有歧义，不补）。

统计 `kingRescuedByYolo`（原 `kingRescuedByLabel`），日志区分两路来源。

帅/将抢救：(4,0) = k（YOLO 框类别当候选 + 九宫 + 找色颜色） —— 整帧不必退回旧路径

⇒ 帅/将两格都走 YOLO 路（一次 OCR 都不用做），规则门通过；字形路仍由自检守护
