# SIFT C++ 后端与原生帧直连（dev-770）

## 实现

用户要求继续提速并下沉 C++。OpenCV 的 SIFT/FLANN 算法此前已经是 C++，dev-768/769 的 Java 后端负责组织调用和处理特征点。本版新增 `sift_matcher.cpp`，将特征提取、FLANN、Lowe 比率、RANSAC、四边形校验、坐标还原和绘图整体放到 C++。

- Java `SiftMatcher` 只保留参数校验和生命周期，API 名称保持 `images.matchSift` / `images.createSiftMatcher`。
- QuickJS 直接借用 NativeFrameStore 的 shared_ptr，不复制全图到 Java Mat；帧释放期间不会被池复用。Rhino 借用 Mat，JNI 参数保留 Java 对象，防止 native 调用期间被 finalizer 删除。
- C++ RAII 管理 Mat、特征点、匹配矩阵及算法对象；模板缓存、局部跟踪和全图回退保持原语义。场景灰度/缩放缓冲区及特征容器可复用，scale:1 时省去额外 resize。
- 临时 QuickJS 图像参数只使用短期令牌，调用后立即从 Java 句柄表释放，也不加入 JS Java 对象 Proxy 缓存。初版压力测试发现 Proxy 缓存累计造成内存耗尽，已修复，最终 70000 次令牌创建/释放通过。
- 结果新增 `backend: 'cpp'`、`inputMode`、`templatePrepareMs` 及 `timings.inputMs/featureMs/flannMs/geometryMs/drawMs`。缓存对象新增 `templatePrepareMs`。既有总耗时日志保留。
- 缓存示例预读大图，传图片对象，显式 scale:0.5，运行 10 次展示首次全图与后续跟踪耗时。图片读取、模板准备、每次匹配和分段耗时均可见。

## 对比测试

K40 / Android 16 / arm64。大图 1080×2340，模板 172×206；相同已解码图片、场景 scale:0.5、模板 scale:1，不绘图，预热后取 5 次中位数。Java 数据是在替换后端前本轮重新运行，Cpp 数据是安装临时构建后运行。

| 模式 | QuickJS Java → C++ | Rhino Java → C++ |
| --- | ---: | ---: |
| 单次全图 | 229 → 205 ms | 219 → 222 ms |
| 缓存模板，全图 | 218 → 178 ms | 212 → 193 ms |
| 缓存模板，稳定位置跟踪 | 33 → 9 ms | 14 → 13 ms |
| 单次传两个文件路径 | 260 → 272 ms | 271 → 267 ms |

明显改善是 QuickJS 的重复匹配，减少复制和桥接开销。Rhino 全图单次基本没有改善；全图仍由 SIFT 计算主导。文件路径模式仍需解码，不能声称所有调用都大幅提速。

典型 C++ 分段：全图特征提取约 160～185ms、FLANN 15～16ms、几何计算约0.4ms；路径读取约42～44ms。稳定局部跟踪特征约6～8ms、FLANN约1.5ms。模板准备是创建时的一次性耗时，未计入每帧 timings。每行测速可能受 CPU 调频影响，这里列出原始5次样本的中位数。

默认特征数量上限仍为0。1500/2000特征上限在这组图片上会漏匹配，未作为默认优化策略。跟踪首次/丢失时仍回到全图；正常返回坐标和至少6个可靠内点，局部跟踪至少8个。具体匹配数量有随机性。
