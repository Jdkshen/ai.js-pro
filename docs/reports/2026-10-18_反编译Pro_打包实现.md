## 0. 摘要（先看这 10 条）

1. Pro 9.3.11 的打包 UI 在 **Flutter**（`libflutter.so` + `libapp.so`），Java 侧只提供“构建后端”：`org.autojs.autojs.flutter.FlutterApkBuilderChannel` → `org.autojs.autojs.build.ApkBuilder`（混淆后为 `okhttp3.internal.io.দ` / jadx 名 `C5448`）。
2. 调用通道是 MethodChannel `nQPRx2ieVnafxSwxjtoU`，方法名是字符串数字 `"1"`~`"4"`；`"1"` = 打包，参数顺序为 **源路径、输出目录、project.json 字符串、signingConfig JSON、buildId(int)**。进度走另一个 BasicMessageChannel `VKokQgshvknFp7rIQglI`，payload 是 `{5:buildId, 6:event, 7:error, 2:outputPath}`。
3. 输出文件固定为 **`<输出目录>/<项目 name>_v<versionName>.apk`**（不 sanitize，中文/空格原样进文件名）。Java 侧不决定目录，目录由 Flutter 传入；Pro UI 默认是 **`/sdcard/脚本/APK输出/`**（仓库既有实机记录：`docs/reports/2026-10-18_打包MCP电脑连接_功能对照.md:24`）。
4. 模板是**轻量模板**：`assets/template/template.apk` 只有 **6,452,337 字节**（`com.stardust.autojs.inrt`，versionCode 9130900，targetSdk 28），**不含任何 `lib/`**；构建时再从“已安装的宿主 APK”里按 `assets/template/excluded-zip-files.json` 的 `general/opencv/v8` 清单补文件进来。
5. 模板释放路径是 **`externalCacheDir/template/9131100.apk`**（源码里是硬编码字面量，恰好等于本 APK 的 versionCode；疑似 Kotlin `const` 把 `BuildConfig.VERSION_CODE` 内联了），先写 `.tmp` 再改名；释放时会把 `general` 清单里的文件从宿主 APK 追加进模板 zip（zip4j，压缩级别 9）。Aapt2 另有一份自己的模板缓存：`cacheDir/template/<longVersionCode>.apk`。
6. 构建工作区是 **`cacheDir/build/`**，编译缓存是 `cacheDir/build-cache`；每次开始构建先递归删工作区，成功后再次删除；失败时**不删**工作区（只清理编译器）。
7. 清单/资源处理：直接改二进制 AXML（包名、versionCode/Name、label、provider authorities、组件名混淆、权限节点），然后**原地重写 `resources.arsc` 里的 256 字节包名字段**（不重新 link 资源）；图标是先解析 `resources.arsc` 找出所有 `ic_launcher`/`splash_icon` 条目，再把用户图覆盖到对应 `res/*` 文件。
8. 自定义 Android 资源（`project.json.androidResources`）走 `libaapt2.so` 子进程：`aapt2 compile` + `aapt2 link`，以 `assets/aapt/android.jar`（26,467,929 字节）和模板 APK 为 `-I`，`--custom-package/--rename-manifest-package <包名> --package-id 0x77 --allow-reserved-package-id`，产物是 `assets/project/<resDir>/resources.ap_`（给运行时自己的资源加载器用，不是 APK 的 resources.arsc）。
9. 签名：**默认 keystore 是所有人的同一份** `files/default_signature.jks`（JKS，alias `autojspro`，固定口令，CN=Default/O=Auto.js Pro，RSA 2048，有效期 27 年）；自定义签名经 MethodChannel 以 `SigningConfigWithPassword` JSON 传入（含 password/aliasPassword/hasSavedPassword 字段），Java 侧只按 keystore+alias+口令加载，未见校验/加密处理；签名用内嵌的 apksig 代码，**v1+v2+v3 全开**（签名者列表恒为 1 项）；签完**不做**校验。失败文案是 `签名错误，请重新设置签名`。
10. 与本仓库 POC 相比，最大的可落地差距：**输出目录不一致**（POC 是 `/sdcard/脚本/构建` 或 `<project>/build`）、**arsc 包名没改**（`ApkBuilder.buildArsc()` 是空实现）、**权限是 diff 而不是精确集合**、**没有组件混淆/aapt2 工程资源/插件与 OCR 资源/build hook/在线加密**、**模板 44.8MB 且不自带补全机制**、**进度只有 4 个阶段**、**签名只有 v1+v2**。

### 2.3 本 APK 的补丁层（必须区分）

- `org.autojs.autojs.build.NativeApkBuilder` 的 `nativeBuild/nativeOptimize` 不再声明 `native`，而是直接调 `LocalApkBuild.build/optimize`（`NativeApkBuilder.java:19-25`）。
- `libaumabuild.so` 不是打包器：它的符号只有 `Java_org_autojs_autojs_build_PublisherConfig_install/finish/configureDart`，字符串里有 `Local publisher configuration did not match this native build` 和 `org/autojs/autojs/localcatalog/LocalApkBuild`——是补丁的“发布者配置 + 离线构建”支撑库。
- `libcorepack.so` 是一个 85 字节 shell 脚本（`exec node …/corepack/dist/corepack.js "$@"`），与打包无关。
- `LocalApkBuild` 还负责 `cleanup()`（关闭编译器线程池）和 `approval()`（`LocalExecutionGate.verifyBuild`），并在构建前把 `features.nodejs` 从 `auto` 归一成 `enabled`（`LocalApkBuild.java:66-107`）。

### 4.2 释放路径与补全（qa5.m8364）

```text

  └─ template/
       ├─ 9131100.apk        ← 硬编码字面量（等于宿主 versionCode）；其他文件会被删
```

步骤（`qa5.java:71-177`）：
1. 先删 `cacheDir/template/`（旧实现遗留）。


## 5. 从项目目录到 APK：逐步流程

### 5.0 入口参数与合法性

- `MainParams(sourcePath, outputPath, projectConfig)` 这个 data class 也存在（`org/autojs/autojs/build/MainParams.java`），但 Flutter 路径实际用的是 `Params(x73)`。
- 包名正则（`C5448.java:591`）：
  ```regex
  ^(?:[a-zA-Z]+(?:\d*[a-zA-Z_]*)*)(?:\.[a-zA-Z]+(?:\d*[a-zA-Z_]*)*)+$
  ```

  不匹配抛 `IllegalArgumentException(R.string.error_invalid_package_name)`（中文：`无效包名，包名只能包含大小写字母、下划线、英文点号，并且至少在非首尾位置有一个英文点号，例如com.example`）。

### 5.1 事件与 hook 一览（先给全貌）


- Flutter 通过 method `"2"`/`"3"`/`"4"` 列出/读取/更新签名配置（Room 表存 keystore/alias/uuid 等；`password`/`aliasPassword` 是传输 JSON 的字段，是否落库未确认）：
  `{id, keystore, alias, uuid, password, aliasPassword, hasSavedPassword}`（`SigningConfigWithPassword.java`）。
- `getSigningConfigs()` 返回整个列表的 JSON；`getSigningConfig(uuid)` 返回单条；`updateSigningConfig` 做 `INSERT OR REPLACE`（`qa0.m8359/m8358`、`mo1886` 分支 2/3/4，`qa0.java:165-251`）。
- 打包时收到的 `signingConfigJson` 经 `toSigningConfig()` 去掉 `id`，保留 keystore/alias/uuid/password/aliasPassword/hasSavedPassword（`SigningConfigWithPassword.java:136-139`）。
- `C5448.m13846` 用 `signingConfig.keystore.isEmpty()` 判断是否使用默认 JKS；否则直接 `new FileInputStream(keystore).load(storePass)`，取 `alias` 的证书和私钥；任一为空抛 `SignatureException(R.string.error_signature)`（中文 `签名错误，请重新设置签名`）。
- password/aliasPassword 为 null 时 `fa1.m4144(...)`（requireNonNull）会 NPE——Pro 假定 UI 一定带口令。

### 7.3 签名实现

- `C5448.java:2886-2907`：
  ```java
  List<SignerConfig> signers = listOf(new SignerConfig("Auto.js Pro", privateKey, [cert]));
  boolean v3 = signers.size() <= 1;
  new C6004(signers, v3, true, "<out>_", "<out>")
      .sign(inputChannel, outputChannel, outputChannel2);
  ```
- `C6004` 是内嵌的 apksig 代码：`new u4(signerConfigs, null, null, minSdk, true, true, v3, false, true, false, "1.0 (Android)", null, null)`（`C6004.java:390`），即 **v1=true、v2=true、v3=true**（`signers.size() <= 1` 恒成立，因为只放了一个签名者），created-by `"1.0 (Android)"`。
- 签名完成后：删除 `<out>_`，发 `clean`，删工作区，发 `success`（`C5448.java:2908-2915`）。
- **没有**签名后校验（不读回 APK 验证 v2/v3、不比对证书）；Flutter 侧是否校验未知（快照里取不到文案）。

### 7.4 签名相关错误

| 触发 | 异常/文案 |
|---|---|
| keystore 里 alias 无证书/私钥 | `SignatureException` + `签名错误，请重新设置签名` |
| 自定义 keystore 口令错误 | `KeyStore.load` 抛 `IOException`（`Keystore was tampered with, or password was incorrect`），原样透传到 Flutter |
| 签名配置为空 | 默认 JKS 分支；不会报“未选择签名” |
| 签名阶段任意异常 | 发 `error`，`<out>_` 可能残留 |

## 10. 可直接落地的修改建议

> 下列建议按优先级排列，均指向现有文件/函数，不需要改 Pro 逻辑以外的东西。

### P0-1 输出目录统一为 `/sdcard/脚本/APK输出`

- `apps/app/src/flutterpoc/java/com/jdkshen/aijspro/flutterpoc/PocPackaging.java:372`
  现在：`new File(Pref.getScriptDirPath(), "构建")` → 改为 `"APK输出"`。
- `apps/app/src/miuix/java/com/jdkshen/aijspro/ui/project/MiuixBuildActivity.kt:322/356/393/413`
  - 打开项目时默认 `<project>/build`，应改为优先 `<脚本目录>/APK输出`（或保留上次选择）；
  - Picker 的默认目录也用同一常量。
- 建议把目录名提成一个常量（例如 `Pref.PACKAGE_OUTPUT_DIR = "APK输出"`），避免两处硬编码再次分叉。
- 对齐依据：Pro `qa0.java:102-104` 用 Flutter 传入的目录 + `<name>_v<versionName>.apk`。

### P0-2 重写 `resources.arsc` 包名（当前是空实现）

- 位置：`apps/app/src/main/java/com/jdkshen/aijspro/autojs/build/ApkBuilder.java:715-718`。
- 实现建议（按 Pro 的做法，避免引入 aapt2）：
  1. 读 `workspace/resources.arsc` 前 12 字节：`ResChunk_header{type=0x0002, headerSize=12, size}`；
  2. 跳过紧随其后的 `ResStringPool`（type=0x0001，读它的 `headerSize` 和 `size`）；
  3. 下一个 chunk 应为 `ResTable_package`（type=0x0200），其 `name[128]` 从 chunk 起始 +12 开始（`header(8) + id(4)`），共 256 字节；
  4. 用 UTF-16LE 写新包名 + 0 填充到 256 字节；
  5. 断言写入偏移落在文件长度内，失败则抛 `IOException("resources.arsc 包名重写失败")`（不要静默）。
- 验证：`aapt2 dump resources <out.apk> | Select-String "package com\\."` 或 `unzip -p out.apk resources.arsc | strings | grep <package>`；再装到 targetSdk 28/30 两台机器上验证资源解析。
- 注意：Pro 的做法假设包名 ≤128 个 UTF-16 字符；超长应直接报错。

### P0-3 进度事件对齐（含 zip/success/error）

- `ApkBuilder.ProgressCallback` 目前只有 `onPrepare/onBuild/onSign/onClean`。建议加：
  ```java
  default void onStage(String stage, String message) {}
  default void onSuccess() {}
  default void onError(Throwable error) {}
  ```
  在 `prepare()/build()/sign()/cleanWorkspace()` 的关键点调用；`zip` 阶段放在 `ApkPackager.repackage` 之前。
- `PocPackaging` 的 `job.stage(...)` 映射到 Pro 事件名（`prepare/build/zip/sign/clean/success/error`），前端按事件名显示阶段；错误时把 `throwable.toString()` 一起回传（Pro 的 key 7）。
- 现状已能在 `PocPackaging.java:391-415` 看到 4 段；补 `zip/success` 后与 Pro 的阶段数量接近。

### P0-4 权限三态精确语义 + 123 上限

- `third-party/ApkBuilder/.../ManifestEditor.java`：
  - 新增 `setPermissionsExact(List<String>)`；
  - `commit()` 里先删除**所有** `<uses-permission>`，再按列表顺序添加；
  - 保留现有 add/remove 供旧调用方。
- `PocPackaging.permissionsOf`（`PocPackaging.java:502-512`）：
  - `permissionConfig` 缺失 / `manifestPermissions` 缺失 → 返回 `null`（保留模板权限）；
  - 显式空数组 → 返回空列表（全删）；
  - 非空 → 精确列表。
- `MiuixBuildActivity` 的 `createAppConfig` 同样按三态传值。
- 在 `ManifestEditor` 或 `ApkBuilder` 里加 `if (list.size() > 123) throw new IllegalArgumentException("androidPermissions size exceed max size 123: size = " + size)`，与 Pro 文案一致。

### P0-5 模板版本键与自检

- `ApkBuilderPluginHelper` 目前按插件版本 marker 缓存。建议缓存文件名/目录带：
  - 宿主 `versionCode`（Pro 的 `9131100` 键）；
  - 插件 `versionCode`；
  - 模板大小/哈希（至少大小）。
- 模板不可用时保留现有可操作异常（`找不到打包用的运行时模板…`），并在异常里带期望路径（Pro 是 `FileNotFoundException(entry)`，不如我们友好）。

### P1-1 BuildInfo 写回源工程 + release 字段

- `apps/app/.../ApkBuilder.java:898-908`：
  - 目录工程：构建完成后把新的 `build_number/build_time/build_id` 写回 `<source>/project.json`（Pro `C5448.java:636-638` 在构建前写回；建议成功后写，避免失败也递增）；
  - `project.json.build` 增加 `"release": true`（POC 的 `BuildInfo` 目前没有该字段，`modules/engine/.../BuildInfo.java`）。
- 这样 buildNumber 才会单调递增，运行端按 buildId 派生密钥也更稳定。

### P1-2 补 ProjectConfig 字段与组件混淆

- 在 `modules/engine/.../ProjectConfig.java` 增加（与 Pro JSON key 对齐）：
  `optimization{removeOpenCv,removeAccessibilityService,obfuscateComponents,unusedResources}`、
  `features{nodejs,activityIntentTasks,builtInOCR}`、`plugins`、`abis`、`type`、`signingConfig`。
- 组件混淆：按 Pro 的 15 项映射 + 随机名（`C5448.java:266-286`）实现；注意 `SelectToSpeakService` 保持 `sercomp.serviceName`。
- 不实现的字段至少在 `ProjectConfig` 里保留并原样写回 `project.json`，避免打包后丢字段。

### P1-3 工程插件与 OCR 资源

- 插件：`projectConfig.plugins` 的 key 为包名，`PackageManager.getApplicationInfo(pkg,0).sourceDir` → `assets/project/plugins/<pkg>.apk`（Pro `C5448.java:2380-2388`）。
- OCR：按 `features.builtInOCR` 从宿主 APK 抽取 `lib/<abi>/**` + `assets/ocr/*`（Pro `m13834`）。
- 这两项都依赖“宿主 APK 里确实有这些文件”，实现前先用 `zipfile` 在宿主 APK 上做可用性检查，缺文件给出明确异常。

### P1-4 build hook

- 在 `ApkBuilder` 加 `runScriptHook(key)`：
  - 从 `project.json.scripts[key]` 取脚本；
  - `/system/bin/sh`，cwd=工程目录（单文件时用父目录，修 Pro 的坑）；
  - env 三个 `BUILD_APK_*` 与 Pro 完全一致；
  - 失败抛 `RuntimeException("exec \"<script>\" failed: <stdout> <stderr>")`。
- 事件名用 `run-script: <key>\n<script>`，前端可以显示“正在执行 hook”。

### P1-5 签名 v3（可选）与压缩对齐

- 若要和 Pro 的“v3 恒开”对齐：在 `KeyStoreApkSigner` 里补 v3 block（或直接引入 apksig 依赖，替换现有手写 v1/v2）。v3 对普通安装不是必需，优先级低于 arsc/输出目录。
- 压缩：在写 APK 时对 `resources.arsc` 与 `lib/**/*.so` 用 `STORED`，并做 4B/16KB 对齐（对齐逻辑可参考 `LocalApkBuild.java:205-218` 的 extra-field 算法）。当前模板 targetSdk 28 不受影响，但升级 targetSdk 30+ 后是硬要求。

### P2-1 模板瘦身（可选，收益大）

- 现状：插件 44.8MB，几乎全是 `template.apk`；Pro 模板只有 6.45MB + 宿主补全。
- 若要做：
  1. 在插件里维护 `excluded-zip-files.json`（general/opencv/v8）；
  2. 模板构建时排除这些文件；
  3. 打包时从宿主 APK 按清单复制（`PocPackaging/ApkBuilder` 已有“从宿主 APK 取 zip entry”的代码可复用）。
- 风险：宿主 APK 若被裁剪（例如我们去掉了 opencv），清单里的文件必须存在，否则构建失败；需要“文件缺失→明确报错/自动降级”的策略。

### P2-2 在线加密（不建议实现）

- Pro 的 `encryptLevel=100` 会把源码 zip 上传到 `interfaceC5624`（服务端），拿回 `classes.dex`；有 1MB 限制和“服务到期”文案。
- 我们已有本地加密 + 证书指纹绑定，安全模型不同；**不建议**接 Pro 的在线服务；对 `encryptLevel=100` 的旧工程应给出明确提示（“在线加密不受支持，请改为本地加密”），而不是静默当 0。

### P2-3 默认签名兼容

- 不要实现 Pro 的公共 JKS；保持 `AutoSigningIdentity`。
- 如需兼容 Pro 工程里的 `signingConfig` 字段：读取 `keystore/alias`，口令缺失时提示用户重新选择；不要回退到公共口令。
