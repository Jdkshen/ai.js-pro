## 1. dev_screen_diff（逐帧差异）

**现状可复用**：capture_screen 已有四种预设与缩放语义（McpTools.kt:284 起的描述：fastest/fast/… + sourceWidth/scale），MCP 图像内容走标准 content 通道；device 侧坐标换算规则已写在 instructions（McpTools.kt:193）。

**最小 API 草案**：`dev_screen_diff{baseline?:string, region?:{x,y,w,h}, mode?:"count|bbox|mask", saveDiffTo?:string, maxDims?}`
- 缺 `baseline` 时与「上一次 capture_screen/dev_screen_diff 的帧」比（进程内保留 1 帧 + sha256，避免落盘）；
- 返回 `{changedPixels, ratio, bbox:{x,y,w,h}, baselineSha256, frameSha256, size:{w,h}}`，`saveDiffTo` 时另存掩码 PNG；
- 显式声明：这是**像素级**差异，不做语义/模板匹配（模板匹配另有 matchTemplate 系列）。

**验收**：单测用两张合成位图（相同 → ratio=0；改一块 → bbox 精确、ratio≈改动面积）；真机用「同屏两次截图」应为 0 或极小值、切到另一界面应显著非 0；K40 上同时给出耗时。

**开放问题**：`mode=mask` 的掩码是否要抗压缩噪声（JPEG 预设会引入噪声）→ 建议默认对 JPEG 预设做 ±N 灰度容差，并在返回里标注容差。

## 2. chain_resume（checkpoint → 重跑最后一公里）

**现状可复用**：编辑会话与检查点已齐（`apk_session_checkpoint/checkpoints/rollback/diff/check`，McpApkToolkit.kt:328-334、:468-470），后台作业与构建也齐（`apk_job_start/job_result`、`apk_build`、`apk_build_project`）。

**最小 API 草案**：`chain_resume{workspaceId, editSessionId, checkpoint?, steps:"build|sign|verify|all", outPath?}`
- 语义：把会话恢复到指定 checkpoint 的 revision（或当前 revision），然后**按固定顺序**跑「回编 → 对齐/签名 → 验签」，把每步结果与产物路径汇总返回；失败时明确停在哪一步，**不伪造整链成功**；
- 返回 `{chain:[{step,status,ms,jobId?,artifact?}], finalArtifact, sha256, verified}`。

**验收**：单测覆盖「checkpoint 不存在 / revision 过期 / 某步失败即停」；真机用一个小 fixture 工程跑通整链并核对产物 sha256。

**开放问题**：是否允许省略 checkpoint（=当前 revision）？我倾向允许，并在返回里回显 restore 来源。

## 3. crypto_（现场加解密）

**现状可复用**：App 内已有 JDK 密码学使用先例（如 `build/TinySign.java`、`build/ApkTemplateInspector.java` 的 MessageDigest/SHA-256 等，全仓 72 处命中），不需要引入新依赖。

**最小 API 草案**：`crypto_{op:"hash|hmac|aes_gcm|rsa_sign|rsa_verify", alg?, keyRef?|keyHex?, ivHex?, inputHex?|inputText?|path?, outPath?}`
- 密钥来源**只允许**显式 hex 或工具目录内的 key 文件（不读 App 私有密钥库，避免把签名身份暴露成工具）；
- 返回 `{alg, outputHex|outputPath, bytes, digestOfInput?}`；解密/验签失败给明确错误码（MAC_INVALID / KEY_INVALID / ALG_UNSUPPORTED）。

**验收**：单测用已知向量（SHA-256/HMAC/AES-GCM 的 RFC 测试向量、RSA 自签自验）；真机跑一次 hash + 一次 AES-GCM 往返。

**开放问题**：是否需要 `crypto_keys`（生成/导入密钥对到工具目录）？我建议**先不做**，只支持显式 key，避免变成密钥管理器。

## 4. entry_（入口分析）

**现状可复用**：Manifest 的 AXML 解析（ResXmlElement 路径，见 ToolkitGadget.patchManifest 与 apk_read_text 的 `axml:` 定位符）、DEX 类/方法列表（`apk_dex_list_classes/_list_methods`）、native 分析（`apk_native_*`）。所以 `entry_` **主要是编排与归类**，不是新能力。

**最小 API 草案**：`entry_{workspaceId, editSessionId}` → 一次返回：Application 类、LAUNCHER activity（含 activity-alias）、所有 exported 组件、`appComponentFactory` 是否存在、每个组件的 `android:process`、native 入口线索（含 `JNI_OnLoad` 的 .so 与其 DT_NEEDED/DT_SONAME 摘要）、以及「本 APK 的提前加载注入应该选哪条路径」的建议（provider/dt_needed/clinit 三选一 + 理由）。

**验收**：单测用合成 Manifest/APK；真机对 2–3 个真实 APK（含带 `:script` 进程的 Auto.js 打包包）比对人工读 manifest 的结论。

**开放问题**：要不要复用 `preload` 的判定逻辑（ToolkitGadgetPreload）以免两处结论不一致？我建议**复用**并在返回里标注来源。

## 5. 整族前缀重构（破坏性改名）

**现状**：dex/so/entry/chain 四个家族前缀都**不存在**（grep `"chain_`、`"crypto_`、`"entry_`、`"screen_`、`"dev_screen` 在 mcp 目录下全 0 命中），现有同名工具是 `apk_dex_*`、`apk_native_*`、`apk_build*` 等。

**建议做法（若 .4 坚持）**：① 先只**新增**前缀别名（canonical 名不动），别名走既有 `McpToolCatalog` 的 9 个别名通道扩展；② 在 initialize.instructions 与 tool_schema 里标注「新名前缀 = 旧名的别名，旧名长期保留」；③ 一个版本后若无人依赖旧名再评估是否切换 canonical —— **不建议本轮做**，因为它会一次性影响 219 个 advertised 名字里的几十个，收益是纯命名一致性，风险是 .4 侧所有脚本与断言都要动。

**验收（若做别名）**：冒烟加「每个新前缀名与旧名解析到同一 canonical、返回值逐字段一致」的断言。

## 6. 结论与建议排期

| 优先 | 项 | 理由 |
|---|---|---|
| 1 | dev_screen_diff | 语义清晰、可完全靠「合成位图单测 + 真机两次截图」验收，不依赖 .4 决策 |
| 2 | entry_ | 复用现有解析能力，属编排；能直接支撑「提前加载三选一」的推荐 |
| 3 | chain_resume | 复用会话/检查点/构建，属编排；验收需要一个小 fixture 工程 |
| 4 | crypto_ | 有现成 JDK 能力，但**安全边界要先定**（密钥来源/是否做密钥管理） |
| 5 | 整族前缀重构 | 破坏性、收益低；建议只做别名并明确弃用期，或请 .4 重新确认必要性 |

**未做/边界**：本文件是**只读调研**，没有改任何代码、没有新增工具；上面所有 file:line 都是本轮 grep/read 实测；「现状可复用」的判断来自代码存在性，**不等于**已按草案验证过可行性。
