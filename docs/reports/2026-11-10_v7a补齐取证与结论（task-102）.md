### 1.2 `backend=ppocr|mlkit` 在「只有 mlkit」时的行为（代码级）

出处：`apps/app/src/main/java/com/jdkshen/aijspro/android/Node24HostBridge.java`：

| 行 | 逻辑 | 结果 |
|---|---|---|
| `:606` | OCR 入口：`{"kind":"ocr","action":"create","backend":"ppocr|mlkit", …}` | — |
| `:661` | `String backend = request.optString("backend", "ppocr")` | **默认是 `ppocr`** |
| `:663-667` | 当 backend 解析为 `ppocr`（含 `paddle`/`paddleocr` 别名）而 ppocr 不可用 | **抛点名错误**：提示「请使用 `createOCR({backend:'mlkit'})` 走内置 ML Kit」 |
| `:684` | `else if ("mlkit".equals(backend))` | **mlkit 分支存在且可走** |
| `:633` | OCR 能力整体未随包（`optimization.removeOcr=true`） | 点名错误（lib 名 + 开关名） |
| `:652` | 从异常文本里识别 `libppocr`/`libmlkit` 缺失 | 用于给出「能力未随包」的定性 |
| 脚本侧 | `assets/modules/__ocr__.js`（脚本入口）+ `qjs-plugins.js` 的 **mlkit→ppocr** 降级（`degradedFrom`，见 `QuickJsPluginsModuleTest:50-51`） | 降级方向是「mlkit 不成 → 回退 ppocr」，**正好与 v7a 需要的方向相反** |

**⇒ v7a 上（只有 mlkit）：**
- 脚本**显式** `createOCR({backend:'mlkit'})` ⇒ **可用**（v7a 的 mlkit 库在，模型资源 `assets/mlkit-google-ocr-models/**` 与 ABI 无关 ✓）。
- 脚本**不传 backend**（走默认 `ppocr`）⇒ **拿到的是点名错误**，不是静默崩溃、也不是自动降级。**这是行为差异**（arm64 上默认能跑、v7a 上默认报错）。
- 要让 v7a 默认可用，最小改动 = **在 v7a 上把 `Node24HostBridge:661` 的默认 backend 改成 `mlkit`**（或按「ppocr 不可用 ⇒ 默认 mlkit」），属**行为变更**、需在发布说明里写清。

## 2. ② vendor v7a ncnn 路（要哪些源 / 工具链 / 时间盒 / 产物多大）

## 3. ③ 验证边界（**可直接照抄进发布说明**）

> **v7a 产物的验收上限（本项目当前）**：我们**没有 armeabi-v7a 真机**，因此 v7a 产物**只能验到**：⑴ 产物内 `lib/armeabi-v7a/` 条目齐全；⑵ `node tools/apk-native-lib-audit.mjs <apk> --expect-abi armeabi-v7a --fail-on-leak` 输出 **`missingAbi=[]`（且 `leaks=0`、`unknown=0`）**；⑶ **16KB 页对齐检查**通过；⑷ **dex 与资源完好**（条目数/结构核对）。
> **不能声称的**：**没有在任何 v7a 设备上启动过**——所以「v7a 能起来」「v7a 上 OCR 可用」「v7a 上插件/无障碍可用」都**不是已验证结论**；**不得**写成「已验证支持 armeabi-v7a」。

## 4. ④ 结论与落地步骤

### 4.1 L1（推荐）：v7a 产物 + OCR 只走 mlkit

**前置（三条都要）**：
1. **重建 v7a Flutter AOT payload**：用 `-PflutterPocAbi=armeabi-v7a`（`apps/app/build.gradle:265-270` 的收窄开关）+ SDK 的 `android-arm-release` 引擎；**并确认打包页在 v7a 上能起**（否则 v7a 用户没有打包 UI，但**产物本身仍可被打出来**）。
2. **保证 v7a 打包走内置瘦身模板（③ 合并路径）**：插件模板是 arm64-only（``1.1` 末两行），若打包机上装了 apkbuilder 插件且命中插件模板，产物会**带 arm64 libs** ⇒ v7a 设备 `loadLibrary` 失败。做法：清 `files/apk-builder/` 缓存 + 不装插件，**或**给插件模板也补 v7a 组（另一件事）。
3. **接受 OCR 行为差异**（`1.2）：v7a 上默认 `backend=ppocr` 会**点名报错**；要么文档写「v7a 请用 `createOCR({backend:'mlkit'})`」，要么把 v7a 默认 backend 改成 mlkit（行为变更）。

**落地步骤（Lead 执行）**：
1. 确认 `excluded-zip-files.json` 的 **v7a 6 条**在位（`general` 5 + `opencv` 1：`lib/armeabi-v7a/{libaijscrypto,libc++_shared,libmlkit_google_ocr_pipeline,libquickjs,libquickjs_jni,libopencv_java5}.so`）；
2. 打包（同工程，同路径），期望日志：⑵ `host lib missing entry=` **不再**包含上述 6 条；⑵ `abis declared=[arm64-v8a, armeabi-v7a] available=[…] produced=[arm64-v8a, armeabi-v7a] missing=[]`；
3. 验收（只读、可复跑）：`node tools/apk-native-lib-audit.mjs <apk> --expect-abi armeabi-v7a --fail-on-leak` ⇒ `missingAbi=[]`、`leaks=0`、`unknown=0`；`node tools/apk-native-lib-audit.mjs <apk> --by-module` 对比 v7a 载荷（**预期 ≈30.75 MiB raw / ≈12.5 MiB 压缩**）；
4. `pwsh -File tools/verify-16kb-alignment.ps1 -Apk <apk>`（注意该脚本 `OwnedList` 目前是 `quickjs|aijscrypto|ppocr|pikafish`——**v7a 场景要确认它覆盖到 `libopencv_java5` 这类**，否则补进名单）；
5. 发布会话里**照抄 `3 的边界段**。

**体积影响（实测口径推算）**：v7a lib 载荷 **32,248,572 B raw**；本产物 lib 压缩比 **0.405**（52,324,640 → 21,192,705）⇒ **v7a 约 12.5 MiB 压缩贡献**（arm64 是 20.21 MiB）。**⇒ 只出 v7a 单 ABI 的产物反而比 arm64 小 ≈7.7 MiB**；**双 ABI 同包则是 +12.5 MiB**。**不是「必然 +X MB」**。

### 4.2 L2（可选）：vendor v7a ncnn 补 `libppocr.so`

### 4.3 风险清单

| 风险 | 现状/量化 |
|---|---|
| **OCR 行为差异** | v7a 无 ppocr ⇒ 默认 `backend=ppocr` **点名报错**（`Node24HostBridge:663-667`），需显式 `backend:'mlkit'` 或改默认（**行为变更**） |
| **包体** | **不是必然变大**：v7a-only ≈ **−7.7 MiB**（lib 载荷更小）；**双 ABI 同包 +12.5 MiB** |
| **`AbiPolicy` warning 语义变化** | 现在（arm64 宿主）`missing=[armeabi-v7a]` 是**恒定的 warning**；补 v7a 后若在 v7a 宿主上打包，`missing=[]` ⇒ **warning 消失**（好事）；但**同一台 K40（arm64）**上打 v7a 产物仍会缺 v7a 源 ⇒ warning 仍在 ⇒ **别把「无 warning」当作 v7a 已成的判据** |
| **Flutter UI 缺失** | 不重建 v7a AOT ⇒ v7a 上的「项目配置与打包」页面不可用（`libapp.so/libflutter.so` 缺） |
| **插件模板 arm64-only** | 命中插件模板 ⇒ 产物带 arm64 libs ⇒ v7a `loadLibrary` 失败（``4.1 前置 2`） |
| **无真机** | 见 `3：**不能声称启动过** |
