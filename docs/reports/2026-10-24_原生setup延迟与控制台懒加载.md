# 原生 setup 延迟与控制台懒加载（2026-10-24）

## 背景

《布局与绑定桥批量优化》测得 M3 示例 Java fast calls 仅 72–93 次，整页主要成本是 ViewPager/Drawer/Grid/Console 的原生 setup。本轮按“合并或延迟”方向处理：

- 新增 `ui.afterFirstFrame(view, callback)`：用 `View.post` 等首帧/attach 后再执行重型 setup，定时器兜底；不再在 `onContentViewSet` 返回后立刻抢主线程。
- 示例 `使用Android原生界面/main.js`：`_setupDeferred` 改走 `afterFirstFrame`；
- **控制台懒加载**：`_setupConsole` 从启动 setup 中移除，改为 ViewPager 切到控制台页（position=1）时初始化；未进入控制台页不初始化。
- ViewPager/Drawer/Grid 的初始化内容未改，仍按原顺序执行；没有把不同原生库调用合并成不可维护的 Java helper。

## 测量

MI8 `ce4d2bdb`，dev-1240，同一 M3 示例探针（脚本内埋点）。旧实现 = 原示例（setTimeout(0) + 控制台立即初始化）；新实现 = afterFirstFrame + 控制台懒加载。

| 阶段 | 旧实现 | 新实现 | 变化 |
| --- | ---: | ---: | ---: |
| show:return | 532ms | 643ms | 波动 |
| onContentViewSet:end | 720ms | 941ms | 波动 |
| _setupViewPager | 744→874ms | 978→1112ms | 基本同量 |
| _setupDrawer | 883→1113ms | 1123→1363ms | 基本同量 |
| _setupGrid | 1118→1271ms | 1376→1558ms | 基本同量 |
| _setupConsole | 1697→1817ms | **未执行** | 控制台 120ms 移出启动 |
| setup tail（最后 setup end） | **1817ms** | **1558ms** | **-259ms（-14%）** |

说明：

- 单次运行有波动；此前 dev-1238 同旧实现测得 tail 2126ms，不能用最大差值宣称固定收益；本次同版本对比取 **-259ms**。
- ViewPager/Drawer/Grid 本身耗时未降；M3 页面首帧没有稳定改善，延迟只是把非首屏工作移到首帧之后/用户切页时。
- 控制台首次切到 console 页时执行 `_setupConsole`，后续切页不再重复；若用户从不打开控制台，这 120ms 完全不发生。

## 验证

- `ui.afterFirstFrame` + 示例改动随 **dev-1240** 构建。
- 真机探针：`M3_FIRST_FRAME` 标记正常，`_setupConsole` 不再出现在启动 phases；ViewPager/Drawer/Grid 均完成。
- dev-1240 真机回归：20 轮动态 UI、4 generation（3 次重建）、28 项断言通过，主进程未重启（elapsed≈207s）。
- dev-1240 binding 批量测试：7/7 通过，`bindingFirst=1, bindingRepeat=0, attrCalls=1`。
- 更新源已为 dev-1240；手机 update.json 可拉取；APK 已装 MI8。
- APK：dev-1240，154,868,699 字节，SHA-256 `399d7e815edd6aea8a7b23cd29ead486055968a7a27839992fb3f540f858e70d`；更新源 1240，MI8 已安装。

## 边界

- 延迟不改变总工作量，只改变执行时机；整页“所有 setup 完成”时间仍约 1.5s。
- 控制台页第一次打开可能多一次初始化；监听器在切页时绑定，不依赖启动阶段。
- 若后续要求进一步降低首帧，需要把 ViewPager/Drawer/Grid 的 setup 合并为更粗粒度的原生调用，或者把部分初始化移到首帧前的宿主预热；本轮未做不可维护的跨库合并。
