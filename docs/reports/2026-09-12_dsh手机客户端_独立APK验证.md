## 2. 确证的缺陷：重启后必然 401（每次启动都要重扫码）

### 2.1 现象

配对成功、界面正常后 `force-stop` 再启动：

```
页面已加载
[dsh 手机客户端]                       ← 回到设置面板
[https://106.55.18.198]                ← 输入框只剩裸地址
服务器返回 HTTP 401，可重新粘贴配对链接后连接。
```

### 2.2 服务端认证矩阵（本轮实测，非推断）

| 请求 | 结果 |
|---|---|
| `/pair-app?device=<正确32位ID>`（带/不带 cookie、cookie 正确/垃圾） | **200 + 下发 `dsh_pair`**（358 973 B） |
| `/pair-app`（无 device 参数） | 200（完整界面） |
| `/pair-app?device=<错误ID>` | 200（**956 B 小页面**） |
| `/pair-app.sw.js`（SW 脚本） | 200（2425 B，不需认证） |
| **`/`（根路径，带或不带 cookie）** | **401**，正文 `dsh web authentication required; reopen the URL printed by dsh web.` |

页面注册了**根作用域 service worker**：`navigator.serviceWorker.register("/pair-app.sw.js",{scope:"/"})`，
所以根路径 `/` 是它接管的导航目标，而该路径在服务端恒定 401。

### 2.3 根因（落到具体行）

`apps/app/src/main/assets/sample/QuickJS 新引擎/项目与打包/dsh 手机客户端/main.js`：

```js
// 第 6 行：重启后从 localStorage 读回 deviceId
let deviceId = String(store.get("deviceId", ""));
// 第 58 行：openClient() 拼 URL —— deviceId 为空时退化成裸地址
function openClient() {
    if (!server) return showSetup();
    hideSetup();
    load(server + "/pair-app" + (deviceId ? "?device=" + encodeURIComponent(deviceId) : ""));
}
```

`deviceId` 一旦为空（或 cookie 未随请求生效），加载目标就退化为**不带 device 的 `/pair-app` 或 `/`**，
服务端按未配对处理 → 401 → `onReceivedHttpError` → `showSetup(server)` → 输入框显示裸地址。
这正是重启后看到的画面。

### 2.4 附带发现：cookie 没有被 `main.js` 显式接管

- Rhino 版（`.artifacts/dsh-qa-project/main.js:10,42,128,317`）**显式**持有
  `android.webkit.CookieManager.getInstance()` 并在 `onPageFinished` / 退出时 `flush()`。
- QuickJS 版把 cookie 完全交给 `ClientRuntime`（`ClientRuntime.java:77` 的 `CookieManager.getInstance().flush()`），
  `main.js` 不接触 cookie。
- 两版都写 `store.put("deviceId", …)`，但**重启路径没有把「cookie 是否真的存活」验证过**。
  本轮证据显示：**重启后请求确实拿不到有效认证**——所以修复必须同时覆盖
  「显式持久化 deviceId/cookie」与「首次导航就用带 device 的 URL」。

## 3. 建议的修复（未实施，待确认）

1. `openClient()` 增加回退链：`server + "/pair-app?device=" + deviceId` →
   若失败再试 `server + "/pair-app"` → 最后才 `server`；并在失败时**保留已填链接**而不是只显示裸 `server`。
2. QuickJS 版对齐 Rhino 版：在 `main.js` 中显式取 `CookieManager`，配对成功后
   `setAcceptCookie(true)` + `flush()`，并在 `started`/`finished` 事件里校验 cookie 是否已建立。
3. `showSetup` 把「deviceId 是否存在」显示出来（例如「已配对设备 20b52aa9…」），
   让 401 这类失败一眼可判，而不是让用户猜。
4. 判定修复成功的可观测标准：**重启后 `dsh_pair` cookie 仍能放行，且不再出现 401 提示**。

## 4. 过程坑（下一位接手必须知道）

1. **`adb shell input text` 在这个 MIUI 输入法上会把字符交错**，长 URL 必然写坏
   （实测得到 `pirapp?devicebaab…`）。结论：**不要用 input text 灌 URL**，走扫码或粘贴。
2. **PowerShell 的 `>` 不能直接存 `adb exec-out screencap` 的字节流**（会加 BOM/换行）。
   必须 `cmd /c "adb ... exec-out screencap -p > x.png"`，再用 PNG 魔数校验。
3. **release 包 `run-as` 被拒**（`package not debuggable`），读不到它的 SharedPreferences；
   `cmd clipboard` 在 Android 10 上不存在（`No shell command implementation`）。
   要读内部状态必须重建**可调试**的包。
4. `am start -a android.media.action.IMAGE_CAPTURE` 可直接拉起系统相机做**对照实验**，
   这是判定「相机不出帧」是环境问题还是实现问题的快捷手段。
5. 大输出会撑爆会话：`Get-ChildItem -Recurse` 顶层 `.artifacts` 时务必加 `-File` + 过滤，
   否则一次能吐十几万行。

## 6. UI 重做（同日第二段工作）

用户反馈「界面不好看」。原界面是深色底 + 系统默认灰色方块按钮，没有任何层次与留白节奏。
本轮按深色移动端规范重做了 `layout.xml`（真机截图：`.artifacts/dsh-ui-new-setup4.png`、
`.artifacts/dsh-ui-new-scanner3.png`）。

设计要点：顶栏 `#131926` 用状态点 + 次级按钮，主区 `#0B0E14`；
品牌区「dsh / 手机客户端」做主次分级；主操作 `#2563EB` 实心、次操作 `#232C3E`；
扫码视图改为「提示条 + 全屏取景框 + 底部说明与取消」。

### 6.1 硬约束：不能动子节点下标

`main.js` 用**子节点下标**挂相机预览面：

```js
new ClientRuntime(ui.web.getParent().getChildAt(0),      // 根垂直布局 [0] 必须是顶栏
                  ui.previewBox.getParent().getChildAt(1)) // 扫码视图 [1] 必须是 previewBox
```

因此布局必须保持「根 = [顶栏, frame]」「扫码视图 = [提示, previewBox, 底部行]」。
**本轮已按此约束验证**：新扫码视图下相机由本 App 持有、预览面正常出帧（1.37 MB 截图）。
该约束已同时写进 `layout.xml` 注释与 `main.js` 注释。

### 6.2 本轮踩到并修掉的三个坑（都会直接让 App 启动即退出）

| 现象 | 根因 | 处置 |
|---|---|---|
| `SAXParseException: name expected @1:2` | **根元素之前不能有注释**，这个 DOM 解析器把注释当标签 | 注释移进根元素内部 |
| `ClassNotFoundException: android.widget.view` | `<view>` 小写会被拼成 `android.widget.view`；inflater 只对 `View` 特判 | 改成 `<View>`（大写） |
| 装机后界面还是旧的 | 测试用临时签名，每次重跑密钥都变 → `INSTALL_FAILED_UPDATE_INCOMPATIBLE` | 先 `pm uninstall` 再装 |

### 6.3 顺带修好的测试问题

`DshClientSamplePackagingTest` 原先断言「产物只声明 3 个权限」，实际产物是 **4 个**：
多出 `android.permission.POST_NOTIFICATIONS`（AndroidX 库清单合并注入，targetSdk 28 下不生效）。
断言已按真实产物固定为 `EXPECTED_PERMISSIONS`，并在失败信息里打印完整清单。
同时把「导出产物」提到权限断言**之前**，并额外导出一份到 `/sdcard/Download/`——
原先断言失败时产物会随测试收尾卸载一起消失，装机和排查都拿不到包。

### 6.5 大字体 / 横屏适配实测（小米 8 = 1080×2248 @440dpi，≈393×818dp）

**先说结论：上一轮只做了视觉重做，没做适配。** 用户追问后补测，并修掉一处确证缺陷。

| 配置 | 做法 | 结果 |
|---|---|---|
| 基线 100% 竖屏 | — | 正常 |
| **200% 字体**（`font_scale 2.0`） | 重启 App | 布局**基本自适应**：顶栏 88→274px，按钮高度随文字增长（「返回页面」62dp），触摸目标全部 ≥48dp，无裁切重叠 |

| **横屏**（`wm user-rotation lock 1`） | 真横屏 2248×1080 | 布局**不崩**：顶栏/提示条/底部行都在；但取景框被上下两条提示压成一条窄带（200% 下约 127dp 高），属于可用但偏紧 |
| 窄屏 | 未测 | — |

#### 找到并修掉的缺陷：大字体下 `tip` 提示被裁

200% 字体时设置面板内容超出屏幕，`tip`（承载「解析失败 / HTTP 401 / 证书校验失败」等关键反馈）
被推到屏幕底边之外，实测边界 `[61,2146][1019,2248]` —— 只露出约一半，**用户看不到报错**。

处置：把 `tip` 从按钮组**末尾**移到输入框**上方**（出错时首屏即可见），并保留面板可滚动。
该位置也更符合直觉：错误信息紧贴它对应的输入框。

#### 未做（明确记录，别当成已通过）

- **横屏专属布局**：没有为横屏做双栏或压缩提示条，取景框在 200% 横屏下偏小。
- **窄屏（320dp）**、**分屏**、**深色/浅色切换**：未测。本界面本来就是深色固定配色，
  与系统深浅色无关；WebView 内部则跟随远端页面。
- **WebView 内部页面的大字体**：远端 dsh 页面自身在 200% 下会溢出（`描述你想要构建的内` 被截断），
  属远端页面行为，不在客户端可控范围。
