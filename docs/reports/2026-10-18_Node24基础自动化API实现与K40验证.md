# Node24 基础自动化 API 实现与 K40 验证

本轮按用户“继续弄 node.js 接口和 API”的要求实施。Codex 负责协议、任务边界、集成审查和 K40 实测，DP 负责分块代码实现。没有改动原生 C++、Flutter Dart 或打包运行时模板。

## 实现范围

- `accessibility`：真实主进程无障碍状态、开启设置页与等待、click/longClick/press/swipe、单指/多指手势、back/home/recents/notifications、Android 11+ 无障碍截图。
- `image`：图片句柄、PNG/JPEG 读写、像素、区域找色、多点找色、比色、同步/Promise 版本、幂等回收。最多 64 张存活图片，单图 16M 像素，总存活 64M 像素；超限前检查，任务结束统一释放。
- `color`：Color、ARGB/RGB、颜色解析与通道读取。
- `media_projection`：真实系统授权、拒绝、nextImage/latestImage、尺寸选项、停止与任务结束清理。使用独立的 `:node24` 授权 Activity，不借用主进程的静态回调表，也不改成无障碍截图冒充投屏。
- `app.viewFile`：检查真实文件，经应用 FileProvider 发起查看，返回真实 boolean。
- `ui.isUiThread` / `ui.uiThread`：改成实际 Looper 判定。ui.run/post 回调仍在 Node 线程，已有 View 消息桥负责切 Android UI 线程，不能理解为完整 UI 线程执行能力。
- Node 找色示例去掉仅为了 Rect 而引用的 OpenCV，使用区域数组，并在 finally 释放图片与投屏。

接口说明和调用示例见 [Node24基础自动化API](../guides/Node24基础自动化API.md)。

## 代码结构与集成修正

新增 Node24AutomationBridge、Node24Images、Node24CaptureConsentActivity，Node24HostBridge 只负责域路由和每次任务的资源所有权。自动化通过 app 现有 AutomationHostClient 连接主进程；没有安装到 RemoteAutomationBridge 的全局后端。

已审查并修正：投屏 options 请求结构不一致、提前 close 截图器持有的原始 Image、帧复制与 release 竞争、主线程迟到构造结果泄漏、Bitmap 注册失败回收、解码前预算检查、写图先删除目标导致失败丢原图、单点按压丢失时长、多指起始延迟、取消唤醒与 native cancel 的竞态。

主进程手势协议新增每条 stroke 首点的可选 startTime，省略时保持原行为；Node 将首点 t 转为 startTime，其余 t 转为 stroke 内偏移。中间点仅定义路径，Android 按总时长调度。

普通 Node 任务预算从 30s 调至 60s，容纳最长约 55s 的系统截图授权等待。UI/keepRunning 沿用现有 10min 上限。未修改权限默认值或其他引擎路由。

## 验证记录

环境：K40 `cccc62c7`，Android 16。没有操作另一台 MI8。证据目录：`output/node-api-1074/`。

- 系统 Node 运行 `node tools/test-node24-automation-api.cjs`：29 passed，0 failed。
- JDK17 运行 `:engine:testDebugUnitTest --tests org.autojs.source.engine.android.Node24*Test`：25 tests，0 failure/error。
- `:app:verifyQuickJsSamplesMarked`、`:app:verifyBundledSamplesNoNode` 均通过。
- K40 图片验证已覆盖相对路径、32×24 固定 PNG 像素、行优先/区域/多点找色、精确阈值、越界、缺文件、PNG/JPEG 写入后再读取、写目录失败仍保留目录、回收后访问、80 次读图释放、64 句柄上限及释放后恢复。
- UI/无障碍实测 10/10：真实 View 句柄、ready 时 enableService、click、120ms press、longClick、swipe、单指、多指、带延迟单点手势（约 505ms）、1080×2400 无障碍截图且找到测试页的 #009688 色块。
- `app.viewFile` 缺文件正确报错；有效截图返回 true，并通过系统图库实际打开，没有设置默认应用。
- 投屏用户拒绝正确抛 ScreenCaptureRequestError。全屏显式停止、全屏脚本结束自动清理、480×800 指定尺寸三组分别完成 15 帧和 latestImage；停止后再取帧正确拒绝。结束后 MediaProjection 均为 null。
- 内置 Node `图片与颜色处理/找色.js` 实际运行成功，exitCode=0，输出包括真实找色坐标，未再 require OpenCV；结束后投屏释放。

初次图片探针有一项“无障碍必须关闭”的前置断言失败：启动测试构建后服务实际已开启，status 正确报告 true；该项未执行点击，也未当成 API 故障。2026-10-19 临时关闭服务后，在 code 1093 的控件候选包上重跑：**16/16 通过**，包括新增的连接前取消检查，证据 `output/node-api-1094/smoke-candidate-result.json`；随后已恢复服务开启。

初次 UI 探针使用缺少必要元数据的 project.json，错误被 Node UI 资源缓存；补齐测试工程后改用独立目录，UI/无障碍 10 项通过。这是测试夹具修正，没有改动资源热更新逻辑。

取消等待的首轮真机复现发现：脚本结束而系统授权子 Activity 仍显示，且存在把取消记成 success 的竞态。DP 提供了授权子 Activity 清理和服务取消标记修正；该委派随后由主控取消并接管集成，不能记为完整交付。

候选包第二次实测：授权框显示期间停止脚本，约 14ms 后返回 `cancelled=true`、`exitCode=1`，系统子授权框同时关闭（`cancel-warm.log`、`cancel-warm-after.png`）。另一次冷启动测试发现停止请求早于 Binder 连接，主控补了客户端待连接取消标记与引擎 `mStopRequested`。

2026-10-19 在后续 DP 已发布的 dev-1093 上补测：先 `client.cancel(id)` 再 `evaluate(request)`，真实返回 `status=CANCELLED/success=false`；投屏授权不操作直到约 55 秒，脚本获得明确超时错误，系统授权框自行关闭，MediaProjection 为 null。证据为 `output/node-api-1094/prebind-cancel-result.json`、`projection-timeout-result.json`、`timeout-before.png`、`timeout-after.png`。没有覆盖发布源为旧版 1074；后续以实际最新版本为发布基线。

## 已知边界

- 当前验证主 App 的 flutterPoc 构建。inrt 模板和非 flutterPoc 构建没有该自动化客户端，本轮没有把接口存在当成打包运行时已经可用。
- 本报告记录基础批次；后续选择器进展见 [控件选择器 API](../guides/Node24控件选择器API.md)。完整 Pro API、无障碍事件、OCR、OpenCV/模板找图仍不在本报告验证范围。
- Promise 接口仍通过同步宿主桥执行，不代表多线程并行；帧复制使用有界的 Java 像素复制，尚未做批量拷贝优化。
- 一个任务最多成功创建一个投屏会话；停止后需重新运行脚本再申请，旧授权不复用。
- 设备覆盖仅 K40；没有宣称所有 ROM、所有示例和全部 Pro API 已兼容。
