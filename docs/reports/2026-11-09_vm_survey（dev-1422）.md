## 1. vm_survey 做了什么（W2 task-25）

新工具 `vm_survey`（canonical **211** / advertised **220**）：

| 能力 | 对应他们 §11.2 |
|---|---|
| dispatch 壳候选打分：`switchCount/switchCases/dispatchLoopBackEdges/arrayIndexOps/invokeCount/instructionCount/classPayloadBytes` → `score` + **逐项 `contributions`** | ① 聚类相同解释器薄壳（前件：找到壳） |
| 按 opcode 直方图的**签名聚类**（精确 + 可调阈值近似） | ① |
| 大常量负载候选（静态 `byte[]`/`String` ≥ 阈值 → length/sha256/first16Hex，`addr:null` 并说明常量池无稳定地址） | ② 字节码地址/长度/引用表 |
| dispatch 数组映射（≤64 项 + `indexBase` + `truncated` + `entriesSha256`） | ③ 引用表索引可核对映射 |
| **用户 opcode 规则 → 线性反汇编**（`coveragePercent` + 停点原因 `unknown_opcode_index:N`/`truncated_instruction`/`max_instructions`/`end_of_blob`） | ④ opcode 规则与版本标识 |
| CFG **只到块起点 + 覆盖计数**（`blockStarts` + `coverage{blocks,instructions,bytes}`），明确不推调用关系 | ⑤ 带覆盖与置信度的 CFG（裁剪版） |

**诚实边界**（写进工具描述 + 返回 `notes`）：静态启发式、不做反编译、**不承诺任意 VMP 一键还原**、不给「解密完成/还原完成」结论；**0 候选是合法结果**并说明扫了多少 dex/类/方法（含 `truncated/maxMethods`）与可能为 0 的原因；分数可解释但不等于「已识别 VMP」。

## 2. 真机跑出来的两个问题与修正（本轮闭环）

**① 纯 blob + opcodeRules 被守卫挡死（真 bug）**：首次真机 `vm_survey{blobHex,opcodeRules}` → `INVALID_ARGUMENT 需要 workspaceId 或 path`。修：给了非空 `blobHex` 即进入 **blob-only 模式**（不扫 DEX、`sources:[]`、`scanned.dexCount=0`、notes 注明），三者都没给才报错。

**② 候选数量太吵**：真实 APK 上 `candidateCount=16102`，看不出有多少像壳。修：新增 `scoreBuckets`（与 candidateCount 同集合、不受 limit 截断）+ notes 提示「候选多不等于壳多」。

## 4. 未做 / 边界

1. **没有真实 VMP 样本**：不承诺能找到壳；分数权重未做真样本校准（top 候选是 androidx 的 switch 密集方法，属合理但非壳）。
2. CFG 偏移单位是 **code units**（dexlib2 `Instruction` 不提供字节偏移）；switch 载荷基准优先按引用推导、推不出退回 `payload_self`，不对的目标进 `droppedTargets`（真实 dex 上哪种情形更多未统计）。
3. 「大常量负载」只看**静态字段初始值**；`fill-array-data` 运行时构造、native 解密后的 blob 看不到。
4. 反汇编是**单 index 单长度**的线性规则，不支持前缀/变长。
5. `payloadRef` 仍需 dex 集；只有 `blobHex` 能免 workspace/path。
6. 随包文档（Guide/Reverse-Guide 工具清单与工作流）与 `tools/mcp-smoke` 未同步 `vm_survey` —— 属 W3/Lead scope，未做。
