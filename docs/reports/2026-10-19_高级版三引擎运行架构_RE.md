## 0. TL;DR（先看这 8 条）

1. Pro 只有 3 类进程：主进程（Flutter/UI + 少量入口 Service/Receiver）、**:script**（全部脚本引擎 + 自动化 + 悬浮窗 + 控制台 + 编辑器/日志/任务页 + 无障碍/通知/Shizuku/MCP）、**:crash_report**（只放 ErrorReportActivity）。没有 :node、:native、:node24 之类的按引擎分进程。
2. 这个版本实际只有 2 个 JS 引擎：Rhino + Node（不是三引擎）。全 APK 字节级大小写不敏感搜索 quickjs = 0 命中；AutoJs 只注册 rhino / xml preview / nodejs 三个工厂；JavaScriptSource 的 flags 只有 ui/auto/nodejs/ui-thread/rhino；仓库旧 Phase1 spec 的结论（Pro 9.3.11 只有 Rhino+Node）与本 APK 一致。若用户认为手机版有三引擎，QuickJS 应来自其它版本/插件，不在本 APK 内。
3. Node 是同进程嵌入：:script 进程里 System.loadLibrary("v8") 加载定制 J2V8 的 libv8.so（1.1 MB，110 个 JNI），它再链接 libnode.so（Node 16/ABI 93，48.8 MB）；Node 由 PlutoJS/a26 在 :script 进程的脚本线程（或 :script 主 Looper / V8ScriptExecuteActivity）里跑 JNI 原生调用，没有 fork Node 子进程。
4. libnodexe.so 不是引擎宿主：它只有 5,904 B，是一个 ELF 可执行文件（main + node::Start(int,char**)，DT_NEEDED libnode.so），被 ab5（TerminalInitializer）软链成 files/bin/node，用于终端/npm/npx/yarn/child_process 的 node 命令；引擎本身不经过它。
5. 一套宿主、一套注册表：主进程 bindService(com.stardust.autojs.ScriptService)（AIDL IScriptServiceInterface，10 个 transaction）→ :script 里 ScriptService.BinderC0496 → 进程内单例 bc4（ScriptEngineService 等价物）→ ScriptEngineManager → 引擎工厂 → 执行对象。停止/列表/计数/前台开关都走同一个 Service。
6. 引擎选择：首行 flags ui=1 / auto=2 / nodejs=4 / ui-thread=8 / rhino=16；C4439.m12687(source, projectConfig)：bit4 → nodejs，bit16 → rhino，否则 project.type==node → nodejs，否则 rhino；"auto"; 就是「按项目 type 自动选」。ui 走 Activity（Rhino ScriptExecuteActivity / Node V8ScriptExecuteActivity，都在 :script），ui-thread 走 f26（:script 主 Looper 执行），其余后台线程；.mjs/.node.js 在无加密头的文件按 Node 处理（JavaScriptFileSource.parseExecutionMode fallback）。
7. 多脚本隔离：同一 :script 进程内多引擎并存（ScriptEngineManager.mEngines 集合 + bc4.f3412 LinkedHashMap<Integer, ScriptExecution>），按 executionId/engineId 管理；脚本间没有进程隔离，一个原生 abort/段错误会带走 :script 内所有脚本（主进程 Flutter UI 不受影响，靠 ServiceConnection 重绑恢复；:crash_report 只负责错误页）。这与「一个脚本一个进程」相反。
8. 我们：主进程 + :script + :native + :node24 + :background 多宿主；三引擎：Rhino/QuickJS 在哪个宿主进程由 PocRuntime 路由决定（主进程/ :script / :native 都可能），Node24 固定 :node24 独立进程；:script 目前无 Activity（headless 主 Looper），UI 模式/投屏/auto 被路由回主进程；Node24 服务是单任务（active.compareAndSet，第二个任务直接 BUSY），取消会 kill :node24 进程。用户说的「脚本宿主跑脚本有问题」很可能就出在这些差异上（详见 §7）。

## 3. 引擎清单与选择逻辑

### 3.1 引擎工厂：只有 Rhino + Node（无 QuickJS）

org.autojs.autojs.autojs.AutoJs.mo13260()（super 之后）注册工厂：

    m13254().registerEngine(new C6632());  // super("rhino")
    m13254().registerEngine(new C6633());  // xml preview factory
    m13254().registerEngine(new C6634());  // super("nodejs")

- C6632.createEngine()：new LoopBasedJavaScriptEngine(application, singletonMap("optimizeLevel", ...))，setRuntime(AutoJs.mo13246()) = Rhino。
- C6634.createEngine()：new a26(application, new ConsoleImpl(...), new LinkedHashMap()) = Node/V8。
- ScriptEngineManager（com.stardust.autojs.engine.ScriptEngineManager）基类还会注册一个基础 Rhino 工厂 C4937（AbstractC4934 构造器里），AutoJs 再用 C6632 覆盖 rhino 名字。
- 全 APK 字节扫描 quickjs（大小写不敏感）= 0；JavaScriptSource 静态 map 只有 ui=1, auto=2, nodejs=4, ui-thread=8, rhino=16；无 QuickJS 相关类/字符串/库/资产。故本 APK 没有 QuickJS 引擎，「三引擎」说法不成立；我们三引擎中的 QuickJS 只能与「我们自己的实现」对照，Pro 侧没有可对比对象。

### 3.2 JavaScriptSource 首行 flag 与文件级语义

com.stardust.autojs.script.JavaScriptSource 静态 map（源码直接可读）：

    ui=1, auto=2, nodejs=4, ui-thread=8, rhino=16

ScriptSource.getEngineName() / StringScriptSource.mo1065()：flags & 4 != 0 → "nodejs"，否则 "rhino"（文件级 source 读不到 flag 时才看 project type）。

JavaScriptFileSource.parseExecutionMode()：先读文件头 8 字节加密头（EncryptedScriptFileHeader）里的 flags；没有合法头时回退到文件名判断（源码分支：.mjs / .node.js → 4/Node，其余 → 0 + 项目默认；由于混淆方法 z45.m11759 的名称语义需谨慎，建议以「.mjs/.node.js 默认 Node」为准，具体边界后续可用样例实测）。

bc4.m2410(task)：从 ExecutionConfig.projectConfig 或向上找 project.json 得到 ProjectConfig，供引擎选择使用。

okhttp3.internal.io.C4439.m12687(source, projectConfig)：

    if (!(flags & 4)) {                    // 不是显式 nodejs
        if (flags & 16) return "rhino";    // 显式 rhino
        if (projectConfig != null && "node".equals(projectConfig.type)) return "nodejs";
        return "rhino";
    }
    return "nodejs";

即：
- "nodejs";（bit4）强制 Node，无论项目类型；
- "rhino";（bit16）强制 Rhino，即使项目 type=node；
- "auto";（bit2）没有独立引擎分支，落到 project.type 判断：type=node 的项目用 Node，否则 Rhino；
- 无声明：看 project.type，缺省 Rhino；
- "ui";（bit1）只是执行模式，不决定引擎；
- "ui-thread";（bit8）只是执行模式（Node 的主 Looper 模式），也不决定引擎。

### 3.3 createExecution 路由（UI / ui-thread / 后台）

ScriptEngineManager.AbstractEngineFactory.createExecution()（Rhino 等通用工厂）：

    source 是 JS 且 flags & 1(ui) == 0
        → new LoopedBasedJavaScriptExecution(manager, task)   // 后台线程 + Rhino Looper 引擎
    source 是 JS 且 flags & 1(ui) != 0
        → new ScriptExecuteActivity.ActivityScriptExecution(context, manager, task)
    非 JS
        → new RunnableScriptExecution(manager, task)

Node 工厂 AutoJs$C6634 重写 createExecution：

    flags & 1(ui)  → new V8ScriptExecuteActivity.C6956(context, task, manager)
    flags & 8(ui-thread) → new f26(manager, Looper.getMainLooper(), task)
    否则 → new RunnableScriptExecution(manager, task)

关键证据：
- Rhino UI 模式 ScriptExecuteActivity.ActivityScriptExecution.start()（com.stardust.autojs.execution.ScriptExecuteActivity）：

      Intent intent = new Intent(context, uiScriptActivity)
          .putExtra(ScriptExecuteActivity.EXTRA_EXECUTION_ID, getExectionId())
          .addFlags(config.getIntentFlags());
      context.startActivity(intent);

  该 Activity 在 :script 进程（manifest），启动后用 executionId 从进程内 bc4 单例取回执行对象，再 LoopBasedJavaScriptEngine.execute(...) 在 Activity 的 UI 线程/内部执行。
- Node UI 模式 V8ScriptExecuteActivity.C6956 extends f26（注意：它继承主线程执行类 f26）：内部通过 startActivity(Intent(context, V8ScriptExecuteActivity).putExtra(KEY_ACTIVITY_ID, MAIN_ACTIVITY_ID)...) 在 :script 打开 Activity；Activity 持有 a26 engine、PlutoJS plutoJs、V8AutoJsGlobal 等，Node/V8 在 Activity 的主线程执行，ui.layout/View 直接由 V8 侧创建。
- ui-thread 模式 f26：start() = new Handler(this.f6015).post(new RunnableC6055(this, 2))；m4024(a26) 设置 workingDirectory/env、a26.init()、然后 a26.m1668(source, c26(...))——Node 引擎在 :script 进程主 Looper 上初始化并执行，而非后台线程。
- 默认（无 ui / ui-thread）Node 走 RunnableScriptExecution：后台线程创建 a26 引擎并执行；ScriptService.mo735(task, false) 返回 execution id。

## 4. :script 内部与多脚本隔离

### 4.1 App 进程分支（为什么引擎只在 :script 初始化）

org.autojs.autojs.App.onCreate()（源码约 120-140 行）：

    if (进程名 == Processes.SCRIPT，即 :script) {      // App.f30005 懒值 = z45.m11759(processName, Processes.SCRIPT)
        FlutterService.f30156.m15167(this);         // 绑定主进程 FlutterService
        AbstractC4934.m13242(this, AutoJs.class);   // 反射创建 AutoJs 单例（引擎/自动化/UIHandler/Console）
        ApplicationBroadcastReceiver...sendBroadcast(...);
    } else {                                        // 主进程（默认进程）
        FlutterActivity...;
        ScriptService.f1244.m722(this, new BinderC6299());  // 绑定 :script 的 ScriptService
        ab5.f2629.start();                           // 终端/Node bin 初始化（见 §5.5）
    }

AbstractC4934 是 AutoJs 基类：m13242(Application, Class) 反射构造进程单例；构造里创建 UiHandler、GlobalConsole、AppUtils、GlobalActionAutomator、AccessibilityBridge、TaskScheduler、ScriptEngineManager、bc4（ScriptEngineService 等价物）等，并初始化 LD_LIBRARY_PATH 等。因此所有引擎/自动化/UI Handler/Console 都只存在于 :script 进程；主进程没有 AutoJs 实例。

### 4.2 多脚本：一个进程、多引擎、一个注册表

- ScriptEngineManager.mEngines: HashSet<ScriptEngine<?>>：每创建一个引擎就 addEngine；createEngine(name, id) 设置 engine id、灌全局变量、加入集合；stopAll() 遍历 forceStop()。
- bc4.f3412: LinkedHashMap<Integer, ScriptExecution>：按 executionId 存执行对象；m2411(id) 取回（UI Activity 用）。
- ScriptExecutionObserver/mExecutionListener：把 started/finished/exception 事件分发给全局监听器、广播（autojs.pro.action.execution.started/finished）和 Flutter 界面。
- 隔离边界 = 进程：同一 :script 内多个脚本共享进程、JVM、native lib、全局 Java 单例；每个脚本有自己的引擎实例/线程/JS context（Rhino）或 V8 runtime（Node），但没有 OS 级隔离。一个脚本原生崩溃（abort/segfault）会直接杀死 :script 进程，连同其它脚本；主进程 Flutter 不受影响，ScriptService 的 ServiceConnection 会重绑（但已死脚本不会自动恢复，列表从空开始）。
- UI 模式脚本的 Activity 也在 :script（ScriptExecuteActivity/V8ScriptExecuteActivity），关闭 Activity 不等同于停止引擎；执行对象仍由 bc4.f3412 持有，靠 executionId 关联。
- u70：当 mo735(task, true)（showFloaty）时，:script 主线程创建 FloatingControllerView + WindowManager 悬浮控制器（Pro 的「运行脚本」悬浮提示条），并做 FloatingPermission.ensurePermissionGranted；这解释了 showFloaty 参数与主线程路径。

### 4.3 停止/任务列表/前台服务

- 任务列表：mo727 → ScriptExecutionInfo(source, config, executionId)；主进程 Flutter 展示。
- 停止单任务：mo728(engineId)；注意参数是 engine id，不是 executionId；ScriptEngine.getId() 由 ScriptEngineManager.createEngine(name, id) 设置（createEngineOfSource 传入 id）。
- 停止全部：mo731/mo733 → ScriptEngineManager.stopAll()（m2413 还会 toast 提示「已停止 N 个脚本」）。
- 前台服务：ScriptService.onCreate 若 Pref.KEY_FOREGROUND_SERVICE 则 startForeground(7001, ...)；mo734 运行中开关；ScriptService 未重写 onStartCommand（默认 START_STICKY）；主进程断线重绑（onServiceDisconnected 立即 m722 重绑），这是 Pro 在 :script 被系统回收后自动恢复 IPC 的机制。
- :crash_report 只负责崩溃上报 Activity，不托管脚本。

## 5. Node 引擎如何拉起（重点）

### 5.1 原生库与 JNI 面

- libv8.so（1,106,856 B）：定制 J2V8 的 JNI 层 + Node embed 入口；ELF 内 JNI 符号共 110 个：
  - Java_org_autojs_autojspro_v8_PlutoJS__1* 11 个：_initNode、_initRuntime、_init、_spinEventLoop、_runEventLoopNoWait、_drainTasks、_emitProcessBeforeExit、_emitProcessExit、_addALooperFd、_removeALooperFd、_cs；
  - Java_org_autojs_autojspro_v8_j2v8_V8__1* 约 97 个（J2V8 全量 API）；
  - Java_org_autojs_autojspro_v8_api_media_NativeMediaProjection_* 2 个。
- libv8.so 的 C++ 侧引用 node::CommonEnvironmentSetup、CreateEnvironment、InitializeNodeWithArgs、LoadEnvironment、SpinEventLoop、StartExecution、EmitProcessBeforeExit/Exit、SetProcessExitHandler、MultiIsolatePlatform、CreatePlatform、Stop 等符号；DT_NEEDED 含 libnode.so。
- libnode.so（48.8 MB）：完整 Node core + V8 + libuv/OpenSSL；字符串里有 NODE_MODULE_VERSION 93 配置、V8 版本 9.4.146.24-node.20（Node 16.14 线）。
- 结论：Node/V8 是加载进 :script 进程的 JNI 原生库；JNI 入口由 PlutoJS 的 native 方法承载，不存在 Node 可执行子进程的拉起点。

### 5.2 启动链（从 AutoJs$C6634 到用户脚本）

1. AutoJs$C6634.createEngine()：new a26(application, console, map)（Node 引擎对象，位于 :script 进程）。
2. a26.init()：f2408 = WeakReference(this)；a26.C0863.m1670(context) 首次把 assets/v8 整个目录复制到 filesDir/v8（SharedPreferences 版本标记 built_in_modules_app_version = 9131100；目录 filesDir/v8、filesDir/v8/built_in_modules、filesDir/v8/autojs-esm-loader.mjs）。
3. a26.doExecution(source)：m1668(source, callback) 组装 Node 启动参数：
   - --experimental-loader=<filesDir/v8/autojs-esm-loader.mjs>（ESM loader，把 bare specifier 解析到 built_in_modules）；
   - --no-warnings、--trace-uncaught（debug 时追加 --inspect-brk=0.0.0.0:9229）；
   - 调 PlutoJS.C6902.m15326(startupScript, args, initCallback, engineCallbacks)。
4. PlutoJS.m15329（静态）：System.loadLibrary("v8") → _initNode(ConnectivityManager, AssetManager, String[] modulePaths)（native 读 assets 注册 built_in_modules/内置模块路径；PlutoJS.f30866 模块 map 在初始化后清空）。
5. PlutoJS.m15326：ye3（V8 runtime，ThreadLocal 每线程一个）→ startNodeJS(callback)；callback 收到 process 与 require；再 _initRuntime(v8RuntimePtr, v8java.js)（n16 构造 JS 反射桥）→ V8AutoJsGlobal.BuiltInObjects 转 V8 对象 → _init(ptr, v8autojs.js) 构建 global.$autojs 并拿回 __emit。

### 7.2 用户「脚本宿主跑脚本有问题」的可能根因（按可能性）

1. UI 模式脚本没有真正的宿主进程：我们把 "ui"; 脚本路由回主进程 ScriptExecuteActivity（:script headless，executeUiOnMainThread 仅 Rhino），而 Pro 是把 UI Activity 放在 :script。结果是 UI 脚本的引擎/Activity/自动化/Console 分散在 main 与 :script，和宿主任务的「停止/日志/生命周期」错位；对依赖同线程/同进程的 UI/native（SurfaceView、第三方 ImGui 桥）尤其明显。这与 task-113/115 在 inrt 处理 UI 模式的经验一致。
2. Node 单任务 + :node24 进程级 kill：任何第二个 Node 脚本都会被回 BUSY；取消/停止走 kill :node24 而不是引擎 stop；对于重入、任务页同时点运行、Node 与 Rhino 混跑的场景，表现为「跑了但没跑/报 BUSY/任务消失/浮窗残留」。Pro 是同一 :script 内多引擎并存，按 engine id 停。
3. 注册/任务/停止不统一：Pro 只有 AIDL 一套 execution/engine 注册表；我们 ScriptHostService/NativeScriptService/Node24Service/主进程旧引擎各自维护 token/任务，导致任务列表重复（handoff 已记录同一脚本显示 :script 与 Node24 两行）、停止全部需要多路广播、状态回声不一致。用户看到的「脚本宿主跑脚本有问题」可能正是任务/停止/日志状态的错位。
4. 自动化/无障碍在 main 导致语义差异：Pro :script 内直接调 AccessibilityService/UiObject/UiSelector/截屏；我们 :script 通过 AIDL 代理，Node24 还要经 Node24HostBridge，事件/时序/能力有差异（旧报告已列 :script 自动化不完整、auto.service=null 等）；auto 脚本还默认留在主进程，造成「有的脚本走 main、有的走 :script」两套环境。
5. 引擎选择语义不完全对齐：Pro 首行 flags 是位组合（"nodejs ui"、"ui-thread nodejs"、"rhino" 等），项目 type=node 影响默认引擎；我们的 JavaScriptSource 只解析字符串指令，且路由顺序（ui→截图→native→auto→:script）会先于引擎选择改变执行环境；对 Pro 脚本/项目直接跑可能出现选错路由/引擎或 UI 模式降级。
6. 单进程多引擎 vs 多进程的取舍：Pro 一个原生崩溃会带走 :script 全部脚本；我们的多进程有更强 crash 隔离（:native/:node24），但代价是跨进程桥/任务/日志/UI 复杂。用户遇到的是「宿主跑脚本有问题」，不一定是崩溃，更多可能是上述 1-4。

### 7.3 可借鉴 Pro 的实现建议（不改本报告范围，供 Lead 决策）

P0（优先对齐，解决「宿主」体验）

1. 统一 :script 宿主 + 一套注册/任务/停止契约：把 ScriptHostService/NativeScriptService/Node24 job/主进程旧引擎的任务注册统一到一个脚本任务注册表（最好 AIDL，类似 Pro IScriptServiceInterface），提供 running 列表、按任务停止、stopAll、前台状态；减少多路广播与重复任务行。可保留 :native/:node24 的进程隔离，但注册/控制面统一到主进程/ :script 代理。
2. 让 :script 真正承载 UI 模式：把 ScriptExecuteActivity（以及 QuickJS/Node 的 UI 宿主）声明到 :script，UI 模式脚本不再回主进程；:script 的 setHeadlessUiMode(true) 只对需要 headless 的 native/Node 用；这与 Pro 模型一致，也能解决 UI 脚本「引擎在 :script、Activity 在 main」的错位。
3. Node24 支持多任务或明确串行语义：至少在「第二个 Node 任务」时按 Pro 语义排队/复用而不是直接 BUSY；取消应优先 engine.cancel() + 关 UI，只有在 native 卡死时才 kill :node24（现在 2.5s watchdog 才 kill，但 active 单任务本身就限制了并发）。如果要与 Pro 对齐，考虑 Node 同进程嵌入（长期）或 :node24 支持多 job/多 Node runtime。
4. 统一引擎选择：在 JavaScriptSource 引入 Pro 位 flags（ui/auto/nodejs/ui-thread/rhino）与 project.type 语义，并把 createExecution 的 ui/ui-thread/后台路由收敛到引擎工厂；避免 PocRuntime 的先路由再选引擎导致的行为分叉。Node24 已有 type/features/flags 解析，可作为参考。

P1（体验/兼容）

5. 自动化/无障碍/悬浮窗/Console 归位：Pro 这些全在 :script；我们至少让 :script 的远程代理覆盖完整（事件、选择器、截屏、auto.service），减少 main↔script 跳转；Node24 的 host bridge 补事件/UI 通道。
6. 日志/任务/停止的单一数据源：Pro 的 Console/GlobalConsole 在 :script，FlutterInterface 回 UI；我们已有 103 统一转发，建议把任务状态也统一到一个广播/注册表，去掉重复行。
7. 生命周期/保活：Pro ScriptService 前台 mediaProjection + 重绑；我们各宿主前台 lease + Node24 hold/kill 语义需要统一成「一个脚本生命周期」；特别是 stopAll、通知栏停止、任务页 ✕、音量键要保证跨 main/:script/:native/:node24 一致。

P2（长期）

8. Node 同进程 vs 子进程/独立进程的最终形态：Pro 同进程 JNI 换来最直接的 Java/UI/自动化能力，但一个 Node 原生崩溃会带走 :script；我们 :node24 隔离更安全、但 API/事件/UI 都要跨进程。若用户主要跑 Pro 兼容脚本（大量 require('app')/device/ui、浮窗、无障碍），同进程或共享 native 的 Node 宿主更易对齐；若重点在崩溃隔离/资源回收，保留 :node24 但需补全 host bridge 与多任务/统一控制面。
9. 引擎数量：我们三引擎（Rhino/QuickJS/Node24）是产品差异；Pro 9.3.11 只有 Rhino/Node，QuickJS 没有对齐对象，需明确「QuickJS 是我们的扩展引擎」并在文档/示例中分开说明，避免用户以为 Pro 行为。
10. 项目/打包运行时：Pro 的 ProjectLauncher/bc4 同构在 :script；我们 inrt 已用 InrtScriptThreadHost 在 :script 主 Looper（task-113/115），与 Pro 模型接近；主 App 的 PocRuntime 路由应作为历史迁移层逐步收敛。

1. 本 APK 没有 QuickJS：这是基于全 APK 字节扫描/工厂注册/资产/类名的强证据，不是反编译遗漏；若产品要求「三引擎对齐」，QuickJS 只能与我们自己的实现对照，需另找带 QuickJS 的 Pro 版本/插件确认其架构。
2. Node 精确版本：任务描述给 Node 16.14.0；静态证据为 V8 9.4.146.24-node.20 + ABI 93（Node 16.14/16.15 线），未从 process.versions 真机读取（本任务只做 RE，不装包）。
3. AIDL 10 个 transaction 的精确方法名/顺序：由 BinderC0496 的 10 个 override（mo727..mo736）与接口 descriptor 计数得到；仓库旧 Phase1 spec 有更细的 tx 映射，可交叉参考。
4. jadx 混淆名：a26/bc4/ye3/f26/C4439/u70/bo0 等是 jadx 重命名；报告用职责标注。部分方法（如 .mjs/.node.js fallback 的具体布尔语义）受混淆 helper 名称影响，需样例实测确认边界。
5. Node 多脚本并发上限：Pro 架构上同一 :script 可并存多引擎；是否所有 Node 版本都允许同进程多 V8/Node runtime 并发、资源上限多少，需要真机压测（本报告只做架构/证据层结论）。
6. UI 模式 Activity 细节：V8ScriptExecuteActivity 2,931 行、ScriptExecuteActivity 内部执行细节未逐行展开；本报告聚焦「在哪个进程、如何启动、和引擎如何关联」。
7. 我们的进程/路由结论基于 dev-1112 工作区源码与 handoff 记录；若后续重构（如 :script 加 Activity、Node 同进程）需要更新对照表。
