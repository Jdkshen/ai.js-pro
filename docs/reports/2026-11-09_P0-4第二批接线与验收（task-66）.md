# P0-4 第二批：CrossProcessPrefs 接线收尾与验收（task-66）

> 接 task-61（候选已验证、未接线）。本轮做**接线 + 真存储 + 回滚开关 + 验收脚本**。

## 1. 白名单 key 与 SettingsModule 的判据（要不要接）

| key | 写者 | 读者 | 本轮处理 |
| --- | --- | --- | --- |
| key_script_dir_path / scriptDirectory.absolutePath | 主进程 Pref.setScriptDirPath（已接：双写 store+XML） | :script / 编辑器进程 | 已接 |
| key_stable_mode | 主进程 Pref.java:87（已接）+ DrawerFragment.java:158（**不在写作用域**，只写 XML） | 引擎 core/pref（已接） | 已接 + **XML 变更重播种**兜住越界写者 |
| key_gesture_observing | 仓库内未找到写者（只读） | 引擎 core/pref（已接） | 已接 |

**SettingsModule 结论：不接。判据（可复核）**：SettingsModule.STABLE_MODE = "stable_mode"（**没有 key_ 前缀**），
而引擎读的是 "key_stable_mode" —— 两者是**不同的 key**，接线并不能把 $settings 的写入喂给引擎；
且 SettingsModule 在 apps/app/.../autojs/api/ 下，**不在本任务写作用域**。
若产品上要求 $settings.setEnabled('stable_mode') 影响引擎的 key_stable_mode，那是**键名映射**问题（另开小任务），不是多进程一致性问题。

## 2. 回滚开关（逐条退回 SharedPreferences）

- 读：getString/getBoolean 在 enabled=false 时**直接**走旧 XML（不碰 store）；
- 写：putString/putBoolean **总是**先写 XML，再在 enabled 时写 store ⇒ 关掉后只写 XML；
- 开关本身只读 XML（不递归），另可用系统属性 aijspro.crossProcessPrefs=off 覆盖；
- store 抛异常：吞掉 + failures 计数 + logcat，回退 XML（不会因为新机制导致设置读写失败）；
- describe() 已 @JvmStatic，脚本可读：Packages.com.stardust.autojs.core.pref.MultiProcessPrefs.describe(context)。

## 3. 一致性的一个真实坑（本轮补上）

只在「store 里没有」时从 XML 播种是不够的：仍存在**只写 XML 的写者**（DrawerFragment 的稳定模式开关、$settings 等，均不在写作用域），
它们的新值永远进不了 store ⇒ 引擎在 :script 里会读到旧值（R1 换个位置复发）。
补法：MultiProcessPrefs.reseedIfLegacyChanged —— 旧 XML 指纹（长度+修改时间）变了就把 XML 的值重播种进 store（纯判定在 MultiProcessPrefsSync，有单测）。

## 4. 真机验收脚本（照抄，在 :script 里跑）

```js
// task-66 P0-4 验收脚本（在 :script 里跑：MCP run_script / App 运行）
var M = Packages.com.stardust.autojs.core.pref.MultiProcessPrefs;
var S = Packages.com.stardust.autojs.core.pref.FileCrossProcessPrefsStore;
var C = Packages.com.stardust.autojs.core.pref.CrossProcessPrefs;
var F = java.io.File;
var ctx = context;
function say(t, v) { console.log('[task66] ' + t + ' = ' + v); }
var K = 'key_script_dir_path';      // 主进程写、:script 读的白名单 key
var X = 'key_t66_script_key';       // :script 侧写的 key（交替写不同 key 用）
var Y = 'key_stable_mode';          // 主进程侧写的 key（用设置页开关稳定模式）
s say = say;
say('describe.initial', M.describe(ctx));

// A) store 优先：直接往 store 写一个和 XML 不同的值，getString 必须返回 store 的值
var store = new C(new S(new F(ctx.filesDir, 'pref-sync')), 'aijspro-settings.pref');
store.put('key_t66_precedence', 'STORE');
say('A.store-preferred', M.getString(ctx, 'key_t66_precedence', '(null)'));

// B) 回滚开关：关掉后 putString 只写 XML、读也只读 XML
M.putBoolean(ctx, M.SWITCH_KEY, false);
M.putString(ctx, 'key_t66_precedence', 'XML');
say('B.switch-off.describe', M.describe(ctx));
say('B.switch-off.read(XML 期望)', M.getString(ctx, 'key_t66_precedence', '(null)'));
M.putBoolean(ctx, M.SWITCH_KEY, true);
say('B.switch-on.read(重播种后期望 XML)', M.getString(ctx, 'key_t66_precedence', '(null)'));

// C) 两个进程交替写不同 key 不丢：本进程写 X，你在主进程改脚本目录/稳定模式（写 Y）
M.putString(ctx, X, 'from-script-' + Date.now());
console.log('[task66] 请现在到 App 里改「脚本目录」和「稳定模式」开关，本脚本会轮询两个 key（各 15 秒）');
for (var i = 0; i < 15; i++) {
  sleep(1000);
  if (i % 3 === 0) {
    say('C.poll.' + i + '.X(script)', M.getString(ctx, X, '(null)'));
    say('C.poll.' + i + '.Y(main)', M.getBoolean(ctx, Y, false));
    say('C.poll.' + i + '.dir(main)', M.getString(ctx, K, '(null)'));
  }
}
// D) 两个 key 都还在（不丢）
say('D.X.kept', M.getString(ctx, X, '(null)'));
say('D.Y.kept', M.getBoolean(ctx, Y, false));
say('D.describe.final(failures 必须为 0)', M.describe(ctx));
console.log('[task66] 判据：A=STORE；B 关时=XML；C 轮询中主进程改的值要出现；D 两个 key 都在；failures=0');
```

## 5. 验证（JVM，可复跑）

- FileCrossProcessPrefsStoreTest（5 项，真实文件）：跨实例可见、原子写不留半份、锁超时降级（lockTimeouts=1 且不丢键）、8 线程并发写 200 key 不丢、指纹随内容变化。
- CrossProcessPrefsTest（6 项）：R1/R2/R3/R4 边界。
- MultiProcessPrefsSyncTest（2 项）：指纹变了才重播种（否则只写 XML 的写者会被忽略）。
- 合计 **13 项 0 失败**（kotlinc + JUnitCore）。

## 6. 未验证边界

1. MultiProcessPrefs 依赖 Android Context（PreferenceManager/Log），**JVM 单测盖不到**：开关回退与重播种的端到端行为由上面的真机脚本证明。
2. 未接 SettingsModule（见 §1 判据）；$settings 的写入仍走 XML，靠 §3 的重播种被引擎看到（下一次读，不是推送）。
3. 跨进程**推送**（R4 变更通知）仍未做；本机制是「读时比对」，不承诺订阅即时回调。
4. 锁超时降级是「无锁继续」：同 key 并发写仍可能后写赢（不会整份覆盖丢键）；超时次数在 store.lockTimeouts 里可见。
5. 首次读的播种写是 best-effort；多进程同时首启可能各写一次同值（幂等）。
