## 3. 缺口 / 待派单 / 已撤回的误报（两轮都**未改主源**）

### G1（**已撤回的误报**）Rhino 自带 `NativeJavaMethod` 的 `Function.prototype`
- **task-53 的（错误）推断**：`javap` 看到 `NativeJavaMethod` 三个构造函数都调无参 `BaseFunction.<init>()`、类内无 `setPrototype`，且 `BaseFunction` 未覆写 `getPrototype()` → 便推断实例方法包装没有原型。**错在只看了包装类本身，没看它的创建者 `JavaMembers`。**
- **task-58 真机复现（修复前观察，K40 `cccc62c7` + 设备4 `192.168.10.4:8765`，两机结果逐字相同，engine=rhino）**：
  - `typeof java.lang.System.out.println` → `function`；**`typeof java.lang.System.out.println.apply` → `function`**（不是 undefined）；
  - `System.out.println.apply === Function.prototype.apply` → `true`；`System.out.println.__proto__ === Function.prototype` → `true`；`hasOwnProperty('apply')` → `false`（继承来的）；
  - `System.out.println.call(java.lang.System.out, 'G1-DIAG-OK')` → 正常调用（返回 `undefined` = println 的 void 返回值）；
  - `new java.util.ArrayList()` 的实例方法：`size.apply(list,[])` → `1`、`size.call(list)` → `2`、`add.apply(list,['x'])` → `size()` 变 `1`（**apply 真的作用在接收对象上**）、`size.bind(list)()` → `1`；
  - Class 实例 API：`java.lang.String.getName.apply(java.lang.String)` → `java.lang.String`；`new java.io.File('/sdcard').getPath.apply(f, [])` → `/sdcard`。
- **更正后的（正确）证据**：`javap -p -c org.mozilla.javascript.JavaMembers` 显示实例成员的创建路径是
  `ScriptableObject.getFunctionPrototype(scope)` → `new NativeJavaMethod(MemberBox, name)` → **`NativeJavaMethod.setPrototype(proto)`**（构造器 `NativeJavaConstructor` 同样有 `setPrototype`）→ 所以 Rhino 自己的实例方法包装**本来就有** `Function.prototype`。
- **结论**：**G1 不成立，无需改主源**；task-58 已把实例方法用例加进回归组（见 §2），并把本条从「缺口」移到「已覆盖」。
- **顺带记录（非本轮目标，不改）**：方法包装的 `f.length` 恒为 `0`（实例方法与 task-52 的静态方法包装都是；Rhino 的 `NativeJavaMethod` 只设了 `functionName`，没设 length），脚本里用 `f.length` 拿形参个数的写法在 Rhino 下本就不成立。

### G2（理论风险，未修）`ScriptJavaObject:52-53` 的 null 作用域
- `getFunctionPrototype(getParentScope())`：若 `getParentScope()` 为 null，Rhino 的 `getTopLevelScope(null)` 会 NPE。现实中该对象总是由 WrapFactory 带 scope 构造，**未观察到**；本轮只登记。

### G3（既有语义，已用测试钉住，不改）`PreferIntJavaObject` 的截断
- 只要第一个参数是 Number 且**参数个数**匹配，就走 int 重载并 `toInt()`：`paint.setColor(1.9)` → `setColor(1)`。测试里明确钉住（`t.setValue(1.9)` → `instance-int:1`），避免以后有人「顺手改」而不自知。

## 4. 防漏机制（两条）

1. **`baseFunctionWrappersAreAllAudited`**：扫描 `src/main/java` 里出现 `extends BaseFunction` / `: BaseFunction` / `new BaseFunction(` 的文件，集合必须**逐字等于** 5 个已知文件（`AijsNativeJavaClass.kt`、`PreferIntJavaObject.kt`、`ReflectiveMethodObject.java`、`NativeView.java`、`ScriptJavaObject.java`）。新增/改名包装类而不登记 → 红，失败信息直接点名要同步的三处。
2. **`scriptVisibleWrappersExposeApplyCallAndBind`**：**9 个**可在 JVM 里触发的包装逐个断言 `typeof` + `.apply/.call/.bind` + `apply === Function.prototype.apply`（含 task-58 补进来的两个**实例方法**包装：`java.lang.System.out.println` 与注入对象的 `list.size`）。
- **局限（诚实边界）**：#4/#5 两个包装依赖 Android `WebView`/`View`，JVM 造不出来 → 只能靠 ① 清单断言 ② 本表登记 ③ task-52 的只读核对（`super(scope, prototype)` / 从 original 复制）保证。

## 5. 未验证 / 边界

- task-53 **只写测试 + 本文档**，未改任何引擎主源；task-58 同样**未改主源**（复现结论是不需要修）。
