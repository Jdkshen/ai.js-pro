## 一、本批实现

| 复盘条目 | 实现 | 关键行为 |

| §6.3 嵌入式 Node 运行形态 | `McpEngineDiagnostics` 新增 `runtime.nodeRuntimeForm` | 明确 `runtimeMode=embedded-shared-library`；给出 `hostExecutable`（app_process64/32）与说明「process.execPath 不能当 Node CLI 依据」；`standaloneCli` 报资产路径/种类/依赖/是否已提取/是否可执行/libnode 是否同目录，`canSpawnStandaloneNode` 只在三项都满足时为 true；`supportedChildScriptRunner` 同时给出 MCP 嵌入式入口与（可用时）CLI 形态 |

## 二、MI8（dev-1333）真机实测

### 1. Node 运行形态（`get_status.engineDiagnostics.runtime.nodeRuntimeForm`）

```text
runtimeMode=embedded-shared-library
hostProcess=com.jdkshen.aijspro
hostExecutable=/system/bin/app_process64
canSpawnStandaloneNode=true
supportedChildScriptRunner=[
  "mcp:run_script engine=nodejs（嵌入式进程池，始终可用）",
  "cli:/data/user/0/com.jdkshen.aijspro/app_node24-runtime/d2165091a8360066/node <script.js>"]
standaloneCli={present:true, executable:true, runtimeLibraryPresent:true, runnable:true,
               toolsDirectoryPresent:true,
               reason:"同目录已有 libnode.so 与可执行启动器，可按需启动独立 CLI"}
```

说明：`node24/tools/node` 是 ELF CLI 启动器（`node::Start`，动态依赖 `libnode.so`/`libc++_shared.so`），由 `Node24Tools.prepare` 提取到运行时目录；本机已提取过，所以三项齐备、`canSpawnStandaloneNode=true`。未提取的机器会返回 false 并说明原因，**不会**用假值糊弄。

## 四、未做 / 边界

1. **Node CLI 未实际执行**：诊断只做只读文件探测（不启动进程、不跑脚本）；真要用 CLI 仍需在终端里显式执行，并自行承担环境（PATH/npm 目录）配置。
2. **`hostExecutable` 只按文件存在性判断** app_process64/32，不做 ABI 探测；32 位设备会报 app_process32。
3. **artifact_open 的目录扫描有预算**（500 条目/200 探测/5 候选）；超预算时消息会提示 truncated 与重扫建议，但不会自动跟随候选打开。
4. **artifact_open 仍不接受 APKS/XAPK/APKM 之外的任意 ZIP**：普通 ZIP 若无 AndroidManifest.xml 会在「APK 缺少 AndroidManifest.xml」处失败（信息明确）。
5. 复盘剩余：P1（有状态 native 分析会话、精简反编译输出与交叉引用增强、应用启动/退出原因关联采集、Frida Java Bridge 与有界会话）与 P2（可验证二进制变换、VM 辅助、统一证据导出）。
