# 布局与绑定桥批量优化（2026-10-24）

## 范围

承接《Node M3 四项底层优化》，本轮只处理布局/绑定桥的细碎调用，不再改 DEX/Java JNI 主体。

- **binding 缓存**：`ui.js` 的 binding 代理缓存 name→viewId 与子 View 句柄；优先使用 show 已返回的 `views` map，不再为每个属性调用一次 Java `viewId`；重复访问直接命中缓存。
- **批量属性**：`View.attr({...})` 改走 `NodeUiLocalSession.viewAttributes(view, json)`，一次宿主调用按顺序应用多个属性；旧宿主缺少该批量方法时逐项回退。
- 新增设备测试 `node24-binding-batch.js`，验证代理/子 View 缓存、重复访问 0 次 Java 调用、批量属性一次调用及属性生效。

## 测量

测试设备：小米 8 `ce4d2bdb`，dev-1237（改前）/ dev-1238（改后），自建 M3 示例探针，脚本内埋点。

| 指标 | 改前 | 改后 | 说明 |
| --- | ---: | ---: | --- |
| M3 示例 Java fast calls | 93 | 72 | **-22.6%**；binding 缓存与 id 复用 |
| binding 首次访问 fast calls | 2 | 1 | 直接命中 show 的 views id，仅一次 findViewById |
| binding 重复访问额外调用 | 1/次 | **0** | 子 View 句柄缓存 |
| `attr({text,alpha,visibility})` | 3 次 | **1 次** | 批量属性入口 |
| show:return | 734ms | 686ms | 波动，未证明页面稳定提速 |
| onContentViewSet | 76ms | 81ms | 同量级 |
| ViewPager/Drawer/Grid/Console setup | 136/224/211/195ms | 133/227/180/198ms | 基本不变；主要是原生库自身工作 |

结论：批量化把桥调用次数降低了约 23%，但 **M3 整页启动没有稳定收益**；当前页面的主要成本仍是 ViewPager/Drawer/Grid/Console 的原生 setup，而不是 JS↔Java 往返。下一步若要继续降整页时间，应做原生 setup 的合并/延迟，而不是继续扩大桥缓存。

## 边界

- 批量 `attr` 只在属性值合法时一次成功；非法值会原样抛错，不会静默逐项重试。
- binding 缓存以当前 Activity 的 `views` map 为准，页面重建/内容替换时清空 id 缓存。
- 仍未把绑定解析和 View 属性写入合并到单个宿主协议请求；本轮只是缓存+单 View 多属性批量化。
