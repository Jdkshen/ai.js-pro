# 象棋自动走棋 · 差分视觉与四个卡点修复（2026-09-20，K40 真机）

> 口径（用户）：**YOLO 只定位一次棋盘，剩下的用「找色判走动 + OCR 认子」**。
> 本轮把它落成差分模式，并在真机上把随之暴露出来的四个卡点逐一定位修掉。
> 相关文件：`悬浮窗运行与测试.js`（面板/视觉）、`src/automation/auto-driver.js`（驱动）、
> `src/automation/move-verifier.js`（验证器）、`src/chess/transition.js`（棋规推断）、`tools/self-check.js`。

## 0. 结论速览

- 差分链路：90 格找色 **19~31ms**，只对「变化格」OCR，每 12 帧回一次全盘对账；拿不准退回全盘流水线。
  真机 tick **884~1273ms**（旧全盘路径 ~2000ms），稳态 `未知格 0`。
- 四个卡点全部是「视觉读数被当成事实」这一类：锚点背 `?`、重建基准丢轮次、起点残影、刚落子的颜色被像素判反。
  修法统一成一条原则：**有更可靠的证据（票据/棋规/已知事实/上一张基准）时，不让单帧读数改账本**。
- 测试：`self-check` **212/0**、`cells-contract` 19/0、`run-regress` 8/8。
- 真机 180s（干净开局）出招 6 次；`确认：UNRELIABLE` 从「每次确认都撞」降到 0~1 次。

## 1. 差分模式（面板 `悬浮窗运行与测试.js`）

```
occupancyScan(image)   90 格逐格找色 → "R"/"B"/"."/"?"（19~31ms）
recognizeDiffFrame()   与锚点占用图比对 → 只重认「变化格」；变化 > 8 格 / 认不出兵种 ⇒ 返回 null 退回全盘
seedDiffCache()        用一次全盘识别的结果当锚点（扫一份占用图）
DIFF_REANCHOR_FRAMES=12  每 12 帧回一次全盘对账（防止长期漂移）
```

- autorun：`{"visionPipeline": "diff", "mode": "auto", "start": true, "declareTurn": true}`（另见 `docs/guides/自建更新源测试SOP.md` 的真机跑法）。
- 锚点里的未知格会被**一直背着**（只有那格再变化才会重读）⇒ 种子化时先用「OCR + 找色」证据补齐，
  之后每帧再顺手重认最多 4 个残留 `?`（失败不算错，维持 `?` 交给驱动自己的证据链）。

## 2. 卡点①：重建基准换了盘面，却沿用旧轮次

真机现场：对方应手 `h9g7` 已经被认出来，可状态却是 `WAIT_TURN｜轮到对方（b）`，
之后差分每帧 `变化 0 格` —— 它在等一个**永不再来的对方走子**，直到超时。

根因：`rebuildBaselineFrom()` 里 `lastReliable = { board: 本帧, side: 旧 side }` ——
那一帧**已经包含对方刚应的那手**，旧 side 还停在「我方刚走完 ⇒ 轮到对方」。

修法（`auto-driver.js`）：

- 重建时用**旧基准 + 这一帧**推一次着法，推得出（一步 / 一步+应手）就用 `inferred.nextSide`，
  推不出才沿用旧值。日志：`按观测量建基准：轮次按着法推出（唯一合法单步：h9g7）→ 现在轮到红方`。
- 顺带：`state-machine` 加 `opponentIdleWarnMs = 20000` —— 等对方且画面 20s 没变时，
  把「多半是轮次判反」写进状态行（只改文案、不出手）：这类死等以前在日志里长得像「对方在想棋」。

## 3. 卡点②：起点「残影」

真机现场：对方卒 `g6g5` 之后，观测在**起点 (6,3) 仍读得到卒**（同时 (6,4) 也有）⇒
差异落在起点上，而容差函数要求「起点必须完全一致」⇒ 任何合法着法都解释不了 ⇒ 轮次推不出来。

修法（`src/chess/transition.js`）：

- `allowSourceGhost` **显式开关**（默认关 —— 单帧分不出「残影」与「其实没走、落点是幻觉」，
  自检 R05e/R05g 的反向保护就靠默认严格）。只有驱动在**有跨帧佐证**的两处打开。
- 另加硬条件：**必须先在落点看到子到位**（`destReceivedPiece`），否则「起点留子 + 落点读空」
  会被误认成走了一手。
- 离线复现：`.artifacts/tools/probe-ghost-source.js`（把起点抹空，`g6g5` 立刻被接受）。

## 4. 卡点③：我方刚落下的子被判成敌方色，还写进了基准

真机铁证（`now9.txt` 17:49）：

```
17:49:10  (2,2)?→C      ← 落点带高亮环，按已知事实补成我方炮（对）
17:49:17  全盘 OCR 改正 (2,2)C→c（像素判成黑）      ← 错
17:49:33  …；基准改正 1 格                        ← 三帧共识把「黑炮」写进基准
```

三处闸门（`auto-driver.js`）：

| 闸门 | 规则 |
|---|---|
| 已知事实覆盖的格子 | **禁止颜色翻转**（棋子一局里不会改颜色；兵种没变时颜色早就是已知的）。日志 `颜色翻转被已知事实驳回：…（已知事实是 C）`，计数 `stats.ocrFlipBlocked` |
| 点击→确认之间 | 我方**落点格整格禁止 OCR 改正**（那一格是什么子驱动自己知道；读数被环骗是已知模式，交给「票据 + 落点补齐」那条路） |
| 重建基准时 | 主动要一次全盘 OCR（绕过限频）：若某格「与上一张基准完全一致（兵种 + 颜色）」而本帧读成别的 ⇒ **保住基准那一格**（`全盘 OCR 证据保住 N 格`） |

再加一条：「OCR 的结论与**账本上已有的值**一致 ⇒ 不必等 3 帧共识」——
那不是在给账本加新事实，是把这一帧读错的格纠正回来。
（真机 18:15：我方炮被读成黑卒，OCR 说 `炮→C` 是对的，但「翻色要 3 帧」× OCR 每 6s 一次 ≈ 18s 才落地，
而轮次看门狗 4s 就先触发了。）

## 5. 验证阶段：未知格改按「唯一解释」判

旧规则要求未知格必须恰好落在「我方落点 / 途经格 / 对方应手落点」上，否则 `UNRELIABLE：还有 1 个未知格（且不全是落点格）`
—— 画面里**任何一格看不清**都会让确认超时（每次白烧 ~15s 恢复）。

新规则（`move-verifier.js`）：把看不清的格**剔出比对**，看候选（「我方这手（对方未应）」/「我方这手 + 某一个合法应手」）
是不是**只有一个**能对上所有看得清的格；唯一才采信，看不清的格按该候选补齐。

- 理由：一次走子只能改**起点与落点**两格，别的格子看不清多少都不影响「谁走了哪一步」。
- ⚠️ 唯一性仍是硬要求：**对方那手的两格都看不清** ⇒ 两种解释都能对上 ⇒ 照样 `UNRELIABLE`。
  旧的两条断言（「任何未知格都不能当成没落子」）已按此改写成「唯一解释」版本，并新增这条歧义守卫。

## 6. 幻影（重复子）：同一枚子在观测里占了两格

真机现场（`now14` 18:20）：模型把 (0,0) 那枚黑車的检测框偏到 (1,0) ⇒ 观测 `rrbakab1r/…` vs 期望 `r1bakab1r/…`
⇒ 确认连刷 5 次「看得清的格子对不上这一手」、轮次也推不出来 ⇒ 恢复。

规则（`clearPhantoms`，两个调用点：确认阶段参照 = 票据预期；其余时候参照 = 上一张可靠基准）：

- **不变量（硬）**：一局里任何一方的子数**只会减少或不变**（吃子少一枚；象棋没有升变/投放）
  ⇒ 「观测里某枚子的个数 > 参照盘面」⇒ 多出来的那些格一定是错觉。
- 判据：参照说那格是空 + 观测那格有子且该子个数变多 + **候选格数 == 多出来的份数**（否则不动手）。
- 日志 `清掉幻影（重复子）N 格（(1,0)r→空）——与…比，多出来的那份；棋子不会分身`，计数 `stats.phantomCleared`。

两个自己踩的坑（都已在代码注释与自检里留痕）：

1. **`?` 不是棋子**：第一版把 `?` 计入个数 ⇒ 把「看不清」的格清成空（`(1,7)?→空`）⇒ 恢复次数 3→9。
2. **落点保护只加在清理动作上，不能排除计数**：预期那边落点有子、观测这边可能读成别的字，
   单边排除会把账算成不平衡 ⇒ 凭空多出 1 枚 ⇒ **误清我方那枚子的起点**（自检直接挂住，二分到手）。
   正确做法：计数照旧，只在「清理候选」里跳过 `activeOwnMove.destIndex`。

## 8. 速度：先量后修（同一晚，用户「继续解决一下速度 / 还是有不知道的格子」）

差分本身不慢（**85 次扫描共 ~2s**，每次 20~31ms ✓）。按 `本轮账` 里的「依赖 top」累计拆账（180s）：

| 项 | 改前 | 真凶 |
|---|---|---|
| `locate`（重定位） | 32.3s / 4 次（**8.1s/次**） | 恢复快路径 `tryReuseGrid` 第一行就要求 `visionPipelineOn`，而**差分模式把它设成 false** ⇒ 每次恢复都全量校准 |
| `ocrCell`（单格证据） | 26.5s / 26 次（**1.0s/次**） | 每次自己 `grabFrame()`（~200ms 抓帧 + 藏窗）；而证据就在刚刚那一帧里 |
| `ocrBoard`（全盘证据） | 28.9s / 25 次（1.1s/次） | 同上（抓帧）+ 逐格扫描（找色开闸后 ~850ms） |
| 全盘帧 `recognize` | 169s / 99 次 | 每 12 帧重锚一次 + 回退帧（`未知格 > 6` / `黑炮 3 个`） |

三处修法：

1. **「最近一帧」短缓存**（面板 `FRAME_REUSE_MS = 800`）：`grabFrame()` 记下这一帧，
   `ocrCell` / `ocrBoard` 在 800ms 内、几何版本一致时直接复用 ⇒ `ocrCell` **1.0s → 94ms/次** ✓。
   ⚠️ TTL 取 800ms：两次点击手势之间约 1s，跨点击复用会把「还没落的子」当证据。
2. **几何沿用快路径补上差分模式**：差分没有流水线，就用**找色占用扫描**（20~30ms）验一帧 ——
   `scanned ≥ 40 且未定 ≤ GEOMETRY_REUSE_MAX_UNKNOWN` 就沿用几何
   （日志 `几何沿用（差分：体检过 + 找色判出 N 格，用时 ~1s，省掉全量校准）`）⇒ `locate` **32.3s → 0.26s** ✓✓。
3. **差分重锚 12 → 24 帧**：全盘那一次是逐格 OCR（~1.2s）；漂移真正由驱动自己的
   「恢复 → 按观测量重建基准」兜底（每 1~2 手就会跑一次）。

真机 180s 对照：

| 轮次 | tick 中位 | 出招 | `locate` | `ocrCell` | 「未知格 = 0」的观察 |
|---|---|---|---|---|---|
| 改前（now17） | 2239ms | 6 | 32.3s / 4 次 | 26.5s（1.0s/次） | 24 次 |
| ＋最近一帧复用（now18） | 1698ms | 4 | 35.5s / 4 次 | **2.5s（94ms/次）** | 24 次 |
| ＋几何沿用（now19） | **1188ms** | **8** | **0.26s / 1 次** | 4.1s（110ms/次） | **42 次** |

> 「未知格」的**主要来源其实是几何轻微错位** —— 几何一沿用（不再每次重算），
> `未知格 = 0` 的观察从 24/35 涨到 **42/50**。剩下的是单格（高亮环/木纹压字），
> 由驱动侧「OCR+找色证据补齐 / 已知事实补齐 / 顽固未知按上一张可靠基准填」三条路各管一段。

## 10. 「又卡住循环」二连修：幻影误清 + 基准改正没写回观测

速度改动落地的两轮真机（now20 / now21）各暴露了一个**新的**死循环，都不是旧问题复发：

### 10.1 幻影规则把人家的卒清没了（now20：`推不出来` 19 次、`清掉幻影` 8 次）

- 现象：我方炮刚落下的那格被模型读成 `p`（黑卒）⇒ 白方黑卒「多了一个」⇒
  `clearPhantoms`（不变量：**任何兵种的数量不许变多**）按「多出来的那个就是幻影」把
  **真·对方卒**清空了 ⇒ 盘面少了对方一枚卒 ⇒ 任何合法着法都解释不了 ⇒ 恢复 → 重建 → 再撞。
- 修：**数量守恒判定要「数全了」才成立** —— 只有当**所有参照棋都还在盘上**
  （`keepCount[ch] === refCount[ch]`）时才允许清；`?` 不参与计数；
  `activeOwnMove.destIndex` 只在**选擦除点**时跳过，计数照算。
- 真机效果：`清掉幻影` 8 → **1** ✓（now21）。

### 10.2 重建基准「保住的那一格」没写回观测（now21：`推不出来` 22 次、`恢复` 6 次）

- 现象：日志成对出现 ——
  `按观测量建基准：全盘 OCR 证据保住 1 格` → `丢掉 N 条已知事实，基准 = 本帧盘面`
  → **同一毫秒级**跟着 `轮次推不出来（UNKNOWN）`，如此 22 次。
- 根因：`rebuildBaselineFrom()` **内部**用全盘 OCR 证据把误读格改回基准值（`board[i] = prev[i]`），
  但它只改了传进去的 `rebuilt`；**同一 tick 紧接着的 `sideFor()` 用的还是原始观测**
  （那格仍是误读）⇒ 又是「没有合法着法能解释」⇒ 恢复 ⇒ 重建 ⇒ 再撞。
  一句话：**改正必须写回观测**，而不是只写回基准。
- 修（`auto-driver.js`，两行顺序很关键）：
  先 `rebuildBaselineFrom(rebuilt)`（它内部会把误读格改回来），**再**把 `rebuilt`
  抄回 `observed.chars` 并刷新 `lastBoard`。写回顺序反了就是空操作 —— 自检当场抓过一次。
- 自检：`驱动·恢复后重建基准…` 用例补断言「`lastBoard()` 里那格也必须是保住的子」，
  夹具改成**一发生重建就停**（多跑几 tick 会把 `lastBoard` 覆盖回原始坏帧，断言失去意义）。

### 10.3 循环丙：改「我方刚落点」时整轮抛异常（now22：`from is not initialized`）

- 现象：日志里 `全盘 OCR 证据（兵种取字形）…按已知事实补齐` 之后紧跟一行
  `本轮异常（已跳过，下一轮重试）：from is not initialized`，然后就是熟悉的
  `轮次推不出来 → 恢复 → 重建 → 再撞`。**这行异常长得像良性提示，实际是死循环的开关。**
- 根因：`applyOcrBoardFixes` 里「我方正在落到的那一格，OCR 不许改」的早退块用了 `from` / `want`，
  可那两个 `const` 声明在它**下面** ⇒ 一命中就是 TDZ（QuickJS 的文案恰好是 `from is not initialized`）
  ⇒ 整个 `applyOcrBoardFixes` 抛出 ⇒ 那一轮作废 ⇒ 落点格的误读留到下一帧 ⇒ 又推不出来。
  而命中的格子永远是我方刚落点（高亮环把那格读成敌色是**常态**）⇒ 每次 OCR 都想改它 ⇒ 每次抛。
- 修：把 `const want = theirs; const from = missing ? "空" : mine;` 提到早退块**之前**。
- 自检新增 `驱动：全盘 OCR 想改「我方刚落点」时整轮不许抛异常`（tap 驱动到 SENT，再让 ocrBoard 说谎）：
  断言**没有** `本轮异常` + 闸门计数 `ocrFlipBlocked ≥ 1`（后者同时验证夹具真的走到了那条闸门）。
- 教训：驱动里 catch 成「本轮异常（已跳过）」的路径必须**有人盯着** ——
  它会把「一个变量作用域写错」放大成「整轮空转 + 死循环」。自检至少要在关键闸门上禁用它。

### 10.4 循环丁：异色异字的落点误读把「已知事实」整条丢掉（now23）

- 现象：`确认：OPPONENT_REPLY…（双方落点都被游戏高亮盖住，均按已知事实补齐）` 之后，
  连着 4 次 `轮次推不出来`，每 ~12s 烧一轮 `恢复 → 重建基准`（now23 里 11 次恢复）。
  日志对照帧里能看见 `(col 2,row 3) C→p` —— 我方刚到 (2,3) 的红炮被模型读成**黑卒**。
- 根因：观察层「已知事实补齐」的 ③ 支只认**同字异色**（C↔c）与**同色异字**（C↔P）两类；
  「异色 **且** 异字」（C↔p）一律按 ④ 判成「真被吃了 / 走开了」⇒ **把记录丢掉** ⇒
  之后每帧都读成 `p` 也没人管 ⇒ 差分「变化 0 格」永远不动 ⇒ 只能等看门狗恢复。
- 歧义拿不准 ⇒ 加**第三票：像素（找色）**。那一格到底是哪一边的墨迹，找色比模型的
  「兵种 + 颜色」判断稳得多（同帧 OCR 也说那格是 C）：
  · 证据站**已知事实**这边 ⇒ 这一帧读错，保住事实（`stats.pixelKeptFacts` + 日志
    `按像素证据保住已知事实：(2,3) 读成 p，但找色说是红（期望 C）→ 这一帧读错`）；
  · 证据站观测这边 / 拿不到证据 ⇒ 照旧丢掉（对方反吃时正是这种，不能把吃子藏起来）。
- 自检新增 `驱动·异色异字的落点误读…`：夹具先让驱动把我方落点登记成已知事实，
  再让观测把它读成 `p`、`ocrCell` 说 RED ⇒ 断言 `pixelKeptFacts ≥ 1` + 那格保住 `C` + 不出现推不出来。
- 通用教训：**「分不出的歧义」别靠更严/更松的阈值，要靠多一路独立证据**（这里是找色）。

## 11. 差分追踪：先看哪一格动了，再问那个兵种能不能这么走（用户 2026-09-20 提的算法）

用户口径：**「按顺序来：对方那个棋子动了，就按棋子的规则检查它走到哪里」** ——
不要「枚举全部合法着法 × 整盘比对」，而是**从差分直接读出动的是哪一枚子，再用它自己的走法规则校验落点**。

### 11.1 与枚举式 `infer()` 的分工

| | 枚举式 `infer()`（原有） | **差分追踪 `inferTracked()`（新）** |
|---|---|---|
| 做法 | 生成该方**全部**合法着法 → 每手整盘比对 | 差分里「起点空了、终点多了个东西」⇒ 只可能是**这一枚子**走的 → `legal.isLegalMove` 过一遍兵种规则 |
| 代价 | 几十手 × 每手 O(90) 比对（容差路还要再乘应手数） | 两个格子 + 一段路程（马腿/象眼/炮架/九宫/过河/自将） |
| 落点格读花时 | **全军覆没**（真机 now24：22 次「轮次推不出来」，全因我方炮被读成黑卒） | **照样认得出** —— 它根本不用落点格那个字，只信「起点空了」+ 规则 |
| 何时用 | 追踪给不出结论时的**兜底**（解释力最强） | 差分干净（恰好一组/两组、无 `?`）时的**快路** |

两者**不冲突**：追踪只在很紧的条件下才敢给结论，其余一律返回 `null` 让枚举路接手；
而且两条路的结果都要过驱动里那套「同一个解释连续两帧一致」的跨帧佐证才会被采信。

### 11.2 判据（宁可返回 `null`，也不乱认）

① **起点空了**就是第一手证据（用户口径：「那个棋不在那个位置」）；起点必须在观测里是空的
   （除非开 `allowSourceGhost` 时的残影）；
② 「同字母换大小写」（C↔c）是红黑读反的噪声，不算「多了一个子」；
③ **落点读成什么都可以** —— 读成敌色 `p`、只读得出 `?`（光环）、甚至整格读不出，都行
   （那格是什么子是着法推出来的已知事实）。只要求**看得到「有东西」**：
   · 非吃子（那格原来空）：必须有子或 `?`；
   · 吃子（那格原来有敌子）：那枚敌子必须**已经不在**了；
   · 两边都读空 ⇒ 多半是「子还在飞」（动画中间帧）⇒ **不认**，等下一帧。
④ **只枚举那一枚子自己的合法走法**（`legal.legalMoves(before, srcCol, srcRow)`，不是全方几十手），
   每一条都要过兵种规则 + 「整张观测只有这两格动过」（别处只容忍红黑读反）⇒ 唯一合法才算数；
⑤ 两步（我方 + 应手）要求恰好两组「空/多」，配对都要过规则，唯一合法才认；
⑥ 返回的盘面是**「基准 + 这一步」**；`reason` 必须**逐帧稳定**
   （驱动拿它做跨帧佐证，把「这一帧读成了什么」写进 reason 会让佐证永远凑不齐 —— 踩过一次）。

### 11.3 落地

- `src/chess/transition.js`：新增 `inferTracked(before, side, observed, options)`，与 `infer()` 同形状，导出；
- `src/automation/auto-driver.js`：新增 `inferMove()` —— **先追踪、给不出结论再枚举**；
  `sideFor()` 与 `rebuildBaselineFrom()` 两处调用点都走它；统计 `stats.trackedMoves / trackedMisses`；
  日志形如 `轮次推断：按差分追踪：c2c6（炮）` / `按差分追踪：我方 c2c6 + 对方应手 g6g5`。
- 自检 6 条：落点被读成敌色照样认出手（真机 now24 场景）、**落点只读得出 `?`（光环）也认得出**
  （用户口径「按原来的位置扫」）、**子还在飞（两边都空）不许当走完**、兵种规则当真（车路被挡 /
  蹩马腿 / 炮吃子没架子三种一律不给结论）、别处有 `?` 就不猜、两步（我方 + 应手）且两个落点都被画花也追得出。

## 12. 光环实测：先测再改 —— 结论是「不该做像素掩膜」

| 复核项 | 实测（K40，1080×2400，几何 origin(81,697) step(115,114)） | 结论 |
|---|---|---|
| “环”到底是什么 | ❌ **先前的“细红圆环 r≈48px”是错的** —— 那是**我们自己画板画的计划出手标记（▶◀）**；

### 12.7 ②「换钥匙重读」实测：钥匙够用，问题是**时机**

探针 `tools/decor-reread-probe.js`（自己走一手兵 c7→c6，动画窗口内连拍 8 帧，
对落点格跑 8 种预处理：clip / gray / up2 / up2gray / otsu / up2otsu / 只取字区0.5 / 字区0.5+灰度）：

```
帧1 (+0ms)    clip=空  gray=空  up2=0?0.78  …全读不出          ← 子还在飞（根本没画上去）
帧2 (+297ms)  clip=兵0.93  gray=兵0.99  up2=兵1.00  …8 种全部读出「兵」
帧3~8        全部 兵 0.92~1.00
汇总：8 种预处理各命中 7/7 帧（唯独“子没出现”的那一帧谁也读不出）
```

- **结论：换钥匙没有收益** —— 读不出来与对比度/放大/二值化无关，纯粹是“**子还没画上去**”
  （动画完成约需 ~300ms）。这直接说明病根在**观察时机**，不在识别能力。
- 由此得到最省的对症实验：把观察的第二帧间隔从 260ms 提到 ~460ms，让它越过那个 ~300ms 的窗口
  （autorun 就能调，不改代码）：`observeGapMs: 460` 的 A/B 见下。

### 12.5 试过但得不偿失：观察撞上走子动画 ⇒ 补一帧（**实测后默认关**）

- 机制（代码读清楚 + 真机对得上）：观察是**抓两帧严格合并**（两帧不一致的格子就降级成未知格）。
  而走子动画只有 ~0.4s（棋子被画暗/半透明）⇒ 只要其中一帧落在动画里，那格必成未知 ✗。
- 实现（`recognizeMerged`，`observeRetryOnUnknown` 开关）：合并后若有未知格，**丢掉最早那帧**、
  隔 `observeRetryGapMs`(420ms) 补抓一帧，用「最后一帧 + 补的那帧」**重新严格合并**；
  只在未知格真的变少时才采用（严格合并的原则不变）。
- ⚠️ **两轮真机 A/B 判它不划算**（now34/35 vs now32，同开局各 180s）：补帧确实命中（日志 5 次），
  但**只要有未知格就会补**（未知格本来就常见）⇒ 每轮多 ~1.4s ⇒ **tick 1203→1761/1653ms、出招 8→4 次**。
  ⇒ **默认关**（代码与自检用例都留着，将来先收紧触发条件——例如只看“变化格”里的未知格、
  且一轮只补一次——再重新 A/B）。
- ④「按这一手的期望填」**本来就在系统里**：有「已知事实」的格子是**立即补**的，
  那个 4 帧等待只留给「一点事实都没有」的真未知格 —— 也就是“宁等不猜”的边界。

### 12.6 反面教材：两次“缩短等待”的尝试都被真机否决

| 尝试 | 想省什么 | 真机结果 |
|---|---|---|
| 「静止 + 未知格 ⇒ 3 帧就重锚」 | 白等 8s→2.5s | now31：重锚 **38 次**空转、点击 **2** ✗（那格重锚也读不出来） |

| 「撞动画就补一帧」 | 未知格→少 | now34/35：tick **+45%**、出招 **8→4** ✗（补帧太频繁） |

两轮都回退了，代码里留了注释+数据防重犯。**教训：在这个系统里“等”比“猜”安全** ——
要解决卡住，得让那一格**读得出来**（或确认它只是装饰），而不是把等待缩短。

下一次该走的路（按性价比）：

1. **动画期判定（推荐先做）**：游戏给刚走过的子画的红环已经量准了（细红圆环、半径≈48px、
   可用相邻帧比对判“在闪/刚画上”）。判到“这格在装饰中”时**不要把它算未知** —— 驱动用“刚落的那个子”
   补（已知事实本来就有）、面板的 FEN 门也放行 ⇒ 既消掉白等，又不用猜。
2. **给同一格多几把钥匙**（用探针在同一帧上 A/B 选命中率最高的）：灰度重试已有；再加
   「放大 2× + Otsu」「只取字区 0.5 高对比」两条 —— 目标是把“读不出来”变成“读得出来”。
3. **观察节奏自适应**：刚走过子（有环）⇒ 拉长帧间隔避开动画再读；静止 ⇒ 拉短。
4. **兜底改成“按这一手的期望填”**：有 `activeOwnMove` / 刚确认的应手时，用推出来的子填，
   而不是“按上一张盘面填”（后者会写出假观测 —— now33 就是这么崩的）。

## §16 now40 A/B：「被未知格挡住就提前兜」把恢复从 25% 打到 13%

1. **状态机分支顺序**（`state-machine.js` onSnapshot）：`!sideKnown`（轮次未知）分支排在

   **2.5s「确认超时 → CANCEL_TICKET」只在 `state === VERIFYING` 的 TICK 里判**
   （onTick 里两段：`WAIT_TURN+unknownSince` 看门狗 / `VERIFYING+verifyDeadline`）——
   TICK 到时状态总不是 VERIFYING ⇒ 超时永不触发 ⇒ 同一张票据活了两分半。
   同 16.11 的「迟到的点击回报」「暂停粘住」是同一类洞：**动作在飞的时候，观测不许改变机器状态**。
2. **恢复动作清了落点保护**（`auto-driver.js` `recover()`）：那两分半里驱动自己跑了一次
   `恢复：重新定位棋盘`，里面无条件 `activeOwnMove = null` ⇒ 我们刚落的車@(6,6) 失去

3. **崩溃点无堆栈**：`自动循环出错：TypeError: cannot convert to object` 没带 stack，

**修法**：

- `state-machine.js`：把 `CLICKING/VERIFYING → return "点击/确认中，等待确认结果"` **整体前移**到

- `auto-driver.js`：`recover()` 里 `activeOwnMove = null` 改为**仅在无活票据时**清

**测试**：自检 **236/0**（新增「确认期间『轮次未知』的观测不许把状态拽出 VERIFYING」——
修前必失败：旧顺序会把状态变 WAIT_TURN；已实测：临时换回旧顺序跑 = 235/1，挂的正是这条）、回归 8/8。

### 16.23 引擎判负 bug：叶子处「对手没有吃子」被当成将死 ⇒ 假杀 29999（2026-09-21 中午，用户「又输了 是算法不够吗」）

**根因（离线复现，`search.js` 的 quiescence）**：
```js
const moves = generateMoves(board, red, !inCheck);   // 没被将时只生成「吃子」
if (moves.length === 0) {
    return -(MATE - ply);   // ← 无条件当「被将死」！
}
```
没被将时「没有吃子」只是安静局面，却被判负 ⇒ **只要我方走一步、让对手在叶子处暂时没有任何吃子，
引擎就以为是「一步杀」**。真机现场（复现探针 `.artifacts/probe-falsemate.js`，FEN = 当时的基准）：
`c6g6` 之后黑方**没被将、45 步合法着法、一个吃子都没有** ⇒ 旧代码给 `c6g6` 打 29999（深度 1、4ms）；
修后同一局面：`best=h2i2  score=-1 depth=4` ✓。

**修复**：只有「确实被将且无逃法」才返回 `-(MATE - ply)`；安静局面（没被将、没吃子）返回 standPat 已抬到的 `alpha`。
（`negamax` 里 `generateMoves(..., false)` 的全着法为空 → 判负 **是对的**，保持原样。）

**测试**：自检 **252/0**（新增用例 = 真机同 FEN：断言 `|score| ≤ MATE-200`，修前必失败）；
**牙齿检验**：还原旧行 ⇒ **251/1**，失败信息就是 `c6g6 评分 29999`；回归 8/8。已推 K40（`search.js` md5 校验 ✓）。

**留下的教训**：`quiescence` 里的「无着 ⇒ 判负」必须**同时以 inCheck 为条件**（无着=将死只对被将的一方成立；
没被将的「无着」在静态搜索里是常态——它只生成了吃子）。这条 bug 也解释了此前 `-29998/-29996` 的「我方被将死」假警报
（反向同一个洞：对手的叶子处我方没吃子 ⇒ 反过来报我被杀）——修后这类分数抖动同时消失。

### 16.25 「红相过河」误判 ⇒ 引擎接入后卡死 14 分钟（2026-09-21 12:22~12:48，真机事故）

象棋象的合法行位是 **红 {9 底线, 7 二路, 5 河沿}**（黑对称 {0,2,4}）——集合里**漏了河沿的 5**，
还错误地把**非象位行 8** 当成合法侧行。触发链：
引擎（Pikafish）走标准着法「飞相 e2→c4」把相停在河沿 (2,5) ⇒ 该格每帧被判「过河」（error）⇒
`engine.js` 的 `inspect()` 以 errors 为准 ⇒ 每步算棋都返回 `ok:false（position）` ⇒ 驱动永远拿不到着法。
**注意：这个局面在真实棋局里是合法且长期的**（相就停在那儿），所以恢复流程永远修不好它 —— 死锁。

**修复**：过河判据改为「真的到了对方半边」（红 `row < 5`，黑 `row > 4`）；象位行改为 `{5,7,9}`（黑 `{0,2,4}`），
非象位行仍出 warning（红线不放宽）。

**测试**：自检 **257/0**，新增 3 条：河沿象位不是过河（红/黑各一）、非象位行仍告警、
以及引擎门面级「飞相到河沿后 `inspect()` 必须为空」。修前这三条必失败。

**教训**：
1. **静态校验器里的「硬错误」必须只包含「真规则」** —— 把可行局面判成非法，会让整条自动化链路死锁
   （校验不过 → 不算 → 恢复 → 还是那个局面），比漏报危险得多。
2. 引擎换成 Pikafish 后**第一步就下出了这个标准着法**（飞相到河沿是常见套路），
   说明这类「罕见但合法」的局面在弱 JS 引擎下几乎不会出现、而在强引擎下是常态 —— 接入强引擎会
   把以前摸不到的校验边界一个个暴露出来，**接引擎的同时要按规则表逐项复核校验器**。
3. 排查路径很好用：日志里出现「算棋失败：棋规校验不过：…（第 X 行第 Y 列）」时，先把自己的读取盘面
   按规则表手查一遍再怀疑识别 —— 这次识别完全正确，是规则表错了。

**顺带落地的 MultiPV（v1.1）**：排除表（循环/长捉）路径以前回退 JS（深度 3~4）；
现在 `pikafishJNI` 支持 `setoption name MultiPV`，Java 按 `multipv` 分组取最深、返回 `candidates[]`，
JS 侧 `pickCandidate()` 取第一路不在排除表里的。全部被挡才回退。`analyze` 现在返回**所有带 pv 的 info 行**。

### 16.26 几何版本失同步 ⇒ 新票据永远拿旧版本、点击全被拒（2026-09-21 13:5x，真机「面板在点、游戏没反应」）

**现场**：面板重启后重新校准到**几何 v2**（钉棋子 (1,-30)px），随后 4 次完整尝试 `d0e1` 全部
「已试 4 次仍未确认落子」→ 暂停（面板状态行能看到「几何 v2」，而票据侧却还是 v1）。

**根因**（`state-machine.js` + `auto-driver.js`）：识别自对齐/钉棋子会让驱动侧的 `grid.version` +1
（`observeOnce` 里的「几何按检测框微调」会收编 `result.grid`），但状态机的 `versions.geometryVersion`
**只在 `GEOMETRY` 事件里更新** —— 而 GEOMETRY 只在「校准」时发。于是：会话中途几何升版后，
**新造的票据仍挂旧版本** ⇒ `click-executor` 的 `grid.version !== ticket.geometryVersion` ⇒ 直接 REJECTED
⇒ 恢复 → 重算 → 又是旧版本票据 → 再拒。与 Pikafish 无关，用 JS 引擎一样会撞。

**修法**：观察帧（SNAPSHOT）带上 `geometryVersion`；`onSnapshot` **只同步版本号、不动状态**
（GEOMETRY 事件会把状态打回 WAIT_STABLE，确认/出手途中不能那么干）。驱动的两处快照
（常规观察 + 「重建基准」那一帧）都带当前 `grid.version`。

**测试**：自检 **258/0**（新增 1 条：夹具发带 v8 的观察帧 ⇒ 新票据必须 `geometryVersion === 8`；
牙齿：临时禁用同步 ⇒ **257/1**，失败信息正是「新票据仍拿着旧几何版本 7（点击器会 REJECTED）」）。

**真机验证**（K40 13:52~13:56，同一局续跑）：面板重启 → 校准 v1 → 会话中途钉棋子升到 **v2** →
声明轮到我方 → `d0e1`(深27)→CONFIRMED、`f0e0`(深29)→CONFIRMED、`e0d0`(深29)→CONFIRMED、
中间一次 UNRELIABLE 两帧自愈、`c6b8`(深35)→CONFIRMED、`g8h6`(**深42**)→CONFIRMED、`h5g5`(深29)→CONFIRMED。
—— 以前必死的场景（几何会话中途升版）现在顺畅通过。

**教训**：「版本号」这类会话凭证必须**跟着同一个真实对象走、在同一处定义**。只在校准处同步、
而识别微调处偷偷改值，就会造出「票据与几何各说各话」的暗雷 —— 它不当场报错，而是在点击器那侧
表现成 REJECTED。排查这类问题时，先打印**两侧的版本号**对照。

  出路：**在棋盘上随便走一步**（标记移走，格子立刻可读）或「菜单→重来」重开一局 —— 面板随即接管。

### 16.28 断点续跑：进程被杀后自动重拉外部脚本（2026-09-21 17:20~17:33）

**背景**：16.27 的「进程被杀」当天又发生三次（16:25:30 / 16:53:11 / 17:19:08）——自动化活跃时
**约每 26~29 分钟被杀一次**（无 crash，`crashCount=0`，疑内存压力）。每次被杀后服务会把进程拉起，
但**脚本不会自己跑** ⇒ 面板窗口消失；断线期间游戏自带「托管」替红方走（弱），白送局势。
手动恢复（am start / force-stop+am start）管用，但人不可能一直盯着。

**修法（外部运行脚本的断点续跑，3 个文件）**：
- 新增 `apps/app/src/main/java/com/jdkshen/aijspro/external/ExternalRunResume.java`：
  · `recordStart(path, execution)`：每次外部「按路径运行」启动成功登记 `{path, startedAt, active}`，
    并在内存里记住该 `ScriptExecution` **本体**；
  · 全局 execution 监听：同一进程里它正常结束（成功/异常/被停止）⇒ 清登记。
    **用对象身份比对、不用 id** —— 进程重启后 id 会从头计数，比对会误伤；
  · `resumeIfNeeded(app)`（App.onCreate 调用）：登记还在 = 上次「跑到一半进程没了」⇒
    延迟 6 秒后**走和人工 `am start …RunIntentActivity --es path …` 完全相同的入口**重新拉起
    （后台起 Activity 靠本应用持 SYSTEM_ALERT_WINDOW 豁免 Android 10+ 的 BAL 限制；
    起不来时兜底直跑脚本）。防重复：任何真实启动刷新 startedAt，重启后 60s 内已有启动就跳过；
    过期 3h 作废；只在主进程生效。
- `ScriptIntents.execute`：`path` 非空且启动成功时 `recordStart`（am start / 快捷方式 / Tasker 全覆盖）。
- `App.kt` onCreate 末尾：`ExternalRunResume.resumeIfNeeded(this)`。
- 日志关键字：`ExternalRunResume`（Log.i：record start / 自动重新拉起 / skip resume）+
  `[self-heal] …`（GlobalConsole，面板里可见）。

**真机验证（首测即通）**：构建 `:app:assembleMiuixCompatDebug`（2m9s）→ `install -r -d` ✓ →
`am start` 面板（17:29:52 `record start` ✓）→ 用 `run-as com.jdkshen.aijspro kill -9 <pid>`
**模拟系统杀**（debug 包可用 run-as；⚠️ PowerShell 的 `$pid` 是只读变量，换名）→ 系统自动重启服务
（新进程）→ **17:31:33 `[self-heal] 上次运行被系统中断（进程重启），自动重新拉起`** → 面板继续
`CONFIRMED` 走子。**杀→恢复全程 ≈1 分钟、零人工**。
- 运维口径更新：正常情况**不再需要手动恢复**；16.27 的 force-stop+am start 仅作为「自动重拉也没上来」
  时的后备手段。想主动停掉续跑 = 在面板上正常停止脚本（触发清登记），或干掉后 3 小时自然过期。

重启后同 tag 看 `自动重新拉起`。后台起 Activity 是否被拦，看 logcat 是否有
`Background activity start … blocked`（当前 K40 实测未出现）。
