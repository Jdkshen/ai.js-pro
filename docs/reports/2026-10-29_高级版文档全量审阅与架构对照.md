## 已证实需要纠正的内容

1. `apk_package_analysis.md` 把 `org.aspectj:aspectjrt` 标成 QuickJS 运行时。这不能作为 QuickJS 实现依据。当前项目的 QuickJS 是 `QuickJsJavaScriptEngine`、`QuickJsNativeBridge` 和实际 native 库。
2. 多份文档把 `0x2d` 当作 `"__console__.js".hashCode()`。实际 Java 哈希值是 **2090448640 / 0x7c99b700**；45 / 0x2d 是内容匹配成功后分配的第二阶段模块索引。现有高级版工具类明确包含这两个阶段。
3. JVM 内存文档声称按 8 字节对齐又把 40→48、64→72。40、64 本身已经是 8 的倍数；文档内部已不一致，且不能直接把其 HotSpot 风格对象头图当成指定 Android ART 的实测布局。
4. “快 3～5 倍”“节省 75%”“冷启动约 1.5 秒”“GC 压力降低 60%”没有附设备、输入、工具和原始记录，保持未验证。没有用它们给本项目标性能提升。
5. 把 equals 换成字符串 `==` 会让内容相同但引用不同的模块名失配；建议版 closeSafely 在没有原始异常时可能吞掉关闭异常。二者都不保持原有语义。
6. 文档主要解释 Rhino 的 `module.exports = function(runtime, scope)` 包装层。高级版 Node 还有独立的 `v8/built_in_modules` 和 `ui/activity.js` 路径，不能把一个静态字符串 switch 当成三引擎统一运行架构。

## 高级版究竟怎样停止

本轮新反编译的手机基准中：

1. `ScriptEngineManager.stopAll()` 在引擎集合锁内逐个调用 `forceStop()`，返回当时引擎数量。
2. Node 对应 `a26.forceStop()`：引擎线程不是 Android 主线程时，先请求 thread.interrupt；再请求该实例 PlutoJS 停止。
3. `PlutoJS.m16027()`：没有 process 对象时直接 terminateExecution；process 已释放则返回；停止计数到第 4 次时强制终止 V8；此前通常在 V8 所属线程直接执行或投递 `process.exit(-9000)`。**这是重复停止请求计数，不是本轮观察到一个自动重试 4 次的定时器。**
4. Node `ui/activity.js` 的 ActivityLifecycle 在 UI 线程上下文注册生命周期和 `process.on('exit')`，退出时注销监听并逐个 activity.finish；最后一个 Activity 销毁后取消其 keepRunning。
5. 引擎 onDestroy 注销广播并释放 PlutoJS；release 检查线程、标记 V8 无效、清掉所持有代理引用，再释放 Node/V8 对象及相关运行时资源。
6. Rhino LoopBasedJavaScriptEngine 则移除 Handler 回调、退出 Looper、关闭 activity；非主线程再执行父类 forceStop。

这些是 Java/JS 静态路径。没有观察到该正常停止链路直接杀整个 Android 应用进程，也没有证实高级版对用户 Android 36 上的同一列表问题绝对不会崩溃。

我们已支持脚本显式 process.exit 的清理包装；本轮需区分的是**外部停止按钮**：当前走 Java UI 清理屏障后 native cancel，并非高级版的 process.exit 优先升级链路。dev-1285 这次修复的是“回调关闭而 RecyclerView 仍布局”的竞态，不应扩大为高级版所有停止语义均已对齐。

停止对照的原始文件在 `advanced-stop/`：`okhttp3_internal_io_a26.java:272`、`org_autojs_autojspro_v8_PlutoJS.java:443/498`、`com_stardust_autojs_engine_ScriptEngineManager.java`、`com_stardust_autojs_engine_LoopBasedJavaScriptEngine.java:94`；JS 从相同手机基准 APK 的 `v8/built_in_modules/ui/activity.js` 提取。JADX 方法编号仅对这次导出有效。
