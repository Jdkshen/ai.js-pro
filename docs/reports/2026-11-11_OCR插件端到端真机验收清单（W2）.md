# OCR 插件端到端真机验收清单（dev-1486 起用；W2 出，供 Lead/W1 对齐）

目标判据（Lead 口径）：⑴ removeOcr + 不装插件 ⇒ $ocr 点名错误；⑵ removeOcr + 装插件 ⇒ $ocr.create() 真能用（worker 线程 detect 出文字）；⑶ 默认（不减 OCR）⇒ 行为逐字不变。

## 一、打包期该看到的三行（logcat 过滤 C-PKG）
- project-res check: sidecars=… hostDigest=…（工程资源包判定；与本任务无关，但同批出现）
- ocr removed (removeOcr=true) files=… bytes=… prefix=… rhinoModule=kept(real module) …
  · rhinoModule 必须是 **kept(real module)**；若是 stubbed(...) 说明真实模块不在（那时才回退桩）
- packaging policy dropped native libs=… (removeOpenCv=false removeOcr=true plugins=…)
  · 期望：OCR 的 lib（libppocr/libmlkit）在 dropped 里；模型目录条目为 0

## 二、产物侧该核对的条目（解包 APK）
- lib/arm64-v8a/libppocr.so 与 libmlkit_google_ocr_pipeline.so **都不在**（removeOcr=true 时）
- assets/mlkit-google-ocr-models/** **不在**
- assets/modules/__ocr__.js **在**（且是真实模块，不是 796B 桩）
- 若装了 OCR 插件：产物里 **不应该**出现插件带来的 OCR 载荷（打包期 PluginOcrSource 目前未接线，属已知边界）

## 三、运行期四段日志（装插件时；过滤 OCR / C-OCR / Plugin）
顺序与含义（dev-1490 起的预期序列；主路径 = 宿主直连工厂 + 共用同一份会话包装）：
1. plugin loaded=true  —— 宿主插件加载成功
1.5 plugin libs lazy staging: ready=true  —— 库已就绪（**注意**：这一版 READY 若在旧版本就已存在，会走「早退补解模型」分支 ⇒ 下一条带 (late)）
2. plugin models staged (late) … files=5  —— 模型抽取；**files<5 会同时出现 count mismatch 的 W**（真机 files 与期望数不一致在落盘那一刻就暴露）
3. host-built session (direct factory) backend=ppocr libDir=… modelDir=…  —— 直连工厂建好会话（主路径证据）
   · 会话由 wrapSession 统一包装（与内置同一份）⇒ 脚本侧调用的是 4 参重载；若又出现 Can't find method PPOcr.detect(ImageWrapper) 或 backend=undefined，说明包装没生效，把日志发 W1
   · W1 已核对：全文件**裸会话出口 0 条**，wrapSession 共 4 处（直连工厂 / 描述符→工厂 / 插件自带会话 / 内置路径）⇒ **任何出口都同形**；pluginSession shape at escape 那条日志用于确认脚本拿到的 detect 是 JS 包装而不是插件 Java 方法
   · W2 侧对齐：插件的 create 现在**只返回描述符**（不再把宿主工厂建的 Java 会话交给 JS —— 这个引擎里 Java 方法不会自动变成同名 JS 函数）
   · 若先出现 direct factory failed (try plugin create): … ⇒ 说明直连失败、回落了插件 create 候选链（老宿主兼容路径）；把这条错误贴 W1
   · 若出现 plugin create unavailable: … ⇒ 把后面每条候选错误贴 W1（注意：这不是方法缺失，见 W2 的定性：JS 侧看到的是包装对象、Java 方法未暴露为同名 JS 函数）
   · 若出现「宿主没有会话工厂（老宿主）⇒ 回退描述符」（W2 插件里的日志）⇒ 不一定是宿主老，可能是插件类加载器隔离
3. 模型侧：plugin models staged pkg=… v=… files=5  —— 宿主从插件 APK 解出 assets/ocr/models/** 那 5 个文件
4. worker 线程 detect 出文字 —— 真识别成功（判据 ⑵ 的最终证据）
   不装插件时应只看到点名错误（OCR 能力未随包…），且**不再**出现 ML Kit 不可用（检查即失败）：ReferenceError…

不装插件时应看到：OCR 能力未随包（optimization.removeOcr=true）…（点名错误；来自 __ocr__.js 内的插件优先判定之后的回退）

## 四、soname 相关的失败形态（若出现，把原文贴 W1）
- UnsatisfiedLinkError: libopencv_* ⇒ 插件 libppocr.so 的 NEEDED（实测 7 个 libopencv_* + jnigraphics/android/log/dl/z/m/c）在宿主进程里没命中 ⇒ W1 走适配层（显式构造），插件侧不动算法
- LibLoadException ⇒ W1 工厂内的点名错误（库名/路径/原因都在里面，直接用）
