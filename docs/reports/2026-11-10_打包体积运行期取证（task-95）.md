# 打包体积：运行期是否真的需要（task-95，引擎/运行时侧取证）

日期：2026-11-10。范围：**只做「运行期是否需要」的取证**，不动打包策略。判据：**零命中/无调用点** 才算可删；拿不准写「需真机 A/B」。

## ① `org/antlr/**`（~2M，含 `.stg`）

- **`.stg` 零命中**：全仓 Java/Kotlin **没有任何调用点读 `.stg`**（`.stg` 是 ANTLR/StringTemplate 的**代码生成**模板，只在构建期/工具期用）。
- **ANTLR 运行时类确有运行期调用点**：`modules/engine/src/main/java/com/stardust/autojs/android/Node24DirectDexGenerator.java:3-7` 里 `import org.antlr.runtime.*`（CommonTokenStream/TokenSource/CommonTree/CommonTreeNodeStream）——这是 **node24 内联 dex 生成**那条路。
- ⇒ 结论：**`org/antlr/runtime/**`（类）与 node24 强绑定**（nodejs disabled 时随 ③ 一起可省，见下）；**`.stg` 模板文件属于「零命中」可删**，但需先确认 APK 里 `org/antlr/**` 中哪些是 `.stg`（打包侧 aapt/zip 清单确认，属 W2 那张表的范围）。

## ② `assets/source-engine-upgrade/**`（2M）

- 读者（全仓 grep `source-engine`/`source-engine-upgrade`）：**没有引擎/运行期代码**；命中的是 `tools/test-check-android-16kb.py`（测试工具）、`apps/app/src/main/assets/template-manifest.json`（模板清单，`nodeRuntimeManifest` 指向它）、`apps/app/build.gradle:1185`（**打包期**剔除）、以及一批**测试**（`Node24PackagingAssetsTest` 等）。
- 运行期真正读它的是 **node24 运行时安装/诊断链**：`apps/app/src/main/java/com/jdkshen/aijspro/mcp/McpEngineDiagnostics.kt:24`（`NODE_ASSET_PREFIX = "source-engine-upgrade/node24/arm64-v8a"`）→ 与 node 运行时同生共死。
- ⇒ **`features.nodejs=disabled` 的工程：不需要它**（没有 node 运行时就不会读）；**但 `McpEngineDiagnostics` 目前会无条件读该前缀** ⇒ 要删得同时让它容忍缺失（或只在 nodejs 启用时读）。
- **`libc++_shared.so` 与 `lib/arm64-v8a/libc++_shared.so` 去重**：`assets/**` 与 `lib/**` 在 APK 里是两个命名空间，**不能靠 zip 去重**；要么运行期从 `lib/` 加载（改 node 运行时加载器）、要么打包期只留一份 + 安装时释放 ⇒ **属「需真机 A/B」**（要验 node 运行时能否从另一条路径加载成功）。

## ③ `assets/node24/**`（21 项）

- 读者：`mcp/McpEngineDiagnostics.kt:105/141`（读 `node24/tools/node`、`node24/tools/tools.json`）+ `android/Node24HostBridge.java`（node24 宿主，:606 起是 OCR 相关 action）+ node24 引擎启动链。
- ⇒ **可省条件**：工程 `features.nodejs=disabled`（`getNodeJsMode()` 为 disabled）**且** `McpEngineDiagnostics` 的 node 诊断在缺资源时**降级而不是报错**。当前 `McpEngineDiagnostics` 的读取是**无条件**的 ⇒ 直接删会在 MCP `get_status` 的诊断段报错 ⇒ **需先把该诊断改成「资源缺失 ⇒ degraded 一行」**（一行判断，属 apps 侧）。

## ④ `res/**`（9M）+ `ai_js_pro_logo.png`（1M）

- **打包版自己的 UI 必需**：`SplashActivity` 用 `R.layout.activity_splash` + `R.id.slug` + `R.string.*`（见 `apps/inrt/.../SplashActivity.kt:45-47`），`LogActivity`/`SettingsActivity` 同理 ⇒ **icon/主题/启动图/布局都在运行期被读**，不是纯死资源。
- **脚本侧 `ui.layout` 不依赖我们的 drawable**：工程布局走**工程资源**解析（`resolveProject*`/`CompiledProjectResources` 那条链），脚本引用的 `@drawable/...` 由工程 parser 解析，**不查宿主 `res/`** ⇒ 这部分不是「为了 ui.layout 才带的」。
- 具体能砍多少（drawable/多语言/多密度）需要 **aapt2 shrink + 真机 A/B**（不在本轮范围）。

## ⑤ OCR（`$ocr` 内建 ppocr/mlkit）显式声明不用

- 现状：`$ocr` 的宿主实现是 `android/Node24HostBridge.java:606`（`kind=ocr`，`backend=ppocr|mlkit`）+ 随包 `libppocr.so`/`libmlkit_google_ocr_pipeline.so`；脚本侧是 `assets/modules/__ocr__.js`；**没有工程级开关**。
- **最小改法（默认不变）**：照既有 `project.json.optimization.removeOpenCv` 的形状加一个 `optimization.removeOcr`（默认 `false`），打包期按它剔除 `libppocr.so`/`libmlkit*` 与 `__ocr__.js`，运行期 OCR 调用给**点名错误**（「本工程已声明不用 OCR」）——**与既有 removeOpenCv 同源**，不改默认行为。
- ⇒ 本轮**只出结论与补丁形状**：具体接线在打包策略侧（`PocPackaging`/`ApkBuilder`/`NativeLibPolicy`），不在本任务写作用域。
