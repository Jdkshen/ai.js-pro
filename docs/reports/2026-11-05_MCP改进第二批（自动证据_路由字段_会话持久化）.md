## 二、用新工具复核真实 VMP 目标（libyj-vmp-lib.so）

方法：`.4` 上该 SO 只有旧版 App，于是把 560,960 B 的 `libyj-vmp-lib.so` 按 64 KiB 分页经 MCP 读回 PC（sha256 `d7b3a251…` 与源一致），再用 `adb push` 送进 MI8 的脚本目录（避免 MCP 单次请求体积限制）；随后用 `native_session_*` 在 MI8 上分析。

```text
native_session_open {path:__vmp/libyj-vmp-lib.so, sha256:d7b3a251…, relocsApply:true}
native_session_query ij  -> ELF64 arm64, 560,960 B, 初始 aaa;Ps 用时 10.0s（此后不再重跑 aaa）
native_session_query iE  -> 导出含 vmInterpret / cacheInitial(7608 B) / getCacheClass(3040 B) 等
native_session_query is~vmInterpret -> 126 0x0003a1e4 GLOBAL FUNC 82684 vmInterpret   ← VM 解释器入口
native_session_query iS~.text        -> 0x46900 (289 KiB 代码)
native_session_query iS~data.rel.ro  -> size 0x3b88
native_session_query il              -> liblog.so libm.so libdl.so libc.so
native_session_close -> projectExisted=true, releasedBytes=2,730,619
```

要点：① 首次分析 10s、后续查询约 5.5s（走 `Po` 复用 project，不再 `aaa`）——这正是「批扫从不可行到可行」的那一步；② `vmInterpret` 82,684 B 是楔入 VM 本体的入口（`cacheInitial`/`getCacheClass` 对应项目总结里的字符串缓存与类初始化链）；③ 结论只写工具实测到的内容，不代替项目侧对 213 条注册表的字节级结论（那份证据在薄壳 `libliuyun.so` 的 `.data.rel.ro @0x22C40`）。

## 三、边界（未做/不确定）

1. **sameUid 仍无法自动**：`/proc/net/tcp` 里的 uid 是 socket 所有者，不是目标/客户端进程 UID；`forDiagnosis` 明确返回 `sameUidRequired=true`，必须调用方补。
2. **/proc 可见性因 ROM/版本而异**：读不到时需用 `terminal_exec`/shizuku 取原文经 `tcpText/tcp6Text` 传入；解析器是纯函数。只解析标准 tcp/tcp6 布局（不含 UDP/sock_diag）。
3. **会话索引不反推历史**：升级前的内存会话（无索引）无法恢复，project 文件仍在磁盘但缺元数据；索引写失败只累加 `indexErrors`，不阻塞会话操作。
4. **路由字段只解析首行**：后续路由行不覆盖首个；`routed=false` 时 `effectiveBackend=requestedBackend`。
5. `vmInterpret` 的**语义**（VMP 字节码解释器 vs 其它）来自导出名与体量推断，本批未做指令级验证。
