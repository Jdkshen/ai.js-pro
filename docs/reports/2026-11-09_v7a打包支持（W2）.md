# v7a 打包支持（W2 / task-74）：清单 + ABI 推导 + OCR 降级

- 决策来源：用户拍板「v7a 做」，走成本最低那条路 = **v7a 走 mlkit OCR 降级**（不 vendor v7a ncnn）。
- 已定事实（W3 task-67，本轮不重复调查）：v7a 可得的库 = libaijscrypto / libquickjs / libquickjs_jni（engine jniLibs v7a）、libc++_shared / libopencv_java5（OpenCV AAR v7a，单库自包含）、libmlkit_google_ocr_pipeline（AGP 合并产物有 v7a，本机 6.47MiB）；**唯一硬缺口 = libppocr.so**（build-quickjs.ps1:57-58 只构建 arm64）。
- 本机复核（本轮实测）：apps/app 的 release 合并产物 lib/armeabi-v7a 恰好这 6 个（aijscrypto 0.01 / c++_shared 0.83 / mlkit_ocr 6.47 / opencv_java5 21.26 / quickjs 0.78 / quickjs_jni 1.40 MiB）；app 用 ABI splits（build.gradle:246-269，include x86/armeabi-v7a/arm64-v8a、universalApk false）→ **安装哪个 ABI 的宿主，宿主 APK 就带哪个 ABI 的 lib**。

## 1. 改动清单
1) **apps/app/src/main/assets/excluded-zip-files.json**（①）：general 追加 v7a 组 5 条（aijscrypto / c++_shared / mlkit_google_ocr_pipeline / quickjs / quickjs_jni），opencv 追加 1 条（libopencv_java5.so，v7a 是单库形态）；**arm64 现有 15 条逐字未动**（有单测钉住）。
2) **新增 apps/app/.../autojs/build/TemplateLibCompletion.kt**（②④）：纯逻辑 —— abiOf / abisOf / abisWithLibs / entriesForMissingAbis / describeSkip。**只从 entry 路径推导 ABI，不写第二份清单、不写死 lib/arm64-v8a**。
3) **改 ApkBuilder.ensureTemplateLibs**（②④）：删掉「模板只要有任何 arm64 lib 就整体跳过补齐」的早退；改成**按清单里的 ABI 逐个判断**：
   - 清单里所有 ABI 都已有 lib → 跳过（日志 template libs already present abis=…，与旧行为等价）；
   - 只带 arm64 的模板 → **只补 v7a 的 entry**（日志 template libs completion: wantedAbis/presentAbis/missingAbis/entriesToCopy）；
   - 无清单时的兜底扫描由「只扫 lib/arm64-v8a」改为**扫所有 ABI**（listHostRuntimeLibs），并按原运行时白名单过滤。
4) **改 modules/engine/src/main/assets/modules/__ocr__.js**（②）：默认后端本来就是 mlkit（"options.backend == undefined ? 'mlkit'"）；本轮补的是**降级不得撒谎** —— mlkit 初始化失败时先查 ppocr 可用性：
   - ppocr **明确不可用**（v7a）→ 抛 Error（code=OCR_UNAVAILABLE，带 reason/ppocrAvailable/requestedBackend），而不是造一个 detect 时才炸的 ppocr 会话；
   - ppocr 可用（arm64）→ **与改动前逐字一致**（degradedFrom/degradeReason/backend='ppocr' 同一套）；
   - 查不到（QuickJS/Node 没有该 Java 桥）→ 返回 null → **保持旧行为**。

## 2. 单一事实来源（谁是真值）
| 角色 | 真值 | 只做什么 |
| --- | --- | --- |
| excluded-zip-files.json | **要补哪些 lib entry**（含 ABI 路径） | 唯一清单；本文件不推导别的 |
| TemplateLibCompletion | 无（纯推导） | 从 entry 路径算 ABI、算「模板已带哪些 ABI」、算要补哪些 entry |
| NativeLibPolicy | 无（纯判定） | 对**候选** .so 做「模板必需 / 工程策略(removeOpenCv/Pikafish) / 内建 OCR」归类，决定保留还是丢弃（丢弃会记 reason） |
| AbiPolicy | 无（纯判定） | 把 project.json 的 abis 与**实际产出**的 ABI 对比：≥1 可产出 → warning，一个都产不出 → 报错；不静默 |
（代码里**没有**第二份 v7a 清单；v7a 的三个事实来源只有 JSON 一处 + 各自判定类。）

## 3. 验收方式
- 单测：TemplateLibCompletionTest 5 项（abiOf 解析 / **只带 arm64 的模板只补 v7a entry** / 齐全则跳过 / 空目录不算已有 / 清单双 ABI 组且 arm64 未动且 v7a 无 ppocr）；既有 PackagingPolicyTest 回归。
- 产物级（Lead 跑）：node tools/apk-native-lib-audit.mjs <apk> --expect-abi arm64-v8a --expect-abi armeabi-v7a --fail-on-leak → 判据 **leaks=0 / unknown=0 / missingAbi=[]**；配套 tools/verify-16kb-alignment.ps1。
- 打包日志判据：template libs completion: wantedAbis=[arm64-v8a, armeabi-v7a] presentAbis=[…] missingAbis=[…]；以及 abis declared/produced/missing（AbiPolicy）。

## 4. 未验证边界（重要）
1. **v7a 无真机** → 只能验到「产物 ABI 齐全 + .so 可解析（audit 的 ELF/ABI 解析）+ 16KB 页对齐检查」级别；**「v7a 上能起来」未验证**。
2. **v7a lib 的来源 = 宿主 APK 的 lib/<abi>/**：安装在 arm64 设备上的宿主是 arm64 分片 → 没有 v7a 源，补齐会逐条 host lib missing entry=…，AbiPolicy 仍给 warning（这是诚实行为，不是 bug）。要在 **v7a 宿主**（或模板自带 v7a）上打包，才能得到 missingAbi=[]。**这条必须在验收前确认宿主 ABI，否则审计结论会张冠李戴**。
3. OCR：v7a 上只能走 mlkit（libppocr 无 v7a）。若某工程强制 backend:'ppocr' → 现在是清晰的 OCR_UNAVAILABLE 错误（不是崩、也不是假降级）。
4. QuickJS 侧 modules/engine/src/main/assets/modules/qjs-plugins.js 有**同类**「退到 ppocr」逻辑，本轮**未加同款可用性守卫**（v7a+QuickJS 组合才会遇到）；记边界待办。
5. 模板内那份 excluded-zip-files.json（模板 APK 里的）未动 —— 需模板重建才同步；本轮的模板补齐读的是「模板工作区 → 主程序 assets」优先级链，所以主程序清单已生效。
6. 未跑构建/装机/发布/git；EOL 全 LF。
