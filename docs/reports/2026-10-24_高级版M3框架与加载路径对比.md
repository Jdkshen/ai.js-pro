## 已确认使用的框架和方法

| 层 | 高级版实物证据 | 对加载速度的含义 |
| --- | --- | --- |
| UI | M3 示例主题是 `Theme.Material3.Light.NoActionBar`；布局为 MaterialToolbar、MaterialCardView、ShapeableImageView、ExtendedFloatingActionButton、BottomNavigationView；列表 RecyclerView，分页 JsViewPager/ViewPager。 | 是 Android 原生 Material 3 View。我们也使用相同类型组件，换 UI 框架不是这次对比得出的方向。 |
| 布局创建 | `ui/activity.js:105` 附近按 layoutId 使用 `android.view.LayoutInflater`，安装 View 后调用 onContentViewSet。 | 界面主体由原生 XML/资源创建，JS 负责组装事件和数据。 |
| Java 桥 | `V8.java` 有 J2V8 的 native 函数执行和 Java 方法注册；`V8JavaMethods.java:63/67/279` 使用 SparseArray 方法 ID 表及 Class→方法名→ID 表，参数来自 V8Array，对象由桥取回 Java 引用。 | 可复用类/方法元数据，并直接围绕 V8 对象和 Java 引用传参。已见桥路径没有采用本项目每次 Java 调用的 JSON 消息协议；未分析所有原生内部实现。 |
| Java 反射 | `V8JavaMethods.java:377` 仍调用 `Method.invoke`。 | 高级版也使用反射，不能把它的速度归因为“完全不用反射”。差异包括缓存方式、传参和调度路径。 |
| 动态 Java 子类 | `r16.java:178–255` 构造带 `.class/.super/.implements` 等指令的 Smali 文本，解析并直接写 Dex，再交给加载器；`:307` 返回异步 V8Promise。 | 这条路径省去本项目 Classfile→临时 JAR→dx 的中间流程。并未看到 DexMaker/ProxyBuilder，因此不将其说成 DexMaker 实现。 |
| 图片 | `ui/res.js` 调用内部 loadImageInto；`V8AutoJsGlobal.java:584` 明确进入 `com.bumptech.glide` 的请求链，且提供 cancel、clearMemoryCache、clearDiskCache。 | 使用 Glide 管理异步请求与缓存/复用，是重复加载图片时值得比较的差异；本轮没有测缓存命中率，也未确认全局每个请求的具体缓存策略。 |
| 工程资源 | `ui/res.js` 发布模式直接加载 resources.ap_；开发模式异步调用 aapt2 后加载。 | 不能笼统说高级版从不编译资源、所有加载都命中缓存或所有工作在主线程。 |

## 与本项目通用 Java UI 路径的差异

1. `node24/prelude.js:211–241` 已有成员缓存和不变 JSON 前缀缓存；但每次方法执行仍把当前参数转 wire、编码 JSON，并经宿主处理及结果解码。不能将它描述为“毫无缓存”，也不能将本地 Java UI 路径一概说成跨进程 RPC。
2. `NodeUiLocalSession.ImageLoader` 当前使用 HttpURLConnection + BitmapFactory.decodeStream，带每 View 请求 token 和 IO 调度，但没有 Glide 那样的图片请求/内存磁盘缓存体系。这与本轮 M3 UI 桥本身的开销需要分开测。
3. dev-1229 已完成 defineClass 真异步、major 51 轻量 dx 和关闭清理。下一轮不能再把“加 async”作为未完成的优化；仍有 Classfile/JAR/翻译链，以及普通 View/监听/binding 的大量细碎桥调用。
4. 我们原有阶段测量显示初始化回调仍约 0.48–0.50 秒，ViewPager/抽屉/Console 等设置占其中一部分；最终候选列表安装一冷两暖为 1460/1270/1253 ms。高级版本轮没有同条件启动计时，所以这些数字不能推算它快了多少倍，也不能证明哪一项贡献最大。

核对期间仓库已有另一条开发线的提交 `2c1a8fbf`，更新源也已是 **dev-1232**。其 [M3Kit 记录](2026-10-24_M3Kit原生DEX接入与宿主ClassLoader修复.md) 已完成原生 DEX 自定义 View 的 inflater ClassLoader 接入、交互 facade 和默认 NATIVE_ALL；报告的 MI8 page ready 为 641–671 ms。该结果来自对应开发线，本轮未重复执行。

这说明本项目已经在做“将组件创建与交互下沉到原生”的方向，不应再把整个方向说成尚未实现。但 M3Kit 的 page ready 与自带 M3 示例的 grid-ready 不是同一测量点，也不是同一工程，不能直接相除得出加速比例。本文对 HttpURLConnection 图片加载与 JSON Java 桥的检查针对通用接口，不能据此否定 M3Kit 原生控件后端已有的优化。
