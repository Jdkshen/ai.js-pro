# 无障碍事件源本地直订（task-64）

日期：2026-11-09。验证机：K40 `cccc62c7`（dev-1445）+ 设备4 `192.168.10.4:8765`（预 task-60 包）。
结论：**既有链路问题，与 task-60 无关**；已修（服务实例在本进程时本地直订）。

## 1. 现象与真机复现（两机一致）

脚本（`run_script`，engine=rhino，跑在 `:script`）同时做三件事：`events.on('accessibility_event'/'toast'/'view_clicked'/'window_state_changed')`、
注册一个**进程内** `AccessibilityDelegate`（与修复同一机制）、自己 `toast("TASK64-TOAST")` 制造事件。

| 观察 | K40 dev-1445 | 设备4（预 task-60） |
|---|---|---|
| `auto.service != null` | true | true |
| `RemoteAutomationBridge.isActive()` | **false** | **false** |
| `events.on(...)` 计数（12s，含脚本自己发的 toast） | **n=0 toastEvents=0 clicks=0 wsc=0** | **n=0 toastEvents=0** |
| 进程内 delegate 收到的事件 | **16 条**（toast 1 / notification 1 / window_content_changed 14） | 4 条（该包无 `AccessibilityEventWrapper`，探针建 JSON 报错，但计数说明事件到了） |
| logcat `AutomationHost` 注册日志 | **无**（订阅根本没发生） | — |
| `RemoteAccessibilityEvent.fromJson(...)` 往返 | 可用（`kind/pkg/windowId` 正常、`toJson` 原样返回） | 可用 |

→ 事件在 `:script` 进程**到得了**（框架把 16 条事件交给了同进程的 delegate），但 `events.on` 收 0 条；且两机（其中一机是 task-60 之前的包）完全一致。

## 2. 根因：task-163 的两个前提都不成立（两条独立断点）

1. **订阅被静默跳过**：`Events.maybeSubscribeRemoteAccessibility` → `ensureRemoteAccessibilityEvents` 第一道门就是
   `if (!RemoteAutomationBridge.isActive()) return;`；`:script` 直跑时该值为 false（`isActive() = sIsolationProcess && sBackend != null`，
   后端由 `ScriptHostService` 安装，MCP 的 runner 不装）→ 连 AIDL `registerEventListener` 都没调用（logcat 无 `AutomationHost` 行）。
2. **即使订阅也收不到**：主进程 `AutomationHostBackend.ensureEventDelegate()` 把 delegate 注册在**主进程**，
   而无障碍服务声明在 `:script`（manifest），主进程 `AccessibilityService.instance == null` → 该 delegate 永不触发。
   （对照：task-163 当时 K40 日志是 `event listener registered count=1 **ready=true**`，说明那时服务在主进程。）

**task-60 无关**：task-60 只把 `:node24` 通路（`AccessibilityEventForwarder`，delegate 注册在服务所在进程 → 一直是好的）的 JSON 抽取搬进
`AccessibilityEventWrapper`；`:script` 反向通道的 JSON（`AutomationHostBackend.accessibilityEventJson`）**一行未动**，而且本 bug 在 JSON 之前就断了。设备4（task-60 之前的包）同样 0 事件 → 既有问题。

## 3. 修复

- `Events`（`modules/engine/.../runtime/api/Events.java`）：`maybeSubscribeRemoteAccessibility` 改为**本地优先**——
  服务实例在本进程时走新的 `ensureLocalAccessibilityEvents()`（`AccessibilityService.Companion.addDelegate(9300, …)`，
  优先级与 Node24 转发 9101、主进程后端 9200 错开）；仅当本进程没有实例时才退回原 AIDL 反向通道。`recycle()` 用 noop delegate 摘掉本地订阅。
- **事件形状同源**：新增 `AccessibilityEventSnapshot.wrapperOf(event)`（automator）作为**唯一的 Android→JSON 字段抽取**，
  由 `:node24` 转发与 `:script` 本地直订共用；JSON 映射仍是 task-60 的 `AccessibilityEventWrapper.toJson()`；
  本地通路复用 `postRemoteAccessibilityEvent(json)` → 与远程通路**同一个**解析/emit 路径（字段不会随进程而变）。
- **不重复发**：`toast`/`notification` 有专用本地观察者（`events.observeToast()/observeNotification()`）；当它已挂上时，
  本地 delegate 只发全量 `accessibility_event`、不再发同名 kind（避免一次事件两次回调）。
  **⚠️ task-69 更正**：这条避重最初只看「观察者已挂」，而观察者**对同包（自身）事件是有意跳过的**
  （`AccessibilityNotificationObserver` 的 `event.packageName == mContext.packageName → return false`）——
  于是脚本自己的 `toast()` 既不进观察者、又被 kind 通道跳过 ⇒ **静默丢失**。现在避重改用观察者**同一条**投递判据
  （`willDeliver`）：同包 toast 由 kind 通道投递。详见下方 §7。
- **早退**：没有任何订阅者时连 JSON 都不建（与主进程 backend 的 `getRegisteredCallbackCount()==0` 一致）。

## 4. 正确用法（③）

- 无障碍事件：`events.on('accessibility_event', e => …)` 或按 kind：`'view_clicked' | 'view_long_clicked' | 'windows_changed' | 'window_state_changed' | 'window_content_changed'`。
- `toast` / `notification`：**沿用 `events.observeToast()` / `events.observeNotification()`**（专用本地观察者，payload 是 `Toast`/`Notification` 对象；
  与无障碍事件流的 `RemoteAccessibilityEvent` 不是同一个类型）；修复后 `events.on('toast')` 单用也能收到（kind 流），但**不要与 observeToast 叠加**（会各自发一次，已在引擎侧避重）。
- 计时：脚本线程 `sleep` 期间不处理回调（与 Auto.js 语义一致），用短 `sleep`/`setTimeout` 轮询。

## 6.1 task-69 追加（2026-11-09）：`observeToast()` 0 回调的真相与修正

- **代码级定案**：`AccessibilityNotificationObserver.onAccessibilityEvent` 对**同包**事件 `return false`（有意跳过）→
  脚本自己的 `toast()`（同包）永远到不了 `ToastListener` ⇒ `observeToast()` 对自身 toast **本来就是 0**（有意行为，不是 bug）；
  但 task-64 的避重把这个「有意跳过」变成了**静默丢弃**（观察者不投递 + kind 通道被跳过）⇒ **真丢事件，已修**。
- **修法**：新增共享纯判据 `AccessibilityNotificationObserver.willDeliver(eventPkg, ownPkg)`（观察者自己用它早退）；
  `Events` 的避重改成 `shouldSkipKindForDedicatedObserver(observerAttached, observerWillDeliver, kind)` —— 只在
  「观察者**真的会投递**」且 kind 是 toast/notification 时让路。单测 `ToastDedupDecisionTest`（3 项：`willDeliver` 真值表 /
  避重真值表 / 两侧同源断言）。
- **真机边界（重要）**：本轮在 K40 dev-1447 上跑分离实验时，`accessibility_event` 计数**也为 0**（服务 bound+enabled、
  `auto.service=true`、logcat 有 `Events: local accessibility event subscription installed (priority=9300)`，注入 adb UI 活动仍为 0）——
  即**本地 delegate 装了但没收到事件**的现象还在，与 W2 长时复核（1825 条）矛盾 ⇒ 修复后的真机行为**未验**，需下一轮复跑确认。

## 6. 未验证 / 边界

- 修复后的端到端（`events.on` 真收到事件）**需要一次构建安装**才能验；K40/设备4 上跑的都是修复前的包。
- ⚠️ **操作事实（task-73 补，实测踩过）**：**装包 / force-stop 之后必须重新 rebind 无障碍服务**，否则 `Events` 的本地直订会「delegate 已安装（logcat 有 `local accessibility event subscription installed`）、`auto.service != null`、服务 `dumpsys` 也显示 Bound+Enabled，但**一个事件都收不到**」——K40 dev-1447 上 task-69 的三次探针全 0 就是这个原因（Lead rebind 后立刻 `AE-FIRST kind=windows_changed` / `FINAL ae=62 onToast=1`）。**判 0 事件前先 rebind**，否则会把环境问题误判成回归。
- 主进程反向通道**保留未删**（服务在别的进程的拓扑仍然需要它）；本轮只改「本进程有实例」时的选择。
- `toast`/`notification` 的避重只在「专用观察者已挂」时生效；若既不 observe 也不 listen，不发。
- MCP `run_script` 不安装 `RemoteAutomationBridge` 后端（`isActive()==false`）本身未改（现在也不再需要它）。
