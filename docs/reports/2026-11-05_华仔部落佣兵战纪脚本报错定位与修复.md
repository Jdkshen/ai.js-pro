# 《华仔部落_佣兵战纪》脚本报错定位与修复（dev-1346/1347）

> 输入：`C:\Users\18101\Downloads\华仔部落_佣兵战纪脚本.zip`（130 项 Auto.js Pro 工程，`hz_ybzj`，含 `@se7en/float_menu-rhino` 库、`module/common/utils.js` 等）。
> 复现方式：解压后推到 MI8 `/storage/emulated/0/脚本/hz_ybzj`，用 MCP `run_script {path:"hz_ybzj/main.js", engine:"rhino"}` 运行。

## 一、为什么报错（四个真实原因）

| # | 现象 | 根因 | 性质 |
|---|---|---|---|
| 1 | 一启动就 `TypeError: [JavaPackage de.mindpipe.android.logging.log4j.LogConfigurator] is not a function, it is object. (__console__.js#61)` | 脚本调用 `console.setGlobalLogConfig({file:…})` 写日志文件，而我们的 `__console__.js` 无条件 `new Packages["de.mindpipe.android.logging.log4j"].LogConfigurator()`——log4j-android 没随包，`Packages[...]` 只是 JavaPackage 对象 | **我们 App 的 bug** |
| 2 | `PluginLoadException: NameNotFoundException: Application package com.hraps.ocr not found` | 脚本按 CR4 硬编码第三方 OCR 插件包名（`com.hraps.ocr` / `com.hraps.ocr32` / `com.tomato.ocr`），没装插件就整脚本失败；且 `analysisChartTools.js` 在**模块顶层**就 `$plugins.load(...)` | **兼容缺口** |
| 3 | 即便有插件，`ocr.detect(bitmap, mode)` 也传的是 `image.getBitmap()`（原始 Bitmap） | 我们的 `Ocr.detect(ImageWrapper,…)` 只收 Auto.js 图片对象（插件文档收 Bitmap） | **兼容缺口** |
| 4 | 修完上面前三条后：`ScriptException: 无障碍服务未启动` | 设备没开无障碍（脚本要截图/点击） | **设备状态，不是 bug**（用 ADB 打开验证） |

## 二、修了什么

1. **console 日志配置不再致命**（`modules/engine/src/main/assets/modules/__console__.js`）：先探测 `de.mindpipe…LogConfigurator` 是否存在，存在就照旧配置；不存在则降级——记录 `scope.__aijsLogConfig{level,file,degraded,reason}`、必要时建父目录、用 `rtConsole.warn` 提示一次，**绝不让日志配置把脚本打断**。
2. **第三方 OCR 插件缺失时回退内置 OCR**（`modules/engine/src/main/assets/modules/__plugins__.js`）：
   - `com.hraps.ocr` / `com.hraps.ocr32` → 返回**实例**（`detect(bitmap, mode)` / `ocrBitmap` / `end` / `release` / `isReleased`）；
   - `com.tomato.ocr` → 返回**构造函数**（脚本写的是 `new ($plugins.load("com.tomato.ocr"))()`）；
   - 后端优先 **ppocr**（随包离线 ncnn 模型，脚本进程实测可用），失败再退 `mlkit`；
   - 返回对象带 `__aijsBuiltInShim=true` / `backend` / `packageName`，并**一次性提示**「插件未安装：已使用内置 OCR 兼容实现」；
   - **其它包名仍然抛真实错误**（不假装成功），已装插件时原样使用插件自身实现。
3. **`detect` 接受 Bitmap**（`Ocr.java` / `PPOcr.java`）：新增 `detect(Object image, …)` 重载 + `Ocr.coerceToImageWrapper()`——`ImageWrapper` 原样用、`Bitmap` 直接包、其它类型给可读错误（`OCR.detect 需要 images.read(...) 的图片或 android.graphics.Bitmap，收到：…`）。

## 四、边界（不夸大）

1. **内置 OCR ≠ 浩然/tomato 插件**：模型/准确率不同，shim 只是让脚本能跑、结构对齐；需要插件原始识别效果请安装对应插件 APK（装了我们就不再替换）。
2. 只对**已知 OCR 插件包**做回退；其它缺失插件仍抛 `PluginLoadException`，不静默。
3. 无障碍是**设备状态**：本轮用 ADB 打开验证；正式使用需用户在系统里开启（或 Shizuku/ADB 一次性授权）。
4. 脚本自身的分辨率告警（标准 1080*2400 vs 当前 1080*2160）是脚本逻辑，不在本次修复范围。
5. 自动化脚本是长循环任务，验证时用 `run_script` 跑到「初始化 OCR + 请求截图成功」即判定启动链路通了，没有做完整跑图流程的回归。
