# MCP 改进第三批：常驻 r2 会话与大函数分段投影（dev-1340→1344）

> 承接 [改进第二批](2026-11-05_MCP改进第二批（自动证据_路由字段_会话持久化）.md)。本批把用户最初要的「一次加载、多次查询」真正做到毫秒级，并补上 82KB 级函数的可读性。
> 说明：本批两个工作流的协作者（native-process / manifest-detector）**中途失败**，留下半成品；由 Lead 接手修完、补测、真机验证与发布。过程与教训一并记录。

## 一、常驻 r2 会话（T4）——从 9.9s 到 45ms

新增 `ToolkitR2Resident`（纯 JVM）+ 接线层的 `R2Pipe`/`R2PipeHandle`，产出 5 个工具：`native_resident_open/command/batch/close/list`。

| 路径 | 同文件（560,960 B 的 libyj-vmp-lib.so）实测 |
|---|---|
| 旧：`native_session_query`（每次新进程 + `Po <project>`） | 首查 9.9s / 15.5s（含 `aaa`） |
| 新：`native_resident_command`（常驻进程同一 stdin/stdout） | **72 ms / 45 ms** |
| 新：`native_resident_batch`（5 条命令一次调用） | **149 ms**（`okCount=4`，`!id` 被 `COMMAND_REJECTED` 拒绝） |

```text
native_resident_open {path:__vmp/libyj-vmp-lib.so, sha256, relocsApply:true}
  -> sessionId=r2r-…, warmedUp=true, argv=[-N,-2,-q,-0,-e,scr.color=0,-e,scr.interactive=false,-e,bin.relocs.apply=true,<input>]
native_resident_command {command:"is~vmInterpret"} -> 72ms，"126 0x0003a1e4 GLOBAL FUNC 82684 vmInterpret"
native_resident_command {command:"iI"}            -> 45ms
native_resident_batch {commands:[ij, iE~cacheInitial, iS~.text, il, !id]}
  -> 149ms, ok=4/5，逐条输出与命令顺序**一一对应**，!id 报 COMMAND_REJECTED
native_resident_close -> closed=true, remainingSessions=0
```

### framing 三次踩坑（都靠真机才暴露）

1. **只有 `-0`（NUL）不够**：r2 非 TTY 下 stdout 块缓冲，读到 NUL 才返回会把输出整体**错位一条命令**（dev-1342/1343 实测：第一条命令读到上一条的残留）。
2. **只有 marker 不够**：没有 `-0` 时缓冲不刷新，marker 永远读不到（dev-1340 实测全部 TIMEOUT）。
3. **最终方案**：`<cmd>;?e <marker>` + 启动加 `-0`——NUL 只用来强制刷新，终止以 **marker 行**为准；`open` 时先跑一条 `?e ready` 预热并把 r2 启动成本提前消化（`warmedUp` 只在真正读到 marker 时才为 true）。

## 二、大函数分段投影（T5）

`ToolkitDecompileView` 新增 `projectSegments(pdgText, address, maxCodeChars, maxSegments, offset)` 与 `summarizeBigFunction(pdgText, pdfjText?, address)`：按行分段、超长段标 `truncated`、`nextOffset` 续读；`summarizeBigFunction` 用 pdfj 的 blocks/ops 给指令数与基本块数，pdfj 缺失时**留 null 并说明不猜**；两者都显式标注 `evidenceLevel=static_inferred`、`relocAware=true`。

配合本轮对真实目标的实测：`native_decompile {address:"0x3a1e4"}`（r2ghidra）成功返回 `vmInterpret` 的伪代码——特点是密集的**混淆间接调用**（`(*(*(*0x8d888 + (*0x8d830*9 ^ 0x9021d5e26d5361c4) + 0x59) + …))()`）与 `//WARNING: Could not recover jumptable at 0x0003a2dc. Too many branches`，即 VMP 的分发结构与未还原跳转表；工具同时给出 `disasmKind=decompiled`、`relocAware=true`、`evidenceLevel=static_inferred`、`boundary.confidence=none`（honest：没有可靠边界信息）。
> 边界：`native_resident_*` 用的是组件自带的 radare2，**没有**注入 r2ghidra 插件路径，所以常驻会话里跑 `pdg` 会提示 "You need to install the plugin with r2pm -ci r2ghidra"；需要伪代码仍走 `native_decompile`。

## 五、边界

1. 常驻会话**不持久化**：进程死了报 `SESSION_DEAD`，需重新 `open`（project 复用路径 `native_session_*` 仍然保留，适合跨进程恢复）。
2. `native_resident_*` 只跑 r2 核心命令；`pdg` 需要插件，走 `native_decompile`。
3. 会话上限 2、TTL 30 分钟、单命令 ≤4096 字符、输出 ≤2 MiB；批量是逐条隔离，一条失败不影响其它条。
4. `projectSegments` 只投影伪代码文本，不含 r2ghidra 注解（`omittedAnnotations=true`）。
