## 一、本批实现

| 复盘条目 | 实现 | 关键行为 |
|---|---|---|
| §4.1 Manifest 基础解析与回退 | 新增独立 AXML 解析器 `ToolkitAxmlLite`，接入 `apk_verify.manifest` | ARSCLib 完整解码失败时不再丢失全部字段：基础字段（package/split/versionCode/versionName/compileSdkVersion/minSdk/targetSdk/maxSdk/extractNativeLibs）由独立解析取回；结果自报 `parseSource=independent-axml`、`fullXmlDecoded=false`，并保留 `failureKind` 与 `primaryDecoderError` 原文 |

## 二、MI8（dev-1332）真机实测

### 1. Manifest 兜底在真实 APK 上触发（复盘问题的直接复现与修复）

被测：`/storage/emulated/0/脚本/bbmimoImGui/main_v1.0.0.apk`（AutoJs6 打包产物）

```text
apk_verify -> manifest:
  status=valid, package=org.autojs.autojs6.ver664.main, minSdk=24, targetSdk=29
  parseSource=independent-axml, fullXmlDecoded=false
  failureKind=resource_context_missing
  primaryDecoderError="Can not decode without package"
  liteElementCount=202
```

这正是复盘 §4.1 里那句 `Can not decode without package`：修复前这类包连 package/minSdk 都拿不到；现在基础字段可用，且来源、失败类别与原始错误都如实标注，不会被误读成“目标清单损坏”。

### 2. 应用查询一致性与归一化

```text
app_list {query:"设置", limit:5}
  -> visibilityLimited=false, scanScope=all_installed, queryAllPackagesGranted=true,
     scanTotal=256, filteredTotal=8, normalizedQuery="设置", limit=5
     items: com.android.settings(设置, matchedBy=label)、
            org.lineageos.lineageparts(LineageOS 设置, labelContains) ...
app_list {query:"ｃｏｍ．", limit:3}     # 全角 + 大点
  -> normalizedQuery="com.", filteredTotal=209, matchedBy=package
```

### 3. 任务保留与错误码

```text
apk_job_list -> activeJobs=0, maxActive=4,
  retention={windowMillis:21600000, maxRetainedFinished:64, maxTombstones:256,
             maxResultBytes:25165824, tombstoneCount:33},
  service={instance:e452392d…, restarted:false, metadataAndResultSeparated:true},
  evicted=[{jobId:65a12708…, code:JOB_EVICTED, reason:retentionWindow, operation:frida_eval}, …]
apk_job_status {jobId:"11111111-2222-4333-8444-555555555555"}
  -> error.code=JOB_NOT_FOUND（带 registry/重启提示）
apk_job_status {jobId:"65a12708-ed91-4ab1-b74f-6fbca7192108"}
  -> error.code=JOB_EVICTED（reason=retentionWindow，说明输出缓存已删除，请重新提交）
```

以前「刚创建的任务读不到」只能看到通用报错；现在“没登记过 / 被淘汰 / 服务重启丢失”三种情况可以区分，并且 `apk_job_list` 能解释墓碑从哪来。

## 四、未做 / 已知边界

1. **回退路径的覆盖面**：`ToolkitAxmlLite` 只解析基础字段，不解析资源引用与组件级 XML；`fullXmlDecoded=false` 时组件/split 细节仍不可用（有明确字段与警告，不会冒充完整 XML）。
2. **Manifest 分类仍可细化**：`failureKind` 目前为 resource_context_missing / unsupported_binary_xml / unsupported_format / decoder_error 四类；「格式或属性暂不支持」与「后端解析异常」的更细区分留待后续。
3. **app_list**：`visibilityLimited` 依据 `QUERY_ALL_PACKAGES` 授权判断（MI8 实测已授权 → false）；工作资料/分身仍可能在 `scanNote` 里保留不确定性，未做真机多用户验证。
4. **任务 owner 不是安全边界**：本轮只按参数透传，未做 HTTP/IPC 身份校验；不同客户端共享 jobs 目录时 registry 为最后写入者胜（无跨进程锁）。
5. **淘汰触发时机**：限于 start/list/status/result/cancel 调用（无独立定时 GC）；墓碑上限 256，超出后最早墓碑退化为 `JOB_NOT_FOUND`；输出缓存无总量上限（仅单结果 24MiB + 条数/窗口）。
6. **provider 的 nextActions**：仍统一为空数组，提示写在 message/hint；结构化 nextActions 需要改 provider/bridge。
7. 复盘剩余：§6.3 嵌入式 Node 运行形态字段、§5.2 的 `artifact_open` 直接回退候选、以及全部 P1（有状态 native 会话、精简反编译、启动/退出采集、Frida Java Bridge）与 P2（可验证二进制变换、VM 辅助、证据导出）。
