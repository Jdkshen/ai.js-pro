## 已实测的结论

Node 的纯 JS 运算接近高级版；原来的主要差距在 Java 桥。缓存反射元数据之后，2000 次 Java 调用的中位耗时由 324ms 降至 102ms，约减少 69%；高级版同项为 83ms。这是一个小型桥接基准，不能推算所有脚本、UI、截图、YOLO 的整体速度。

| 实现 | 20 万次局部 JS 整数循环中位数 | 2000 次 Java 调用中位数 |
|---|---:|---:|
| 我们的 Rhino，dev-1117 | 2014ms | 42ms |
| 我们的 QuickJS，dev-1117 | 5ms | 114ms |
| 我们的 Node，dev-1117 | 2ms | 324ms |
| 我们的 Node，反射缓存后 dev-1119 测试包 | 2ms | 102ms |
| 手机已有 AutoJs 高级版 Node | 3ms | 83ms |

方法：相同脚本体、局部函数作用域、整数累加并校验 `-1474936480`；Java 调用均为 `android.os.SystemClock.elapsedRealtime()`，计时也用该单调时钟。每次脚本 5 轮；高级版与缓存后 Node 各运行 3 次，共 15 轮。其余三项各 5 轮。0–3ms 的短循环接近计时分辨率，不能把 2ms 对 3ms 宣称为普遍快 50%。

## 慢在哪里，改了什么

1. **Rhino 的 JS 循环慢**：本项目 `RhinoJavaScriptEngine` 配置 `optimizationLevel=-1`，按解释模式执行。它的 Java 调用在这组基准中反而最快。不要把“解释 JS 运算慢”扩展为“所有自动化 API 都慢”。本轮没有贸然改变 Rhino 编译模式，以免影响调试、停止和兼容性。
2. **Node Java 桥重复工作**：每次解析类、遍历完整 public 方法和父类链，再做重载选择。已加入每任务独享的有界缓存（256 类名 + 256 组方法候选）。逐次参数转换和重载选择保持原有规则，任务结束释放缓存；不跨任务固定插件 ClassLoader。
3. **结果晚显示**：原 Node stdout 已实时读入，但应用控制台等整个脚本结束才镜像。已增加有界逐行实时回传与最终补漏去重，保留原有取消 watchdog。
4. **等级丢失**：原 Node 输出全部经 `console.log` 镜像成 Debug。新增 console 适配模块，保留 Node `util.format`、中文、emoji、多行、assert 不抛异常的语义，实时和最终补漏都恢复 V/D/I/W/E/A；普通 stdout 仍按 Debug 显示。
5. **跨进程批次染色**：真机发现 Rhino / QuickJS / Node 共用的 200ms 批次原来只带最高等级，整批可能都变成 Error/Assert。已按每段保留其等级，同时继续有界批量发送；三引擎在主进程与执行进程的六档日志顺序和内容一致。

Node 仍有 JSON 序列化、JNI、参数转换和反射调用成本。这里优化了已测到的一部分，没有换用高级版的旧 Node 二进制，也没有声称所有桥接开销已消除。

启动和图像流水线需分开看：旧 MI8 暖 Node 请求到用户首行约 258–294ms；30 帧找图示例整段 22.044 秒包含截图、匹配与示例等待，不能当作纯 JS、单个截图 API 或 YOLO 推理耗时。旧 dev-1034/1035 的 K40 时间只作历史代码分析，不进入本报告比较表。
