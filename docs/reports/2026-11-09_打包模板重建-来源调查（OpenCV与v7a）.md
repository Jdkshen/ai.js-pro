# 打包模板重建：来源调查（OpenCV 单库与 v7a 补齐）

> 交付范围：**只调查 + 可复跑脚本**，不改任何 APK 资产（构建/装机/发布是 Lead 的域）。
> 脚本：[`tools/apk-native-lib-audit.mjs`](../tools/apk-native-lib-audit.mjs)（任意 APK/AAR 的 .so 逐条 KEEP/DROP + 来源判定，判据与 `NativeLibPolicy` **同源**）。
> 判据出处：`apps/app/src/main/java/com/jdkshen/aijspro/autojs/build/NativeLibPolicy.kt:13-64`（TEMPLATE_REQUIRED / PUZZLE_ENGINE / OPENCV_+libtbb / OCR_LIBS / libv8|flutter|node）。

## 0. 一句话结论

| 问题 | 结论 |
|---|---|
| 宿主 OpenCV 从哪来 | **官方 OpenCV 5.0.0（16kb-page-fix 资产）为基底 AAR + 我们用 OpenCV 5 源码自建 arm64 的库后重打包**（`docs/guides/SIFT特征匹配示例.md:84-100`） |
| 能否产 Pro 那种单库 | **形态可行、名字不可行、收益≈0**：我们能产单库（`BUILD_opencv_world`/静态链接 + `tools/package-opencv-features.py` 重打包），但 Pro 的是 OpenCV **4.x** 的 `libopencv_java4.so`，我们是 **5.0.0**（`libopencv_java5.so`），改名无意义；且单库只减文件数、不减代码量 |
| 能不能靠删 .so 变小 | **不能**：arm64 当前 10 个 .so **全部在依赖链里**（DT_NEEDED 见 `2），删任一 → 加载即 `UnsatisfiedLinkError` |
| v7a 补齐清单 | **3 项就位 / 1 项必须补 / 1 项建议不补**：`libppocr.so` 是唯一硬缺口（**仓库只 vendor 了 arm64 的 ncnn 静态库**），`libpikafish.so` 建议不补；另需在 `excluded-zip-files.json` 加 **v7a 条目组** |

## 1. 宿主 OpenCV 的来源（每条有出处）

| 事实 | 证据 |
|---|---|
| 依赖入口是**本地 AAR**，不是远程坐标 | `modules/engine/build.gradle:77-79`：`api(name: 'opencv-5.0.0-16kb-page-fix', ext: 'aar')`；文件 `modules/engine/libs/opencv-5.0.0-16kb-page-fix.aar`（**48,116,619 B**） |
| 基底来自**官方发布资产** | `docs/reports/项目说明.md:51`：「原生库来自 OpenCV 5.0.0 官方发布资产 `opencv-5.0.0-android-sdk-16kb-page-fix.zip`」+ SHA-256 |
| **arm64 的库是我们自建后替换进去的** | `docs/guides/SIFT特征匹配示例.md:86-100`：`cmake -S D:/opencv_5_gpu_workspace/src … -DBUILD_LIST=core,imgproc,dnn,imgcodecs,features,java` → `--target opencv_java` → `python tools/package-opencv-features.py --base-aar .artifacts/sift-opencv-backup/opencv-before-sift.aar --output-aar modules/engine/libs/opencv-5.0.0-16kb-page-fix.aar` |
| 打包器**只换 arm64**，所以 v7a/x86 仍是基底形态 | 同文件 `:100`：「打包器保留基底 AAR 的资源及其他 ABI，**仅为 arm64 更新**同一次构建的 native 库与 Java 包。**其他 ABI 尚未补齐 features**」 |
| 代码里也写明了这个形态差异 | `modules/engine/src/main/cpp/build-quickjs.ps1:29-36`：「arm64 packages OpenCV as several shared libraries, while older ABIs use the monolithic libopencv_java5.so」 |
| 没有 `opencv-strip` 这类后处理脚本 | 全仓 grep `opencv-strip` = **0 命中**（`tools/` 下与 OpenCV 相关的只有 `check-android-16kb.py` / `verify-16kb-alignment.ps1` 这类**校验**脚本） |

**AAR 内原生库实测**（`node tools/apk-native-lib-audit.mjs --aar modules/engine/libs/opencv-5.0.0-16kb-page-fix.aar`）：

```text
arm64-v8a: 10 libs, 33.38 MiB   ← 拆库形态（需要我们 BUILD_LIST 里的那些模块）
  libc++_shared 1.23 | core 5.59 | dnn 11.90 | features 0.68 | flann 0.79
  geometry 1.24 | imgcodecs 2.33 | imgproc 7.76 | java5 1.12 | tbb 0.74   (MiB)
armeabi-v7a: 2 libs, 22.09 MiB  ← 单库形态：libc++_shared 0.83 + libopencv_java5 21.26
x86:         2 libs, 52.43 MiB  ← 同样单库
```

> ⚠️ **这是 AAR 内未 strip 的体积**（AGP 在打包时 strip）→ **不能**拿 33.38MiB 直接和 Pro 的包内 17MB 比。要比就比**产物 APK** 的 `lib/arm64-v8a`（用审计脚本，见 `4）。

## 2. 单库可行性 + 裁剪判据（硬证据，可复跑）

**DT_NEEDED（`--needed` + `--needed-abi`）**：

```text
arm64-v8a libopencv_java5.so → libopencv_{features,imgcodecs,dnn,imgproc,geometry,flann,core}.so
                               + libdl/libm/liblog/libjnigraphics/libc
arm64-v8a libopencv_core.so  → … + libtbb.so + libz.so          （tbb 必须留）
armeabi-v7a libopencv_java5.so → 只有系统库 + libc++_shared     （单库自包含）
```

**判据**：
- **必须留（7+2）**：`libopencv_java5.so` + `core/imgproc/dnn/imgcodecs/features/geometry/flann` + `libtbb.so`（被 core 需要）+ `libc++_shared.so`（v7a 单库需要）。
- **可去**：当前 10 个里 **0 个**可去——每个都在依赖链上。删任何一个 → `System.loadLibrary` 直接 `UnsatisfiedLinkError`（不是"少个功能"，是**起不来**）。
- 所以 **「删 .so 让包变小」这条路对我们当前构建不可行**；要变小只有两条：
  1. **改构建去掉模块**：把 `features/flann/geometry`（我们为 SIFT 自建、AAR 内约 **2.7MiB 未 strip**）从 `BUILD_LIST` 去掉 → 回到底座模块集；代价 = SIFT/FLANN 示例失效。
  2. **按工程不带**：已有 `removeOpenCv=true` 策略（`NativeLibPolicy.kt:52-57`），适合"该工程不用图像"的场景。
- **单库化怎么做（可行、但只是形态）**：在同一次 cmake 里用 `-DBUILD_opencv_world=ON`（产 `libopencv_world.so`）或 `-DBUILD_SHARED_LIBS=OFF` 让 `opencv_java` 导出单个 .so，再 `tools/package-opencv-features.py --output-aar` 重打包。**不要**改名为 `libopencv_java4.so`：这个名字属于 OpenCV 4.x，Java 侧 `org.opencv.*` 与 JNI 符号绑定，5.0 改成 4.x 名字只会误导 + 破坏加载。
- **形态差异不是我们比 Pro 大的主因**：Pro 单库 17MB 是 **4.x**、且是**包内 strip 后**的数字；我们 AAR 未 strip、且是 **5.0 + 自建 features/flann/geometry**。要判"谁大多少"必须量产物（`4` 命令）。

## 3. v7a 补齐清单（对照 arm64）

**逐库对照**（arm64 来源 = `modules/engine/src/main/jniLibs/arm64-v8a` + AAR；v7a 现状 = `jniLibs/armeabi-v7a` + AAR + AGP 合并产物）：

| # | 库 | arm64 | v7a 现状 | 判定 / 怎么补 |
|---|---|---|---|---|
| 1 | `libaijscrypto.so` | ✓ jniLibs | ✓ `jniLibs/armeabi-v7a` | **齐** |
| 2 | `libquickjs.so` | ✓ | ✓ | **齐** |
| 3 | `libquickjs_jni.so` | ✓ | ✓ | **齐** |
| 4 | `libc++_shared.so` | ✓ AAR | ✓ AAR（0.83MiB） | **齐** |
| 5 | `libopencv_java5.so` | ✓ AAR（1.12MiB 拆库 shim） | ✓ AAR（**21.26MiB 单库**） | **齐**（v7a 不需要 arm64 那 7 个模块 .so） |
| 6 | `libmlkit_google_ocr_pipeline.so` | ✓（`com.google.mlkit:text-recognition-chinese:16.0.1`，`engine/build.gradle:114`） | ✓ AGP 合并产物里有 v7a（6.78MiB，`apps/app/build/intermediates/merged_native_libs/.../armeabi-v7a`） | **可得**：只需在 `excluded-zip-files.json` 补 v7a 条目 |
| 7 | `libppocr.so` | ✓ jniLibs + `.cxx` | **✗ 没有 v7a 构建**（`jniLibs/armeabi-v7a` 3 个库、`.cxx/quickjs-r27/armeabi-v7a` 同样 3 个，均无 ppocr） | **唯一硬缺口**：`modules/engine/src/main/cpp/build-quickjs.ps1:57-58` 写明「**PP-OCR（ncnn）只在 arm64-v8a 构建：仓库只 vendor 了 arm64 的 ncnn 静态库**」→ 要补得先 vendor v7a 的 ncnn，或 v7a 走 **mlkit OCR 降级**（`qjs-plugins.js` 已有 ppocr→mlkit 降级先例） |
| 8 | `libtbb.so` / `libopencv_{core,imgproc,dnn,imgcodecs,features,geometry,flann}.so` | ✓ arm64 | n/a（v7a 单库自包含） | **不需要**（这正是 arm64/v7a 形态差） |
| 9 | `libpikafish.so` | ✓ arm64 only（`third-party/Pikafish`） | ✗ | **建议不补**：只有象棋工程需要；保持 `AbiPolicy` 的 warning 语义（`plugins/xiangqi-plugin/build.gradle:31` 也写明"引擎只有 arm64-v8a 一份构建"） |

**清单层面（必须一起改，否则补了也进不去）**：`apps/app/src/main/assets/excluded-zip-files.json` 的 `general`(6) 与 `opencv`(9) **全部是 `lib/arm64-v8a/…` 条目**（`:3-19`）→ 瘦身模板合并时**只会补 arm64**。要出 v7a，需要新增 v7a 条目组（至少 `lib/armeabi-v7a/libc++_shared.so`、`lib/armeabi-v7a/libopencv_java5.so`、`lib/armeabi-v7a/libmlkit_google_ocr_pipeline.so`；ppocr 取决于 `7` 怎么定）。

## 4. 补齐后怎么验（命令行，全部可复跑）

```bash
# ① 产物 ABI 齐全 + 每个 .so 的来源判定（判据与 NativeLibPolicy 同源）
node tools/apk-native-lib-audit.mjs <产物.apk> --expect-abi arm64-v8a,armeabi-v7a --fail-on-leak

# ② 机器可读（给 CI/对比用）
node tools/apk-native-lib-audit.mjs <产物.apk> --json

# ③ 模板/AAR 侧对照（arm64 vs v7a 形态差异 + 单库 DT_NEEDED）
node tools/apk-native-lib-audit.mjs --aar modules/engine/libs/opencv-5.0.0-16kb-page-fix.aar
node tools/apk-native-lib-audit.mjs --aar modules/engine/libs/opencv-5.0.0-16kb-page-fix.aar --needed libopencv_java5.so --needed-abi arm64-v8a

# ④ 16KB 页对齐（自研库 quickjs/aijscrypto/ppocr/pikafish 不达标直接 FAIL）
pwsh -File tools/verify-16kb-alignment.ps1 -Apk <产物.apk>
```

**验收数字（期望值）**：
- `--expect-abi` 两个 ABI 都出现；`missingAbi=[]`；
- `leaks=0`；`unknown=0`（若 `unknown>0` 说明出现新库没归类，**要停下来归类**，别默认放行）；
- 每 ABI 的 `[abi] N libs, X MiB` 与上表一致（arm64 ≈ 14 个、v7a ≈ 7 个，具体以便携性为准）；
- 打包日志 `abis declared/available/produced/missing` 里 `missing=[]`（`AbiPolicy` 不再出 warning）；
- 真机侧：**K40 是 arm64，没有 v7a 真机** → v7a 只能靠「产物 ABI 齐全 + .so 可解析 + 16KB 检查 + 模拟器/旧机型」；**"v7a 能起来"本轮属未验证**。

## 5. ⚠️ W2 的独立发现：真机那次**没覆盖**瘦身模板补齐路径

W2 独立复核报告（`docs/reports/2026-11-09_打包策略独立复核（W2）.md:32`）实测（K40，旧模板）：打包日志是 **`template libs already present count=15 (旧全量模板，跳过从宿主补齐)` + `template libs added=0`** —— 即真机上用的是**旧的全量模板**（自己就带全部 lib），所以：
- 真机验收**只覆盖了工作区级策略**（`build/` 套娃、`pikafish` 泄漏、`autojs.keystore`、插件回显、ABI warning）；
- **`excluded-zip-files.json` → `ApkBuilder.ensureTemplateLibs` 的"瘦身模板补齐"路径在真机上根本没被走到**（`added=0`）。
- ⇒ **模板重建后必须补一次该路径的回归**：判据 = 日志出现 `added>0`（或 `merged slim template bytes=…`，见 `ApkBuilderPluginHelper.mergedBundledTemplate()` `apps/app/src/main/java/com/jdkshen/aijspro/build/ApkBuilderPluginHelper.java:259-310`）**且**产物 `lib/` 清单与模板一致（用 `4①` 的脚本核对）。
- 与本调查的关系：**v7a 补齐与单库化都只影响"模板里有什么"**，而真机那次连合并路径都没走 → 两件事的验收**都必须换到"瘦身模板 + 补齐"这条路上做**，否则会得到假绿。

## 6. 边界（未验证 / 不可外推）

1. **没跑构建**（本轮只调查）：单库化与 v7a 补齐**都没有实际产出过 APK**，`2` 的"可行"是**基于现有工具链与脚本的可行性判断**，不是已验证结果。
2. **AAR 体积 ≠ 包内体积**：`1` 的 33.38MiB 未 strip；与 Pro 的比较必须用产物 APK。
3. **v7a 无真机**：`4` 的验收只到"产物 + 16KB 检查"级；"v7a 真能跑"**未验证**。
4. **`libppocr.so` 的 v7a 方案未定**：vendor v7a ncnn（成本高）vs 走 mlkit 降级（改行为）——**需要你定夺**；我未改任何构建脚本。
5. **`项目说明.md` 里的 AAR 大小（`2026-10-18` 报告写 58,243,218 B）与当前文件（48,116,619 B）不一致** → 说明该 AAR 后来又重打过；`项目说明.md` `:38/:51` 的"官方 5.0.0"口径仍成立，但**具体字节数以当前文件为准**（本调查用的就是当前文件）。
