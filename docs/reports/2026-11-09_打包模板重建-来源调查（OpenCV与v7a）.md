# 打包模板重建：来源调查（OpenCV 单库与 v7a 补齐）

> 交付范围：**只调查 + 可复跑脚本**，不改任何 APK 资产（构建/装机/发布是 Lead 的域）。
> 脚本：[`tools/apk-native-lib-audit.mjs`](../tools/apk-native-lib-audit.mjs)（任意 APK/AAR 的 .so 逐条 KEEP/DROP + 来源判定，判据与 `NativeLibPolicy` **同源**）。
> 判据出处：`apps/app/src/main/java/com/jdkshen/aijspro/autojs/build/NativeLibPolicy.kt:13-64`（TEMPLATE_REQUIRED / PUZZLE_ENGINE / OPENCV_+libtbb / OCR_LIBS / libv8|flutter|node）。

## 0. 一句话结论

| 问题 | 结论 |
|---|---|
| 宿主 OpenCV 从哪来 | **官方 OpenCV 5.0.0（16kb-page-fix 资产）为基底 AAR + 我们用 OpenCV 5 源码自建 arm64 的库后重打包**（`docs/guides/SIFT特征匹配示例.md:84-100`） |
| 能否产 Pro 那种单库 | **形态可行、名字不可行、收益≈0**：我们能产单库（`BUILD_opencv_world`/静态链接 + `tools/package-opencv-features.py` 重打包），但 Pro 的是 OpenCV **4.x** 的 `libopencv_java4.so`，我们是 **5.0.0**（`libopencv_java5.so`），改名无意义；且单库只减文件数、不减代码量 |
| 能不能靠删 .so 变小 | **不能**：arm64 当前 10 个 .so **全部在依赖链里**（DT_NEEDED 见 `2），删任一 → 加载即 `UnsatisfiedLinkError` |
| v7a 补齐清单 | **3 项就位 / 1 项必须补 / 1 项建议不补**：`libppocr.so` 是唯一硬缺口（**仓库只 vendor 了 arm64 的 ncnn 静态库**），`libpikafish.so` 建议不补；另需在 `excluded-zip-files.json` 加 **v7a 条目组** |

## 1. 宿主 OpenCV 的来源（每条有出处）

| 事实 | 证据 |
|---|---|
| 依赖入口是**本地 AAR**，不是远程坐标 | `modules/engine/build.gradle:77-79`：`api(name: 'opencv-5.0.0-16kb-page-fix', ext: 'aar')`；文件 `modules/engine/libs/opencv-5.0.0-16kb-page-fix.aar`（**48,116,619 B**） |

| 没有 `opencv-strip` 这类后处理脚本 | 全仓 grep `opencv-strip` = **0 命中**（`tools/` 下与 OpenCV 相关的只有 `check-android-16kb.py` / `verify-16kb-alignment.ps1` 这类**校验**脚本） |

**AAR 内原生库实测**（`node tools/apk-native-lib-audit.mjs --aar modules/engine/libs/opencv-5.0.0-16kb-page-fix.aar`）：

```text

  libc++_shared 1.23 | core 5.59 | dnn 11.90 | features 0.68 | flann 0.79
  geometry 1.24 | imgcodecs 2.33 | imgproc 7.76 | java5 1.12 | tbb 0.74   (MiB)
```

## 2. 单库可行性 + 裁剪判据（硬证据，可复跑）

**DT_NEEDED（`--needed` + `--needed-abi`）**：

```text
arm64-v8a libopencv_java5.so → libopencv_{features,imgcodecs,dnn,imgproc,geometry,flann,core}.so
                               + libdl/libm/liblog/libjnigraphics/libc
arm64-v8a libopencv_core.so  → … + libtbb.so + libz.so          （tbb 必须留）
armeabi-v7a libopencv_java5.so → 只有系统库 + libc++_shared     （单库自包含）
```

**判据**：
- **必须留（7+2）**：`libopencv_java5.so` + `core/imgproc/dnn/imgcodecs/features/geometry/flann` + `libtbb.so`（被 core 需要）+ `libc++_shared.so`（v7a 单库需要）。
- **可去**：当前 10 个里 **0 个**可去——每个都在依赖链上。删任何一个 → `System.loadLibrary` 直接 `UnsatisfiedLinkError`（不是"少个功能"，是**起不来**）。
- 所以 **「删 .so 让包变小」这条路对我们当前构建不可行**；要变小只有两条：
  1. **改构建去掉模块**：把 `features/flann/geometry`（我们为 SIFT 自建、AAR 内约 **2.7MiB 未 strip**）从 `BUILD_LIST` 去掉 → 回到底座模块集；代价 = SIFT/FLANN 示例失效。
  2. **按工程不带**：已有 `removeOpenCv=true` 策略（`NativeLibPolicy.kt:52-57`），适合"该工程不用图像"的场景。
- **单库化怎么做（可行、但只是形态）**：在同一次 cmake 里用 `-DBUILD_opencv_world=ON`（产 `libopencv_world.so`）或 `-DBUILD_SHARED_LIBS=OFF` 让 `opencv_java` 导出单个 .so，再 `tools/package-opencv-features.py --output-aar` 重打包。**不要**改名为 `libopencv_java4.so`：这个名字属于 OpenCV 4.x，Java 侧 `org.opencv.*` 与 JNI 符号绑定，5.0 改成 4.x 名字只会误导 + 破坏加载。
- **形态差异不是我们比 Pro 大的主因**：Pro 单库 17MB 是 **4.x**、且是**包内 strip 后**的数字；我们 AAR 未 strip、且是 **5.0 + 自建 features/flann/geometry**。要判"谁大多少"必须量产物（`4` 命令）。

## 4. 补齐后怎么验（命令行，全部可复跑）

```bash
# ① 产物 ABI 齐全 + 每个 .so 的来源判定（判据与 NativeLibPolicy 同源）
node tools/apk-native-lib-audit.mjs <产物.apk> --expect-abi arm64-v8a,armeabi-v7a --fail-on-leak

# ② 机器可读（给 CI/对比用）
node tools/apk-native-lib-audit.mjs <产物.apk> --json

# ③ 模板/AAR 侧对照（arm64 vs v7a 形态差异 + 单库 DT_NEEDED）
node tools/apk-native-lib-audit.mjs --aar modules/engine/libs/opencv-5.0.0-16kb-page-fix.aar
node tools/apk-native-lib-audit.mjs --aar modules/engine/libs/opencv-5.0.0-16kb-page-fix.aar --needed libopencv_java5.so --needed-abi arm64-v8a

# ④ 16KB 页对齐（自研库 quickjs/aijscrypto/ppocr/pikafish 不达标直接 FAIL）
pwsh -File tools/verify-16kb-alignment.ps1 -Apk <产物.apk>
```

**验收数字（期望值）**：
- `--expect-abi` 两个 ABI 都出现；`missingAbi=[]`；
- `leaks=0`；`unknown=0`（若 `unknown>0` 说明出现新库没归类，**要停下来归类**，别默认放行）；
- 每 ABI 的 `[abi] N libs, X MiB` 与上表一致（arm64 ≈ 14 个、v7a ≈ 7 个，具体以便携性为准）；
- 打包日志 `abis declared/available/produced/missing` 里 `missing=[]`（`AbiPolicy` 不再出 warning）；
- 真机侧：**K40 是 arm64，没有 v7a 真机** → v7a 只能靠「产物 ABI 齐全 + .so 可解析 + 16KB 检查 + 模拟器/旧机型」；**"v7a 能起来"本轮属未验证**。

## 5. 模板链路现状与回归清单（按 Lead 更正口径）

**B-2 判据（按 Lead 更正：③ 路径下 added>0 按构造不可能发生，不能拿它当判据）**

> **为什么改**：device4 的日志顺序是 **merged slim template bytes=41045538**（来自 ③ mergedBundledTemplate()）**→ 然后才** template libs already present count=15 (旧全量模板，跳过从宿主补齐) / added=0。也就是说 **③ 已经在合并时把宿主 lib 补进去了**，轮到 ApkBuilder.ensureTemplateLibs 时自然「什么都不缺」→ **在 ③ 路径下 added>0 永不出现**，拿它当判据会**永远判「未覆盖」**。

**判据（4 项门 + 2 项对照）**
1. **命中 ③**：/sdcard/template.apk **不存在**（或不可用）**且** files/apk-builder/ 缓存**已清空** → 强制走 bundled 合并；**或**直接用 openTemplateSelection(context, true)（forceBundled=true，ApkBuilderPluginHelper.java:96-98）。
2. **日志-合并确实发生**：出现 **merged slim template bytes=X**（ApkBuilderPluginHelper.java:310），且 **X 明显大于瘦身资产 19,814,709 B**（= 瘦身资产 + 宿主 lib；device4 实测该值为 41045538）。
3. **合并物 vs 产物一致**：把合并出来的 **files/apk-builder/template.apk 也跑一遍审计脚本**，其 lib/ 清单 **== 产物 lib/ 清单**（同一套 KEEP/DROP 判据）。
4. **产物判据**：node tools/apk-native-lib-audit.mjs <产物.apk> --expect-abi arm64-v8a,armeabi-v7a --fail-on-leak → **leaks=0、unknown=0、missingAbi=[]**（v7a 未定夺前按**显式豁免**，不能默认忽略）。
5. **added>0 不适用于 ③**：它只作为**非 ③ 路径**（① /sdcard 外部模板、④ 插件模板）的判据——那两条路径下 ensureTemplateLibs 面对的是**自带 lib 的全量模板**，才会出现 already present / added 的可比数字。
6. **反例对照（保留）**：用**插件全量模板**再打一次 → 必须 **added=0 且 merged slim template bytes=… 段不出现**；两次结果不同才证明「命中 ③」这条判据有牙。
**B-3 通过标准**：B-2 的 **1/2/3/4 全绿** + **第 6 条反例对照成立**（第 5 条是适用范围说明，不是判据）。

### 9.1 变体 A：单库化（opencv_world）——**预计省 0 B**
1. 配置（同一 build 目录，加 world）：
   ~~~powershell
   cmake -S D:/opencv_5_gpu_workspace/src -B D:/opencv_5_gpu_workspace/build_world `
     -DBUILD_LIST=core,imgproc,dnn,imgcodecs,features,java `
     -DBUILD_opencv_world=ON -DBUILD_SHARED_LIBS=ON `
     -DANDROID_SUPPORT_FLEXIBLE_PAGE_SIZES=ON `
     -DCMAKE_TOOLCHAIN_FILE=<NDK r27c>/build/cmake/android.toolchain.cmake -DANDROID_ABI=arm64-v8a
   cmake --build D:/opencv_5_gpu_workspace/build_world --target opencv_java --parallel 8
   ~~~
2. **注意**：BUILD_opencv_world=ON 的产物是 **libopencv_world.so + libopencv_java5.so（JNI shim）= 2 个**，**不是 1 个**；要做到 Pro 那种「一个 .so 含 JNI + 全部模块」，还要 -DBUILD_SHARED_LIBS=OFF 让模块静态化并把 JNI 整体链表（-Wl,--whole-archive）——风险与工时都显著上升。
3. **JNI 名字是硬约束**：Java 侧 org.opencv.* 由 Core.NATIVE_LIBRARY_NAME 决定加载名；改名/换名会让 System.loadLibrary 找不到 → 要单库必须保持 libopencv_java5.so 这个名字（或同步改 Java 常量并重编全部调用方）。
4. 重打包：用 9.0 的 package-opencv-features.py --output-aar 覆盖 AAR（**只换 arm64**，v7a/x86 不变——现流程就是这样）。
5. 验证：node tools/apk-native-lib-audit.mjs --aar <新aar> --by-module（对比 `8.2 表：**总量应≈不变**，只是模块行合并）+ tools/verify-16kb-alignment.ps1 + 宿主构建后 --by-module。
6. **预计耗时**：arm64 重编 4-7 个模块 **10-30 分钟**（本机未实测；把 cmake --build 墙钟记进日志）；加重打包与两轮构建验证 = **半天**。

### 9.2 变体 B：裁剪模块（去掉自建 SIFT 三件套）——**省 2.71 MiB（5.4%）**
1. 配置：把 -DBUILD_LIST=core,imgproc,dnn,imgcodecs,features,java 改成 -DBUILD_LIST=core,imgproc,dnn,imgcodecs,java（**去掉 features**；flann/geometry 作为其依赖不再被拉入——**这条要实跑确认**，看配置日志的 To be built 列表）。
2. **必须同步下线脚本 API**：modules/engine/.../core/image/{SiftMatcher,FeatureMatcher,ImageFeatures}（否则脚本调用会 UnsatisfiedLinkError/NoSuchMethodError）-> 属**功能变更**，要单独一轮，不在「打包瘦身」里顺手做。
3. 验证同上；--by-module 应显示 opencv-features/flann/geometry 行消失，总量 -2.71 MiB。

## 10. 收益判定（终态）

| 选项 | 判定 | 理由 |
|---|---|---|
| **单库化** | **不做（关闭）** | 省 **0 B**（只减文件数）；还要处理 JNI 加载名、16KB 重验、world/静态链接两种复杂度；**无体积与功能收益** |
| **裁剪模块** | **仅 features/flann/geometry 可选（5.4%）**；dnn/OCR 不裁 | 2.71 MiB 是唯一「纯省」；再省必须牺牲功能，而 OCR 14.33 MiB 是 vs Pro 差的主因（Pro 插件按需装），属**产品决策** |
| **都不做** | **默认（保持现状）** | 不用的工程可用 removeOpenCv=true 整体不带；libpikafish 已按工程排除；体积差已定位到 OCR/dnn 两个**功能项**而非形态 |

**关闭结论（单库化）**：**不做**。**重开条件**（三条同时成立才重开）：① 出现**硬约束**要求减少 .so 文件数（如某商店/平台限制单 APK 内 native lib 数量，或实测到 .so 数量导致的加载/符号冲突）；② 该约束收益可量化且**大于**重建成本（半天 + 16KB 重验 + 回归）；③ 愿承担 JNI 加载名与静态链接的改动风险。

**给产品决策的另一条（不在本任务范围）**：若目标是「把包做小到 Pro 量级」，**唯一有效方向是 OCR 形态对齐 Pro（内建 14.33 MiB -> 按需插件）**，不是 OpenCV 单库化。
