## 1. 结论（先看这里）

| 问题 | 结论 |
| --- | --- |
| 我们有多进程偏好一致机制吗 | **没有真正跨进程的偏好实现**。只有：进程内 SharedPreferences 缓存 + 2026-10-18 评估定下的「写者分区 + 每 run 下发快照」**约定** |
| 那份评估的第一批落地了吗 | **没有**。SET_SETTING(104) / RUN settings 快照 / 隔离进程判断泛化：全仓 0 命中（见 §2.3） |
| Pro 的 Tray 是什么 | ContentProvider + SQLite 的 SharedPreferences **替代品**：putXxx 立即写穿、apply() 空实现 ⇒ 没有进程内缓存、读写天然一致、可跨进程监听 |
| 轮到我做什么 | ① 写清现状/缺陷；② 因生产迁移的调用点（Pref.java / SettingsModule / 首启导入）**不在本轮写作用域**，本轮交付**候选实现 + 单测 + 验收口径**；③ 终表**不落「已等价」** |
| 候选实现如何保证跨进程一致 | 读前按**文件指纹**重载（治 R1 读旧值）；写=**文件锁内「读盘 → 只合并本次改动 → tmp+rename」**（治 R2 丢键/R3 异步）；同步提交、无 apply 语义 |
| 跨进程监听（R4） | **未做**（要广播/Binder，第二批）；单测明确钉住「跨进程写不会凭空回调」 |

## 4. 本轮交付：CrossProcessPrefs（**候选，未接线**）

modules/engine/src/main/java/com/stardust/autojs/core/pref/CrossProcessPrefs.kt

- 存储抽象成 Store（read / writeAtomically / withFileLock / fingerprint）⇒ **不依赖 Android**，
  真实现是「应用私有目录文件 + FileChannel.lock + tmp/rename」，单测用内存实现。
- 读：先比指纹（长度 + 内容校验和），变了才整份重载 ⇒ 别的进程写过，本进程下一次读就能看到。
- 写：锁内「读盘 → 只合并本次改动 → 原子替换」⇒ 两个进程交替写不同键不丢（治 R2/R3）。
- 监听：同进程即时回调，**每个有效改动恰好一次**（首版曾重复回调，单测抓到并修）。
- **没有抄反编译实现**：Pro 的 Tray 只作思路参照；存储格式自定（key\u0001value 行格式，便于单测直验）。

单测：modules/engine/src/test/java/com/stardust/autojs/core/pref/CrossProcessPrefsTest.kt（6 项，纯 JVM）

## 5. 验收口径

- **用哪两个进程验**：**主进程 ↔ :script**（同一份偏好文件、两个实例）。
  - JVM：两个 CrossProcessPrefs 实例 + 同一份 Store（就是「两个进程」的等价物）——本轮已跑通。
  - 真机：主进程改一个偏好 → :script 进程**下一次读**看到新值；两个进程交替写不同键，键不丢。
- 单测覆盖：R1 可见性、R2 不丢键（核心）、R3 同步提交、类型/转义往返、R4 边界（不跨进程推送）、指纹不变不重载。

## 6. 未验证边界

1. **真机未验**（本轮只到 JVM）：Store 的真实现（FileChannel.lock + tmp/rename）**还没写**，本轮只交付 seam + 内存实现。
2. **未接线**：Pref / SettingsModule / 首启从 XML 导入 / 回滚开关都属第二批，且调用点在 apps 侧（不在本轮写作用域）
   ⇒ **生产行为零变化**；本类是「已验证的候选」不是「已生效的修复」。
3. **跨进程变更通知（R4）未实现**：需要广播或 Binder（第二批）。
4. **并发写不是事务**：文件锁只保证「读-合并-写」互斥；没有锁超时策略、也没有多键原子事务。
5. **迁移细节未评估**：XML 偏好的类型/Set 支持、DISPOSABLE_BOOLEAN、脚本 storages（建议保持「写者唯一」不迁移，与 Pro 一致）。
6. **终表口径**：应落「部分等价（写者分区约定）+ 候选实现已验证存储一致性，接线属第二批」，**不是**「已等价」。
