## 宿主层真正遗漏的缓存信息

`Node24HostBridge.handleJava(newRef)` 返回了 `$obj/$class/$view`，却漏掉 `$type`。普通方法返回对象的描述符早已携带 `$type`；构造对象因此不能从第一步就参与前端按 Java Class 身份建立的方法元数据缓存，多个 TextView 等同类对象会重复查询方法。

修复：为构造返回补上 `mJavaMembers.typeId(created.getClass())`。复用的是方法元数据，调用闭包仍各自绑定对象，字段仍实时读取。没有按类名缓存可变字段值，也没有改变数字重载规则。

原有 JS 合约的模拟描述符已带 `$type`，所以未发现真实宿主的遗漏。新增真机回归 `modules/engine/src/test/device/node24-constructor-cache.js`，直接检查实际构造描述符，以及两个 Rect / StringBuilder 的字段和方法接收对象独立性。

## 项目层修改

1. 把 `dm.density` 提前读成 JS 数值。原来的 `S.dp(v)` 每次都会跨桥读取 Java 属性；现在每次内容视图创建时重新采样密度。
2. 首页先创建，其余四页首次点击时创建并保留。页面内容和导航索引不变，已构建页面不重复创建。
3. 重建时清理旧的定时器、播放器和页面容器，再绑定新视图，防止页面和标签累积。
4. 三份脚本使用关闭状态和界面代次丢弃过期 UI 更新。快速返回测试暴露了 M3 定时更新在关闭后访问 `binding.fill` 的错误，已用生命周期取消处理；没有伪造不存在的 View。
5. 主页面状态栏、导航栏颜色与页面背景一致。保留此前字体相对路径、布局 `-1/-2` 常量、Promise 错误处理及布局合并修复。

## 测量

同一台小米 8 / Android 15，Node 24.22.0。下表为构建代码阶段日志，不包括 APK 冷启动、首次运行时解包，不是与原版音乐 APK 的性能对比。

| 阶段 | 工作量 | 本轮记录 |
| --- | --- | --- |
| 前一候选项目 | 同时创建五页 | 12242 ms；分段采样另记 12461 ms |
| 补齐构造类型编号 | 同时创建五页 | 5851 ms |
| 再缓存屏幕密度 | 同时创建五页 | 5064 ms |
| 首页优先最终版 | 只创建首页及共享导航/播放条 | 3060 / 2855 / 2792 ms，中位 **2855 ms** |
| 首次点击其余页 | 点击至 ready 日志，含输入与轮询开销 | 收藏 0.292s / 歌单 0.207s / 分类 1.180s / 我的 0.707s |
| 一次界面重建 | 重新创建首页 | 2604 ms，页面数恢复为 1、标签数为 5 |

首页优先改变了首屏工作量，不能把它描述为同样五页代码运行速度提升四倍。全五页的缓存修复和首屏按需创建是两个独立改动。

分段采样中，Java 快通道 2220 次调用合计约 1.94 秒，SVG 路径构造约 0.45 秒。其余耗时还包括构造、元数据查询、字段读取和控件工作，不能全部当作 JSON 开销。

验证了 `androidx.core.graphics.PathParser.createPathFromPathData` 可直接调用，不需要报告中失败的 varargs 反射写法。当前项目试验没有观察到提速，因此最终保留原有图标解析器，没有加入额外原生解析路径。

## 边界与后续

- 原报告的 Android 16 / Mali 设备仍未复测；本轮结果不能替代那台设备的退出原因与 native 堆栈。
- MCP `ui_input` 混用待写文本与查找条件的问题仍作为独立待办保留，输入回归通过 Rhino 无障碍选择器完成，没有宣称该工具已修复。
- 后续若继续减少启动开销，应优先考虑 XML / 原生列表和明确异常边界的桥批处理。通用 Java 接口的同步返回值、字段实时性和线程身份必须保留。
- 原版听海 APK 身份和资源核对、ANR 定位详情见 `2026-10-26_听海NodeUI兼容修复.md`。这份项目是界面与离线音频演示，不连接原版音乐服务。
