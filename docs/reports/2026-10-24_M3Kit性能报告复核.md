# M3Kit 性能报告复核（192.168.10.4）

日期：2026-10-24。复核范围：经手机 MCP 读取 `M3Kit/docs/Performance-Report.md` 至 §16 dev-1242，以及原始日志、M3Kit JS 和本仓库宿主实现。本轮为评审，没有修改手机工程、启动 UI 基准、安装或发布 APK。

## 结论与顺序

报告记录的 dev-1242 启动和页面构建数据明显改善，但还应继续处理以下五项。先修功能与生命周期，再处理微基准；“200 个 View 上限”应从待修清单撤下，现有日志不支持该结论。

| 顺序 | 项目 | 证据级别 | 建议 |
|---|---|---|---|
| 1 | runtime.loadDex 后 XML 直接使用 DEX 类失败 | 设备原始错误 + 宿主代码一致 | 统一当前脚本的运行时 ClassLoader 与 UI inflater 的可见链 |
| 2 | 缓存切页重复订阅；原生 listItem 缺 onToggle | 源码 + 离线复现 | 每个缓存 View 只安装一套业务监听，补齐原生 facade 契约 |
| 3 | 整页预取占用 UI 线程的风险 | 源码明确，掉帧尚未测量 | 按需/空闲调度，拆分大任务，并补生命周期和取消边界 |
| 4 | add(int,int) 路径约 100µs | 设备日志有耗时；分段根因未定位 | 分别测方法解析、装箱、线程调度、调用，之后再做安全快路径 |
| 5 | inflateBatch 不支持 JS 自定义 Widget | 当前代码明确拒绝 | 补每个实例独立的展开、绑定和清理；保留 parent 不自动挂载的契约 |

## 1. DEX 可见性应从宿主层修

`docs/direct-1242.log` 仍有 `ClassNotFoundException: m3native.NativeView`；错误里尝试的 projectDex/caller 都指向宿主 base.apk 的 PathClassLoader。

本地对应实现：

- `Node24HostBridge.java:1619` 的 `loadRuntimeDex` 更新 `mRuntimeClassLoader`，却没有把它注册到 UI 使用的 `Node24GeneratedClasses` 所有者注册表。
- `$java.defineClass` 路径会注册这个所有者的最新 loader。因此当前 `native.install` 生成 `m3ui.NativeView` 包装子类后可以绕过该缺口。
- `NodeUiLocalSession.java:320` 的 inflater 通过 `javaClassOwner` 查询上述注册表；`Node24HostBridge.java:1116` 还仅在有生成类或 realJava 标记时透传 owner。两处需要一起对齐。
- `loadRuntimeDex` 当前每次以 `mContext.getClassLoader()` 作 parent。多次 loadDex 应检查是否需要保留既有运行时链，避免后载入的 DEX 使前一个 DEX 从当前入口不可见。

建议：运行时 DEX 和生成类共用**按脚本所有者隔离**的最新 loader 链；UI 创建前后都能更新；结束时清理。不要采用全局共享项目 ClassLoader 的办法。

验收：只 loadDex、不 defineClass，直接 inflate 原类；Activity 创建前后各测；A/B 两个 DEX 连续加载；普通/batch inflate；停止重启及两个脚本互不串类。修通后再考虑移除 M3Kit 包装子类，保留旧宿主回退。

## 2. 缓存页监听和原生组件行为需要先补齐

远端 `main.node.js:97–104` 命中缓存后仍调用 `onPageReady`，后者 `:39` 每次新增 `nav.onSelect`，`:54–56` 再次执行 wire。`src/native.js:270–274` 的 `on` 是追加订阅，绑定在同一 View 的 WeakMap 元数据内，没有自动替换旧监听。

本地宿主 `ui.js` 的 `realBindings`/`childCache` 会复用绑定对象，不能假定每次 binding 访问都会产生独立的空订阅表。

已用 MCP 读到的原始 `main.node.js` 和 `src/native.js` 做离线复现（Android View 为 mock，未运行手机 UI）：缓存页进入 5 次，存下 5 个 select handler，一次点击分发 5 次。真实 `show` 的“当前页不变则返回”能拦住部分重复切页，但不会移除订阅；chip/segmented 的重复业务回调同样值得修。

另一个明确缺口：`examples/app.js:478–479` 使用 `listItem.onToggle`，而原生 facade 没有该方法，`bindNativeEvents` 也没有 listItem 分支。当前条件判断会静默跳过监听，属于接口行为不齐；本轮没有验证原生列表开关的实际触摸表现。

建议：区分“View 创建时绑定一次”和“重新显示时恢复状态”；记录并释放本页自己持有的监听。补齐 listItem 的 onToggle、状态读写及用户操作事件。不要为省事删除其他调用者的全部订阅。

验收：来回切页 20 次，每个用户动作只触发一次业务回调；主题重建后旧回调不再生效；chip/nav/segmented/switch/listItem/slider/textField 在 JS 与 nativeAll 两种模式下对齐。

## 3. 预取应增加调度和生命周期约束

`main.node.js:144–175` 在 800ms 定时器后，通过 `ui.runOnUiThread` 一次 inflate 整个预取页。延迟 800ms 不代表手机此时处于空闲，用户可能正在滑动；报告里的原生组件页构建也有 41ms。

这是源码可见的卡顿风险，**本轮没有帧数据，不能直接认定已经掉了多少帧**。

建议：首帧完成后按需/空闲预取；大页面拆成小段或使用列表复用；每段检查当前页、主题 generation 和 Activity 生命周期。主页面 render 回调也应检查是否已过期。Activity 销毁时取消定时器并释放其页面缓存、监听；检查重建后是否复用了旧 Activity 的 View。Android View 创建仍留在 UI 线程。

验收：首次启动后立即滚动、快速切页、预取中换肤、退出/重开和 Activity 重建；记录帧耗时、输入延迟和缓存是否失效，不能只看 inflate 完成日志。

## 4. add(int,int) 应继续定位，但不能泛化成全部整数调用慢

`docs/jni-ui-1242.log` 的 add ×20000 为 2031.6ms（101.6µs/次）。`native/m3native/JniBench.java` 的 add 只有一个实现，没有自身重载；没有保存对应 JS 基准脚本，尚不能确认 JS 侧是否缓存过方法访问。

当前宿主 `invokeJava`（`Node24HostBridge.java:1389`）会缓存零参数 Method；有参数调用仍执行候选选择，之后反射调用和参数转换。类型化 JNI 边界（`java_fast_jni.h:79–104`）仍创建参数数组并装箱。它已经省掉 JSON，但仍有可测量成本。

建议先分段取证：直接/缓存后的方法访问、普通线程/UI 回调、Java 内循环/每次跨桥、无重载/有重载、不同参数个数分别对照。若确认解析占比高，可针对唯一适用签名优化；有重载时必须保留按实际数值选择的语义，尤其 int/long/double、null、引用和不同 ClassLoader。

报告 §15 已记录 UI 长循环触发 ANR。后续微基准应拆成有限的小段并记录线程/预热/GC 条件，不能再次靠长时间堵住 UI 线程取得“稳定”数字；也不能承诺优化 add 会等比例加速整页。

## 5. 自定义 Widget 的批量接口仍可补

`ui.js:1917` 对已注册自定义标签明确报“不支持”，不是本轮发现的随机 inflate 故障。普通 `ui.inflate` 已有 `expandCustomWidgetsInXml` 与 `attachCustomWidgets`；批量路径尚未打通两者。

建议复用展开模板，但每个 item 必须有独立 ID/Widget 实例、属性、binding、监听与 mounted/清理流程；批量失败时不残留半套状态。原生 M3Kit 当前已有可用路径，可在前面功能修复后补这项。

`parentChilds=0` 是当前接口按 `attachToRoot=false` 创建的预期结果。parent 用于生成 LayoutParams；不要擅自改成自动 addView，否则会改变现有调用者行为。

## 需要更正的报告结论

1. **§16.4 的“300 个 TextView 到 200 停止”与原始日志矛盾。** `budget-1242.log` 实际依次打印 50/100/150/200/250/300，然后 `all`、`attached`。应改成“本次至少 300 个创建并挂载完成，未复现此前约 200 的现象”。这不能证明无限制；宿主 batch 的单次 count 1..256 是另一项明确接口边界，不是页面总 View 数限制。
2. **526/547ms 是脚本首行到 onPageReady。** 报告 §2 已写明不含 GPU 绘制与动画，因此 §16 的“可见/可交互”和“冷启动”应明确测量边界，不能等同 App 冷进程启动到实际首帧或首次可响应输入。dev-1242 只有两次启动样本，后续应报告固定条件下的多轮中位数/尾部耗时。
3. **批量对比用相同数量。** §16.3 同为 50 个时，batch 23ms vs 循环 46ms；100 个 batch 41ms 可单列，不能直接把它与 50 个循环当作等工作量结论。
4. **改善不宜统一归因为 JNI。** 版本、入口统一、预热和构建设置都可能影响结果；最新的 nop/setText 改善幅度也没有全部达到 35–75%。保留各项原始数字，避免一句话概括成所有路径都同比提速。
