## 起因

K40 现场报「有一格棋子读不出来（未知格 1）→ 一直卡在恢复中不出手」，以及「计划行里实际层数显示 ?」。

层数那条已单独修（候选缺 `depth` 时回落宿主的顶层 `depth`、日志改打「—（引擎未回深度）」）。

## 取证：先把「读不出来的格子」看清楚

### 1) 造了一把「电脑上能跑真识别代码」的尺子

`tools/probe-glyph.js` 必须在手机上跑（要 `images.*`）。这次新增 **`tools/glyph-pc-eval.js`**：

- 用 Node 自带的 `zlib` 解 PNG，手写一套 `images.*` 语义（grayscale / clip / threshold /
  countColor / **matchTemplate=TМ_CCOEFF_NORMED** / pixel / resize）；
- 几何与真值来自仓库里的评测集（`docs/reports/chess-skin-eval/eval-9.json`，
  由新增的 `py/export-eval-9.py` 从 py 定位导出），不依赖手机；
- 跑的是**同一份** `src/vision/glyph-recognizer.js`，模板也是工程 `assets/glyph-tpl`。

**忠实性验证**：基线跑出 `763/784 = 97.3%`，与电脑 py（`py/run-py-eval-9.py`）和真机
`probe-glyph` 的 763/784 完全一致 ⇒ 这把尺子可以当作迭代识别链的日常工具（改一行几秒出结果）。

### 2) 逐格量三道门 + 最佳 NCC，找出「会变成未知格」的格子

`python -X utf8 .artifacts/glyph-gate-metrics.py`：9 帧 810 格里，**只有 5 格**「三道门都过、
但匹配分低于 0.70」（= 工程里会读成 `?`）。其中唯一的真棋子是 **skin-c r9c7（真值 馬）**，
匹配分只有 **0.48**；另外 4 格在 `skin2-04` 的中路，是**落子动画的中间帧**（真值本身就是空/不确定）。

### 3) 那格到底怎么了：逐尺度量一遍

```
skin-c r9c7（馬）
  scale 1.00 -> 馬 0.543 @(-2,-13)      ← 现有搜索窗（±6/±20）拿到的就是这个分
  scale 1.10 -> 馬 0.879 @( 0,-12)      ← 与次名（車 0.590）拉开 0.29
  scale 1.16 -> 馬 0.766
```

结论：**棋子被点起/刚落地时，游戏会把棋子和字一起放大（≈1.10）并上移 ≈12px**。
原尺寸模板在门限下拿不到分 ⇒ 那一格每帧都读成未知。

## 改动（`src/vision/glyph-recognizer.js`）

1. **触发面扩大**：复核从「完全没匹配上（`!m`）或读成九宫外的士/仕」扩到
   **「分 < SAFE_CONF(0.82)」**。旧行为下「读成合法但错的字形、分只有 0.7x」是没人复核的。
2. **`rescueMatch`（多尺度抢救）**：按 `[1.10, 1.06, 1.18, 0.94]` 逐档（最可能先试、命中即 break），
   搜索窗 ±(8, 22)，并且**只有同时满足**下面两条才采信：
   - 分 ≥ `RESCUE_CONF`（0.80）；
   - 「头名 − 次名」≥ `RESCUE_MARGIN`（0.12）—— *宁可留一个未知格（状态机不出手，看得见），
     也不要认错子（走错棋，看不出来）*。
3. **阵营扫描抢救**：車/馬/炮 判红黑时暗样本太少（遮罩/动画）→ 采样步长 4→2、样本下限 30→12 重判；
   `R-B > 45` 的门限不动（红墨的 R-B 很硬，不会把黑子判成红）。
4. **成本上限**：一帧最多抢救 3 格、总预算 2500ms（超预算就不再抢救剩下的格子）；
   缩放模板按「模板对象 + 边长」缓存，避免重复 resize。
5. **可观察**：`recognize()` 现在回传 `rescued / rescues / rescueMs / notes`，字形源（`pipeline-factory`）
   把它们写成面板日志（未知格明细**只在变化时**打，不刷屏）：
   - `字形抢救 1 格：r7c4 抢救成「馬」（0.88，×1.1，原本是「相」0.71）（抢救 1 次，耗时 210ms）`
   - `字形未知格：r4c3 没读出来：最佳「士」0.19，次名「車」0.15`
6. 删掉被取代的 `matchSelectedScale`（旧的「选中放大」复核）；新增 `bestMatchRanked`（带次名/分差）。

## 附：把「定位那套」搬到判决层 —— 盘面级判决（守恒 + 棋规）

重新看了一遍**棋盘定位**为什么稳（`lattice-detector.js`）：它不逐条线独立判生死，而是把 95 条线的证据
放进**一个全局拟合**（origin/step 全搜 + trimmed 求和，允许最弱 1~2 条线缺席）。
字形识别相反 —— **逐格独立**判决，于是两个缺口：

1. 「字形认得、只有红黑分不出（車/馬/炮 笔画颜色样本不足）」→ 只能留 `?`，而状态机要求「未知格 0」⇒ 整盘卡住；
2. 读数违反棋规/子力上限也照单全收 —— 字形链此前**没有** `consistency.repair`（旧检测链有）。

新增 `src/vision/glyph-resolve.js`（字形源里在圆证据/占位记忆之后调用）：

- **① 违规修复**：复用 `src/chess/consistency.js` 的成熟逻辑（降级 / 改阵营，日志可见）；
- **② 守恒补全**：对 `gate="side"` 的 `?` 格（字形已确认、只差颜色），把两个候选（红/黑）各试一次，
  要求「不引入新错误 + 无硬棋规违规」；**恰好一个合法才补**，多解或都违规就保持 `?`（宁缺勿错）。
  （`gate="match"` 的格默认不补：实测空盘/木纹的假最高分能到 0.32~0.39、被动画盖住的格 0.19~0.36，
  都不足以证明「这里有子」，而「空」永远合法 —— 补全无从谈起。）

验证：`tools/self-check.js` 新增 5 条探针（唯一解补全 / 多解不补 / 两候选都违规不补 / 违规格被修 / 正常盘面零副作用），
自检 320/320；电脑侧评测 9 帧仍 **806/809 = 99.6%**（新增一层不引入退化，skin2-04 那格黑馬×3 的违规读数
被修成合法读法并在日志里标了「改阵营」）。

⚠️ 它**不会**修掉下面那 3 格动画帧：被飞子盖住的格子连「有没有子」都不可判（分数 0.19~0.36），
守恒又推不出必须放什么 —— 单帧无解，真机上靠多帧投票丢帧。
