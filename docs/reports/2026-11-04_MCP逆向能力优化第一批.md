# MCP 逆向能力优化第一批（工作区 / 文件发现 / 验签分层）

> 版本：dev-1331（仅 LAN）。来源：手机 `/storage/emulated/0/脚本/AI.js-Pro-MCP-逆向能力优化建议.md`（GPT 实战复盘，已收录为 [docs/plans/2026-11-04_AIjsPro-MCP逆向能力优化建议（GPT复盘）.md](../plans/2026-11-04_AIjsPro-MCP逆向能力优化建议（GPT复盘）.md)）。
> 本批只做复盘里的 **P0 第一阶段**中的 3 组可靠性项；P1/P2 见文末「未做」。

## 一、本批实现

| 复盘条目 | 实现 | 入口 | 关键语义 |
|---|---|---|---|
| §3 工作区配额一致性 | 工作区清单 + 受控 GC | `apk_workspace_inventory`、`apk_workspace_gc` | 配额 16 可解释；`dryRun` 默认 true；saved/当前/活动引用/编辑会话/未知 owner 一律保护；orphan/dangling 只报告 |
| §5.2 非标准扩展名发现 | ZIP 魔数 + APK 结构判定 | `file_discover_apk`、`file_stat.apkProbe` | 扩展名只加分：`.apk.1`/`.bak`/无扩展名/临时名都能命中；带 truncated/skipped/stopReason 与深度/条目/探测/字节/时间预算 |
| §5.1 路径访问诊断 | 双后端只读诊断 | `file_access_diagnose` | `backend` 必须显式 `app|shizuku`，不静默切换；返回原始 errno/UID；无法区分「不存在/不可见」时给 `UNCERTAIN`+`uncertainty` |
| §4.2 验签错误分层 | 分方案状态模型 + 后端探针 | `apk_verify.signature`（并进入 `toolkit_status` 声明） | `valid/invalid/backend_error/input_error/not_run`；`backendDiagnosis.asn1AnnotationsRetained` 把「后端注解是否可用」变成证据；后端异常不再被当作目标签名无效 |

其它：`apk_workspace_open` 配额报错改为指引「先 inventory，再 gc dryRun」；`open` 支持记录可选 owner/clientId/sessionId；`proguard-rules.pro` 显式保留 apksig ASN.1 注解与模型类（防御性，见下）。

工具规模：公开入口 **174**（经典 165 + 9 个兼容别名），toolkit 工具 **104**。

## 二、MI8（dev-1331）真机实测

1) 工作区配额可解释（此前只知道「配额满」）：

```text
apk_workspace_inventory -> quota=16, totalCount=3, totalBytes=5,297,616,             
  byState={saved:0, temporary:0, expired:3, dangling:0}, orphanCount=0, danglingCount=0
apk_workspace_gc {dryRun:true} -> dryRun=true, applied=false, wouldDeleteIds=[],
  wouldReclaimBytes=0, skipped=3   # 未知 owner/未显式 includeTemporary 时保守不动
```

2) 非标准扩展名发现（复盘里真实踩坑的 `影安加固-测试demo.apk.1`）：

```text
file_discover_apk {path:"/storage/emulated/0/脚本/__discover_test", recursive:true}
  -> count=1, stopReason=eof, bytesRead=295808
     影安加固-测试demo.apk.1: zipMagic=true, zipStatus=ZIP_OK, entryCount=3602,
       hasAndroidManifest=true, hasResourcesArsc=true, hasClassesDex=true,
       extensionHint=apk.numbered, candidate=true, confidence=high
     （同目录的假 fake.apk 是纯文本，被正确排除）
file_stat(同一个 .apk.1) -> apkProbe 同样给出上述结构字段
```

3) 路径访问诊断（app 身份；MI8 未运行 Shizuku，如实报告）：

```text
file_access_diagnose {path:"/storage/emulated/0/Android/data", backend:"app", compareWithShizuku:true}
  -> conclusion=ACCESSIBLE, distinguishable=true, uncertainty=null, uid=10296,
     executedBackends=["app"], shizukuAvailable=false, shizukuExecuted=false
```

4) 验签分层与后端探针（`apk_verify`，被测包为 V2 签名的 AutoJs6 证书 APK）：

```text
signature.status=valid, verdict=valid, verified=true
signature.schemes: V2=valid(1 signer); V1/V3/V3.1/V4=not_run（没有签名者，不再显示成“验证失败”）
signature.backendDiagnosis: annotationClassPresent=true, modelClassPresent=true,
  modelAnnotated=true, asn1AnnotationsRetained=true
```

结论：本机 release 包里 apksig 的 ASN.1 运行时注解是保留的，因此复盘里那次 `ContentInfo is not annotated with Asn1Class` **不能**再从“R8 把注解删了”直接解释；现在无论它来自验签还是重签路径，都会被归到 `backend_error` 并附 `backendDiagnosis` 证据，而不会污染目标 APK 的签名结论。proguard 的 apksig 保留规则作为防御性措施保留。

## 四、未做（下一批候选，按复盘顺序）

1. **§4.1 Manifest 基础解析与回退**：ARSCLib 失败（`Can not decode without package`）时的独立 AXML 字符串池/标签解析，并区分「目标损坏 / 格式不支持 / 资源上下文缺失 / 后端异常 / 基础字段已取到但 XML 不可用」。
2. **§5.3 应用查询一致性**：先 filter 后 paginate 已确认无「先截断」问题，但仍缺 `visibilityLimited`、Unicode/空白归一化、`matchedBy`。
3. **§6.1 任务隔离与结果保留**：按 clientId/sessionId 隔离、未读结果保留窗口、`JOB_EVICTED`/`SERVICE_RESTARTED`/`JOB_NOT_FOUND` 明确错误码。
4. **§6.3 嵌入式 Node 运行形态**：`runtimeMode/hostExecutable/standaloneNodeExecutable/canSpawnStandaloneNode`，不要伪造 `process.execPath`。
5. **§5.2 收尾**：`artifact_open` 失败/目录/非 ZIP 时直接回退到 discovery 候选（目前只给 nextActions）。
6. **P1**：有状态 native 分析会话、精简反编译输出与增强交叉引用、应用启动/退出原因关联采集、Frida Java Bridge 与有界持续会话。
7. **P2**：可验证二进制变换、VM 薄壳辅助、统一证据导出与分级。

已知边界：Shizuku 在 `:tools` 进程的真机可用性未验（不可用会如实返回 `BACKEND_UNAVAILABLE`/`UNCERTAIN`，不回退 app）；shizuku 后端没有原始 errno（shell 只给布尔）；ZIP64 有代码无 fixture；`apk_workspace_gc` 在有活动 job 但记录不到 workspaceId 时保守跳过全部临时工作区。
