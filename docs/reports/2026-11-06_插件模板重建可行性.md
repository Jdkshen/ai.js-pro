## 4. 风险

### 4.1 88MB LFS 对象

- `plugins/apkbuilder-plugin/src/main/assets/template.apk` 是 LFS 对象：`.gitattributes:18-19` 明确两条 template.apk 走 `filter=lfs diff=lfs merge=lfs -text`；`git lfs ls-files` 显示当前 pointer `1ca77ad131`。
- 若重建后模板字节变化，会产生新的 88MB 级 LFS 对象；旧对象仍在历史，仓库/CI 的 LFS 拉取、备份、带宽都会增加。提交时必须是 LFS pointer + 推送对象，不能把二进制直接塞普通 Git。
- 若只改 `template-manifest.json` 而漏提 `template.apk`（或反过来），`verifyManifest`/`verifyTemplateApk` 会硬失败；两项必须原子提交。

### 4.2 插件版本号是否需要 bump

- 当前插件 `versionCode=1 / versionName=1.0.0`（`project-versions.json:6-7`）；重建模板不改这两项。
- 若发布新插件 APK：应 bump `apkBuilderPluginVersionCode/Name`（至少 versionCode +1），否则：
  * `PluginDownloads` 只按固定文件名 `apkbuilder-plugin.apk` 下载（`PluginDownloads.java:24-39`），没有版本比较/自动更新逻辑；同版本重装不会给用户明确更新提示。
  * `ApkBuilderPluginHelper` 的插件模板缓存按**宿主 versionCode** 分目录（`ApkBuilderPluginHelper.java:270-280`），不是插件版本；旧缓存仍可能被优先使用（`openTemplateApk` 第 80-94 行先 mergedBundled，后 cached/plugin），升级插件后也不一定刷新。
  * `ApkBuilderPlugin.ensureTemplate` 只比较 `target.length() == expected`（`ApkBuilderPlugin.java:74-108`），不比较内容 hash/版本；同 size 的新旧模板可能误复用。
- 若只是 repo 资产同步、不发布：不需要 bump；但 CI/后续插件发版会把同 versionCode 的新内容作为最新附件，语义上仍建议下一次正式发布时 bump。

### 4.3 与宿主瘦身模板的一致性 / `Node24TemplateConsistency` 是否报警

当前关键事实（本机读文件）：

- 插件 manifest 的 Node 哈希（`template-manifest.json:6-10`）：`libnode.so d2165091...`、`libc++_shared.so 4397241b...`、`libajsnode24bridge.so d18673a2...`。
- 宿主 `modules/engine/src/main/assets/source-engine-upgrade/node24/arm64-v8a/runtime.json:1-5` 的 3 个哈希完全相同。
- 因此按当前源重建，如果 inrt 侧 Node 资产没变，`Node24TemplateConsistency` **不会出现 Node 哈希漂移告警**；如果 inrt 更新了 Node 库，可能只是打包期告警。

行为与判定：

- 构建期硬校验：`Node24TemplateManifest.verifyTemplate`（缺 Node 资产直接失败，`Node24TemplateManifest.java:101-128`）和 `verifyManifest`（模板/manifest 哈希不一致直接失败，`:131-150`）；`:inrt:buildApkPlugin` 与插件 `verifyTemplateApk` 都会调用。
- 打包期 `Node24TemplateConsistency.verifyWorkspace`：模板与宿主 Node 哈希不同**只写日志告警**（`Node24TemplateConsistency.java:122-130`；测试里对应 `[drift]` 打印，`NodeScriptProtectionTest.java:303-311`）；只有工作区缺件/实际内容与 runtime.json 不一致才按 strict 抛错（`Node24TemplateConsistency.java:53-56,139-149`）。
- 宿主瘦身模板与插件全量模板是两条独立管线：插件重建**不会**改 `apps/app/src/main/assets/template.apk` / `excluded-zip-files.json`，`verifySlimPackagingTemplate`（`apps/app/build.gradle:1176-1213`）不受影响；反过来跑 `tools/build-slim-template.ps1` 也不会覆盖插件模板（脚本 `:15,177` 明说）。
- 代码注释 `Node24TemplateConsistency.java:40-44` 仍写 2026-10-29/30 和旧 `libnode` 哈希（`d2165091` vs `50cfa7b0`），这是**过期注释**；真正 manifest/宿主当前已同为 `d2165091`。重建后应更新注释，否则下一个维护者会被误导（本轮不改源码）。

### 4.4 CI / 发布脚本的副作用

- `.github/workflows/android.yml:44-55` 的 verify job 就跑 `:apkbuilder-plugin:assembleDebug`；由 1.2 的依赖，这会在 CI 工作区**重新生成** `template.apk`/`template-manifest.json`。如果新构建字节与仓库已提交版本不同，CI 只构建不提交，仓库 tracked 模板会和 CI 产物不一致；release job（`:117-148`）会从当前源重新生成并上传 `apkbuilder-plugin.apk`，因此**必须在打 tag 前把模板+manifest 一起提交**，否则发布资产与仓库记录漂移。
- `tools/dev-update.ps1:355-385` 只是把**已经构建好的**插件 APK 作为附件放入更新源，不会主动构建插件；如果本地没先构建插件，更新源会跳过，不会自动生成。
- `plugins/apkbuilder-plugin/README.md:56-66`：没配 `AIJSPRO_*` 时 `assembleRelease` 产物是 `-unsigned.apk`，发布脚本只挑已签名产物；debug 签名产物可用于本地真机自测。

### 推荐：B. 等下次插件发版一起重建（现在只准备，不构建）
