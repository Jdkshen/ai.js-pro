# 第三方 ImGui 项目跑不起来的诊断（auto_jspro_imgui）

> 对象：`C:\Users\18101\Downloads\auto_jspro_imgui-fdf74aaeafba4e7f8c52cc0b8f4a516.zip`
> 结论：**项目源码本身在当前 Android 16 手机上跑不了**（Auto.js Pro 9.3.11 也不行），但它包里自带的打包 APK 能跑。不是我们 JS 引擎的语法/API 问题。

## 1. 项目结构（不是纯 JS）

```
auto_jspro_imgui/
  main.js                  # "ui"; 入口，floaty.rawWindow + ImGui 回调
  project.json
  lib/arm64-v8a/libImGuiBridge.so   # 6.5MB 自带 native 库（JNI + EGL + OpenGL ES）
  lib/ImGuiBridge.dex               # 自定义 com.imgui.bridge.ImGuiBridge
  src/js/imgui.js                   # DexClassLoader 加载 dex，System.load 加载 .so
  build/AutoJS_ImGui_v1.0.0.apk     # Pro 9.3.11 打包产物（targetSdk 28）
```

`imgui.js` 的关键做法：把 `lib/ImGuiBridge.dex` 和 `.so` 复制到 `files/so_<rand>/`，用
`DexClassLoader(dexPath, optDir, soDir, ...)` 加载 `com.imgui.bridge.ImGuiBridge`，再由该类的
`static { System.loadLibrary }` / `JNI_OnLoad` 把 native 方法接上，在 floaty 的 Surface 上渲染 ImGui。

## 2. 三种运行结果（K40，Android 16 / API 36）

| 方式 | 结果 | 证据 |
| --- | --- | --- |
| 我们的 App 源码运行（运行项目） | dex/so 加载成功（`ImGuiBridge: ImGui ready`），随后 **native SIGSEGV**（Data Abort，tombstone 指向 `files/so_58aaf0d2/libImGuiBridge.so`），主进程崩溃回桌面 | logcat：`F DEBUG : esr: ... Data Abort` + 该 .so 帧 |
| Auto.js Pro 9.3.11 源码运行 | 脚本进程直接拒绝：`E utojspro:script: Attempt to load writable dex file: /sdcard/脚本/AutoJS_ImGui/lib/ImGuiBridge.dex` → ImGui load failed | logcat 该行 |
| 安装包里自带的 `build/AutoJS_ImGui_v1.0.0.apk` | **成功**：ImGui demo 窗口正常显示、按钮可点 | 截图 `output/imgui-probe/built-apk2.png` |

## 3. 为什么

- 自带打包 APK 用 Pro 9.3.11 打包模板（targetSdk 28），打包时项目被复制到应用**私有目录**
  （`/data/user/0/com.example.autojs_imgui/files/project/...`），脚本跑在独立的 `:script` 进程，
  dex/so 从私有目录加载 → 系统允许、native 环境也是它编译时面向的那套。
- 源码直接在 Pro 9.3.11 里跑时，项目在 `/sdcard/脚本/...`（可写外部存储），新版 Pro 已禁止
  从可写目录 `DexClassLoader`（Android 14+ 的安全限制）→ 直接加载失败。
- 在我们的 App 里没有这条限制，dex/so 能加载，但该 `.so` 是给旧 Pro 运行时编的，
  和我们 `ScriptExecuteActivity` + `floaty.rawWindow` 的 Surface/线程/EGL 模型不一致 → native 崩。
  我们的脚本跑在主进程，**没有 native 崩溃隔离**，所以一崩就把整个 App 带走。

## 4. 结论与建议

1. 想用这个效果：直接装包里的 `build/AutoJS_ImGui_v1.0.0.apk`（已验证可跑）；
2. 想要源码可维护：让作者改成不再 `DexClassLoader` 加载可写目录 dex（把桥接类编进 APK/插件，
   或改用宿主内置 ImGui）；
3. 若希望不依赖这种第三方桥：我们引擎自带 ImGui（QuickJS 有 `imgui` 能力），可改写成内置 API 版本；
4. 我们这边可排期的两项通用改进：脚本运行进程隔离（native 崩溃只死脚本进程）、Rhino 内置 ImGui API。

## 5. 继续定位与实验（dev-939 / dev-940 / dev-941）

### 5.1 已排除的两个猜测

1. 悬浮窗缺硬件加速：给 RawWindow 加 FLAG_HARDWARE_ACCELERATED（dev-939）——崩溃点不变，已回退。
2. 我们引擎导出的 ImGui 符号被它的 PLT/dlsym 抢到：libquickjs_jni.so 里编进了我们自己的 ImGui（v1.91.9b），原来这些 C++ 符号是 default visibility，会进进程全局符号表。dev-940 用 -fvisibility=hidden -fvisibility-inlines-hidden 隐藏所有非 JNI 符号（JNI 入口都带 JNIEXPORT，全部保留），确认新 APK 里已无 _ZN5ImGui 符号——崩溃点仍是同一个，说明符号冲突不是根因（但这项修改保留：APK 小 491KB，也不再污染进程符号表）。

### 5.2 崩溃点精确定位

用 llvm-objdump 反汇编它的 libImGuiBridge.so：崩溃 pc 0x12bc4c 落在它自己的 ImGui::ButtonEx 里，指令是 ldr x24, [x26, #0x15e0]，而 x26 是从 GOT 读出的 GImGui——等于 NULL，fault addr 正好是 0x15e0。也就是它自己的 ImGui 上下文在调用 Button 时是空的。它自己的 nativeInit 里确实调用了 ImGui::CreateContext 并打印 ImGui ready，说明初始化被执行，但随后 NewFrame/Button 这一侧看到的上下文为空——其桥接层假设「进程里只有一个 ImGui 运行时、一份 GImGui」，而宿主进程里已有一整套脚本引擎/ImGui 运行环境，两者上下文/符号作用域天然冲突。

### 5.3 结论（不改脚本的唯一可行路径）

要在我们 App 里源码模式、不改脚本跑通它，需要把脚本执行放到独立进程（像 Auto.js Pro 的 :script 进程），让第三方 native 库在干净进程里有自己独立的 ImGui 上下文和符号空间；主 App 只通过桥接收 UI 帧/事件。这是引擎级改造（服务进程化 + 执行桥 + 生命周期），不是脚本问题。

在此之前，零改脚本的可用方案就是安装它包里自带的打包 APK（已验证可在 K40 上正常运行）。
