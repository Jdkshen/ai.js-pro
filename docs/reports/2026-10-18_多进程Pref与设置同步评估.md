# 多进程 Pref 与设置同步评估（Phase 1-D）

> 范围：Phase 1 把脚本执行全面切到 `:script` 进程后，现有 `SharedPreferences`/`Pref` 体系是否够用、
> 风险在哪、第一批必须做什么。**结论：风险真实存在且已有存量代码踩线；Phase 1 第一批不做
> prefs 底层替换，只做「写者分区 + 每次 run 下发快照 + 隔离进程不写设置」三条约束；第二批
> （Phase 1 验收后）再上 ContentProvider，与 Pro 的 Tray 方案对齐。**

## 1. 结论（先看这里）

| 问题 | 结论 |
| --- | --- |
| 多进程 Pref 有风险吗 | 有，三类：**读到旧值**、**并发写整份覆盖丢键**、**变更监听不跨进程** |
| 现在有代码在踩线吗 | 有：`:native` 已运行一段时间，且 `App.onCreate` 在**每个进程**都执行；`:script` 上马后 `$settings` 写入会变成跨进程写 |
| 第一批（全面切 :script）需要做吗 | 需要，但只需**流程/契约层**改动（见 §6.1），**不需要**替换 SharedPreferences |
| 第二批需要做吗 | 需要。常驻 `:script` 要与主进程设置实时一致，就得走 ContentProvider（对齐 Pro），见 §6.2 |
| 能用 `MODE_MULTI_PROCESS` 吗 | **不能**。API 23 起废弃且官方明说不可靠，不能作为方案（§5-B） |
| Pro 怎么做的 | 用 **Tray**（ContentProvider + SQLite）替换 SharedPreferences；脚本进程常驻并监听设置变更（§4，反编译证据） |

## 2. 现状：我们有几个进程、谁在读写 Pref

### 2.1 进程清单

| 进程 | 声明/入口 | 职责 | Pref 现状 |
| --- | --- | --- | --- |
| 主进程 | `src/main/AndroidManifest.xml` `<application android:name=".App">` | UI、设置页、定时任务、无障碍、打包 | 主要读写者（`Pref`、设置页、`$settings` 目前都在这） |
| `:native` | `src/flutterpoc/AndroidManifest.xml` `NativeScriptService`（Phase 0） | 带 `.so/.dex` 的项目隔离执行 | 只读（App 初始化时顺带读了几处），Phase 0 已知限制：无自动化 |
| `:script` | `src/flutterpoc/AndroidManifest.xml` `ScriptHostService`（Phase 1，本任务注册） | **所有脚本**默认执行 | **待评估**（本文） |
| `:background` | `src/main/AndroidManifest.xml` `FireSettingReceiver` | Tasker 插件 fire（内部只 `startActivity`） | 无直接读写，但同样会跑 `App.onCreate` 全量初始化 |
| `:node24` | `src/main/AndroidManifest.xml` `Node24Service` | Node 24 引擎，独立进程 | 不读写 prefs：**参数全部经 Bundle 下发**（正面例子，见 `Node24Service.java:29-33,45-50`） |

> （`App.kt:47-62`）。所以 `:native`/`:script` 里同样会 `AutoJs.initInstance`、注册静态监听、
> 走 `ExternalRunResume` 等路径，其中不少会碰 Pref。

### 2.3 脚本执行路径上真正会碰 Pref 的代码

1. **`$settings` API（`SettingsModule.java`）**：`isEnabled` 读 5 个键、`setEnabled` **写 5 个键**
   （`stop_all_on_volume_up`/`not_show_console`/`foreground_service`/`stable_mode`/
   `enable_accessibility_service_by_root`）。`:script` 里脚本调用 `$settings.setEnabled(...)`
   ⇒ **脚本进程直接写默认 prefs 文件**，与主进程设置页形成双写。
2. **`storages`（`LocalStorage.java`）**：`put` 用 `apply()`、Pro 版用 `commit()`；每个 storage 一个
   prefs 文件。设计上只有脚本写、主进程不写 ⇒ 只要**同一时刻只有一个脚本进程**就安全。
3. **引擎读取**：`Config.isPrintJavaStackTraceEnabled()`（异常打印开关）、`core/pref/Pref.kt`
   （`stable_mode`/`key_gesture_observing`）、`RootAutomatorEngine`（`key_touch_device`）。
   进程启动后读取一次 → 常驻进程里**不会自动刷新**。
4. **`App.onCreate` 的隐藏访问**：虽然 `App.kt:98-112` 对 `:native` 跳过了主进程职责，但
   `setUpStaticsTool/setUpDebugEnvironment/init()` 的前半段（`AutoJs.initInstance`、MCP/DevPlugin
   生命周期回调、`ExternalRunResume.resumeIfNeeded`）**在所有进程都跑**。`ExternalRunResume` 自己
   有主进程判断（`J137-142`，正面例子），其它入口没有。

## 3. 风险清单（按优先级）

**R1｜进程内缓存 → 读到旧值（中高，Phase 1 后必然出现）**
`SharedPreferences` 每个进程各有一份内存缓存，只在进程内第一次读取时从文件加载；文件被**其它进程**
修改不会通知也不会自动重载。`:script` 常驻后，主进程设置页改了 `stable_mode`/`not_show_console`
等，正在跑的脚本进程仍是旧值，直到进程重启。

**R2｜两个进程同时写 → 整份覆盖丢键（高，`$settings` 上马后必然出现）**
`SharedPreferencesImpl` 写盘是「序列化整份内存 map → 临时文件 → rename」，进程内合并、跨进程不合并。
主进程与 `:script` 各持一份旧 map，谁后写谁**整份覆盖**：会丢掉对方刚写的键（文件本身不会写坏，
但值丢失）。典型场景：设置页刚改「前台服务」，脚本里 `$settings.setEnabled('stable_mode', true)`，
后写的一方把前一个改动抹掉。

**R3｜`apply()` 异步 + 跨进程时序（中）**
`apply()` 只是排队异步写盘；主进程写完立刻让 `:script` 读，可能读到旧文件。R1/R2 会放大这个窗口。

**R4｜`OnSharedPreferenceChangeListener` 不跨进程（高，与 Pro 的行为差距）**
监听器只在注册它的进程内回调。`Pref.java:34-44,141-143` 在静态初始化里注册了监听（无障碍守护模式、
音量键控制），`:script` 进程里注册的那份**永远收不到主进程的修改**。
对照组：Pro 的 `ScriptService.onCreate` 在脚本进程注册监听，用来即时启停前台通知、初始化音量键
监听（反编译 `ScriptService.java:117-131,449-454`）——**Pro 是依赖「设置改动跨进程即时生效」的**，
这也是 Pro 必须上 Tray 的原因之一。

**R5｜`MODE_MULTI_PROCESS` 不可靠（否决项，见 §5-B）**

**R6｜`:script` 里重复执行主进程职责（高，集成必修）**
`App.kt:114-127` 的 `isNativeIsolationProcess()` 只匹配 `":native"`，`:script` 会走完整初始化：
`TimedTaskScheduler.init`、`DynamicBroadcastReceivers`、`BundledSampleSync`（后两者会写状态/prefs）。
Phase1-B 已在 `ScriptHostService` 类注释里标了这个 TODO，属 Phase 1 集成必修项（`App.kt` 不在本
任务写作用域）。

**R7｜`:native` 与 `:script` 并存期 `storages` 双写（中）**
`PocRuntime` 的路由：`PocScriptHost.isEnabled()`（默认 true）时全走 `:script`，否则退回
`:native`/主进程引擎（`PocRuntime.java:103-121`）。若两个脚本进程同时运行（一个脚本在
`:script`、回退开关切回后另一个进 `:native`），两边同时写同一个
`autojs.localstorage.<name>` 就会踩 R2。**约束：同一时刻只允许一个脚本进程写 storages。**

**R8｜定时任务/设置项的边界（低，第一批接受）**
主进程的定时任务触发 run 走 `:script` 后，脚本对 `$settings` 的修改在主进程要等设置页重读才可见；
第一批按「下一次 run 生效」约定，不承诺即时一致（§6.1）。

## 4. 参考 Auto.js Pro 的做法（反编译证据）

反编译树：`.artifacts/pro-official/src/sources/`（classes2.dex，JADX 输出）。

### 4.1 进程模型与真实 AIDL 方法集

Pro 打包运行时脚本进程是 `js_imgui:script`（见
`docs/reports/2026-10-17_Phase0_native隔离进程MVP.md` §6 真机对照）。主进程 bind
`com.stardust.autojs.ScriptService`，脚本进程 `onBind` 返回 AIDL Stub
（`ScriptService.java:151-172,428-432`），descriptor 为
**`com.stardust.autojs.IScriptServiceInterface`**（反编译 `okhttp3/internal/io/yx0.java`，
transaction 1-10）：

| t | 方法 | 说明 |
| --- | --- | --- |
| 1 | `int run(ScriptExecutionTask, boolean uiMode)` | 传 Parcelable 任务对象，返回 engineId |
| 2 | `void stop(int engineId)` | 按引擎 id 停止 |
| 3/4 | `int getEngineCount()` / `int getRunningCount()` | 计数 |
| 5 | `List<ScriptExecutionInfo> getExecutions()` | 运行中脚本列表 |
| 6 | `void setForeground(boolean)` | 前台服务通知 |
| 7 | `Map callService(String service, String action, Map args)` | **通用服务转发——自动化能力的实际通道** |
| 8 | `Map getServiceState(String service, ...)` | 服务状态 |
| 9 | `void setCallback(IScriptServiceEventCallback)` | 把主进程 Binder 传进脚本进程 |
| 10 | `List<RunningActivityInfo> getRunningActivityInfo()` | 界面信息 |

反向回调 AIDL：**`com.stardust.autojs.IScriptServiceEventCallback`**，只有一个
`void postEvent(String event, Map data)`（反编译 `okhttp3/internal/io/xx0.java:39,54-55,78-79`，
由 `ScriptService` 的 `mo729`/`setCallback` 保存为 `f1251`）。

⇒ **Pro 的「脚本进程 → 主进程」能力（含自动化）不是独立接口，而是 `setCallback` 传入的
Binder + `callService` 通用转发**；我们的 `IAutomationHost`（本任务）是同一方向的类型化版本，
spec 对齐时可选择「照抄 Pro 的通用转发」或「保留类型化接口」（§8）。

### 4.2 Pref 实现：Tray（ContentProvider + SQLite）

Pro 的 `Pref` 内部换成 `TraySharedPreference(AppPreferences(...))`
（`com/stardust/autojs/core/pref/Pref.java:38,47-57,80-82`）。Tray = 基于
ContentProvider + SQLite 的跨进程 SharedPreferences 替代；
`TraySharedPreference$Editor.apply()` 是空实现、`commit()` 恒 true、`putXxx` **立即写穿到
provider**（`TraySharedPreference.java:46-140`），即没有进程内缓存 ⇒ 读写天然一致、可注册跨进程
变更监听。

### 4.3 脚本进程常驻并监听设置

`ScriptService.onCreate` 注册 `OnSharedPreferenceChangeListener`
（`ScriptService.java:117-131,449-457`），用来即时启停前台通知、初始化音量键监听。

### 4.4 残留的自研 provider

Pro dex 里还有一个未被引用的 `PrefContentProvider`
（SQLite 表 `pref(name,key,value)`，`PrefContentProvider.java:21-46,63-70`），生产路径没用它。
若第二批选自研 provider，可直接照这个最小表结构做。

### 4.5 写者分区

Pro 的 `LocalStorage` 仍是普通 SharedPreferences
（`core/storage/LocalStorage.java:12-16,34-40`，`put` 用 `commit`）——说明 Pro 的策略是：
**设置类**（主进程/脚本进程都要读写）走跨进程 prefs（Tray）；**脚本私有 storage** 只由脚本进程
写，靠「写者唯一」保证安全。

## 5. 方案对比

| 方案 | 跨进程一致性 | 改动量 | 风险 | 结论 |
| --- | --- | --- | --- | --- |
| A. 保持默认 prefs + 写者分区 + 每次 run 下发快照 | 中（下一次 run 生效） | 小 | 低 | **Phase 1 第一批（推荐）** |
| B. `MODE_MULTI_PROCESS` | 低 | 极小 | 中 | **否决**：API 23 起废弃、官方文档明说不可靠；现代系统上不提供跨进程变更通知，仍可能读旧值/丢更新 |
| C. 每次 run 前重启 `:script` 进程强制重读 | 中 | 小 | 中高 | 仅调试/救急；会打断常驻进程里正在跑的任务 |
| D. 「一次性读取 + 写回广播」 | 中 | 中 | 中 | 只能做过渡：广播有时序、进程未启动收不到、仍不解决并发写丢键 |
| E. 自研 ContentProvider（对齐 Pro 的 Tray 思路，SQLite `pref(name,key,value)`） | 高 | 中 | 中（迁移/首启导入） | **Phase 1 第二批（推荐）** |
| F. 直接引 `net.grandcentrix:tray`（Pro 同款） | 高 | 小-中 | 中（库停更多年、AGP8/清单合并/并发需验证） | 备选：第二批先花半天验证 F，不通过再走 E |

## 6. 建议落地

### 6.1 Phase 1 第一批（本次迁移必须做；不新增依赖、不动 prefs 底层）

1. **`:script` 不写设置（写者唯一）**：`$settings.setEnabled` 不直接落盘，改为发回主进程。
   最小改法（不新增 AIDL）：复用现有 Messenger——服务端用 `RUN` 携带的 `msg.replyTo` 向主进程
   发一条新消息 `what=104 SET_SETTING {key,value}`，`PocScriptHost` 收到后转调主进程 `Pref`
   落盘。协议扩展点属 Phase1-B（`ScriptHostService`）/Phase1-C（`PocScriptHost`）。
2. **每次 run 下发设置快照**：`RUN{path,workDir,token}` 追加可选 `settings`（JSON 字符串）。
   `:script` 侧「参数优先、本地 prefs 兜底」，避免常驻进程读到旧值；第一批覆盖本次运行相关设置
   （脚本目录/日志目录/console 上限/`stable_mode`/引擎选择等）。
3. **`App.onCreate` 隔离进程判断泛化到 `:script`**（R6）：与 `:native` 合并成
   `isIsolatedScriptProcess()`，`:script` 也跳过定时任务/动态广播/示例同步。**这是集成必修**，
   否则 `:script` 会写主进程职责的状态。
4. **单脚本进程约束（R7）**：Phase 1 第一期路由默认全 `:script`（`PocScriptHost.isEnabled()` 已默认
   true）；`:native` 只作为回退开关。回退/调试时不要并行跑 `:native` 脚本；调试页/文档标注。
5. **生效语义写清楚**：第一批约定「设置改动 → 下一次 run 生效」；不要在 UI/文档承诺即时生效。
   设置页改动后可选「正在运行的脚本不受影响」提示。

> **落地现状（2026-10-18 核对）**：`ScriptHostService` 目前只有 `MSG_RUN=1` / `MSG_STOP=2` /
> `REPLY_STARTED/FINISHED/ERROR=100/101/102`，以及预留但未发送的 `REPLY_CONSOLE=103`；
> **尚未实现 104 SET_SETTING，也没有 RUN settings 快照**。native-process 已确认愿按本节方案实现
> （服务端用 `replyTo` 反向发 104、主进程落盘；RUN 可选 settings JSON、参数优先/本地兜底）。
> 若第一批决定落地，需 Lead 为 Phase1-B（服务端 `ScriptHostService`）与 Phase1-C（客户端
> `PocScriptHost`）各开一个后续小任务；task-13/14 完成时均未包含这两项。

> 第一批**不需要**做：ContentProvider、Tray、`Pref` 重构、`LocalStorage` 改造、prefs 迁移。

### 6.2 Phase 1 第二批（验收后/Phase 2，与 Pro 对齐）

1. 新增 `PrefContentProvider`（自研，`exported=false`，authority `${applicationId}.pref`，
   运行在主进程；SQLite 表 `pref(name,key,value)`，参考 Pro 残留实现）。
2. 首次启动把现有默认 prefs 导入 SQLite（一次性迁移，保留旧 XML 只读导入 + 回滚开关）。
3. `Pref` / 引擎 `core/pref/Pref.kt` / `Config` / `SettingsModule` 改为经 provider 读写；
   建议照 Pro 的 `TraySharedPreference` 写一个 `SharedPreferences` 适配器（`apply()` 空实现、
   写操作立即提交、监听用 `ContentObserver` 回调到 `OnSharedPreferenceChangeListener`），
   这样上层调用点几乎不改。
4. `LocalStorage` 维持现状（写者分区）；第二批验收时确认 `:native` 已退役或单进程约束仍生效。
5. 回滚策略：保留 `SharedPreferences` 实现一个构建开关，出问题可切回第一批行为。

## 7. 验收清单（真机）

- [ ] 主进程改「稳定模式/不显示日志」→ 常驻 `:script` 的下一次 run 生效（第一批）；第二批要求 ~1s 内生效。
- [ ] `:script` 里脚本 `$settings.setEnabled('stable_mode', true)` → 主进程设置页显示一致、杀进程重启后仍保持。
- [ ] 主进程设置页与脚本交替写不同键，不出现丢键（第二批 provider 专项；第一批验证写者唯一）。
- [ ] 强杀/崩溃后 prefs 不损坏、无键丢失（观察无 `preferences.xml.bak` 长期残留）。
- [ ] `:script` 进程 logcat 无 `TimedTaskScheduler`/`DynamicBroadcastReceivers`/`BundledSampleSync` 初始化日志（R6 修复验证）。
- [ ] 回退到 `:native` 时确认没有第二个脚本进程同时写 `storages`（R7）。
- [ ] 定时任务触发 → `:script` 运行 → 任务列表/停止正常（回归，与 prefs 无关但同批）。
