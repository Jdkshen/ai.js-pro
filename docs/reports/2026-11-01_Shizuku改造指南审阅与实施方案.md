方向可行：先让各运行进程可靠取得 Binder，再共用一个受控执行后端，最后接三引擎、终端和MCP。**不能直接粘贴原文整套实现**，尤其是“终端两套实现”“补Binder后三引擎自动可用”“返回与terminal_exec一致”三处与当前源码不符。

## 5. 建议实现架构

```text
主App / inrt 的Application
  -> 共享ShizukuClient：进程识别、早期多进程开关、Binder生命周期、权限状态
  -> 共享特权任务后端：execute/read/write/cancel + owner/executionId
       -> Java UserService/Binder（脚本高频调用优先）
       -> RishRuntime（终端命令入口）
  -> 三引擎门面 / App终端 / MCP终端
```

### A. 连接与状态

- 在Application早期阶段启用多进程支持；取Binder的ContentResolver调用按需在工作线程进行，不把它变成每次冷启动的同步等待。
- 每个进程一次初始化，注册Binder收到/死亡监听；未启动服务时保留可重试状态，后启动能够恢复。不能通过反复调用requestBinder堆积接收器。
- 返回真实诊断：`sdkSupported/binderAlive/permissionGranted/serverVersion/backendUid/processName/lastError`；查不到的字段为null，不能伪造false或2000。
- 普通shell默认仍为应用UID；只有明确选择Shizuku后端的调用使用授权身份。
- 主应用及独立APK都要声明Provider，authority用运行时实际包名；不能把主App已授权当成独立APK已授权。

### B. Rish资产与命令

- 推荐共享代码/资产放在`:engine`可复用的位置，避免只进主APK而遗漏inrt。原文手机导出的文件先作对照，正式集成需记录官方来源/提交、SHA和许可证。
- 私有目录惰性准备、校验和原子升级，不在App.onCreate吞掉全部异常后假装成功；跨进程同时启动要有文件锁。
- DEX须不可写；创建、完整性校验和替换流程应考虑加载时序，不只在使用前随手chmod。[Android动态代码加载要求](https://developer.android.com/about/versions/14/behavior-changes-14#safer-dynamic-code-loading)
- 使用实际`context.packageName`设置RISH_APPLICATION_ID，避免BuildConfig命名空间与运行时包名不同。仅对子命令设置，不修改所有引擎的全局动态库搜索路径。
- 保留官方rish参数传递，不把所有调用强制拼成一个`$*`字符串；终端仍为管道模式，不能把裸rish宣传成已获得PTY/全屏交互支持。[官方rish入口](https://github.com/RikkaApps/Shizuku/blob/master/manager/src/main/assets/rish)
- `i`应走明确的单包/split安装事务，支持中文空格/引号路径；私有目录APK不能假定shell UID能读取，使用受控暂存或从应用侧流式写入安装会话。默认不强加`-g --user 0`。
- ARM adb、自配对/自启动放后续可选工具方向；不为本轮客户端接入往主包塞整套工具链。

### C. MCP契约（建议新增，当前尚未存在）

优先给`terminal_exec`增加显式后端选择，缺省app；若保留原文工具名`shell_rish`，也让它创建同一任务系统的Shizuku任务，返回jobId，而不是伪称与旧同步返回相同。工具名称/别名/分类/Schema/说明/测试必须同时更新。

以下只是**拟定的新协议**，当前1303不能直接调用：

```json
{"name":"terminal_exec","arguments":{"command":"id","backend":"shizuku","timeoutSeconds":30}}
```

结果继续使用现有任务结构：`jobId/status/output/nextOffset/truncated/processActive/exitCode`，可增加`backend`与身份诊断字段；`terminal_read/write/stop`仍按jobId操作。沿用`requireExecution()`和参数验证。

特权任务必须持有远端命令句柄并按owner清理。现有应用UID的`kill(-pgid)`不能作为“远端shell及孙进程已退出”的验收证据；需验证超时、脚本停止、客户端死亡、MCP关闭后的远端清理。不得用kill整个Shizuku服务或其它任务兜底。

同步脚本结果建议保留`code/result/error`及非零退出时的stdout，不要把stdout清空并全部挤进error。连接/权限/超时/命令非零分别诊断。Node以Promise暴露，Rhino/QuickJS保持各自脚本线程调用方式；参数、结果与权限语义对齐，异步差异在文档中明确。

## 7. 集成验收清单

1. **权限/连接**：未安装、未启动、已启动未授权、拒绝/不再询问、已授权、撤销、服务死亡与重启，逐进程返回一致。
2. **三引擎**：同参数执行id、exit 7、stdout+stderr、无换行输出、超量输出、sleep超时；Node Promise和停止回收均验证。普通shell依然应用UID。
3. **终端/MCP**：两端共享实现但任务互不影响；测试stdin、offset/truncated、并发限额、取消清理，以及客户端断开/服务重启策略；不要只看本地rish进程结束。
4. **安装**：中文/空格/单引号/美元符号文件名、单包/split、私有路径、大文件、不足空间、签名冲突、当前用户、失败输出；安装完成再报告Success。
5. **资源与发布**：正常包/共存包/独立包的实际ID、Provider authority、RISH_APPLICATION_ID，R8保留、资产SHA、内置模板及外置模板边界。
6. **系统**：现1303的target28与另行提高target版本分别验证；Android14+只读DEX、真实Android17设备服务端兼容单独记录；原文手机fork的release崩溃拿到日志再定位，不以debug通过替代release验收。
