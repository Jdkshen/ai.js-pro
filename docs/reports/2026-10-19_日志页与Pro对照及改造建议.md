## 0. 结论（TL;DR）

1. **现有 Flutter LogPage 功能上已经覆盖 Pro FileConsoleView 的几乎全部行为**（解析/逐行着色/等级过滤/搜索/清空只清显示/自动滚底/虚拟化/首读 256KB 窗口/最大行数截断），还多了“加载更早/复制日志/断线保留上次内容”。**不需要重写，也不要大改。**
2. **“Phase1 后 Flutter LogPage 空白”是数据加载问题，不是渲染问题**：Flutter 调 `LocalBridge.call('logs')` -> `PocBridge`（PocBridge.java:149）-> `PocRuntime.logs()`（PocRuntime.java:568-624）-> `ScriptRunLog.listRecent(activity, 1)`（ScriptRunLog.java:133）-> `logsDir(activity)`（114-129：优先 `getExternalFilesDir(null)/logs`，异常/为空回退 `getFilesDir()/logs`）。**这个目录解析发生在主进程**；Phase1 后日志由 :script 进程的引擎写盘，若 :script 侧 `getExternalFilesDir(null)` 不可用而回退到 internal `files/logs`（或反之），两边就会扫不同目录 -> 主进程 `listRecent` 取不到文件 -> 返回空 content -> 页面空白。P0 修复应放在桥/引擎侧（联合扫描两个目录 + 诊断字段），**Flutter LogPage 一行都不用改**。
3. 视觉上 Pro 日志页 = **Compose 的 LogActivity + FileConsoleView（RecyclerView+TextView 逐行着色 + SwipeRefreshLayout + 100ms 轮询 + 菜单内等级 Spinner + ActionBar SearchView）**；我们是玻璃主题的 Flutter 独立页，语义对齐、视觉走自家设计。要“更像 Pro”只需 3 个小项（下拉刷新/等级文案与默认项/搜索框形态），合计约 0.5 人日，见 §2.3。

### 2.2 数据加载（P0 阻塞项，必须先修）

**现象**：Phase1 后脚本在 :script 跑，运行日志文件正常，但 Flutter LogPage 空白。
**链路取证**：`LocalBridge.call('logs')`（Dart 282-284）-> `PocBridge.java:149-151 case "logs"` -> `PocRuntime.logs()`（568-624）-> `ScriptRunLog.listRecent(activity, 1)`（ScriptRunLog.java:133-151）-> `logsDir(activity)`（114-129，**在主进程解析**：先 `getExternalFilesDir(null)/logs`，异常/为空回退 `getFilesDir()/logs`）。

**根因判断（按概率排序）**：
1. **两个进程解析出的 logs 目录不一致**：:script 侧 `ScriptRunLog.attach`（ScriptRunLog.java:105-111）用 :script 的 Context 解析目录；若 :script 冷启动时 `getExternalFilesDir(null)` 不可用（存储未挂载/权限时序）则写 internal `files/logs`，而主进程读 external `files/logs`（或反之）-> listRecent 扫空 -> content="" -> 空白。这也解释“文件正常但页面空”。
2. 主进程仍有一个**更新的空文件**（例如残留主进程引擎/历史文件）被 listRecent 的 mtime 排序取为第 1 个。
3. Flutter 首轮 readOffset 逻辑对空 content 的处理（概率低，PocRuntime 已做换行对齐）。
**最小修复（P0，改桥/引擎，不改 Flutter）**：
- 在 `ScriptRunLog` 增加 `listRecentAll(Context, int)`：同时扫描 `getExternalFilesDir(null)/logs` 与 `getFilesDir()/logs`，按 mtime 合并去重；`PocRuntime.logs()` 改用它取最新（必要时按需再取第 2 个给历史选择）。
- 返回 JSON 增加诊断字段（向后兼容，Dart 忽略未知字段）：`"dir"`（实际选中的绝对路径）、`"file"`（文件名）、`"mtime"`、`"candidates"`（各目录计数），便于真机定位是“目录不一致”还是“空文件”。
- `ScriptHostService` 侧统一用 Application Context 写日志，并在启动时把实际 logs 目录记一条日志，便于验证。
- 验收：运行 :script 脚本（Rhino+QuickJS 各一）-> 脚本结束后打开 Flutter 日志页，能看到本次日志；两处 logs 目录（external/internal）都不再“只有一边有文件”；脚本运行中每 0.5s 增量刷新。

## 3. 结论与落地顺序

1. **是否已足够接近 Pro：是**。数据/渲染语义已逐条对齐（§2.1 前 14 项全一致，且多出 3 项超集）。真正缺的是 **Phase1 后的数据加载**（P0）与 **3 个视觉小项**（P1/P2）。
2. 落地顺序（避免大改）：
   - P0（必须，先做）：桥侧联合扫描 external/internal 两个 logs 目录 + 诊断字段；验证 Rhino/QuickJS 日志页可见（0.5-1 人日，含真机验证）。
   - P1（样式，task-25 可直接做）：下拉刷新 + 等级文案/默认项（合计约 0.5 人日）。
   - P2（可选）：搜索框形态、历史日志选择（约 1 人日）。
3. **直接复用现有 Flutter LogPage**；不建议按 Pro 重写或改成 Compose。

## 4. 风险与注意事项

- **进程/目录不确定性**：Android 10+ 分区存储下 external files dir 一般稳定，但冷启动时序/多用户仍可能让一边回退 internal——所以必须“两目录联合扫描”，不能只依赖单一路径；诊断字段保留一段时间再考虑移除。
- **Pro 视觉基线不完整**：本次只有 Pro 面板截图（ap_log_open.png），独立 LogActivity Compose 页未截图（约束不跑 adb）；如 Lead 要求 1:1 验收，按 §1.3 步骤补图。
- **“八档”勘误**：按 6 档验收；若按 8 档做会让 task-25 返工（已实测 ConsoleActions.logLevels 仅 6 项）。
- **日志文件增长**：Pro 首读 256KB + 最大 10000 行；我们同参数，但“加载更早”会放大内存——已限制总行数（383-385），保持即可。
- **轮询与前台**：我们只在页面可见+前台轮询（231-245），符合省电；不要为对齐 100ms 改成常驻轮询。
