## 二、补齐评估 A：`AccessibilityServiceTool` —— **不是缺口，我们的更全**

| | Pro（`core.accessibility.AccessibilityServiceTool`，Kotlin object→Java） | 我们（`com.jdkshen.aijspro.tool.AccessibilityServiceTool`，325 行 Java） |
|---|---|---|
| 主要入口 | `checkAccessibilityService()` / `checkAccessibilityServiceBlocking()`（协程 + 阻塞双形态） | `enableAccessibilityService()`（阻塞式决策） |
| 启用路径 | `enableAccessibilityServiceByRootAndWaitFor`、`enableAccessibilityServiceBySecureSettings` | **Shizuku/secure-settings 快启（后台线程 + 4s 等待 + 失败回传 `getFastEnableError()`）**、root 路径（`Pref.shouldEnableAccessibilityServiceByRoot()`）、兜底 `goToAccessibilitySetting()` 引导 |
| 结果模型 | `CheckAccessibilityServiceResult` sealed（`Success`/`Failure`） | 无独立结果对象（布尔 + 静态错误串） |
| 探测命令 | `settings get secure enabled_accessibility_services` 的 shell 片段 | 走 `ShizukuShell`/`ProcessShell` 的既有封装 |
| 超时 | `WAIT_FOR_ENABLED_TIMEOUT = 2000` | 快启 4000ms（另有 `AccessibilityServiceUtils` 的等待工具） |

**评估**：**不需要照着补**。若想吸收 Pro 的形态，只值得做一件事：把「检查服务是否已启用」抽成一个**返回结果对象**的小 API（`Success/Failure + 原因`），供 UI/脚本调用；预计 **50–100 行**，复用 `AccessibilityServiceUtils`，风险低。

## 三、补齐评估 B：`NoMemoryLeakAccessibilityService` —— 真缺口，中收益/高风险

### 3.1 Pro 的做法（`android/accessibilityservice/NoMemoryLeakAccessibilityService.java`，72 行）

- **包名占用**：把类放进 **`android.accessibilityservice`**（框架包），从而 `extends AccessibilityService` 并能访问其非公开成员 —— 这也是它为什么不会出现在「Pro 业务类」的常规统计里（它不在业务包，属于 Pro 自己塞进框架包的类）。
- **反射隐藏字段**：构造函数抓 `AccessibilityService.mGestureStatusCallbackSequence`、`mGestureStatusCallbackInfos`、`mLock`。
- **修补**：`dispatchGestureNoMemoryLeak()` 在 `mLock` 内调用 `dispatchGesture(...)` 并读回 callback sequence 号；`removeGestureCallbackInfo(int)` 事后从 `SparseArray` 里删除该回调；另有 `nativeDispatchGesture(...)`（native 变体）。
- 目的：框架的 `dispatchGesture` 会在 `mGestureStatusCallbackInfos` 留下回调条目 —— 长跑/高频手势场景会累积（内存泄漏）。

### 3.2 我们现在的状态

- `com.stardust.view.accessibility.AccessibilityService` 直接继承 **`android.accessibilityservice.AccessibilityService`**；**我们仓库没有 `android.accessibilityservice` 包**。
- 手势路径在 `GlobalActionAutomator.kt`（`dispatchGesture` + `GestureResultCallback`）、`AutomationHostBackend.java`（binder 线程派发 + 超时等待）、`ScreenCaptureAutoConsent`（自动同意截图）。**没有任何回调表清理**。

### 3.3 评估

| 维度 | 判断 |
|---|---|
| 收益 | 中：只影响**高频/长跑手势**场景；普通脚本（偶发 click/swipe）几乎无感 |
| 风险 | **高**：① 反射 `mGestureStatusCallbackInfos`/`mLock` 属隐藏 API，Android 高版本 hidden-API 名单与字段改名会让它失效（要 `try/catch` 降级）；② **占用 `android.accessibilityservice` 包名**在 App 里可行但脆（类加载顺序、加固/多 dex、与框架类同名冲突）；③ 我们的无障碍服务已多处自定义（多进程宿主 `AutomationHostService`），改基类影响面大 |
| 前置 | **先量再改**：跑「连续 N 次 `dispatchGesture`（如 10k）→ 观测 `mGestureStatusCallbackInfos.size()` 是否单调增长」；不增长就不必修 |
| 建议实现 | **按行为自研**：在我们自己的类里做「锁内 dispatch + 记录 sequence + 完成后 remove」，反射失败就退回原行为；**不搬运反编译代码** |
| 工作量 | 自研约 **100–200 行 + 真机泄漏量测**（含降级路径与单测/真机验证） |

### 3.4 ⚠️ 来源与合规（必须先说）

Pro 是**闭源商业版**；仓库里 `.artifacts/pro-*/` 与本次上传的 `源码树/` 都是**反编译产物**。把它们的代码直接搬进我们的仓库有**合规风险**。建议：**只把「问题现象 + 修复思路」作为需求输入**，实现与命名都用我们自己的形态（例如 `LeakSafeAccessibilityService`），并在提交信息里写明「思路来源：对 Pro 9.3.11 行为的观察」，不复制其代码/注释。

## 四、下一步（按性价比排序）

1. **量泄漏**（半个上午）：写一个真机脚本连续 `dispatchGesture` 若干次数，观测回调表增长 —— 决定 B 要不要做。
2. **A 的小 API**（低风险，50–100 行）：`checkAccessibilityService(): Result{Success|Failure(reason)}`，复用 `AccessibilityServiceUtils`。
3. **159 真缺口的「功能级复核」**（1–2 天）：把 `core.image`(6)、`project`(6)、`com.stardust.app`(4)、`core.console`(4)、`core.pref`(3)、`core.timing`(2) 这些**非 V8** 的条目逐个查「我们是否已有等价实现（换名/换模块）」，产出「真缺 / 已等价」终表；V8 线 ~30 个不必逐条核（整条线都没有）。

## 五、边界

- Pro 侧是反编译产物：`com.stub.*`(544) 不在业务树、Dex2C 的 2,622 个 native 方法体看不到、101 个类只有 smali（本次统计只覆盖有 `.java` 的 505 个业务类）。
- 「真缺口」只按**名字**判定，不含功能等价复核；「假缺口」也只按**简单名**命中判定（同名不同职责的极小概率未排除）。
- 本轮**未做任何真机实验**（泄漏量测、无障碍启停、启动耗时都还没跑）。
