## 3. 与方案有意偏离的三处（都有实测依据）

1. **§3.4 的「缩放到 192×192 + CLAHE」没做** —— 实测（`tools/ocr-prep-probe.js`，两帧 20/21 格 × 10 种预处理）：
   - 放大：2× 37→45ms、3× 63→77ms，识字数**不升反降**（det 阶段本来就会把长边归一到 `targetSize`）；
   - 二值化（Otsu 各档）：识字 **3~12/20**（现状 17/20），木纹被切成斑块、笔画断掉；
   - **灰度**：识字持平略升（第二帧 18/21），每格还快 ~8ms；但会把一部分原本读对的读错（馬 1.00→志 0.67）。
   ⇒ 落地为「**彩色优先，灰度只当重试**」（且必须那格确实有墨迹才重试）；真机：`全盘 OCR：灰度重试救回 3 格`。
2. **§3.5 的门槛 0.70/0.55 改成 0.6/0.45 + 共识闸门** —— 0.70 会把 `将 0.74`、`帅 0.51` 一起挡掉。
   现在的做法是「低分先记 `?`，由规则层/多帧共识决定」：写可靠基准要**连续 2 帧一致**（翻色 3 帧）+ 分数 ≥0.6 + 像素颜色不冲突。
3. **§3.6 的颜色算法从 Lab/HSV 特征改成「引擎找色计数」** —— 用户口径「新引擎不是有找色的案例吗」。
   原生 `images.findAllPointsForColor` 逐通道容差，实测红/黑墨迹命中数是**数量级**分开的，
   比阈值特征稳，且**22ms/32 格**（老的逐点采样 137ms）。

## 4. 主要缺口（按优先级）

### 缺口 1（最高）：§11 的验收指标没有成体系地跑过
现状只有零散日志。要把它们变成**可复现的数字**，需要一条「验收式」统计：
- 开局静止帧连续 N 次识别 → 32 子全对率、未知格数分布；
- 一局连续走 N 回合 → 错点/重复点/轮次错判/非法点击计数；
- 红黑准确率（可用「找色计数 + 人手核对」当近似真值）与字形准确率。

现成可挂的东西：`tools/ocr-benchmark.js`（耗时 + 代理准确率）、`tools/board-replay-test.js`（历史帧回放）、
以及本轮的**场景回归框架**（`tools/run-regress.js`，适合放「判定逻辑」；统计类适合做成独立入口）。

### 缺口 2：§7 性能预算与实测口径不一致
方案按「单次完整识别 ≤1.2s」算；真机一轮观察 **7~11s**（含 2×shell 抓帧 ~1.2s/帧 + 全盘 OCR 2.7~3.3s + 驱动循环）。
两者口径不同，但**全盘 PP-OCR 2.8s 也确实超出方案给的 800ms 临时预算**。要么明确「预算按识别段计」，
要么走阶段 D（专用模型）把 32 格压到 ≤260ms。

### 缺口 3：阶段 D 专用字形模型未做
数据脚本已有（`tools/collect-piece-samples.js`）。它是把「字形准确率 ≥98.5%」和「32 格 ≤260ms」
两个指标同时解决的正道 —— 也顺带解决帅/将那类难字。

### 缺口 4（小）：`overlay-draw` 在真机上的可用性没有结论
代码与面板接线都在，但没有「打开后确实画对了」的真机截图结论。

## 6. 性能分期落地（2026-09-20 晚，K40 真机实测）

用户选了「先只做性能分段计时」。做法：
- 新增 `src/runtime/timing.js`（纯 JS 分段计时，PC/真机同一份）；
- `board-service.recognizeSmart()` 打点：**抓帧（含藏窗）/ 稳定帧 / 流水线 / 退回旧路径 / 收尾**，并暴露 `lastTiming()`；
- `vision-pipeline.recognize()` 内部打点：**检测(YOLO) / 逐格(OCR+找色+融合) / 抢救·规则补全 / 收尾**，挂在 `result.timing`；
- 面板每轮观察打一行（限频 2s），形如：

```
耗时分期（最近一次识别）：抓帧（含藏窗） 927ms｜稳定帧 2ms｜流水线 169ms｜收尾 0ms｜合计 1098ms
  ｜流水线内 检测(YOLO) 29ms｜逐格(OCR+找色+融合) 137ms｜抢救/规则补全 1ms｜收尾 1ms｜合计 168ms
```

真机连续三帧：

| 轮次 | 抓帧 | 稳定帧 | 流水线 | 流水线内（YOLO / 逐格） | 本轮观察 |
|---|---|---|---|---|---|
| 1 | 927ms | 2ms | 169ms | 29 / 137ms | 5581ms（同一 tick 里还跑了 2.2s 的全盘 OCR） |
| 2 | 913ms | 1ms | 251ms | 35 / 213ms | 2759ms |
| 3 | 933ms | 2ms | 354ms | 37 / 314ms | 2841ms |

**结论（第一次把「7~11s」拆开）**：
1. **抓帧是绝对大头**：shell `screencap` ~930ms/次；而驱动一次观察默认抓 **2 帧**（`observeFrames=2`）⇒ ≈1.9s，占本轮观察的 **~2/3**；
2. **流水线本身很便宜**：0.17~0.35s（YOLO 29~37ms、逐格 137~314ms、抢救/规则门 ~2ms）—— 逐格这么快是因为静止盘面命中**逐格缓存**（日志 `OCR 成功 28／缓存 24`）；
3. **全盘 OCR 对照**每 15s 一次、单独 2.2s，不是每轮成本，但会把那一跳的「本**轮**观察」撑到 5.5s；
4. 剩下的差额是稳定帧采样 + 驱动内部簿记 + `tickMs=2400` 的调度等待。

⇒ 方案 §7 的「单次完整识别 ≤1.2s」按**识别段**算其实**已经达标**（1.10s / 1.17s / 1.29s，几乎全是抓帧）；
真正该优化的是**抓帧次数**（能不能只抓 1 帧做观察、或换更快的抓帧通道），而不是 OCR。

### 6.1 抓帧快通道落地（raw RGBA，2026-09-20 晚，K40）

拆解（各 3 次取中位数）：`screencap -p`（PNG）**893ms** / 其中 PNG 编码 ~700ms；`screencap`（raw）**194ms**；
`images.read` 解码 56ms；写到 `/data/local/tmp`（绕开 FUSE）897ms ⇒ **瓶颈是 PNG 编码，不是写盘**；
MediaProjection 那条路 1078ms（ póź 315ms），都不如 raw。

做法（用户选的「B 方案」）：
1. **引擎加 `images.readRaw(path, width, height)`**（`quickjs_jni.cpp`，纯 C++，不涉 Java）：
   `screencap`（不加 `-p`）写出的文件是 **16 字节头 + RGBA 像素**（头 = int32 宽｜高｜格式)｜保留，
   PC 侧逐块比对确认：`header=16 + RGBA` 误差 **0.00**，BGRA 误差 40+ ⇒ **不用换通道**）；
   原生侧自动识别有无头（头里的宽高对得上就跳 16 字节），再用 `NativeFrameStore::createFromRgba` 建帧。
   改完必须跑 `modules/engine/src/main/cpp/build-quickjs.ps1` 重编 `.so`并重打 APK。
2. **适配器**（`aijs-adapter.captureViaShell`）raw 优先、PNG 兜底，并把通道名写成 `shell(shizuku/raw)`；
   能力探测只做一次（失败就别每帧白试）；新增 `capabilities().imagesReadRaw` 与 `shellCaptureInfo()`。
3. ⚠️ **面板原来自己写了一遍 shell 抓帧**（`grabFrameRaw()` 里裸调 `screencap -p` + `images.read`）⇒
   引擎刚加的快通道在面板这条路上**根本用不上**（真机：适配器 202ms vs 面板 1011ms）。
   已收口：面板改用 `adapter.capture(...)`；`adapter.readImage()` 支持**帧直通**（raw 帧没有磁盘路径，
   而 `locateBoardInImage()` 原来是「拿路径再读一次」，现在传帧就不必重复解码）。

真机结果：

| 指标 | 改前 | 改后 |
|---|---|---|
| `adapter.capture('full')` | 921ms | **202ms** |
| 面板一轮观察里的「抓帧（含藏窗）」 | 1011 / 1157ms | **195 / 218ms** |
| 单次识别合计 | 1.10~1.38s | **0.30 / 0.53s** |
| 一轮观察（墙钟） | 2948 / 5824ms | **1565ms**（首次 3922ms，同 tick 里还跑了 2.8s 全盘 OCR） |
| 识别结果 | 确认 20~21／未定 4~5、规则门通过 | **一致** |
| raw 与 PNG 同帧像素对照 | —— | **6/6 一致** |



## 6.2 「其他时间呢」——一轮决策的完整账（2026-09-20 夜，K40）

依赖 top ocrBoard 6003ms×2｜tap 981ms×2｜foregroundGuard 51ms` —— 即一招 = 6 次识别 + 2 次全盘 OCR + 2 次点击 + 1 次面板对照。

### 根治：空框格先找色，再决定要不要 OCR（`board-scan.inkGate`）

**为什么贵**：`board-scan.scan` 对 90 格逐格 `session.detect`（≈34ms/格）⇒ 2.9s；而它只想找「模型漏检/误读」的证据。

**为什么能跳**：空格子里没有墨迹，而有子的格子一定有。引擎找色是**原生**实现，实测比 OCR 便宜两个数量级。

探针 `tools/board-scan-cost-probe.js`（同一帧，K40）：

| 阶段 | 结果 |
|---|---|
| A 现状全盘 scan（90 格都 OCR） | **2895ms**，28 格有字，灰度重试 11 次救回 9 格 |
| B 90 格逐格找色预筛 | **19ms（0.2ms/格）**；有墨迹 30 格 = 恰好是全部有框的格子；无墨迹 60 格；**假阴性 0** |
| C 只扫「有框 ∪ 有墨迹」 | **1015ms**，读到 28 格，与 A 逐格结论**完全一致（0 处不同）** |

落地后（真机面板日志）：

| 指标 | 改前 | 改后 |
|---|---|---|
| 面板「全盘 OCR 对照」 | 2797~3027ms | **945 / 947ms**（`跳空框无墨迹 60 格`） |
| 驱动依赖 `ocrBoard` | 2967~3019ms | **1155 / 1167ms**（长 tick 里两次 = 2363ms） |
| 证据能力 | —— | 仍然抓到真漏检并改正：`(2,3)空→C(OCR 炮)`、`(4,6)空→c`、`(4,5)空→c`、`(6,3)空→C`、`(7,2)空→c`；`全盘 OCR 证据（模型漏检） c（下标 40）` |
| 识别结果 | 规则门通过、确认 30／未定 2 | **不变**（规则门通过、确认 26／未定 3） |
| 离线套件 | 自检 199、契约 19、场景 8/8 | **自检 200**（+1 条闸门用例）、契约 19、场景 8/8 |

⚠️ 闸门的三条守则（都有自检/实测证据）：
1. **没框但有墨迹 ⇒ 照样 OCR**（漏检证据不能丢；真机上正是这批格子被改正）。
2. **没有找色能力的宿主（Rhino/离线夹具）自动关闸**，回到「逐格都试一次」的老行为。
3. 被跳过的格子**照样把「无证据」写实**（`chars=null`、`sides=UNKNOWN`）——不写就是稀疏数组，下游 `=== null` 判断会踩空。

## 6.3 第二轮：复用「刚读过的证据」+ 几何沿用（2026-09-20 深夜，K40）

### ① 全盘 OCR 询问：2967ms → 1155ms（找色闸门） → **1155ms → 292ms（复用）**

**思路**：驱动每 ≥6s 要一份「全盘 OCR 证据」，而面板**刚为同一帧**读过那些格子（OCR 字形 + 找色颜色）——
同一份东西重读一遍纯属浪费（1155ms 里 ~950ms 是那 28 格的 OCR）。

实现：`board-scan.reuseFromEvidence(evidence)` 把流水线 `result.evidence` 摊成 `scan({ reuse })` 载荷；
面板 `rememberPipelineEvidence()` 记住证据（≤3s 且几何未变才复用）。
**只复用够确定的格**（有字形、分数 ≥0.6、颜色已定）——其余仍由 `scan` 自己读（灰度重试就出在那批格上）。

| 阶段 | 面板「全盘 OCR 对照」 | 驱动依赖 `ocrBoard` |
|---|---|---|
| 原始 | 2797~3027ms | 2967~3019ms |
| + 找色闸门 | 945 / 947ms | 1155 / 1167ms |
| + 复用同帧证据 | **55 / 55ms**（`复用上次识别 27~28 格`） | **292 / 293 / 308ms** |

（询问的 292ms = 抓帧 ~200ms + 检测 ~40ms + 找色 19ms + 0 次 OCR。）
沿用不变：漏检改正照旧落地（`(7,2)空→c(OCR 炮)`、`全盘 OCR 证据（模型漏检） c（下标 25）`）。

### ② 一条死路（已测量，别再试）：整盘一次 `detect` 拿不回逐格字形

探针 `tools/ocr-batch-probe.js`：

| 路 | 结果 |
|---|---|
| A 逐格 detect（现状） | 1073ms（32 格） |
| B 整盘裁剪一次 `detect(clip, { max: 60 })` | 696ms，**只回 16 块**：PP-OCR 把整行字合成一条文本行（`車馬象士将士象馬車`），且**没有 bounds** ⇒ 无法映射回格子 |
| C 整帧 + region 一次 detect | 689ms，同上 |

⇒ 逐格裁剪 + `detect` 是这套后端唯一能拿到「每格一个字」的路，**别为省时间改批量**。

### ③ 重定位：**8397ms → 361ms**（几何沿用快路径）

账本揪出来的单项最大：恢复路径一触发就是 `校准完成…用时 7975ms` —— `calibrateGrid` 把 ~40 个候选
**逐个整帧识别**一遍。但棋盘压根没动（`几何 v1` 一直没变）⇒ 纯白等。

实现：`tryReuseGrid()` —— 已有几何时先做两道路验证：① `grid-sanity` 行体检（抓「整行偏」）
② 用现几何真读一帧，未定格 ≤4。两道路都过就**直接沿用**，否则老实走全量。

真机：`几何沿用（体检过 + 未定 0 格，用时 117ms，省掉全量校准）｜几何 v1`、`重定位 1 次共 361ms`（同一场景此前 8397ms）。

### ④ 现在的稳态账（K40，恢复/等待状态）

```
tick 1.2~2.3s｜守前台 ~0.1s｜驱动 1.1~2.2s（识别 2 次 0.84~1.4s｜重定位 0~0.36s）｜全盘 OCR 0~0.5s
```

剩下的最大单项就是**每次观察的 2 帧**（`observeFrames:2` + `observeGapMs:260`）≈0.85~1.4s ——
它是「防动画中间帧 + 让融合两帧确认」的保险；要动就得先想清楚点击后的确认延迟会不会变长（建议做成可配置项做真机 A/B）。

### ⑤ 调试用的「全盘 OCR 对照」：默认关；开着也白拿（**894ms → 0ms**）

它是 2026-09-19 排查「黑炮凭空消失」时加的**调试日志**，之前每 15s 在 tick 里花 ~900ms（抓帧 + 检测 + 扫描）。
两处改动：
1. **默认关**（`autorun` 里显式写 `"ocrBoard": true` 才开）—— 驱动自己的「全盘 OCR 证据」日志
   （`全盘 OCR 改正／对账：无可改正`）已经把同一件事说清楚了，日常跑不需要它。
2. 开着时**只用「刚识别过的那一帧」的逐格证据**拼盘面（`ocrBoardFromLastEvidence()`）：0 抓帧、0 检测、0 扫描；
   证据不新鲜就**跳过**并说明原因，绝不为一行调试日志去花 900ms。

真机：`全盘 OCR 对照（读到 22 格有字；复用上次识别的 27 格逐格证据，未覆盖的格不参与比对，用时 0ms）`（4/4 都是 0ms）
+ 启动早期一次 `对照：跳过（没有新鲜的逐格证据，不另花一次抓帧+扫描）`；差异行照旧（`差异 6 处：(4,0)驱动k｜OCR没看到；…`）。

⚠️ 这条「白拿」路**只给对照日志**：驱动要的那份证据必须真扫（`ocrBoard()`）——
它的价值就在「**没框但有墨迹**」的漏检候补格（流水线只看有框的格，见 §6.2）。

## 6.4 A/B：把每次观察从 2 帧降到 1 帧？（2026-09-20 深夜，K40）

**为什么要试**：所有其它大头都降完之后，稳态里最大的单项就是**每次观察的 2 帧**
（`observeFrames:2` + `observeGapMs:260`）≈0.85~1.4s/tick。它在结构上是「防动画中间帧 + 让融合两帧确认」的保险。

**怎么做的**：面板新增两个可配置项（autorun 里写，默认仍是 2 帧/260ms，驱动侧 clamp 到 1~3）：
```json
{ "observeFrames": 1, "observeGapMs": 260 }
```
启动日志会写明 `观察帧数：1 帧（间隔 260ms；默认 2 帧/260ms）`；汇总用新工具
`tools/analyze-panel-log.py`（一次给出：出招/确认次数、**确认耗时**、未看清/帧不稳定/规则门否决/恢复次数、
tick 与观察耗时中位数、各依赖合计）。

**结果（各跑 3 分钟，同一台机、同一局面的相邻时段）**：

| 指标 | 2 帧（默认） | 1 帧 |
|---|---|---|
| tick 中位 | 1919ms | **1029ms**（−46%） |
| 观察中位 | 1540ms | **923ms** |
| 该时段 tick 数 | 52 | **3** |
| `确认：UNRELIABLE：有 1 处关键冲突` | **0** | **348**（每次还带一行「确认观测」dump） |
| 帅/将抢救 | 208 | 701 |
| 出招 | 0 | 1（随后卡在确认里空转） |
| 恢复 | 9 | 0 |

**结论：1 帧不能直接换上去。** 速度红利是真的（每 tick 省 ~0.9s），但代价是**点击确认路径反复 UNRELIABLE**
（同一观测连续 348 次）、面板 tick 几乎停摆（3 个/152s）——驱动在「确认/恢复」子循环里空转，
比省下的 0.9s/tick 亏得多。

⚠️ **这次 A/B 有污染**：这一局本身卡在已知的「对方在途棋子永不落位」状态（2 帧那组也 0 出招、恢复 9 次），
`UNRELIABLE` 也可能是那 1 处关键冲突放大的结果 —— 所以严格说只得到一个**保守结论**：
**「1 帧」没有体现出净收益，默认保持 2 帧。** 要真正量化「确认耗时/误判率」，得在**新局面**上再跑一轮。

**如果还想要那 0.9s/tick**，正确的切法是**按状态给不同帧数**（还没做）：
等对方/待稳定时 1 帧（只看变化），出手前后与确认时 2 帧（要稳）——这需要在驱动侧把 `observeFrames`
从常量改成「状态相关」（或加一个 `framesForState` 钩子），并且要用新局面重跑 A/B 才能下结论。

## 6.5 新局真机对局实测（2026-09-20 深夜，K40）——能走了，但每两手会被「动画帧」打断

前几轮都是在一局**卡死的残局**上做性能；这次换成**全新开局**（0 步、全子齐备）跑 3.5 分钟，
用 `tools/analyze-panel-log.py` 汇总：

| 指标 | 数值 |
|---|---|
| 出招 | **5 次（1.4/分）** |
| 确认 | CONFIRMED 4｜UNEXPECTED 3｜其它 6 |
| 确认耗时（点击 → 确认） | 中位 **2184ms**｜最大 2766ms |
| tick / 观察耗时 | 中位 1954ms / 1227ms |
| 驱动询问 `ocrBoard` 合计 | 8949ms（≈0.3s/次，性能改造后的常态） |
| 未看清 / 帧不稳定 / 规则门否决 | 1 / 2 / 0 |
| **恢复 9 次｜「轮次推不出来」32 次** | ← 就是下面这个卡点 |

### 卡点：对方应手的**动画中间帧**（同一枚子同时出现在起点与终点）

13:14:22.926 点击 `g6g4` → 13:14:25.396 判 **UNEXPECTED**，紧跟两次恢复、然后 **30 秒** 的
「轮次推不出来（UNKNOWN）：既没有合法单步也没有「一步+应手」能解释」空转（每 1.9s 一次观察，白跑）。

日志把真因写得很清楚（`确认观测` 与 `期望` 的 FEN 差 **1 格**）：

```
确认观测：2bakabr1/r8/1cn3nc1/p3p3p/1n7/6C2/P1P1P1P1P/4C4/9/RNBAKABNR
期望：     2bakabr1/r8/1cn3nc1/p3p3p/9/6C2/P1P1P1P1P/4C4/9/RNBAKABNR b - - 0 1
                                  ↑ row4 多了 1n（黑馬），而**没有任何一格少子**
```

* 观察里凭空**多了一枚子**（33 枚）⇒ 任何一步棋都解释不了 ⇒ 验证器只能判 UNEXPECTED（作废票据 + 恢复）；
* 同一帧前后还出现 `单格重拍没找回（降阈值重认仍为 (2,2)=空（已知事实 n））` ⇒ 那枚馬的**起点格在同一帧读不出**：
  典型的「棋子在起点与终点同时可见/起点先花掉」的**动画中间帧**（人机对战应手很快，在我方确认还没走完时就动）；
* 更麻烦的是 `全盘 OCR 改正 1 格：(1,4)空→n(OCR 馬)` + `待定 1 格…连续 2 帧一致才写基准`：
  这套「OCR 证据」会把动画中间帧的**伪影**当成漏检证据 → 一旦凑够 2 帧就可能写进基准 ⇒ 之后每一帧都对不上 ⇒ 30s 空转。

### 待修的三个点（按性价比）

1. **验证器：认出「动画重复子」**。现在 `OPPONENT_REPLY` 的容差只允许差异落在我方落点/应手落点两格（≤2 格、
   且必须是同色异兵种或读成空）；应手**动画**那种「多一枚同型子、没有格子少了子」的形状一律落空 ⇒ UNEXPECTED。
   建议：新增一条「动画中」判定（多子 = 起点未清 / 起点读成空），返回 **UNRELIABLE（等下一帧）**而不是 UNEXPECTED + 恢复。
2. **推断路径同样要给这条容差**：`轮次推不出来` 的 30s 空转就是在拿「多一枚子」的盘面去套「一步 / 一步+应手」，
   永远套不上。判定为动画帧时应当**跳过推断**、等下一帧（现在的看门狗是 8s，等到动画结束早就够了）。
3. **OCR 证据闸门**：`applyOcrBoardFixes` 的「连续 2 帧一致」在**动画帧**上会凑成事实。
   建议在写入基准前加一道「该格在本帧的像素/字形是否稳定」的判据（或要求两帧**间隔 ≥6s 且帧间该格无变化**，
   而动画帧的变化恰好会被这一条挡住）。

⚠️ 这三条都是「让状态机在动画期间**等**，而不是**改**」的思路 —— 和仓库里既有的事故记录一致
（「跨帧佐证拦不住它」「别在补齐表里打补丁」）。性能侧的账（§6.2/§6.3）在这局里已经完全兑现：
驱动询问 0.3s/次、重定位 0.4s、对照 0ms，剩下的时间大头是**识别本身**与上面这些**动画期空转**。

## 6.6 「用视觉重新对局面」（用户口径）——恢复后按观测重建基准（2026-09-20 深夜，K40）

### 为什么需要
上一节（§6.5）的卡点再往下一层是：**驱动的「已知事实 / 可靠基准」会反过来压住视觉的新读数**。
真机铁证（新局 h4h9）：

```
13:43:14.020 可靠基准已按观测改正那格（(4,2) 置空）
13:43:14.021 票据里的盘面已按当前基准重建：h4h9｜新 base=…/n5nc1/…   ← 黑炮被从基准里删掉
13:43:14.028 确认：UNEXPECTED：与基准差 3 格：(7,0) r→C；(7,5) C→空；(4,6) P→c
```

对方那枚炮**在飞**（画面上是隐形的），单格 OCR 隔 1.5s 连读两次「没字」就被当成空格 →
那枚子从基准里被删掉 → 它落位时「期望里没有、观测里有」→ 永远解释不了 → 恢复 → 空转 30s。

### 改法（两条，都是「按视觉为准」）
1. **单格 OCR 判空门槛 1500 → 3000ms**（`ocrEmptyCorroborateMs`）：飞行 + 命中特效 + 高亮环能让一格
   隐形 2 秒以上；真·卡死仍由后面的「连续读空 N 帧 → 催游戏 → 仍不行才放弃」兜底。
2. **恢复后按观测重建基准**（`recover()` 置 `needFreshBaseline` → `rebuildBaselineFrom()`）：
   丢掉全部已知事实，**基准 = 本帧视觉读数**（YOLO 定位 → 找色 → OCR 融合本来就是逐帧重读的），
   轮次交给下一帧的变化去推。两个守卫：① 未知格 ≤ `rebuildMaxUnknown`（2）；
   ② 每个未知格都能用旧事实填上（可靠基准不能含 `?`，填不上就等下一帧）。
   ⚠️ 这条思路来自用户：「不是可以用 yolo 重新来点位 再颜色判断 再重新对局面？」—— 完全正确。
