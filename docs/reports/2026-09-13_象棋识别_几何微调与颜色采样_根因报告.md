# 几何自动微调（autoAlign）与颜色采样：根因报告（2026-09-13）

执行单 §9「第二批」里那条 **「缓存框几何对颜色不利的根因」** 结案报告。
结论先说：驱动侧那串「非法局面」不是漏检，也不是几何定位错，而是 **`autoAlign` 把几何挪到了
颜色采样不能待的位置**；而历史上被当成「定位系统性偏差」的那个 `(-7,-14)`，
其实是**检测框自身的偏置**，不该靠挪几何去凑。

状态 RECOVERING｜算棋失败：…

新增取证探针 `tools/p4-align-debug.js`（设备端）：抓一帧 → 定位 + 会话级校准 → **只做一次检测**，
把「检测框 + 几何 + 两种几何策略的结果」落盘成 `/sdcard/xiangqi-p4/align-debug.json`，
PC 上就能离线重放这个决策（不用每次上手机）。

### 同一帧、同一个校准几何，三条读数对照

| 几何 | 布局串 | 结果 |
| --- | --- | --- |
| 原始定位几何（未校准） | `RnbakabnR/9/1C5C1/P1p1P1p1P/9/9/P1P1P1P1P/1C5C1/9/rNBAKABNr` | ✗ 颜色错（红黑对调一片） |
| **校准后的几何（校准 v1，偏移 -6,-3）** | `rnbakabnr/9/1c5c1/p1p1p1p1p/9/9/P1P1P1P1P/1C5C1/9/RNBAKABNR` | ✓ 合法开局 |
| 按检测框拟合挑出的偏移 **(12,6)** | `rNbakabnR/9/1C5C1/P1P1p1P1P/9/9/P1P3P1P/1C5C1/9/RNBA1ABNR`（红 28 / 黑 2） | ✗✗ 非法 |

每格「红笔画占比 / 暗笔画占比」（`piece-side` 的判定输入）：

```
校准几何：  0,0=R:0.180/0.158  1,0=N:0.158/0.168 … 0,9=R:0.440/0.000  4,9=K:0.391/0.000
(12,6)：    0,0=R:0.191/0.153  1,0=N:0.195/0.162 … 0,9=R:0.475/0.000  4,9=K:0.439/0.000
```

校准几何上黑方子「红 / 暗 ≈ 0.15/0.16」势均力敌 → 判黑 ✓；挪到 (12,6) 之后所有子的红占比
整体抬高（0.15 → 0.19），越过 `redShare > darkShare × 1.2` 这条线 → 黑子被判成红子 ✗。

**根因**：`piece-side` 的采样框是「格距的 84%」且**以交点为心**。棋子画在交点上，所以采样框
必须框住棋子；而 `alignGrid` 的目标是「让检测框心贴近交点」——两个目标**不是一回事**：
检测框本身带 ~12px 系统性偏置，把它当基准去挪几何，就把采样框推离了棋子中心，
木纹（偏红）大量进入采样框。校准（`calibrateGrid` 用「修复动作数 + 未知格」评分）恰好压住了这一点，
所以「校准后正确、微调后又错」——正是执行单里那条「缓存框几何对颜色不利」。

## 二、修法（两处，都在 `src/vision/recognizer.js` 的 `alignGrid`）

### 1. 挑选目标改成纯几何（旧目标有病，而且不幂等）

旧目标：**出界框最少 → 残差和最小 → 冲突最少 → 未知格最少**。

- 「冲突 / 未知格」是**分类阈值的产物**（`maxResidual` / `conflictGap`），不是几何质量。
  把它们放进目标 = 奖励「把边缘框刚好推过阈值」，于是选出的几何会把噪声框也认成子。
- 该目标**不幂等**：挪完几何后「未知格 / 冲突」又变了，于是每帧在 `(0,3)` / `(0,-3)` 之间来回，
  几何版本被反复 +1（真机日志里那串 `几何按检测框微调：原点偏移 (0,±3)` 就是它）。

改成：`cost = Σ score × min(1, 框心到最近交点的归一化距离)`（分数加权、封顶 1，<0.2 分的框不参与），
**只看框与点阵的贴合度**；要求相对改善 ≥ 15%（`minGain`）才动，同代价取位移更小的。
纯几何代价是「(框, 偏移)」的纯函数 → 幂等，挪到位后下一帧增益为 0、不再动。

### 2. 给位移加上限 `maxApply`（默认 6px）：大位移一律拒绝

几何有两个消费者：

- **框归格**：用「最近交点」，0.4 格（≈46px）以内的偏置都扛得住，不需要靠挪几何帮忙；
- **判阵营的像素采样**：以交点为心、格距 84% 的框，**离不开颜色校准过的位置**。

所以几何该按后者选（校准已经做了），前者本来就不需要救。真错位几十像素时不该偷偷微调，
那是 `suspect`（框大量出界 / 框心整体远离）→ 状态机 `RECOVERING` 重新定位的活。
报告字段新增 `refused`，把「想挪但被拒」的原因写出来，便于诊断。

对应断言（`tools/self-check.js`，105 → **111**）：对准时不挪 / 连跑两次第二次不动（幂等）/
12px 偏置拒绝并报原因 / 位移在 `[minApply,maxApply]` 内才改几何并把版本 +1 /
小于 `minApply` 只改本帧读数 / 40px 错位不硬凑且报 `suspect`。

## 五、遗留与建议（未动手，先记录）

1. **检测框偏置应该在「框侧」补，而不是挪几何**：把「框心 − 最近交点」的中位数当作
   `boxBias` 减掉再归格/拟合几何。本次没做（会动识别主链，需要单独验收）；
   本报告的 `align-debug.json` 就是现成的复现夹具（32 个框 + 几何）。
2. `consistency.repair` 的**改阵营**路径（`tryFlipCell`）会把子的红黑翻来翻去以凑数量上限：
   单帧颜色噪声会让它把一片子翻色。本次只把「喂给它的几何」修稳，repair 本身未审。
3. `calibrateGrid` 的评分仍是「修复动作数 × 1000 + 未知格数」——同样依赖分类阈值。
   它这次给出的几何是对的（颜色正确），但机制上与 alignGrid 是同一类风险，值得单独审。
