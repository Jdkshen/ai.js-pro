# 新手机车炮往返与盘面独立核对

## 现场结论

设备为 Xiaomi 2602BRT18C（Android 16），宿主 dev-801，象棋工程 0.6.70。

现场存在两段车炮往返：我方车 `h0h1 ↔ h1h0`、对方炮 `i1i0 ↔ i0i1`；后续又出现 `h0h3 ↔ h3h0` 和 `i3i0 ↔ i0i3`。求胜策略已记录重复，并请求五路候选。返回车时只有一个合法应对；另一个回合存在替代，但其评分明显低于保留的重复着法，超过 20cp 的求变预算。因此旧版本仍执行重复着法。

不能把原因简单归为“部分棋谱”：部分历史仍通过 `position fen ... moves ...` 传给原生引擎。本轮以现场 FEN 重放三个车炮循环，原生 Pikafish 仍选择 h0h1，评分 10cp；返回车时仅 h1h0 合法。其 245 深度及毫秒级返回也在本地复现，不能据此断言引擎失效。此重放验证了该段循环，未恢复现场从开局起的完整棋谱。

旧基准与 18:22 的屏幕不同：基准有 i4 黑卒、i3 红兵及 g7 黑车；截图有 i4 红兵、空的 i3 及 g6 黑车。**补充严格对账后，全部差异可以被合法双步 `i3i4`（红兵吃卒）+ `g7g6`（黑车应手）完整解释**。两份数据并非同一捕获时刻，因此不能据此认定识别错误或多造了一枚红兵。此前将这两格差异直接解释为识别误判的判断已撤回。

原生搜索对照：仅修改基准的 i4/i3 两格，头名从 4cp 变为 -65cp，其他候选也从明显较低变为接近。这是控制变量的局面比较，不能当作发现了现场错误的证据。根据后来截图的完整盘面，头名为 h0i0 / -47cp。评分是本次搜索结果，不代表保证获胜。

将原始截图交给 APK 内的生产字形识别链，在 K40 上比较旧网格、旧基准参考、Y 偏移及重新定位四种配置，四种均识别为同一个正确布局，未知格为零，耗时 196～215ms。这验证静态图片及现有模板能识别该画面，尚不能确认运行时的初次错误发生于捕获、动画还是后续基准修订。

## 修复

1. 同一个盘面及行棋方累计确认三次时，在下一次算棋前独立读取两张完整新帧。核对请求不带参考棋盘，不经过已知落点补齐、基准纠色或其他历史修订。
2. 新帧与算棋盘面不同、仍有未知格、帧间冲突或几何变化时，暂停并打印最多六格差异。不把未经确认的新盘面自动写进棋谱。
3. 两帧完全一致时继续使用已确认棋谱和正常的候选分差保护；每个重复盘面在同一会话中仅核对一次。
4. PAUSED 的驱动不再继续后台观测和基准重建，避免暂停后的画面变化覆盖事故棋谱。

此改动增加持续往返时的独立取证，并修复暂停后仍修改棋谱的问题。真实盘面中只有保和线路、其他线路明显较差时，仍可能重复；没有将“避和”实现为强制走明显劣势候选。它不是针对本局已经证实的识别错误，也不能宣称已消除和棋。

- 新增 `repeated-board-audit` 驱动回放：18 项断言，在现场 FEN 上人工构造两格差异，覆盖差异拦截、独立两帧、同盘面放行并限频、未知格、两帧冲突、第二帧失败、显式关闭、暂停后停止采集并保留棋谱。人工差异用于验证防护，不能算作现场识别错误复现。
- Gradle 编译、内置示例检查、工程架构检查及 APK 全量源码指纹校验通过。
- K40 已安装 dev-802，缓存已同步 APK 的 320 个文件；在安装包内的 QuickJS 上运行四个便携回放场景，共 94 项断言全部通过，耗时 2104ms。
