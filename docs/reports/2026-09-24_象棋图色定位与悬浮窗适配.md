# 象棋图色定位与悬浮窗适配（2026-09-24）

## 改动

- 手机运行时的棋盘几何只走 `src/vision/lattice-detector.js`：原生找色统计、9×10 格线梳状拟合、格距与边界校验。`tools/locate-board.js` 从 636 行收至约 185 行；旧区域扫描不再是运行回退。旧 `board-locator.js` 仅留给历史离线自检，不由定位入口调用。
- 720px 宽画面扫描步长改为 3px；1080px 及以上仍为 4px。竖线证据少于 8/9 或横线少于 9/10 时定位失败，驱动不会拿猜测坐标点击。
- 悬浮窗由固定 1020px 改为根据屏宽缩放按钮、状态、日志窗和收起条；主界面与悬浮窗改用浅色圆角、蓝色主操作的 MIUIX 风格。
- QuickJS 宿主增加 `win.setDragHandle(viewId, onEnd)`；标题栏在 Android UI 线程拖动，结束时向脚本发一次事件。整窗不接管触摸，原按钮仍可点击。旧宿主没有此 API 时保留 JS 兼容拖动。

## 证据与边界

- 电脑端用与手机原生相同的逐通道 RGB 容差在 K40 真实截图上回放：`scr-now`、`scr-live` 和 skin4 连续 9 帧均有 9/9 竖线、10/10 横线。720×1600 缩放帧改用 3px 后得到 9/9、10/10，起点 `(58,464.75)`；1280×2844 缩放帧为 9/9、10/10。缩放图只验证分辨率行为，不能替代该分辨率设备的实拍。**四张较早的游戏皮肤实拍当时因「横 8/10」被全部拒绝——原因与修复见文末「后续修复」。**
- 响应式尺寸自检覆盖 720×1600、1080×2400、1280×2772，确保窗口和最长按钮行不超屏宽。
- 图色参考色来自当前游戏皮肤；游戏换皮肤、棋盘大面积被盖或分辨率很窄时可能明确定位失败，需要新的实拍样本调色，不允许静默猜坐标。
- 本次没有改变棋子 OCR、算棋、点击/落子确认的安全闸门；整局胜负仍需真机逐手验收。

## 后续修复：四张较早实拍的「横 8/10 全拒」（2026-09-24 凌晨，dev-664）

现象：四张较早的游戏皮肤实拍（`eval-fast-720x1600`、`after-auto-1080x2248`、`shot-64-1080x2400`、
`newphone-now-1280x2772`）在真机与电脑回放里全部只报「竖 9/9、横 8/10」→ 被门槛拒绝；dev-663
因此不作为验收版。逐像素诊断后共有三处根因（均可在电脑端复现）：

1. **外侧两条线被整行棋子压住是常态，不是证据缺失**：起始局面首/末行各摆 9 枚棋子，最外两条
   横线只剩 ~22%~32% 支撑度（0.52~0.86，内部线 2~2.8）。原 `matched` 门槛（0.35×前 3 强均值）
   把它们全判缺失（8/10）→ 改为 **0.2×前 3 强均值**，并新增**绝对下限 `minLineSupport=0.15`**
   （真机实测：空槽 0.00~0.04、被压住的线 0.52+，下限落在两个量级中间）。
2. **±1 格距平移梳三连平局**：trimmed 求和把「一条线空掉（0.00）」与「一条线被压住（0.5+）」
   同分，锚点 -1/0/+1 完全同分、靠扫描顺序唎选 → `shot-64`/`newphone` 选对（0），
   `after-auto`/`eval-fast` 选错（起点偏一整格：502.6→真值 617、519.9→真值 443.75）。
   修法：新增「存在的线」计数加成（`presenceCount`×0.05/条），真梳比平移梳多 1~2 条存在的线而胜出。
3. **纯相对门槛在全噪声图上会「全命中」**：当晚负例检查发现文件列表截图（全线 0.01~0.02）
   会被算成 10/10「命中」→ 由 `minLineSupport` 绝对下限拦住（该图及抽屉、桌面等
   一系列 UI 负例全部转为 0/9、0/10 明确拒绝）。

验证（修复后）：

- 电脑端回放：四张目标图全部 ok（竖 9/9、横 10/10），起点 `(58,443.75)`／`(80.6,617.0)`／
  `(80.8,665.75)`／`(88,784.5)`，与像素级真值逐一吻合；`scr-now`/`scr-live`/`scr-720`/`scr-1280`
  无回归；负例（抽屉/文件列表/桌面/小卡片）全部拒绝。
- 真机 K40：`tools/lattice4-replay.js` 回放 **4/4 通过**（435~1439ms/张），几何与电脑端一致；
  `tools/self-check.js` 真机 **300/300**（新增 4 条回归：压线锚点、真缺线、口径、噪声）。
- 工程版本升到 `0.6.3`；`lattice-detector.js` 新增 4 个可调项（`matchedRatio`/`minLineSupport`/
  `presenceRatio`/`presenceBonus`）并导出 `presenceCount/matchedCount` 供自检锁定口径。

边界（未变）：外线被压 >85%（几乎全盖）时无法与「空槽」区分，锚定仍可能靠扫描顺序——
这由下游 grid-sanity 平移救回兜底；「不是棋盘」的画面靠绝对下限拒绝，0.15 是当前实拍的最优折中。

### 收尾归并（同日，行为不变）

三天的修复各自加了一套线计数（strong / presence / matched），共 3 个函数、3 个导出、1 个多余参数。
归并为**单一 `lineEvidence` 判据**：`present`（存在的线，≥max(最强线×presenceRatio, minLineSupport)）
同时供锚点加成与入口门槛使用；`strong` 只留加成用途（实测去掉后 scr-now 锚点偏 13.5px，不能删）。
删掉 `matchedCount`/`matchedRatio`（「前 3 强均值×0.2」口径），负数个概念变 2 个。
验证：PC 全样本（正 10 / 负 6）与真机四图回放**逐项一致**（几何到 0.1px 相同）、自检 300/300（PC+QuickJS）。
另外实测：参考色 cast 不能减到单色（board-k40/dialog1 会在弱光下失守），强线加成不能删。

## 悬浮窗收敛与外观修订（同日，工程 0.6.4）

- 悬浮窗只保留对局中需要立即点的模式、开始/暂停、停止、定位、识别、轮次声明、换我方与重开本局；算棋时间和线程滑条仍可在对局中调速。离线自检、契约测试、识别绘制、清日志、关闭悬浮窗使用主界面已有入口。抓帧遮挡沿用自动判定，几何微调默认关闭，不再占按钮位置。
- 主面板从 418px 缩到 364px（1080px 基准），按钮间留 8px，主按钮高对比、辅助按钮浅色。原来写在普通 `text`/`vertical` 上的 `radius` 不生效，现用宿主已支持的 `cardCornerRadius` 绘制真正圆角；底部日志用不透底的圆角卡片保证文字可读。
- “收起”改用单行 780×54px 控制条。Mi 8 真机发现负坐标会被系统夹回屏顶，旧实现会留下整块空面板；改为 QuickJS `setContentVisibility(8/0)` 切根 View，窗口不从 WindowManager 移除，并同步切换触摸。实测收起和展开均恢复正常。
- 验证：Mi 8（1080×2160）运行当前工程脚本、检查圆角/按钮/日志、实际点击收起与展开；电脑端 `tools/run-regress.js` 11/11、legacy 自检 311/311、契约 19/19。720/1080/1440px 的最长按钮行与内容高度均小于对应面板内宽/高度。Mi 8 仅用于界面预览，没有在其上开始走棋；K40 原对局未被中断。

## 无棋盘画面冷启动修复（同日，工程 0.6.5）

- K40 设备日志显示：从 AI.js Pro 主界面启动脚本时，屏幕尚无游戏棋盘。线定位返回竖 0/9、横 0/10，回退检测也没有棋子框。此时 `boardService` 和 `app` 仍为 `null`；autorun 几何验证读 `recognizeSmart` 报错，随后点悬浮窗“开始”读 `app.controller` 导致脚本退出。
- 自动定位失败时明确拒绝自动开始；几何验证先检查棋盘、再初始化识别服务。悬浮窗按钮统一经延迟初始化的控制器执行，失败只显示原因，不杀掉脚本。手动“开始”在没有棋盘几何时先尝试定位，仍失败则明确拒绝，避免空转。
- 现场操作顺序：先把象棋游戏棋盘切到前台，再点悬浮窗“定位校准”和“开始”。当前设备日志显示 shell 不可用，因此从 AI.js Pro 启动时无法依赖 shell 自动切到游戏；`floaty-autorun.json` 中的 `stopAfterMs:30000` 是测试限时参数，若要持续运行应移除。
- 验证：Mi 8 在启动器画面模拟相同的无棋盘 autorun，点“开始”后仅记录定位失败和拒绝开始，悬浮窗脚本未因空控制器崩溃；电脑端回归与契约自检通过。该验证只覆盖无棋盘失败路径，未证明整局自动走棋可胜或自动切前台。
