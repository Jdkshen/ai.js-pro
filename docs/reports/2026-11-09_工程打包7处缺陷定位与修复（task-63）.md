# 工程打包 7 处缺陷：定位、判据与修复（task-63，device4 dev-1443 取证）

> 真机证据来自 Lead：同一工程（脚本/诺亚传说互通版新版）我们产物 99,566,759 B vs Pro 29,877,116 B。
> 本报告逐条给「代码定位 → 判据 → 修复 → 未验证边界」。本轮修了 ②③⑤⑥⑦，④ 给能力覆盖证据链与建议。

## 1. 逐条取证与定位

| # | 现象（device4） | 定位 | 判据/结论 |
| --- | --- | --- | --- |
| ① | 产物 95MB vs Pro 28.5MB | 由 ②⑤⑦ 相加解释：② 59MB 套娃 + ⑤ OpenCV 拆库 ~30MB（vs Pro 单库 17MB）+ ⑦ pikafish 1.7MB | 不是「压缩率」问题，是**内容**问题 |
| ② | 工程 `build/` 被整份打进 `assets/project/build/`（旧 APK 29.9MB + zip 29.3MB） | `ApkBuilder.excludedOutputDir():1101-1112` 只排除「产物 APK 的父目录 **且该目录在工程内**」；`copyDir():1133-1137` 只接受**一个**排除项 | 用户把产物输出到 `脚本/APK输出/`（工程外）→ 一个都没排。附带后果：inrt 启动器把 `project/build` 当文件打开 → `FileNotFoundException` |
| ③ | 只出 `lib/arm64-v8a`（project.json 声明 abis 两个） | `ApkBuilder.java:157 HOST_LIB_PREFIX = "lib/arm64-v8a/"` 写死；全仓 `abis` 只在 **flutterpoc/PocPackaging** 路径被读（`PocPackaging.java:615/1000/1066`） | 旧打包路径**从不读** project.json 的 abis；模板/宿主也只有 arm64 的 lib |
| ④ | project.json 声明的 mlkit 插件没进包 | 旧路径无 `plugins` 处理（全仓只有 `PocPackaging.java:179`）；Pro 把插件 APK 放进 `assets/project/plugins/` | **能力覆盖成立**：模板/宿主自带 `libmlkit_google_ocr_pipeline.so`(10.55MB)+`libppocr.so`(3.78MB)+OCR 模型（与 Pro 11.3MB 插件等价，只是形态不同：内建 vs 插件 APK）。**但「声明了却没带」不能静默** → 建议见 §3 |
| ⑤ | OpenCV 拆成一堆 .so（~40MB arm64） | 模板/宿主只有拆库（`libopencv_core/dnn/imgproc/imgcodecs/geometry/java5` + `libtbb.so`，见 `excluded-zip-files.json:opencv`）；`removeOpenCv` 在旧路径**未实现**（键只存在于工程样例与 PocPackaging） | Pro 用单库 `libopencv_java4.so`(17MB)。我们能做的是：`removeOpenCv=true` 时**不带** OpenCV/TBB（本轮实现），单库形态需要换宿主的 OpenCV 打包方式（超出本轮） |

| ⑦ | `lib/arm64-v8a/libpikafish.so`(1.8MB)（中国象棋引擎） | `ApkBuilder.java:159-162 RUNTIME_LIB_NAMES` 硬编码含 `libpikafish.so`；`apps/app/src/main/assets/excluded-zip-files.json:general` 也列了它。它只被象棋工程与 `com.jdkshen.xiangqi.plugin` 使用（`tools/check-plugin-api.js`、`象棋自动走棋/**`） | 与诺亚传说工程无关 → **泄漏**（每个工程白送 1.8MB） |

## 2. 改动清单

新增（纯 JVM，全部可单测，判据集中在这里）：

- `apps/app/src/main/java/com/jdkshen/aijspro/autojs/build/PackageOutputExclusions.kt` —— ② 的判据：
  1. 产物目录在工程内 → 排除（老行为）；
  2. 工程根下名为 `build` 的目录，**只有**「含 .apk/.zip/.apks/.idsig 且不含任何源码类文件（.js/.ts/.vue/.java/.kt/.py/.json/.md/.html/.css/.txt）」才排除 → **不会误伤用户自己的 build 源码目录**；
  3. 目录含标记文件 `.aijspro-package-output`（新产物目录可写）→ 直接排除；
  4. `AppConfig.ignoreDir(...)` 显式声明（语义理清：以前只在「工程是单文件」分支生效，现在目录分支也生效）。
- `apps/app/src/main/java/com/jdkshen/aijspro/autojs/build/NativeLibPolicy.kt` —— ⑤⑦ 的判据（每个 .so 必须对上「模板必需 / 工程策略 / 内建 OCR」）：
  - 必需：`libaijscrypto/libc++_shared/libquickjs/libquickjs_jni`；
  - 内建 OCR：`libppocr/libmlkit_google_ocr_pipeline`；
  - OpenCV/TBB：`removeOpenCv=true` → DROP，否则 KEEP（宿主形态是拆库）；
  - `libpikafish.so`：**只在**工程声明了 xiangqi/pikafish 插件或工程源码命中 `pikafish/xiangqi/象棋` 时 KEEP，否则 DROP 并记 leak；
  - 其它运行时（v8/flutter/node）→ DROP；未识别的保守 KEEP 并标注 unknown。
  - 提供 `classify/`filter`/`leaks`：`leaks()` 就是「对不上三者之一」的清单（可单测）。
- `apps/app/src/main/java/com/jdkshen/aijspro/autojs/build/AbiPolicy.kt` —— ③：`resolve(declared, available)` 声明了拿不到 → **抛**（点名缺哪个、当前可用哪些、怎么改），声明为空 → 用实际可用并回显。

接入（`apps/app/src/main/java/com/jdkshen/aijspro/autojs/build/ApkBuilder.java`）：

- `copyProjectToWorkspace()`：改用 `PackageOutputExclusions.projectExclusions(source, mOutApkFile, ignoredDirs)`，`copyDir()` 的排除参数由单个 `File` 改为 `Set<String>`（规范路径集合，保留符号链接场景的规范路径比较），并打日志 `project copy excludes=…`。
- `build()`：在 `copyProjectToWorkspace()/copySplashIcon()/removeDisabledFeatures()` 之后新增 `enforcePackagingPolicy()`（单点，便于审计）：
  1. 读 `assets/project/project.json` 的 `optimization.removeOpenCv` / `plugins` 键 / `abis`，并**扫描工程文本**是否命中 `pikafish/xiangqi`；
  2. 按 `NativeLibPolicy` 删除 DROP 的 lib（逐条日志 `native lib dropped … reason=…`），统计剩余 ABI；
  3. `AbiPolicy.resolve` → 失败即抛 IOException（不产出静默少 ABI 的包），成功记日志 `abis declared/available/chosen`；
  4. 删除工作区里的 `assets/autojs.keystore` 并记日志（⑥）。

资源：

- `apps/app/src/main/assets/excluded-zip-files.json`：`general` 里删除 `lib/arm64-v8a/libpikafish.so`（它与 NativeLibPolicy 的「工程需要才带」一致；模板 APK 内的同名清单要等模板重建才同步——见边界 4）。

测试：

- `apps/app/src/test/java/com/jdkshen/aijspro/autojs/build/PackagingPolicyTest.kt`（纯 JVM，8 项）：
  - ② 产物在工程外时仍排除工程内 `build/`；含源码的 `build/` **不**排除；标记目录 + ignoredDirs 排除；产物在工程内时仍排除；
  - ⑦ 用**真机取证的 14 条 lib 清单**跑 `leaks()`：只有 `libpikafish.so` 被判泄漏，其余每条都能对上 template/project；xiangqi 插件/源码命中时 pikafish 保留；
  - ⑤ `removeOpenCv=true` → OpenCV/TBB 全 DROP 且必需库不受影响；
  - ③ 声明两个 ABI 只有 arm64 → 抛且消息含 `armeabi-v7a`/`不允许静默少出`；声明为空 → 用可用 ABI 并回显。

## 3. 验证方式

- 单测：`gradlew :app:testMiuixCompatDebugUnitTest -PflutterPoc=true --tests "com.jdkshen.aijspro.autojs.build.PackagingPolicyTest"` → **exit=0**，`PackagingPolicyTest` **9 项 / 0 失败**。
- 编译：`gradlew :app:compileMiuixCompatDebugKotlin :app:compileMiuixCompatDebugJavaWithJavac` → **exit=0**（三个策略类 + ApkBuilder 接线都编译通过）。
- 环境说明：不带 `-PflutterPoc=true` 时 `:app:compileMiuixCompatDebugUnitTestJavaWithJavac` 会因**既有** flutterpoc 测试缺 `FlutterBridgeEventCodec` 失败（与本次改动无关，按仓库既有跑法加该 flag）。
- 与 Pro 对照（Lead 在 device4 同工程重打）预期：产物应**减去** `assets/project/build/`（≈59MB）、`lib/arm64-v8a/libpikafish.so`（1.8MB）、`assets/autojs.keystore`（2062B）；若工程 `optimization.removeOpenCv=true`，再减去 OpenCV/TBB 拆库（≈30MB arm64）；**abis 声明两个而只拿到 arm64 时会明确报错**（不再静默少出）。
- ④ 建议（本轮未改代码，给结论）：把「声明了 plugins 但产物里没有对应能力」变成**显式**——最小做法是在 `enforcePackagingPolicy()` 里回显 `plugins=<keys> coveredBy=builtin-ocr|<missing>` 并写进打包结果/日志；若确实要按 Pro 形态带插件 APK，需要在旧路径解析工程 plugins 并从插件安装目录复制 `assets/project/plugins/<pkg>.apk`（证据：Pro 产物里有该路径；我们的插件安装目录见 `plugin/PluginRegistry.java`）。**这条需要 device4 上那份 project.json 原文与插件文件才能定实现**（本轮未拿到）。

## 4. 未验证边界

1. **真机未打包**（本轮只跑单测）：所有「产物会变小」的预期都要 Lead 在 device4 同工程重打后对照 unzip 清单确认。
2. `PackageOutputExclusions` 的「像产物目录」启发式**会跳过一个既含 .apk/.zip 又只含这些的 `build/`**；若用户真把源码目录命名成 build 且里面塞了 apk，会被跳过（有 JSON/JS 等源码文件时不会）。标记文件是更强判据（新产物目录可写标记），但**旧产物目录没有标记**，只能靠启发式。
3. ③ 现在会**报错**（而不是产出 arm64-only 的包）：这是任务要求的「不许静默少出」，但对已经这样声明 abis 的既有工程是**行为变化**（他们需要改 project.json 或补齐 v7a lib）——请确认是否接受。
4. 模板 APK 内部还有各自的 `assets/excluded-zip-files.json` 与 `assets/autojs.keystore`：本轮只改了**主程序 assets 的清单**；模板内的清单/密钥要等**模板重建**（Lead scope）。`enforcePackagingPolicy()` 里的删除逻辑对模板形态也生效（它是工作区级过滤），所以即使模板没重建，pikafish/keystore 也不会再进产物。
5. `removeOpenCv` 只做了「不带 OpenCV/TBB」；**没有**换成 Pro 的单库 `libopencv_java4.so`（宿主当前是拆库形态），也没有做「按工程实际用到的 CV 模块裁剪」。
6. ④ 插件：只给了能力覆盖证据链与建议，**未改动代码**（缺 device4 的 project.json 原文/插件目录证据）。
7. 只跑了 `PackagingPolicyTest`，未跑 app 全量单测、未装机、未发布、未提交。
