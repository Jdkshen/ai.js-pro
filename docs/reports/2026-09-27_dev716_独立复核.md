## 1. P1：定时器取消自身会释放正在执行的回调，升级后仍然崩溃

位置：`modules/engine/src/main/cpp/quickjs_jni.cpp:193`、`:2581-2584`。

`dispatchDueTimers()` 直接把 `timer->callback` 交给 `JS_Call()`，没有为本次调用保留额外引用。回调内调用 `clearInterval(id)` 时，`nativeClearTimer()` 删除 timer 并释放其 callback。C++ 的 `shared_ptr<TimerEntry>` 只保护结构体，不保护其中的 QuickJS 对象。回调继续执行时会访问已释放对象；自取消后抛异常还会进入再次释放 callback 的路径（`:204` / `:222`）。

验证使用当前源码中原样提取的 `registerTimer`、`dispatchDueTimers`、`nativeSetInterval`、`nativeClearTimer` 函数，链接 dev-716 **同一份** arm64 `libquickjs.so`，在已连接的 K40 上以独立进程运行：

| 用例 | 当前 JNI 原函数 | 仅修改测试副本的引用保护 |
| --- | --- | --- |
| 普通 interval，外部收尾 | 正常退出，0 | 未重复执行 |
| interval 内 clearInterval 自身，再分配函数 | Segmentation fault，139 | 正常退出，0 |
| interval 内 clearInterval 自身，再 throw Error | Segmentation fault，139 | 正常取得 Error，退出 0 |

复现核心：

```js
globalThis.id = setInterval(function () {
    clearInterval(id);
    globalThis.items = [];
    for (let i = 0; i < 1000; i++) items.push(function () { return i; });
    globalThis.after = 1;
}, 0);
```

测试副本的两处改变：调用期间额外 `JS_DupValue`，用局部析构守卫释放；取消时将 timer 内的 callback 置为 `JS_UNDEFINED`，再释放原引用。**这些改变尚未写入产品代码，不是已完成的产品修复。**

业务中存在同类路径：`src/app/panel/lifecycle.js:194` 创建心跳，`:279` 在心跳内执行自动重载，`:165` 清掉自身 `aliveTimer`。传感器回调中注销传感器也有类似自取消路径。

复现生成器：`.artifacts/review-quickjs-716-native-check.py`；原样和保护版本分别在 `.artifacts/review-quickjs-716-native/timer-check.cpp` 与 `timer-check-protected.cpp`。手机独立程序目录为 `/data/local/tmp/codex-review-716`。

这证明新版仍存在 JNI 崩溃缺陷；**尚未证明历史 tombstone 14–17 全都由这一处引起**。该缺陷是升级前已有、此次未处理的问题。

## 2. P2：预思考的禁止查库参数在 worker 边界丢失

位置：象棋项目 `src/automation/prethink.js:44-46`、`src/automation/search-worker.js:199-211`、`:37-76`。

prethink 传入 `openingBook:false`、`bookOwnMoves:0`、`criticalReview:false`，但 `search-worker.start()` 没有把这些字段放进 `threads.start` 的载荷；`workerTask()` 也没有传递 `openingBook` 和 `criticalReview`。实际 worker 因此仍可能命中默认开局库，直接返回书中着法，根本没有进行预期的 Hash 预热。正式搜索传入的步数上限和其他策略字段也有相同的丢失问题。

用真实 prethink/search-worker 配合记录参数的 threads 桩验证，载荷中的三个字段全部为 `MISSING`。应同时补齐 start → 线程载荷 → workerTask → engine 的整条参数链。

## 3. P2：预思考取消没有等待旧任务退出

位置：`src/automation/prethink.js:34-37`、`src/automation/search-worker.js:161-171`。

prethink 注释声称取消后会等待有界任务退出，但实际调用通用 `worker.cancel()`，立即 `thread.interrupt()` 并清掉 thread/pending；`busy()` 随即为 false，下一任务能够启动。400ms 重启间隔不能证明旧线程已退出。`create({cooperative:true})` 也不起作用，当前 worker 根本未实现这个选项。

桩验证结果：取消一次后 `interrupts=1`、`busy=false`、`canStartAnother=true`，原线程的 getResult 仍报告 running。需要保留取消中任务并等待其退出，且明确共享 worker 的所有权；不能仅靠时间间隔代替完成确认。这是代码行为验证，未据此宣称已经复现原生并发崩溃。

## 其他已有的生命周期风险

`QuickJsJavaScriptEngine.java:155-165` 等待脚本线程最多 2 秒，即使仍存活也继续调用 native destroy；后者在 `quickjs_jni.cpp:10242-10243` 直接释放 context/runtime。`ScriptExecuteActivity.onDestroy():217` 可触达该路径。如果线程尚在阻塞的 native 调用中，返回后仍可能访问已释放状态。此项为静态发现，未在运行中的 App 上强行触发。

此外 `QuickJsHostBridge.runJsCallbackOnMain():5442-5447` 在主线程回调超时或等待被中断时返回，未撤销/等候已投递回调；JNI 回调入口没有运行时互斥保护。需要纳入后续生命周期审计。

历史崩点位于 libquickjs、build-id 相同，只能说明当时执行了哪一份库，不能排除桥接误用、释放后使用或线程竞态。当前最应优先处理的是上述已复现的 timer 缺陷，再补 worker 专项验收；之后才有依据继续观察长局稳定性。
