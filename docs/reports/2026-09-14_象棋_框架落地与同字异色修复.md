## 3. 本轮查到并修掉的真机 Bug：同字异色被当成「关键冲突」

### 现象

一轮 165s 的运行里，日志刷出 **48 次**

```
[driver] 确认：UNRELIABLE：有 1 处关键冲突
[driver] 原始读数被修正 2 格：(1,7)?→C (2,7)?→空
```

状态停在 `THINKING`，永远等不到「无冲突」的那一帧。

### 根因（在视觉层，不在验证器）

`src/vision/cell-assignment.js` 的 `conflictGap` 分支：同一格最高分与次高分差 < 0.15 就
`stats.conflicts++` 并把该格判未知。而**模型会把同一个字在红黑之间抖**（`C` 红炮 ↔ `c` 黑炮，
同一个字形、同一个格），两候选分差天然很小 → 每帧都算「关键冲突」→
`move-verifier` 只看到 `conflicts > 0` 就**一票否决整帧** → 永远等不到干净帧。

日志里那句 `(1,7)?→C`（`C` 就是炮）正是这个抖动的痕迹。

### 修法（分两级，保住原本的安全底线）

| 冲突类型 | 判定 | 处理 |
|---|---|---|
| **同字异色**（`C/c`、`K/k`、`P/p`…） | 两候选**忽略大小写相同** | **不计入关键冲突**；格子照样判未知、照样留明细。缺的只是红黑，而红黑恰好是下游「同字异色修正 + 棋规唯一解释补齐」能靠基准盘面还原的信息（那条路已验证可用） |
| **异字冲突**（`C` vs `N`） | 连兵种都不同 | 照旧计入关键冲突 → 一票否决，等新观测 |

配套：
- `stats.sameGlyphConflicts` / `stats.conflictCells`（最多 8 格明细）新增，经 `recognizer.report` 透出；
- driver 在确认前打印一行**冲突明细**（哪一格、两个候选、各自分数、同字/异字），
  以前只报「有 N 处关键冲突」，只能靠翻源码猜（这次就是这么花掉的）；
- 自检新增 2 条契约断言：`同字异色冲突不算关键冲突` / `异字冲突仍然按关键冲突否决`。

## 6. 追加（同日稍晚）：补齐记录被「红黑抖动」丢掉 —— 真机每帧推不出来的根因

### 现象（真机 r1.log）

我方第二手 `c2c6` 确认成功后，从下一帧起**每一帧**都是：

```
[driver] 轮次推不出来（UNKNOWN）：既没有合法单步也没有「一步+应手」能解释，需要恢复
[driver] 诊断基准 rnbakabnr/9/1c2c4/p1C1p1p1p/9/9/P1P1P1P1P/7C1/9/RNBAKABNR b
[driver] 诊断观测 rnbakabnr/9/1c7/p1P1p1p1p/9/9/P1P1p1P1P/7C1/9/RNBAKABNR b
```

与基准只差三格，全是「游戏装饰 + 模型抖动」：

| 格 | 基准 | 观测 | 性质 |
|---|---|---|---|
| (2,3) | `C`（我方刚落下的炮，带高亮环） | `P` | 同色不同兵种 |
| (4,2) | `c`（对方刚落下的炮，带高亮环） | 空 | 整格漏检 |
| (4,6) | `P` | `p` | 同字异色（只是红黑读反） |

这三格**都在「已知事实补齐」表里**（登记日志能看到下标 29 与 22），却没被补回来。

### 定位手段：离线回放（本轮新增工具）

`.artifacts/tools/diag-patch-life2.js` —— 用**真机日志原话的着法与原始读数**逐帧喂给真实驱动：

- 第一版（回归帧只有「漏检 + 同色不同兵种」）：**能被补齐** → 说明夹具还没抓到真机那一段；
- 让它先喂一帧「同一格被读成**同字异色**」（`C` → `c`）：**立刻复现**——那一格记录被丢掉，
  随后所有帧都推不出来。

### 根因

补齐表第 ④ 支写的是「换成异色 → 真的被吃/走开了 → 丢掉记录」。
而这台机器上**模型会把同一格在红黑之间反复抖**（`C` ↔ `c`，视觉层那 48 次「关键冲突」就是它）。
于是**一帧抖动就足够把记录丢掉** —— 之后再来的「同色读错」帧没人补，
盘面永远差一格，没有任何合法着法能解释 → 看门狗 → 整轮停住。

### 改法

| 观测到的字 vs 记录 | 判定 | 处理 |
|---|---|---|
| **同字异色**（`C`↔`c`、`P`↔`p`） | 同一兵种红黑读反 | **按记录补齐并保留**（新增 `stats.sameGlyphPatched` 计数） |
| 同色不同兵种（`C`↔`P`） | 兵种被装饰读错 | 按记录补齐并保留（原行为） |
| 异色**且**不同兵种（`C`↔`n`） | 真的被吃/走开了 | 丢掉记录（不隐藏吃子，原行为） |

同时给「轮次推不出来」的诊断**补了一行补齐表内容**（含每格本轮读到什么）——
以前只报「推不出来」，分不清是「表里没有记录」还是「有但没补上」，为此白跑过好几轮真机。

自检 152 → **153**（新增契约断言：同字异色抖动不许丢掉已知事实记录）。

### 真机验证（K40，r2/r3.log）

- 连走两手：`b2c2` → CONFIRMED、对方应手 `h7e7` **严格推断成功**、`c2c6` → CONFIRMED；

## 7. 追加：等待对方应手期间的前台读数（诊断留痕）

面板的脚本宿主是一个**透明窗口**，之前怀疑「它拿到焦点 → 游戏被 pause → 对方不应手」。
本轮给等待路径加了 `keepGameInFront()`（限频 4s，点击租约期间不动），并**打出两个读数**：

```
等对方应手期间的前台：触摸焦点 com.tencent.qqgame.xq／栈顶 com.tencent.qqgame.xq
```

实测结论：**等待期间游戏本来就是前台**（触摸焦点与栈顶都是游戏），这个假设不成立；
该函数一次都没触发切换（保留它是为了以后换设备/ROM 时能自动兜住，并留下读数）。

顺带记两条**踩过的坑**（都因为「用眼睛估坐标」）：

- 「菜单」里点「重来」点到了**「提和」**上（弹出了确认框）→ 游戏内菜单项位置**必须从截图像素量**，
  不能按比例估算（实测差了 ~130px）；
- 悔棋有限（这台 ROM 上悔两次之后就不再生效），所以「把棋局弄回 0 步」不能只靠悔棋。
  ③ 从非标准开局起跑时，用 autorun 的 `declareTurn: true`（把当前局面声明为「轮到我」）更可靠。


