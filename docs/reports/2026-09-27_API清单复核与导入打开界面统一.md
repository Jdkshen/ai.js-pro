# API 清单复核与导入、打开界面统一

## API 结论的边界

本次接收的是用户整理的 smali、403 个示例和 `@autojs/types-pro9` 对照结论，没有重新运行这 403 个官方示例，也没有据此宣布两套引擎完全兼容。本次 UI 修改不更换引擎、不修改象棋算法。

对“经典 API 基础相近、主要移植工作在扩展和调用差异”的方向可以保留，但建议将表中的“直接能用”改成“已找到接口证据，按目标引擎验证行为”。Java 方法存在、类型定义存在、JS 能访问、参数/返回值一致、真机完整流程成功，是不同层次的证据。

根据此前提供的《Auto.js Pro官方API文档.pdf》，有两处明确需要修正：

- **`$ocr` 不是 Pro 完全没有的接口。** PDF 第 181–185 页记录 Pro 9.2 新增的 `$ocr.create()` / OCR 对象，依赖官方 PaddleOCR 插件；ML Kit 是另一条插件路线。应写“当前项目与目标 Pro 版本的 OCR 插件、创建方式和返回结构需要适配”。
- **找全部色点的公开入口是 `images.findAllPointsForColor(img, color, options)`。** PDF 图片模块直接给出该调用。底层 ColorFinder/ColorMapping 类名不能作为 JS 经 `colors` 暴露的证明。

其余条目建议按以下方式验收：

| 条目 | 应验证什么 |
| --- | --- |
| `requestScreenCapture` | 对外 JS 包装层的无参、布尔方向参数和 options 对象；不能由 Java 的四参数签名直接推断脚本必须异步调用。字符串 `"portrait"` 不作为可移植写法。 |
| `floaty.window(xml, options)` | options 属于当前 fork 扩展；移植时核对目标 Window 的位置、显隐接口，尤其不能默认 `setVisibility` 在目标版本也存在。 |
| `engines.execScriptFile` | `config.path` 模块搜索路径数组与脚本相对路径解析的行为；在目标引擎实际加载子模块。 |
| Shell → Pikafish | 有流与回调只证明有实现基础；还要验证可执行文件部署、ABI/执行权限、UCI 握手、持续输出、超时中止与进程回收。 |
| 图像识别回退 | 不能只测函数存在；同一棋盘截图对照识别结果、耗时、坐标、内存释放和循环运行。 |
| `events.bus` / YOLO | 当前脚本是否实际引用要以当前提交为准；“没有用到”不代表整个框架从来不用。 |

第一代 API 对齐仍不以接入 V8 为前提。Rhino 与 QuickJS 的行为测试应分别记录。

## 三处界面统一

用户确认范围：主页点“导入”、从外部文件管理器打开文件、项目位置选择与切换。

### 统一文件选择器

入口统一使用 `MiuixFileChooserDialog`：

- 同一套 Miuix 圆角面板、主题配色、文件夹图标、搜索框和底部按钮。
- 可横向滑动、点击跳转的路径导航；显示完整路径，支持上一级及返回键逐级退出。
- 从当前目录开始浏览；路径失效时退到仍存在的上层目录。
- 导入支持原有脚本及可编辑文本，包含 `.md` / `.markdown`，不改变脚本执行过滤器。
- 项目模式在弹窗中检查 `project.json`，无有效配置时说明原因、禁用确认。
- 读取失败、目录为空、搜索无结果分别显示。目录切换重新建立列表滚动状态，不能在列表尚未布局时等待 `scrollToItem()` 再读取文件。

调用方式：

```kotlin
MiuixFileChooserDialog.showImport(activity, storageRoot, currentDirectory) { path ->
    // 用户确认后导入这个文件。
}
MiuixFileChooserDialog.showDirectory(activity, "选择项目所在文件夹", storageRoot, parentDirectory) { path ->
    // 选中当前文件夹。
}
MiuixFileChooserDialog.showProject(activity, storageRoot, currentProject) { path ->
    // 打开有效项目；未保存修改仍走保存/放弃/取消流程。
}
```

### 外部文件统一进入新编辑器

`EditIntentActivity` 以前对普通文件路径使用 `ProCodeEditorActivity`，对无法解析为路径的 URI 则退回旧 `EditActivity`，这是同样“打开文件”却出现两种界面的原因。

现在文件路径与 `content://` 均进入 `ProCodeEditorActivity`。外部文档通过 `ContentResolver` 读取到独立缓存，保留原 URI 作为保存目标，不猜测第三方 provider 的物理路径。写回使用截断模式，避免短文本覆盖长文本后残留尾部内容。

保存失败会保留未保存状态，并提示使用菜单“另存为…”。另存流程复用同一目录选择器，校验文件名和重名，成功后编辑器切换到新文件。外部缓存不写入正常工作区的最近标签页；页面重建时暂存草稿及未保存标记，不向原文件偷偷写入。

外部“导入”的名称弹窗取消后会完成操作、关闭入口 Activity 并释放输入流，避免剩下空白页面。复制失败不会再返回成功路径。
