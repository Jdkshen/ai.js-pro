# Node24 API 现状与缺口（2026-10-18）

> 任务：Node API 对齐第一步——盘点 Node24 引擎 API/模块现状并在 K40 实测探测（fs/path/process/Buffer/require/ui 等）。
> 环境：K40（M2012K11AC，Android 16，设备 id cccc62c7），App dev-1055/1056 工作区代码。
> 探测方法：在 `/sdcard/脚本/node24probe` 放一个 `"nodejs";` 开头的项目（project.json + main.js），从文件列表点击运行（Node24 引擎在 `:node24` 进程），脚本把结果写到 `/sdcard/脚本/node24probe-result.json` 并 `console.log('PROBE_RESULT=...')`。探测脚本与结果：`.artifacts/node24probe/`、`.artifacts/node24probe-result.json`。

| 项 | 值 |

| Node | **v24.22.0** |
| platform / arch | android / arm64 |
| V8 | 13.6.233.17-node.57 |

结论：Node24 引擎是**真实 Node 24 运行时**（libnode.so），不是 JS 模拟层；Node 内置模块能力原样可用。

| 全局 | 状态 | 备注 |
|---|---|---|
| Buffer / process / require / console | ✅ function/object | process.version/versions 正常；process.argv 可见 prelude 注入源码（argv[1] 是 prelude 首行） |

## 3. 内置模块探测（require）

全部可 `require`（✅）：`fs, path, os, util, events, stream, crypto, http, https, child_process, worker_threads, url, querystring, zlib, net, tls, dns, vm, assert, buffer, process, module, timers, tty, readline, string_decoder, punycode, v8, perf_hooks, async_hooks, diagnostics_channel, inspector, repl, wasi, node:fs, node:path`。

仅探测里两个名字失败（**非真实缺口**）：`sea`（不是可 require 的模块名）、`test`（应要求 `node:test`；后续 task2 补探测）。`node:` 前缀可正常解析。

## 4. 实际功能探测

- **fs**：写/读 `/sdcard/脚本/node24probe-fs/a.txt` ✅（内容 hello-node24，stat=12，readdir 正常，exists=true）——Node 脚本可直接操作公共存储（App 有存储权限时）。
- **path**：join/dirname/extname/resolve 正常。
- **Buffer**：`Buffer.from('hello')` hex/base64 ✅；UTF-8 `Buffer.byteLength('你好')=6` ✅。

## 5. Auto.js / UI 模块现状

- **`$autojs`（prelude 注入）**：keys = `java, projectDir, scriptFile, keepRunning, stopRunning, on, off, pollEvents, registerModule, isRoot`；另有 `androidContext` getter（不可枚举，探测未列出）。`$autojs.java` 是**反射代理**（new/static/call/field/setField/classOf/context），`defineClass` 明确抛「暂不支持」。
- **`require('app')`**：`openUrl, startActivity, getPackageName, toast`（4 个方法，能力有限）。
- **`require('ui')`**：存在且返回 object（B 的 `assets/node24/ui.js`，overlay/Activity 双模式）；本轮只探测 typeof，未逐一验证 layout/Activity/事件 API（属 task3 范围）。
- **`require('rhino')`**：prelude 内置兼容模块（Java 包代理），供老脚本 `require('rhino').install()` 使用。
- 宿主桥：`__autojsHost` 单向 string 契约 + 轮询事件（25ms），无 Java→Node 反向调用；`ui` 模块与宿主 `kind=ui` 走 raw JSON。

## 6. 缺口清单（按优先级）

### P0（阻塞常规 Node 脚本）
1. 入口脚本 **无 CJS 包装**：`module/exports` 全局 undefined，依赖 `module.exports` 的入口/模块写法需要验证与补齐（Node 原生 require 子模块通常有包装，但 prelude 注入后入口是拼接源码）。
2. **npm 第三方模块/package.json 解析**未探测：`require('lodash')`、`node_modules` 查找、`require.resolve`、ESM `import()` 均待 task2 实测。
3. `$autojs` / `app` 能力远小于 Auto.js Pro：无 device/files/events/engines/storages/threads 等常用 API；`app` 仅 4 个方法。

### P1（UI/兼容）
4. `ui` 模块完整度：需逐项验证 `ui.layout/ui.setContentView/ui.run/ui.Activity/ui.getWindow` 等（overlay 与真 Activity 两模式差异）。
5. `rhino` 兼容层只覆盖 Java 包访问；Rhino 特有 API（importClass/JavaAdapter 等）需确认。
6. `$autojs.androidContext` 拿到的 Java 对象在 Node 侧的属性/方法访问边界（反射代理）需用例覆盖。

## 7. 给 task2/task3 的可执行信息

**task2（Node 模块/CJS 语义）建议探测脚本项：**
- 入口脚本 `typeof module/exports`、`module.exports={}` 是否生效；新建 `lib/a.js` 用 `module.exports` 后被 require 是否正常；
- `require('lodash')`/自定义 `node_modules/x/index.js`、`require.resolve('x')`、`require.cache`、`require('../lib/a')` 相对路径、`package.json "main"/"exports"`；
- `node:test`、`node:sqlite`（Node 24 内置 sqlite）、`node:sea`；
- ESM：`import('node:fs')`、`.mjs` 文件、`import.meta.url`；
- worker_threads 创建 Worker 并收发消息（Android 上是否可用）；
- 若入口 CJS 缺失：在 Node24Prelude 注入时给用户源码加 `(function(module,exports,require,__filename,__dirname){ ... })` 包装或提供 `module.exports` 兼容对象（改 Node24Prelude / native 侧注入方式，属 A 侧）。

**task3（Auto.js API/UI 对齐）建议：**
- 以 `$autojs` 暴露面为清单，逐项补 `device/files/app/events/engines/storages/threads/ui`（优先 samples 使用频率高的）；
- `ui`：用 NodeAndroidUI 示例做基准，覆盖 `ui.layout/ui.setMainActivity/Activity 生命周期/事件/资源 id`，区分 overlay fallback 与 NodeUiActivity 真 Activity 两种模式；
- `app`：补 `versionName/versionCode/launch/startActivityForResult/sendBroadcast` 等；
- 探测方式复用本任务：`/sdcard/脚本/node24probe` 项目 + 结果 JSON 落盘（不依赖 UI 自动化）。
