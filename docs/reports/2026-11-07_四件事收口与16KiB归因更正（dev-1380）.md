# 四件事收口：Rhino `.class`/精度/Array.set、任务结果导出、16 KiB 归因更正（dev-1380）

> 用户点名四件：① 32 条墓碑找不回；② `#15 Packages.<类>.class`（Rhino）；③ Rhino 整数精度与 `Array.set`；④ gadget `.so` 的 16 KiB 对齐。多任务并行收口，**其中 ④ 把自己的错误归因更正了**。

## 一、① 墓碑：找不回是真的，但给了"以后不会再丢"的工具

- 32 条墓碑的输出缓存**已经删了，物理上找不回**（保留策略：6 小时 / 最多 64 条已完成，超出即删）。
- 新增 **`apk_job_export{jobId, outPath}`**：把结果**原样**原子导出到工具操作目录（默认导出全部，`offset`/`maxChars` 可分页）。
- **K40 实测**：把一个 `SUCCEEDED_WITH_WARNINGS` 的 `apk_decompile_class`（`Interpreter`）结果导出 → `bytes=81228`、`chars=81162`、`sha256=08fb2a70c61a…`、`truncated=false`；再用 `file_stat` 复核导出文件 `size=81228`、`targetVersion=08fb2a70c61a…` —— **与工具返回逐位一致**。
- 导出文件在 `jobs/` 缓存之外，**淘汰不影响它**（JUnit 用例也证明了：先导出 `kept.json`，再触发淘汰，`kept.json` 仍在）。
- `apk_job_list.nextActions` 已指向该工具；保留窗口评估结论：**保持 6 小时/64 条**（`.4` 是 64 条上限先触发，单纯延长窗口只增驻留；64×24MiB ≈ 1.5GiB 已是上限）。

## 二、②③ Rhino：`.class` / 任意类静态方法 / 整数精度 / `Array.set` —— 全部修好且没弄坏引擎

**路线**：新增 `AijsNativeJavaClass`（继承 `NativeJavaClass`），**只经 `WrapFactory` 包装 Class 对象**，**不动 `Packages`/top-level scope/ClassCache**（dev-1377 的教训）。

队友还用设备上的 `JavaAdapter` 覆盖 `wrapJavaClass` 做了**路由实验**，证明 `Packages.java.lang.String` 确实经过 `WrapFactory.wrapJavaClass` —— 路线可行性是"证据"而不是"猜"。

**K40/dev-1380 实测（改前 → 改后）**：

| 探针 | dev-1379（改前） | dev-1380（改后） |
|---|---|---|
| `console.log(1+1)` | 2（引擎健康）| **2**（引擎仍然健康 ✅ 第一件事就查它）|
| `Packages.java.lang.String.class.getName()` | `InternalError: … has no public instance field or method named "class"` | **`java.lang.String`** |

## 三、④ gadget 16 KiB：**我们先前的归因是错的，已更正**

队友逐段解析 ELF 后推翻了原结论：

| 结论 | 证据 |
|---|---|
| 那 5 条 `ELF_PT_LOAD_ALIGNMENT_16K` 来自**目标 APK 自带的库** | `lib/arm64-v8a/libroot_automator.so`（段 2/3/4，`p_align=0x1000`，段 3/4 还不同余）+ `lib/arm64-v8a/libyj_aj_02_309.so`（段 2/3，`p_align=0x4000` 但不同余）|
| **注入前后完全一致** | 未注入的原包 `yj-orig.apk` 单独 `apk_verify` → **同样 5 条** |
| **注入的 Gadget 没有告警** | `libaijsgadget.so`（arm64）3 个 `PT_LOAD` 全部 `p_align=0x4000` 且同余 |
| 上游差异只在 **32 位** | arm64-v8a / x86_64：3/3 通过；armeabi-v7a / x86：3/3 失败（`p_align=0x1000`）|
| 两台测试机都**不是** 16 KiB 页 | K40 `getconf PAGE_SIZE=4096`；`.4`（SDK 37）也是 4096 |

**为什么会误判**：`partialReasons` 当时只有 `check` + 错误码，没有"是哪个文件"；我按"5 条 ≈ 4 ABI + 1"猜成 Gadget，还把它写进了 note 和随包文档。**教训：结构化诊断缺 `entry` 时，"归因"等于猜。**

**处置**：
- `partialReasons[]` 逐条带 **`entry`/`scope(target|injected)`/`owner`/`upstream`/`impact`/`segmentIndex`/`pAlign`**；`upstream:true` 只给注入的 Gadget。**K40 实测 5 条全部 `scope=target`, `owner=target`, `upstream=false`** ✓。
- `note` 改写为「partial 原因来自目标 APK 自带 native 库的 PT_LOAD 页对齐（见 `partialReasons[].entry`）；本工具注入的 Gadget（64 位 ABI）本次检测通过…」。
- 随包 Guide/Playbook 的归因段落**已改写**；两份旧报告（dev-1378/dev-1379）追加了「⚠️ 更正」小节。
- **不改 Gadget 组件**（官方 64 位已合规；32 位不合规但 16 KiB 页设备是 arm64，收益为零）；目标库只能由目标提供方用 NDK r27+`-Wl,-z,max-page-size=16384` 重编。
