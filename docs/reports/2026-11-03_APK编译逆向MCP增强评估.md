# APK 编译与逆向 MCP 增强评估

日期：2026-11-03。基线为 `290ab045` / LAN dev-1327。

本轮为源码核查、只读 MCP 工具清单读取、电脑 ZIP 对齐夹具验证及上游文档核对；未改产品源码，未安装新组件，未操作手机界面或第三方 APK，未发布新版本。下列新增工具名全部为建议，不是已经可调用的接口。

## 结论

当前基础编辑和导出链路已经可用，但 Java 阅读、连续导航、资源源码编译、导出验收与长任务管理仍有明显提升空间。建议先补导出质量和不增加大组件的导航能力，再把 JADX、AAPT2 等做成显式下载的可选组件，保持主 APK 体积。

“编译 APK”有三种不同来源：现有 `apk_build` 是对编辑会话重打包并可重新签名；现有 JavaScript 打包依赖运行时模板；Java/Kotlin/Gradle 源码工程从零构建则是另一套工具链。不能把前两项当作第三项完成。

## 当前已经有的能力

手机 `tools/list` 实际返回 128 个工具名称，文件/APK 工具组含状态入口共 58 个；不重复把 dev-1325 的旧缺口列成待开发项。

| 能力 | 当前实现与边界 |
| --- | --- |
| APK 编辑与导出 | 独立 `:tools` 进程、不可变快照、编辑会话、版本/原字节校验、原子写入、源包保留 |
| DEX / Smali | 类/字段/方法大纲、Smali 阅读、入向 xref、跨 DEX exact/slot/dispatch 匹配、类/方法编辑、新增类、编辑时 Smali 汇编 |

| 原生 | ELF 元数据、多架构反汇编、直接引用/部分重定位引用、CFG 摘要、符号解码、受控等长指令补丁和字符串补丁 |

证据：`McpToolkitCatalog.kt:5`、`McpToolkit.kt:19`、`McpApkToolkit.kt:58`、`ToolkitDex.kt:64`、`McpBuildTools.kt:10`、`AndroidBuildTool.java:21`，均位于当前仓库的对应 app/engine 源目录。

## P0：先完善导出的质量检查

### 已复现：普通 Stored 条目的 4 字节对齐漏项

源码 `apps/app/src/main/java/com/jdkshen/aijspro/mcp/ToolkitArchiveAlignment.kt:16` 的规则是：`.so` 16384、`resources.arsc` 4、其他 1。普通未压缩的 Manifest、assets、DEX 等因此没有统一按 4 字节对齐。

电脑直接调用当前编译产物中的生产 `ToolkitArchiveAlignment.align`，然后用 Android build-tools 34 的 `zipalign -c -v 4` 检查，得到：

| 条目 | 数据偏移 | 结果 |
| --- | ---: | --- |
| AndroidManifest.xml（Stored） | 49 | BAD，余数 1 |
| assets/a.bin（Stored） | 102 | BAD，余数 2 |
| classes.dex（Stored） | 148 | OK |
| resources.arsc（Stored） | 212 | OK |
| lib/arm64-v8a/libprobe.so（Stored） | 16384 | OK，同时满足 16KB ZIP 对齐 |

官方工具退出码 1。夹具是含占位字节的合成 ZIP，只验证条目对齐；它不用于证明 APK 可安装或 ELF 可运行。初次使用本机旧 zipalign 不支持的 `-P 16` 被拒绝后，已改用其支持的普通 4 字节检查；SO 的 16KB 数据偏移另行核对。完整日志、JSON、Java 调用夹具留在 `.artifacts/mcp-apk-capability-audit-20261103/`。

后续应修普通 Stored 文件的 4 字节基线，并增加奇数长度文件名/内容、Unicode 文件名、混合压缩、签名前后对齐的回归。现有 `ToolkitArchiveAlignmentTest.kt:15` 仅覆盖两个需对齐条目，未覆盖普通 Stored 文件。

这是 MCP 重打包路径的规则缺口；本轮没有对 dev-1327 主应用的 Gradle 发布门禁提出新的失败结论。

### 新增输出验收接口

建议 `apk_verify` 汇总：

- 真正执行签名完整性验证，分别返回证书读取、签名是否有效、使用的签名方案和平台区间；复用 apksig/受控 verifier，不能以“有证书”代替成功。
- 分开检查 ZIP 数据对齐与 ELF LOAD 段对齐，报告 ABI、SDK、压缩方式和必要的 split；有条件才给出安装兼容结论。
- 导出完成后重新读取产物，保留各阶段证据和错误；安装/启动测试作为独立显式动作，不能静默安装任意被分析 APK。

现有 `McpApkToolkit.kt:495` 主要做结构读取检查，`:539` 构建后检查证书元数据；`ToolkitSignatures.kt:95` 已正确标明 `verified=false`，要增加的是 verifier 功能。APK 对齐本身不能把 4KB ELF 重新链接成 16KB ELF。

## P1：最值得增加的功能

| 功能 | 建议接口（未实现） | 具体价值与验收 |
| --- | --- | --- |
| 方法级搜索和连续调用导航 | `apk_dex_search_members`、`apk_dex_call_graph` | 当前 Smali 搜索命中主要回到类，xref 主要查谁引用目标。增加方法/行范围锚点、向外调用、继承/实现关系、限定深度调用链；复用已有跨 DEX xref，不重复造同一接口。验收重载、虚调用、多 DEX、循环及预算截断 |
| Java 反编译阅读 | `apk_decompile_class`、`apk_decompile_method` | 可选 JADX 组件，按类延迟生成 Java，保留 Java↔Smali/原描述符跳转、错误列表和降级输出；可选 R8/ProGuard mapping 别名。没有 mapping 时不能承诺恢复混淆前原名；Java 输出用于理解，不承诺任何 APK 原样重编 |
| 资源源码编译 | `android_resources_compile` | 直接把项目 res/Manifest 与宿主依赖编译为 `project-res.apk` + sidecar，返回文件/行/错误和宿主资源摘要。解决当前 Node 项目仍需电脑手工编译资源的问题。采用可选 ARM64/Android AAPT2 后端，需先验证实际设备可运行，不能把桌面二进制直接当作手机工具 |
| 独立 DEX / SO 分析 | `artifact_open`（类型明确） | 当前 APK 工作区打开要求 `.apk` 和 Manifest；将 `ToolkitDex`、`ToolkitElf` 等已有解析器复用于独立文件，不再要求用户自己封装 APK。JAR/class 的 Java 语义读取另依赖可选反编译器 |
| 长任务、会话对比与回退 | `apk_job_start/status/cancel`、`apk_session_diff/checkpoint/rollback` | 现有 Provider 调用有全局同步区；已有终端 job 不等于 APK 编译/分析 job。长操作返回 jobId，分阶段进度/取消/超时，配合每工作区锁。区分结果分页与真实续扫，失败不留半成品；会话可预览修改并按检查点回退 |
| 真实能力矩阵 | 扩展 `toolkit_status` | 每功能返回 available/partial/unavailable、backend、版本、探测证据、安装命令；让 MCP 知道 JADX/AAPT2/汇编器是否就绪，不凭入口存在猜测可用 |

按包体和实施收益，第一批宜做 **P0 + 方法级搜索/调用导航 + 独立 DEX/SO + 状态矩阵**；JADX、资源编译后端作为下一批可选组件。这里将 JADX 视为用户扩展逆向能力的新需求，优先级不受旧 MT-MCP 对齐范围限制。

## P2：更深入的增强

1. **现代 DEX 引用**：当前 `ToolkitDex.references` 主要处理 Method/Field/TypeReference。补 call-site、method-handle、invoke-custom 等静态可解析信息，避免现代 lambda/字符串拼接等路径被略过；动态目标仍标为未知。
2. **拆分 APK**：APKS/XAPK/APKM/base+split 的整组读取、签名/版本/ABI 一致性及资源视图；AAB 可选接 bundletool。不能承诺任意 splits 无损合并成一个通用 APK，部分动态模块不进入 universal 包。
3. **Java 源码编译**：可选 ECJ/JDK 后端 → class → 复用 D8 → DEX，补 classpath、android.jar、min API 和错误定位；再考虑简单源码工程 APK。此前用户取消的完整 Java/Gradle/SDK 工具链，本轮仅列为可选方向，没有恢复或安装。
4. **原生深入分析**：在已有反汇编/CFG 之上，补 JNI 导出/注册映射、Java↔SO 定位、可选电脑端伪代码分析后端；重型反编译组件不默认塞进手机 APK。
5. **大包分析**：DEX/资源索引缓存、按类延迟反编译、预算内分页/续扫，必要时提供导出任务；不直接取消当前 64MiB 条目分析上限去冒内存风险。

## 可分派任务与通过条件

- A / 导出校验：只负责 `ToolkitArchiveAlignment`、签名 verifier、`apk_verify` 契约和对应测试。输出必须通过独立 zipalign/apksigner oracle；故意篡改签名应失败。
- B / DEX 导航：只负责 ToolkitDex/Search 的方法定位、出向调用及 schema；保留旧 locator 和跨 DEX 解析模式。依赖不存在、反射、间接调用必须报告不完整。
- C / 任务与会话：只负责 job/会话模型、IPC 取消/进度/检查点。实现者需与 A/B 约定接口，避免共同修改总 dispatch；主助手统一集成。
- D / 可选组件：先做 JADX/AAPT2 在 Android 的兼容性与独立进程小样，给出实测体积/内存/版本 pin，再决定是否产品接入；失败不能把功能标为已就绪。

本段仅为可执行任务草案，没有发出写代码任务。DP 本轮是独立只读审查任务 `b89a112feda44bdd`，已完成；主助手复核 source evidence 并执行上述 ZIP 对齐夹具。既有 dev-1326 验收报告继续有效，但不能覆盖本轮发现的新条目类型及新增功能。

## 上游依据（已核对）

- [JADX](https://github.com/skylot/jadx)：DEX/APK → Java 及使用点导航；其文档也说明无法保证全部代码正确反编译。
- [AAPT2](https://developer.android.com/tools/aapt2)：资源需要 compile + link；输出资源 APK 本身没有 DEX 和签名。
- [D8](https://developer.android.com/tools/d8)：输入是 Java 字节码，不是 Java 源码。
- [Apktool](https://github.com/iBotPeaches/Apktool)：资源解码、修改后重建及 Smali 工作流，可作为工作流设计参考。
- [apksigner](https://developer.android.com/tools/apksigner)、[zipalign](https://developer.android.com/tools/zipalign)：签名验证及签名前对齐顺序；Stored 普通文件按 4 字节、SO 可做 16KB ZIP 对齐。
- [16KB 支持](https://developer.android.com/guide/practices/page-sizes)：区分 ZIP 打包与原生 ELF 兼容，不把归档填充当作重新链接。
- [bundletool](https://developer.android.com/tools/bundletool)：按设备生成/安装 APK 集，universal 模式的模块范围有边界。
- [ECJ batch compiler](https://help.eclipse.org/latest/topic/org.eclipse.jdt.doc.user/tasks/task-using_batch_compiler.htm)：支持独立调用和编译进度/取消；Android 具体适配仍需另验。
