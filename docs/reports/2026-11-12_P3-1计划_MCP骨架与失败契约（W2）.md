## 1. 契约 v1（请先冻结）
| 字段 | 类型 | 何时出现 | 语义 |
| --- | --- | --- | --- |
| ok | bool | 总是 | false = 调用失败（此时 data 不得被当作结果） |
| reasonCode | string | ok=false 时必有 | 机器可读原因（见 1.1） |
| message | string | ok=false 时必有 | 人可读中文（Dart 直接显示） |
| data | any | ok=true 时 | 成功结果（含「成功但结果为空」的既有自描述字段：hasMore/nextAfterId/items=[]） |
| empty | bool | **当前未引入** | **保留字段**：等第一个「自身字段无法表达空」的工具出现时再引入（见下） |
| paging | object | 可选 | offset/limit/total/hasMore |

三态唯一口径（**2026-11-12 更正，与实现同步**）：① 失败 = ok=false + reasonCode + message；② **空结果 = 由工具自身的字段表达**（例如 read_apk_logs 的 hasMore/nextAfterId、continue_result 的 hasMore、列表类工具的 items=[]）—— **不引入新字段**；③ 成功 = ok=true + data 有内容。
· **为什么删掉 empty=true 的强制形态**：实测既有工具的空结果**本来就可判别**（hasMore/next* 等自描述字段）⇒ 新字段是**零调用点负债**（本会话已三次验证这条模式：pluginRow 无调用者、无字面引用、helper 无钉子 ⇒ 都会腐化）；ToolkitIo.empty(...) 因此**已删除**，并加钉子「**不得无声回归**」（要加回必须同时接线 + 补测试）。
· **将来引入 empty 的条件**：出现一个工具，其自身字段**无法**表达「成功但为空」时，才加该字段（届时同步 Dart 侧 + 登记本表 + 钉子）。
禁止：用 data={} 表示失败；用 ok=true 掩盖异常。

### 1.0 两条冻结补充（Lead + W4 消费方反馈，2026-11-12）
1. **message 是权威字段**；原生**同时**把它镜像进 error（**兼容镜像**，过渡用，文档标明）—— 因为现有 Dart 读的是 error，只给 message 会让失败退化成「操作失败」。
2. **领域码允许共存**：下面 8 码是「骨架/通用码」；工具可追加领域码（checksum/package/missing…），但必须**登记 + 单测钉住**；**消费方遇到未知码必须回退显示 message**（强制条款）。
3. **分层（Lead 裁决）**：协议层参数**形状**错 ⇒ 继续 McpInvalidParamsException（语义「never a tool execution error」）；工具层**业务参数**错 ⇒ invalidArg；**工具层不得吞掉协议层异常**（协议层错误必须原样冒泡，不得被 internal 兜底改写）。
4. 失败结果沿用既有 MCP 约定：**isError=true**（McpToolResultShapes 里已有该判据）+ structuredContent 内写 ok=false/reasonCode/message/error 镜像。

### 1.1 reasonCode 取值表 v1（8 个码；前 5 类沿用既有 PluginFailureReason 口径）
| code | 含义 | 谁产生 |
| --- | --- | --- |
| invalidArg | 参数缺失/类型不符/超限 | 骨架层 |
| notFound | 目标不存在（文件/包/页面/记录） | 工具层 |
| permission | 权限/无障碍/悬浮窗/存储未授予 | 工具层 |
| unsupported | 设备/ABI/版本不支持该能力 | 工具层 |
| busy | 资源占用/并发冲突 | 工具层 |
| timeout | 操作超时（含等待上限） | 工具层 |
| network | 网络或远端失败 | 工具层 |
| internal | 未预期异常（骨架兜底）：必须同时 Log.e + message 带异常类型 | 骨架层 |

规则：只能追加码；每个码值都要有单测断言字符串（防漂移）。

### 1.0.1 既有失败信封的更丰富形态（不要以为只该有 reasonCode+message）
dev-1522 真机基线（tools/call 原始回包）显示，**协议层失败今天已经是**：isError=true + errorCode=INVALID_ARGUMENT + error（对象）+ details + baseline（外加 ok=false）。
⇒ 契约描述必须**补全既有字段**（只增不删），否则后人读文档会以为那些字段可以删。
**已知不对称（不是遗漏）**：协议层（JSON-RPC handler）今天**只有 errorCode、没有 reasonCode**；补 reasonCode 镜像会影响所有工具调用的失败路径（面太大）⇒ 排到 P3-1 第 2 批或长期；**在此之前不得因此把 ToolkitIo 的双写简化掉**（那是新契约的权威字段）。

## 2. 骨架三层（一个新文件 + 一个新测试）
1. 参数层：取值/默认值/类型校验（缺参或类型错即 invalidArg，禁止后续 NPE）；
2. 分页层：offset/limit 归一 + 上限（超限给 invalidArg，不静默截断）；
3. 回包层：ok()/fail(reasonCode, message)/empty() + catch-all 兜底（internal）⇒ 契约上永不抛（与 BridgeCall.run 同口径）。
兜底只能是最后手段：Log.e + message 带异常类名与位置，不得掩盖可归因失败。

### 3.1 分页/上限口径（Lead 裁决 (a) + 三条守门，2026-11-12）
1. **既有读取点**（已用 coerceIn 的 5 处：timeoutSeconds 600 / limit 500 / count 10000 / intervalMs 2000 / maxChars 65536）⇒ 走 McpArgClamp.clampInt，**行为逐字不变**（仍然夹紧），但**必须**把 clamped/requested/effective 写进 **ToolkitIo.json(...) 的顶层**（与 ok/data/error/nextActions 同级）；
   · **为什么只能是顶层（Lead 定死，不留「或」）**：真机上 structuredContent 与 content[0].text 是**同一份对象的两个镜像**（Lead 实测 keys 都是 data,error,nextActions,ok）⇒ 只要加进 json() 两边就都有；而 Dart 侧读的是 content text（jsonDecode）⇒ 只进 structuredContent 会让 **Dart 读不到**；
   · **验收判据**：**同时**在 structuredContent 顶层与 content[0].text 解析出的对象里都能看到 clamped（钉子照此写）；**不得只写日志**。
2. **32 KiB 护栏覆盖**：clamped 字段计入 DATA_MIRROR_LIMIT_BYTES ⇒ 1c 回归要加一条「带 clamped 的结果不会被 summarize 掉」；
3. **将来新增参数一律严格模式**：超限 ⇒ fail(invalidArg)，**不夹紧**（防止后人照抄既有写法）；
4. 抽取时**默认值/上下限逐个照抄原处**，**不许统一成一个数**。

每批通用验收：① 三态输入断言 ok+reasonCode+data；② 该工具原有单测全绿（禁止改断言语义）；③ :app 编译（等 Lead 给窗口）；④ diff 只含「骨架调用 + 返回包装」，不得含业务逻辑改动；⑤ **32KiB 护栏回归**：证明新增字段没有把该工具推进摘要名单（测：构造接近上限的结果，断言 structuredContent 仍含 data 且未被 summarize）。

## 5. 风险
| 风险 | 处置 |
| --- | --- |
| 面广（89–128 fun/文件） | 样板先行 + 每批独立 + 不一次铺开 |
| 契约漂移 | 1.1 表先冻结 + 每码值单测断言 |
| internal 兜底掩盖真异常 | 兜底必须 Log.e + 带异常类型；可归因失败必须用具体码 |
| **加宽 catch 的固有风险**（本批实证） | **加宽 catch 前必须枚举既有异常类型，并确认归类正确** —— 本批 structuredCall 加 internal 兜底后，工具内 require(...) 抛的 IllegalArgumentException 会被降级成 internal（本应是 invalidArg）⇒ 要么用**自定义异常**精确 catch，要么先证明该类型来源单一（实测 mcp/** 里 require( 有 720 处、IllegalArgumentException 476 处、分布跨 44 个文件 ⇒ **来源不单一**，不得用宽 catch） |
| Kotlin check(...) 走 IllegalStateException | 既有 structuredCall 把 IllegalStateException 映射成 WORKSPACE_STATE_CONFLICT ⇒ 工具里用 check(...) 做参数/前置校验会被误标成「工作区状态冲突」（既有行为，登记为待办，不在本批改） |
| 客户端未适配 | 只增字段；Dart 先按 ok/reasonCode 显示，data 判空沿用 |
