# 大文件分享后台化与复核

日期：2026-10-24。状态：**已打包发布 dev-1243，双机更新清单及 MI8 完整下载校验通过，尚未安装。** 详见[发布记录](2026-10-24_dev1243发布.md)。下文保留源码复核及本地检查的证据边界，实际分享仍待原场景复测。

## 用户现象和证据边界

用户确认：从 AI.js Pro 分享到其他应用，内容约 80 多 MB。尚未明确是单文件还是文件夹，也未明确是在接收应用选择前或选择后退出。

本轮只读取得 K40、小米 8 的 crash buffer，没有找到能对应本次分享的堆栈；其中旧的 Node 回调和 log4j 记录不能归为本次原因。`192.168.10.4:8765` 的连接超时，未取得原问题设备日志。没有停止或安装两台手机上的应用。

因此，以下是对源码中确定缺陷的修复，**不能据此宣称已经确诊或真机修复这一次闪退**。

## 已确认的问题

- Flutter 文件列表的 `share` / `shareFile` 经 `PocBridge.handle → execute → PocWorkspace.share` 同步执行。分享文件夹时，ZIP 遍历和压缩占用 Android 主线程，大工程有无响应风险。
- 旧逻辑在整个 ZIP 写完后才检查 128MiB 限制；写入中途出错时也没有完整的临时包清理。
- Flutter 的一般桥超时为 20 秒，分享没有列入允许较长等待的操作。改成后台压缩后，也必须同时调整等待时限。
- 原 Flutter 分享出口没有复用通用分享的 ClipData 权限传递路径。

单文件原本已用 content URI 传递，未把整个文件放进 Intent。80MB 本身不是这条路径的文件大小限制；不能把文件夹压缩问题直接当成所有单文件分享失败的根因。

## 本轮修改

1. **后台分享**：`PocBridge` 将 `share` / `shareFile` 提前路由到 `PocWorkspace.startAsync`。文件校验、文件夹压缩和 URI 准备在专用工作线程执行；主线程只打开系统分享选择器并回复结果。
2. **重复点击与生命周期**：准备期间只接受一个分享任务；页面已关闭时不再弹出选择器，失败会释放准备状态并清理本次生成的 ZIP。Flutter 引擎销毁造成的回复异常只记录日志，不在主线程再次抛出。
3. **统一分享权限和 MIME**：复用 `ProjectSharing.createSendIntent` 的 `EXTRA_STREAM + ClipData + FLAG_GRANT_READ_URI_PERMISSION`。未知类型按 `application/octet-stream` 发送，避免把未知二进制默认标为文本。已知扩展名继续使用原映射。
4. **流式压缩限额**：`ProjectArchive.create(source, cache, maxBytes)` 在写出压缩数据时检查上限，包含 ZIP 头和中央目录。Flutter 文件夹保留原有 128MiB 压缩包上限；单个普通文件不增加这一限制。原两参数 ProjectArchive 调用保持原有不设此上限的行为。
5. **关闭与清理**：ZIP finish/close 本身可能抛出超限异常，因此单独持有并关闭底层文件流，确保异常后可以删除部分 ZIP。该问题被 Windows 下的清理用例捕获并修正。
6. **等待时间**：Flutter `share` / `shareFile` 允许等待 5 分钟，普通桥方法仍为 20 秒。本轮无需改变界面操作方式。

## 后续装机验收

- 本轮改了 `flutter-ui/lib/bridge.dart`，出新包前必须重建 Flutter AOT，再构建宿主；不可直接复用 dev-1242 的旧 AOT。
- 用 80–90MiB 单文件和同量级完整工程文件夹分别验证：打开分享面板、取消、选择目标应用后读取完整数据、返回原应用。
- 同时检查压缩期间 UI 响应、重复点击、超限、源文件消失和压缩期间退出页面。系统分享面板和接收应用可能有各自的行为，需记录实际退出的是哪个进程。
- 原设备重新连通后，对齐分享时刻、进程和崩溃堆栈，再决定是否还存在额外的内存、渲染或接收应用问题。
