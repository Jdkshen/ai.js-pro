## 截图中需要修正的推断

| 截图表述 | 源码核对结果 |
| --- | --- |
| Node 最多 4 个并行实例 | `Node24Pool.SLOTS=3`，默认运行在 `:node24_1..3`；`:node24` 是旧回退通道。不能按 Manifest 中进程名称数量认定正常支持 4 路并发。池满后当前 init 会在 acquire 抛错时尝试旧通道，后续应明确区分“容量已满”和“池启动故障”，避免容量限制被意外绕过。 |
| 三引擎 API 都来自同一套 51 个 JS 文件 | 只有部分 common-* 实现共用；Node 还有独立 prelude/模块和宿主桥，QuickJS/Rhino 各有适配。文件在 APK 中存在不代表三个引擎都使用或行为一致。 |
| 37 个 DEX 说明卡顿原因 | 构建确实关闭了 minify/shrink，但 DEX 数量不能直接证明启动瓶颈。必须测实际类加载、主线程、布局和桥调用。 |
| source-engine-upgrade 路径说明运行时可以热升级/下载 | 当前 `Node24Libraries.prepareFiles` 明确只使用内置 assets；缺失时报错，不走网络下载。旧 Downloader 类还在源码中，不代表当前生产加载路径使用它。保留用户要求的离线 Node。 |
| extractNativeLibs 意味着所有 Node 资源都会在安装时解压 | `lib/` 由 Android 安装机制处理；Node 在 assets，走自己的首次准备、文件锁、SHA 校验及进程内加载路径，两者不同。 |
| libquickjs.so + libquickjs_jni.so 是重复引擎 | 名称或数量不足以判断重复依赖；需要核对 JNI/ELF 依赖与实际加载方。本次仅确认两库存在，没有据此提出删除。 |

Flutter 主界面、Java 自动化内核、原生 Node UI、多进程服务这些分层基本正确。高级版 API 全量兼容、native 稳定性与 16KB 真实内核兼容均不能由静态盘点确认。

## 体积盘点：不要混淆原始体积与压缩贡献

以下单位均为 MiB；“压缩贡献”是 ZIP entry 的 compressed size 之和，不包含所有 ZIP/签名开销。

| 内容 | 原始体积 | APK 压缩贡献 |
| --- | ---: | ---: |
| Node source-engine-upgrade | 107.69 | 41.20 |
| lib/arm64-v8a | 72.41 | 31.39 |
| 打包模板 template.apk | 16.40 | 15.92 |
| assets/models | 14.88 | 11.91 |
| 示例 | 13.44 | 11.86 |
| 编辑器 | 10.09 | 2.41 |

两处 libc++_shared.so 内容完全相同；一份压缩后约 0.43 MiB。与 Node 独立运行时路径、SHA pins 和动态链接机制有关，是否合并需要专项验证，收益较小，排在上述项目之后。不能直接从 assets 删除。

assets 模板的存在也暴露文档漂移：`apps/app/build.gradle` 约 209 行仍写“宿主不包含 template.apk”，后面的构建硬门却明确要求它。建议随下一次打包整理一并修正，避免后来维护者误删。
