# 把「算棋」挪到独立引擎线程（worker）：真机量化与验收（2026-09-14）

对象：`apps/app/src/main/assets/sample/QuickJS 新引擎/项目与打包/象棋自动走棋`

## 1. 为什么做

面板/主界面此前把 **采集、识别、算棋** 全排在脚本线程上：算棋一步 `movetime = 1200ms`，
实测端到端 1263~1299ms。这 1.2s 里悬浮窗的触摸事件、心跳、日志渲染全被挡住 ——
用户观感就是「点了没反应 / 很卡」。上一批只做了止损（隐藏抓帧「自动」、日志 250ms 合并渲染、
仪表可视化），这次才是把长阻塞**搬离脚本线程**。

## 2. 机制事实（都经真机/源码确认，别再踩）

| 事实 | 依据 |
| --- | --- |
| `threads.start(fn, args)` 起的是**独立 QuickJS 引擎**（自己的线程）→ 真并行 | `QuickJsHostBridge.threadsExec()` → `engines.execScript`；两 worker 并发 1368ms vs 串行 ~2400ms |
| 句柄的 `getResult()` **非阻塞**：`{status:'running'/'success'/'error'}` | `quickjs_jni.cpp` 里 `makeThread` / `resultState(0)` |
| worker 的源码是**内存串**，`__dirname` = `"."` → 必须用**绝对路径** `require` | `scriptDirectory("QuickJS-Thread")` = `"."`；已用 `__args.dir`（调用方 `__dirname`）解决 |
| 脚本体形式 `threads.start("...")` 里写顶层 `return` 会报 `SyntaxError: return not in a function` | 实测；函数形式会被序列化成 `(fn)();`，`return` 才合法 |
| worker 回传值里**以 `{` 开头的字符串会被引擎提前 `JSON.parse` 成对象** | 实测：只认字符串时报 `worker 回传的内容解析不了：[object Object]` |
| 函数任务**不捕获外层闭包**，数据只能走 `__args`（JSON） | 文档 + 实测 |

## 3. 实现

- 新增 `src/automation/search-worker.js`：`create({dir, graceMs})` → `start(position, {movetime})` /
  `poll()`（非阻塞）/ `cancel()` / `isRunning()`；worker 侧 `workerTask()` 用绝对路径 require
  同一份 `src/engine/engine.js`，只回传必要字段（`ok/iccs/score/depth/nodes/ms/mateIn/reason`）。
- `src/automation/auto-driver.js`：
  - `compute(effect)` 改成「起 worker → 立刻返回」，结果由 `pollCompute()` 在后续 tick 里收回，
    再走**原有的** `JOB_RESULT` 事件喂回状态机（状态机本来就按 `jobId` 作废旧结果，S02/S03 不变）。
  - 保留同步兜底 `computeInline()`：宿主没有 `threads`（如离线自检的 Node）或 `computeMode:"inline"` 时用它。
  - worker 只回 ICCS，着法对象由主线程用 `legal.allLegalMoves()` 反查（着法生成比搜索便宜得多）。
  - 新增 `computeGraceMs`（默认 4000）：worker 卡死也要有结论，否则状态机会永远停在 THINKING。
  - 新增 `isThinking()` / `pollCompute()`；`stop()` 与 `CANCEL_JOB`（局面变了）都会 `cancel()` worker。
  - 统计：`thinkOffThread` / `thinkInline` / `thinkMs`；`describe()` 里报算棋模式。
- 悬浮窗面板 / 主界面：算棋中把下一轮轮询间隔压到 **120ms**（本轮不截图，只 `getResult()`），
  算完第一时间出手；面板 autorun 支持 `"computeMode":"inline"` 做对照。

## 4. 真机实测（小米8 = MI 8 Explorer，LineageOS 15，1080×2248）

探针：`.artifacts/stage-m8/_thread-probe.js`（worker 机制）、`_driver-probe.js`（驱动整条链路，
桩识别 + 真引擎）。口径 = **最长心跳间隔**（1s 心跳，空载 ≈1000ms）。

| 场景 | 算棋耗时 | 算棋结果 | 主线程最长心跳间隔 |
| --- | --- | --- | --- |
| 驱动 inline（老路径，本线程同步） | 1263 / 1280 / 1277 / 1282 ms | `b2e2` 深度 2 | **2193ms（≈本线程被占 1193ms）** |
| 驱动 worker（新路径，独立引擎线程） | 1285 / 1285 / 1299 ms | `b2e2` 深度 2（同解） | **1026ms（未阻塞）** |
| 两 worker 并发 | 合计 1368ms（串行应 ~2400ms） | 两次均 `b2e2` | — |

**验收达成**：算棋期间本线程阻塞 ~1193ms → **~26ms**（目标 <200ms）。
代价：算棋结论到出手多约 0~150ms（120ms 轮询粒度 + 结果回收），总耗时 1.5s 左右（含轮询）。

## 5. 顺手修掉的仪表口径错误

原「线程阻塞峰值 = 心跳间隔 − 1000ms」**会少算一个时钟周期**：小米8 上一次 1279ms 的同步算棋
只被报成 **290ms**（定时器是「上一次触发 + 1000ms」重排，长阻塞只体现在第一次迟到上）。
现在面板**直接报「最长心跳间隔」**（空载 ≈1000ms，超过 1200ms 才计数），不再做减法。

## 6. 回归与门禁

- `node tools/self-check.js` → `SELF_CHECK OK passed=116 failed=0`（新增 5 条：无 threads 时退回 inline、
  worker 起不来仍能出着法、pollCompute 空闲返回 null、回传载荷对象/JSON 串两种形态、导出面）。
- 设备端：`_thread-probe.js`、`_driver-probe.js` 均通过（上面表格）。

## 7. 小米8 真棋局实测（2026-09-14 深夜，补记）

环境：小米8（MI 8 Explorer，LineageOS/Android 15，1080×2248）+ 天天象棋 4.4.5.2（从腾讯官方 CDN 装，
QQ 扫码登录）+ 投屏授权（`共享一个应用 → 天天象棋`，adb 点选）；
root 情况：**adb shell 本身就是 root**（userdebug），但系统**没有 `su`** → App 拿不到 root；
Shizuku 13.6.0 已装并用 adb(root) 启动（新版启动器是 `lib/.../libshizuku.so`，**没有 start.sh**）。

跑法：面板 autorun `{"start":true,"mode":"advice","declareTurn":true,"stopAfterMs":60000,"computeMode":"worker"}`。

这一轮（投屏通道、未修抓帧层之前）观测到的事实：

- 抓帧与几何：走 `captured-frame` 通道，定位 + 校准 **6.6s**，偏移 (0,-9)、未知格 1、起点 (83,628)、
  格距 (115,114) —— 与 K40 的 (81,666)/(115,114) 同量级。
- **单帧观察 490~550ms**（K40 同流程 165~200ms）：小米8 这条 capture 通道更慢。
- 心跳口径（本报告修过的那一条）实测读数：空载 ~1000ms；每轮观察后 ~1509/1470ms
  （多出的 ~500ms 正是那次观察）；启动+校准期间一次性 **8496ms**。
- 当时读出的局面是错的（`RNbakabNR/9/1C5C1/…/rnBAK?BNr`：顶行两端判成红、中间判成黑），
  且驱动卡在 `RECOVERING｜棋盘几何不可信`。
- **这两件事后来都定位成抓帧通道问题**（半帧 + 投屏预热），不是分类器问题 —— 见第 8 节与第 9 节：
  同一帧用 root `screencap` 抓成文件识别是**全对的**，改成 shell 通道后驱动也读对了。


## 8. 抓帧层两个真机 bug（已修，commit 8516377）

真棋局一开始读不出局面（`子 0 空 90`、左列 a9-c9 全空、首次观察卡 113 秒）。查下来是
**抓帧通道**的问题，不是识别链路：同一帧用 root `screencap` 抓成文件再识别是**全对的**
（`rnbakabnr/…/RNBAKABNR`、未知格 0），说明定位/分类器/几何都没问题。

1. **半帧丢左列**：`tools/recognize-board.js` 的「复用已校准几何」分支原来写死
   `adapter.capture("full", 300)` —— 投屏通道慢时拿到「半更新帧」，左列直接丢子。
   → 默认超时改 **1200ms**（`opts.timeoutMs` 仍可覆盖）。
2. **投屏授权同步阻塞 113 秒**：同一分支先调 `requestCapture()`；有 Shizuku/shell 通道时这纯属多余，
   会弹投屏框并阻塞到有人点（实测 `本轮观察：113212ms`、心跳间隔 113615ms）。
   → 面板支持显式选通道：autorun 里 `"captureBackend":"shell"`（`adapter.setCaptureBackend`）。
   ⚠️ 面板的「识别一帧」走 `grabFrame()`（本来就是 shell 优先）所以一直是对的，驱动那条路不是 ——
   排查时**要按「哪条路抓的帧」分开看**，别把两个通道的现象混在一起。

## 9. 真机全链路验收（通过，2026-09-14 01:2x，小米8）

跑法：面板 autorun `{"start":true,"mode":"advice","declareTurn":true,"stopAfterMs":70000,`
`"computeMode":"worker","captureBackend":"shell"}`（② 着法建议，不点击棋盘）。

```
截图通道偏好：shell
识别：子 31 空 59 未知 0｜局面 rnbaka1nr/9/1c5c1/p1p1p1p1p/9/9/P1P1P1P1P/1C5C1/9/RNBAKABNR
[driver] 算棋（worker 线程）：轮到 红，预算 1200ms
状态 THINKING｜轮到我方，开始算棋
状态 THINKING｜算棋中（worker 线程，已 123ms）→ 已 1127ms      ← 主线程只 poll，没被占
[driver] 算棋：轮到 红，b2c2（深度 3，1307ms，评分 220）        ← 真棋盘上出了着法
状态 RECOVERING｜出手前核对不通过：当前模式禁止点击（只识别/着法建议）  ← advice 模式的正确行为
```

- 观察耗时：首帧 10.9s（Shizuku 预热），之后 **469~510ms/帧**（shell 通道比投屏 490~550ms 略快）。
- 结论：① 的「识别 → worker 算棋 → 计划 → 核对」在**真棋盘上跑通**；算棋期间主线程每 120ms
  只做一次 `getResult()` 轮询，不再被 1.2s 的搜索挡住。

## 11. 追「g0 的象漏检」：其实是半帧 bug 的又一个症状（2026-09-14）

在小米8 开局帧（棋盘看得很清楚：32 子全在、0 步）上，用探针把同一帧跑四组配置：

| 配置 | 原始框 | 结果 |
| --- | --- | --- |
| v5r 矩形 + 整屏（默认） | 33 | 子 31 空 59 未知 0，`rnbakabnr/…/RNBAKABNR` |
| v5r 矩形 + 整屏 + confidence 0.10 | 37 | 仍然 31（多出来的都是低分噪声） |
| v5r 矩形 + 棋盘 | 32 | 31（同上） |

- **两端的底线其实都是完整的**（`rnbakabnr` / `RNBAKABNR`）→ 之前看到的 `rnbaka1nr`（(6,0) 的象没了）
  是**半帧 bug 的又一个症状**，已随第 8 节的 1200ms 修复消失。
- 这帧真正缺的是 **(4,3) 的黑卒 e3**：原始框里「兵/卒」类只有 **9 个**（应有 10 个），
  而且把 confidence 降到 0.10 也**出不来这个框** → 是模型的**纯漏检**，不是阈值问题。
  同时「帅/将」类给出 **3 个**框（应有 2 个），两个真将帅的分数只有 0.47 / 0.65，多出来的那个是假阳性。
  ⇒ 归到 v5r 矩形档的实测精度里（冻结集 97.0%；本帧 31/32 = 96.9%），不单独修。
- 顺带发现一个**回滚陷阱**（已修）：只把 `MODEL_FILE/LABELS_FILE` 改成方形档、
  不改 `INPUT_HEIGHT`（还是 320）时，方形模型会直接崩：
  `OpenCV reshape2_layer.cpp: Assertion failed outTotal == inpTotal`。
  现在 `loadDetector` 加了防呆 —— 传方形 `inputSize` 时自动把两维拉平（真机验证：两组方形配置都变成
  `输入=160x160`、不再崩），文档（`assets/models/README.md` + 文件头注释）也改成「要改五个常量」。
