## 四、必须记下的教训：dev-1377 引擎全坏（未发布）

- 为修 #15，队友把 Rhino 的 `Packages`/`java`/`org`/`com`… 换成自定义的 `AijsJavaPackage`。
- **后果**：Rhino 在**任何**脚本上都报 `Can't find top level scope for ClassCache.get`（连 `console.log(1+1)` 都跑不了），Node 不受影响。根因：Rhino 的 `ClassCache` 绑定在自己的 top-level package 上。
- **为什么单测没挡住**：JVM 单测（`AijsJavaPackageTest`）与编译全绿 —— 这类"作用域对象替换"只有真机跑一个 trivial 脚本才暴露。
- **处置**：dev-1378 回退（删 4 个新类 + 测试，恢复原 `Packages`），保留其余修复；回归验证 Rhino `trivial=2`、`abs=5`（#14）、`catch=UnsatisfiedLinkError`（#16）、Node `Array.set=5` 全部正常。
- **写进流程**：以后改 Rhino 的包/作用域/`Packages`，构建后第一步先在设备上跑 `console.log(1+1)`。

## 六、仍未做 / 新发现（下一批候选）

1. **#15 `Packages.<类>.<静态方法>` / `.class`（Rhino）** —— 仍不支持。当前可用替代：`java.lang.Class.forName("全限定名")`；静态方法走 Rhino 原生 `Packages.<类>.<方法>`（多数可用）。要真做需要**不动 top-level package** 的前提下介入类对象创建（例如 WrapFactory 层），有风险，需单独评估。
2. **Rhino 整数精度**：`java.lang.String.valueOf(42)` → `42.0`（Node 侧是 `42`）。属 Rhino 原生行为，与 #14 的 `Method.invoke` 收窄不是同一条路径。
3. **Rhino `Array.set(int[],0,5)`** 仍报数组元素类型错误（Node 侧已修）——它走 Rhino 自己的成员调用，不在我们的桥里。
4. **新发现：注入的 gadget `.so` 不满足 16 KiB 页对齐**（`partialReasons` 报 5 处 `ELF_PT_LOAD_ALIGNMENT_16K`）。这在 16 KiB 页设备上可能影响加载，建议下一批处理组件 `.so` 或明确文档化。
5. `apk_job_result` 的 **JSON schema `maxChars` 上限仍是 200000**（默认读取已 1 MiB，够用；客户端显式传 >200000 仍需改 asset）。
6. `apk_inject_gadget` 的 `detail` schema 字段由队友加在 `ToolkitReverseTools.kt`（超出其允许清单一行）——已保留（否则 `tools/list` 看不到该参数）。

## ⚠️ 更正（2026-11-06 当晚，由队友 ELF 调研推翻）

本报告曾把 `apk_inject_gadget` 的 `verification.status=partial` 归因成「**注入的 gadget `.so` 不满足 16 KiB 页对齐**」。**这个归因是错的。**

`docs/reports/2026-11-06_gadget-ELF-16KiB对齐调研.md` 逐段解析 ELF 后证明：

| 结论 | 证据 |
|---|---|
| 那 5 条 `ELF_PT_LOAD_ALIGNMENT_16K` **来自目标 APK 自带的库** | `lib/arm64-v8a/libroot_automator.so`（段 2/3/4，`p_align=0x1000`，段 3/4 还不同余）+ `lib/arm64-v8a/libyj_aj_02_309.so`（段 2/3，`p_align=0x4000` 但不同余）|
| **注入前后完全一致** | 对**未注入的**原包 `yj-orig.apk`（sha256 `ffe1365a…`）单独 `apk_verify` → **同样 5 条** |
| **注入的 Gadget 没有新增告警** | `libaijsgadget.so`（只注 arm64）3 个 `PT_LOAD` 全部 `p_align=0x4000` 且同余 |
| 上游 Gadget 的差异只在 **32 位** | arm64-v8a / x86_64：3/3 通过；armeabi-v7a / x86：3/3 失败（`p_align=0x1000`）|
| 两台测试机都**不是** 16 KiB 页设备 | K40 `getconf PAGE_SIZE=4096`、`.4`（SDK 37）也 `=4096` |

**为什么会误判**：`partialReasons` 当时只给了 `check=native` + 错误码，没给**具体是哪个文件**；我按"5 条 ≈ 4 ABI + 1"猜成了 gadget，并用它写了 note 与文档。**教训**：结构化诊断必须带 `entry`，否则"归因"就是猜。

处置：① `partialReasons[]` 增加 `entry`/`scope(target|injected)`，`upstream:true` 只给注入的 Gadget；② note 与随包文档改写；③ 不改 Gadget 组件（官方 64 位已合规）。
