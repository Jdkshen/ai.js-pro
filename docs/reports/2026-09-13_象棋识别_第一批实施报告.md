## 3. P0：空格契约与计数（执行单 §3.1）

**已确认的问题**：`recognizer.js` 的空格在 FEN 字符层是 `null`（既定契约：`fen.layoutOf`、`rules.pieceAt` 都按 falsy 判空），
而 `scoreGrid()` 用「不是 `.` 且不是 `?`」数棋子 → **null 空格全部被算成棋子**。真机表现是「子 90、未知 0」这种不可能的读数，并且**退化网格因此被评为最优**。

**修法**：新增 `cells.js` 作为唯一计数/判定入口。

```js
// 正向白名单，不做「排除法」
const PIECE_CHARS = "RNBAKCPrnbakcp";
isPieceChar(ch)  // 长度 1 且在白名单里
isEmptyChar(ch)  // null / undefined / '' / '.'（兼容外部输入，集中在此转换）
stateOf(ch)      // PIECE / EMPTY / UNKNOWN / INVALID
count(chars)     // { total, pieces, empty, unknown, invalid[], ok, reason }
```

行为测试（`node tools/test-cells-contract.js`，**15/15 通过，退出码 0**）覆盖执行单点名的用例：

| 用例 | 结果 |
|---|---|
| 开局 32 PIECE / 58 EMPTY / 0 UNKNOWN，总数 90 | ok |
| 空格两种写法（`null` 与 `'.'`）计数一致（事故点） | ok |
| 合法残局 2 / 4 / 8 子：计数与 FEN 往返一致 | ok |
| 含 1 个 UNKNOWN：三态数量准确（不算空、不算子） | ok |
| 非法字符 / 长度 89 / 全空 / 缺将 / 坏 FEN：都有明确原因 | ok |
| 退化网格拒绝：无检测框 / 棋盘在搜索范围外 / 框全在棋盘外 | ok |

## 4. P1：几何搜索（执行单 §4.1 / §4.2）

### 4.1 反复加载与选项丢失

- 旧 `scoreGrid()` 每个候选都调 `run()` 且不注入 detector → `run()` 内部 `loadDetector()`…`close()`，**171 次加载/关闭**；同时构造临时 opts 时**丢掉了 model/labels/inputWidth/inputHeight 等**（多模型评测时会对不上模型）。
- 现在：`pickGrid` 每次调用**只加载一次**（除非调用方注入），候选评分全部复用同一个 detector；`finally` 关闭自建 detector（调用方注入的不关，错误/早退/取消都不漏）；模型与输入尺寸选项原样透传。

### 4.2 缓存框几何搜索（把几何与检测解耦）

一次检测（裁剪范围比棋盘多留一圈，覆盖 ±radius 候选）→ 之后每个候选用**纯坐标运算**评分（`cell-assignment` + 棋规校验），只对胜出几何再做一次完整识别（拿颜色/修复/布局）。

**真机实测（同 9 帧，K40）**：

| 几何实现 | 每帧耗时 | 候选数 | 严格含阵营 | 纯阵营错 | 占用召回 |
|---|---|---|---|---|---|
| 旧：每候选一次完整 `run()`（历史实测） | **≈19800ms** | 171 | （未重复测） | — | — |
| 中：共享 detector + 每候选 `run()` | 未单独取到（见 §8「未取到」） | — | — | — | — |
| 新：缓存框搜索（cached） | 检测 10~18ms + **搜索 58~82ms** + 末次识别 129~147ms → **总计 70~170ms** | 100~321 | 88.9%（700/787） | 62 | 94.7% |
| 定位器 + `calibrateGrid`（现役执行路径） | **160~176ms** | — | **99.4%（782/787）** | **0** | **98.5%** |

**结论（按执行单「不预先承诺，先比较再选」）**：
- 采用 **定位器 + `calibrateGrid`** 作为执行路径（质量最好）；缓存框搜索作为**定位器失败时的兜底**（比旧实现快约 120 倍，且能定位残局）。
- 证据说明**「19.8 秒」里推理占很小**：单帧像素判色 `sideMs` ≈ 87~106ms、预处理 ≈ 0.35ms、DNN 推理 ≈ 8.5~11.6ms ⇒ 171 候选 ×（判色为主）≈ 15~18s，与历史实测吻合。
- ⚠️ 诚实记录：**缓存框搜索的几何对「颜色采样」不如定位器 + calibrateGrid**（即使后接 `calibrateGrid`，严格 88.9% vs 99.4%）。原因是它的代价只用「框心残差」，而颜色正确性取决于采样点是否落在棋子笔画中心；这条要留给第二批继续查（见 §8）。

## 5. P0/P2：评测口径重建（执行单 §6.1）

`p4-skin-eval.js` 现在每次输出：

- 帧级：总帧 / 识别成功 / **拒绝（定位失败，不进成功率分母，逐帧列原因）** / 真值完整帧 / **整盘布局完全正确帧**
- 格级：真值覆盖（`787/810`）、真值未知格、**可计分格数**、严格含阵营、仅兵种位置、**纯阵营错格数**
- 占用格召回、**错空**、**空格假阳性**（并给出空位正确数）——避免大量空格掩盖棋子错误
- **原始 vs 一致性修复后**：预测 UNKNOWN 合计（与修复前对比）、降级数、翻色数、**修好/修坏格数**
- 定位方式分布、几何版本、几何搜索与识别的耗时拆分（`pickGrid` 检测/搜索/末次识别、crop/detect/side、native 预处理/推理）
- 机器可读行：`SKINE_JSON {…}`（逐帧）与 `SKINE_JSON_SUMMARY {…}`（汇总，含混淆矩阵）

**命名纠正**：`787/810` 那类数字是**严格含阵营的格子准确率**；本批新基线为 **782/787 = 99.4%（格子）**，
而**整盘布局完全正确帧 = 0/3**。两者不可混称。

## 6. 几何版本与执行一致性（执行单 §5）

已实现的部分：

- `alignGrid` 的微调**量化**：|dx|+|dy| < 3px 只当诊断，**不动执行几何**（同一格内落点不变，票据不必作废）；
  达到阈值时真的换几何并 **version + 1**（`alignedFrom` 记录原版本），避免「旧几何算出的票据去点新几何的格子」。
- 每帧上报 `suspect`（残差 > 0.25 格或有框出界）→ 交给状态机 RECOVER 重新定位。
- 票据本身已绑定 `geometryVersion`（`src/automation/move-ticket.js`），本轮未改票据与取消逻辑。
