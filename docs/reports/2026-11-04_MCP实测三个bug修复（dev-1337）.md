## 一、Bug 1 ✔ `node_script_command` 参数形状导致 MCP Internal error

- **现象**：`{"scriptPath":"…/test.js","args":"--out …/a.txt"}`（args 是**字符串**）→ `McpException: Internal error`。
- **根因**：接线层直接 `getAsJsonArray("args")`，字符串不是数组即抛异常，异常穿透成 MCP Internal error。
- **修复**：① 库层新增 `nodeScriptCommandFromRaw(scriptPath, JsonElement?)` 与 `parseArgs()`，接受 **字符串/数组/null**，字符串按 shell 风格拆分（引号内空格、反斜杠、空引号）；非法类型返回结构化 `{ok:false,error:{code:"INVALID_ARGUMENT",…}}`，**不抛**；② 接线层用 `runCatching` + `helperError()` 兜底，辅助工具不再暴露 Kotlin 异常栈。
- **真机验证**：

```text
args:"--out /storage/emulated/0/脚本/a.txt" -> ok=true, args=["--out","/storage/emulated/0/脚本/a.txt"],
    command="node /storage/emulated/0/脚本/test.js --out /storage/emulated/0/脚本/a.txt"
args:[a,b]        -> ok=true, args=["a","b"]
args:42           -> INVALID_ARGUMENT："args 必须为字符串或字符串数组，收到 primitive"
scriptPath:"   "  -> INVALID_ARGUMENT："scriptPath 不能为空或仅空白"
```

## 二、Bug 2 ✔ `apk_workspace_gc` 配额死锁（干跑 0 可删、永远回收不了）

- **现象链**：配额满 16 → 按提示 `gc(dryRun=true)` → `wouldDeleteCount=0`（默认保护 unknown_owner/unknown_client，旧记录 owner 全 null）→ 即便 `includeUnknownOwner=true` 也被 edit_session 永久保护 → 只能手动 `apk_workspace_delete` 逐个删。
- **修复**：
  1. 显式同时传 `includeUnknownOwner=true` + `includeTemporary=true` + `minAgeMinutes=0` 时，`expired` 且 `pendingCleanup=true` 的工作区可删；编辑会话不再永久保护，删除时计入 `releasedEditSessions`；`saved`/`current`/分页引用仍保护。
  2. 配额报错改为**可直接复制**的命令（inventory、`gc {"dryRun":false,"includeUnknownOwner":true,"includeTemporary":true,"minAgeMinutes":0}`、`workspace_delete`、`session_release`），并说明旧 `owner=null` 必须显式 includeUnknownOwner。
  3. 新增 **`apk_session_release`**（`workspaceId` 或 `all`），只释放 `sessions/`、不删工作区，返回 `releasedSessions/releasedBytes/remainingSessions/idempotent`，重复调用幂等。
  4. 新建工作区未提供 owner 时落 `owner=mcp-host`、`ownerSource=server-default`（调用方提供时 `ownerSource=caller`），inventory 暴露 `ownerSource`；旧记录不伪造身份。
- **真机验证**（MI8，4 个工作区全部 owner=null）：

```text
apk_workspace_inventory -> quota=16, used=4（1 temporary + 3 expired，owner=null）
apk_session_release {all:true} -> releasedSessions=0（当时无会话，幂等）
apk_workspace_gc {dryRun:true, includeUnknownOwner:true, includeTemporary:true, minAgeMinutes:0}
  -> wouldDeleteIds=[4 个], wouldReclaimBytes=157,072,021, skipped=0
apk_workspace_gc {dryRun:false, …同上}  -> deletedIds=[4 个], reclaimedBytes=157,072,021, failures=[]
apk_workspace_inventory -> used=0, remaining=16   ← 死锁解除（此前 wouldDeleteCount=0）
```

## 三、Bug 3 ✔ Frida listen 跨 UID 被 SELinux 静默 DROP（且未在文档提示）

- **实测证据**：gadget 注入/安装/启动成功、27042 确实 LISTEN（`/proc/net/tcp` state=0A）；connect 超时；决定性证据是客户端侧 `SYN_SENT(02)` —— SYN 被静默丢弃，不是 RST，跨 UID loopback 被 SELinux 拦。
- **修复**：
  1. 新增 `ToolkitFridaDiagnosis`（纯 JVM）：`classifyConnectFailure(errorText, portListening, synSentObserved, sameUid)` → `selinux_loopback_suspect`（有 SYN_SENT=high / 仅超时=medium）、`port_not_listening`、`component_missing_or_command_error`、`same_uid_connect_failure`、`connection_refused`、`unknown`；**超时/SYN_SENT 不允许被解释成“组件没装”**；`not found` 文本不判 SELinux；证据不足返回 unknown。
  2. `frida_status` 失败时错误信息直接给出下一步（改用 script 模式 / 同 UID / `frida_eval` 一次性路径 / `grep -i ':69A2' /proc/net/tcp` 确认 LISTEN）；成功时返回 `listenModeLimits`、`gadgetScriptMode`、`connectDiagnosis`（调用方可传 `portListening/synSentObserved/sameUid` 证据）。
  3. **实现 Gadget script 模式**：`apk_inject_gadget` 新增 `interactionType=listen|script` 与 `scriptPath`；script 模式生成 `{"interaction":{"type":"script","path":…,"on_load":"resume"}}`，**不监听端口、不经过 loopback**，绕开跨 UID SELinux；script 模式必须给 scriptPath，否则结构化报错。
- **真机验证**（传入 portListening=true、sameUid=false 的失败路径）：

```text
frida_status -> FAILED，错误信息：
  "Frida listen 连接超时：跨 UID loopback 可能被 SELinux 静默 DROP（confidence=medium），这不代表组件没装。
   下一步：改用 Gadget interactionType=script（不碰网络）或把执行端放进目标同 UID；
   先 grep -i ':69A2' /proc/net/tcp 确认 state=0A(LISTEN) 再 cat /proc/<client-pid>/net/tcp 看是否 SYN_SENT(02)。
   原始错误：connect 127.0.0.1:27042: Unable to connect to remote frida-server"
```

## 五、未做 / 边界

1. **script 模式**：脚本路径必须目标应用可读、启动前存在；没有网络通道，脚本需自行把结果写到 MCP 可读文件；未在本轮做真实 APK 注入验证（只验证了参数校验与配置生成路径）。
2. **SELinux 判定是概率分类**（基于 SYN_SENT/超时特征），不读取 `getenforce`/sepolicy；`portListening/synSentObserved/sameUid` 需要调用方或运维证据，且 `/proc` 可读性因 ROM/版本而异。
3. `apk_session_release` 只释放编辑会话，不删除工作区/`base.apk`；`all=true` 作用于所有工作区。
4. GC 在有活动 job 时仍保守跳过临时工作区（避免删掉正在用的快照）；已知 owner 的工作区仍受保护。
5. 项目总结里的 17 项遗留属“被逆向项目”自身收尾（shader main()、清理与重打包等），不在 MCP 侧改动范围。
