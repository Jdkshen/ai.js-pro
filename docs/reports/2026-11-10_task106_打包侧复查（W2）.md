# task-106：打包侧改动复查（隐患 A + 7 条）

## 隐患 A（Lead 定位）——判定：真隐患，已修
- 原状：pruneDisabledPackagingAssets() 用 OcrAssetDiscovery.find(workspace/assets) **按目录名匹配、命中整目录删**。今天安全的原因：用户工程内容进 assets/project/**，工作区 assets 顶层只有模板资产（+ assets/sjbc/**），所以顶层名字命中判据的目录只可能是模板资产 —— **但这是"当前布局"的巧合，不是判据本身保证的**。
- 修法（已改）：**删除目标 = 名字候选 ∩ 「宿主/模板确实提供的 assets 条目」**。
  · OcrAssetDiscovery 新增 candidates(assetsDir)（纯名字，供日志/诊断）与 find(assetsDir, providedAssetPaths)（求交）；
  · ApkBuilder 新增 hostAssetEntryNames()：列宿主 APK 里 assets/** 的条目名（ZipFile 只读）当 providedAssetPaths；
  · **providedAssetPaths 为空 ⇒ find 返回空 ⇒ 一个都不删**（fail-safe，并打 W「拿不到宿主/模板的 assets 清单 ⇒ 保守不删任何东西」）；
  · 名字命中但不被提供的（用户内容）⇒ 保留 + 打 I 日志「按名字命中但模板未提供，保留不删 <名字>」。
- 为什么改完更安全：判据从「名字像 OCR 资产」升级为「名字像 **且** 模板/宿主真的有这个资产」；用户哪怕将来把目录放到 assets 顶层、只要模板没提供，就不会被删。
- 反例单测（新增）：assets 顶层造 my-ocr-models/ 与 mlkit-ocr/（都命中名字判据）、模板只提供 mlkit-google-ocr-models 与 modules/__ocr__.js ⇒ candidates 列出三者、**find 只返回模板提供的两个** ✓；provided 为空时 **find 返回空** ✓。
