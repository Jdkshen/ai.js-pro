## 实现细节

### 1. 状态与缓存键

状态文件是运行时目录内的 `.runtime-cache.json`，schema 1，包含：

- **全部三个运行时 SHA-256 pins**（不是只存 `libnode.so`）；
- 应用安装身份：`packageName:versionCode:versionName:firstInstallTime:lastUpdateTime`；
- 规范化后的运行时目录绝对路径；
- 每个文件：canonical path、size、mtime、readOnly、`BasicFileAttributes.fileKey()`（可用时是设备/inode 标识）。

任意字段不一致、JSON 损坏、state 文件过大或 pin 集合不完整，都视为 miss，进入完整校验。未知/缺失 pin 直接拒绝，防止 loader 静默漏掉新文件。

### 2. 快路径

在 `.extract.lock` 跨进程锁内：

1. 读取并严格校验状态；
2. 检查三个文件存在、非符号链接、canonical path 与状态一致；
3. 检查 size、mtime、read-only 属性和 fileKey；
4. 全部一致才 `cache=hit`，**本进程不读取 106 MiB 文件做 SHA**。

状态文件写坏、文件被删除/截断/改写、只改 mtime、变为可写、pins 变化、应用更新，都会转到完整校验。

### 3. 完整校验与恢复

完整校验逐文件按 runtime pin 计算 SHA-256：

- 内容与 pin 一致且只读：保留现文件，不重写；
- 内容不同、缺失、不可读、可写或不是普通文件：从内置 assets 写入同目录 `.part`；
- `.part` 在拷贝过程中同步计算 SHA-256，`fsync` 后再与 pin 比较；
- 通过后设为只读，并用同目录原子 rename 覆盖目标，最后才提交状态文件。

因此不是“改过的 pin 只查 core”，bridge 或 libc++ 单独更新也会重新检查全部三个文件。也没有原地截断/写目标 `.so`：已有进程映射的旧 inode 不会被新内容覆盖，新进程在锁内准备完成后才加载。

### 4. 状态提交与失败语义

- 状态先写同目录临时文件，`FileOutputStream.getFD().sync()`；
- 用 `Files.move(..., ATOMIC_MOVE, REPLACE_EXISTING)` 提交；平台不支持 atomic move 时回退普通 replacement，最坏留下不完整/旧状态，下次会完整校验；
- 状态写入失败不阻止加载已经完整校验的运行库，下一次进程会重新完整校验；
- 解压失败抛出 `IOException`，不提交状态；`.part` 做只读属性清理后删除，重试可从 assets 恢复。

## 日志与设备验收

`Node24Libraries` 保留 `C-NODE24` tag，新增一行类似下面的日志（格式示例，不是真机输出）：

```
runtime cache cache=hit reason=hit fullVerify=false hashFiles=0 hashBytes=0 hashMs=0 extractFiles=0 extractBytes=0 extractMs=0 cacheUs=... lockMs=... stateMs=... prepareMs=... state=reused runtimeJsonMs=... prepareFilesMs=... totalMs=...
```

命中路径仍会短暂持有原来的 `.extract.lock` 以读取/核验状态，因此多个 Node 进程同时初始化时可能看到少量 `lockMs`；这避免了并发读到半成品状态，也避免多个进程重复计算同一份 106 MiB SHA。

慢路径会显示 `cache=miss reason=pins-changed|app-changed|state-missing|state-invalid|metadata-changed|writable|file-missing`，以及 `hashFiles`、`hashBytes`、`extractFiles`。不含应用身份、路径或用户数据。

主助手可通过 `adb logcat -s C-NODE24` 观察：

1. 首次安装/覆盖安装后第一个 Node 池进程：完整 hash（或从 assets 解压）并提交状态；
2. 同一版本后续 Node 池进程：`cache=hit`、`hashFiles=0`、`extractFiles=0`；
3. 只更新 bridge pin：`reason=pins-changed`、`hashFiles=3`、`extractFiles=1`；
4. 更新 APK：`reason=app-changed`、`hashFiles=3`；
5. 改动/截断/设为可写运行时文件：能恢复，并回到只读状态。

首次安装及每次升级后的第一个进程仍必须付出完整 hash 成本，这是完整性约束，不是缓存回归。

## 已知限制与保守结论

1. 新核心使用 `java.nio.file`（API 26）。现有 Node24 应用路径为 Miuix `minSdk 26`，但本次未构建验证其他变体；若未来在 API 21 路径调用 Node24，需要改成 API 21 可用实现。
2. `BasicFileAttributes.fileKey()` 在部分文件系统可能为空，此时仍依赖 canonical path + size + mtime + read-only；Java NIO 没有直接暴露 Unix ctime，未伪造该字段。
3. `.runtime-cache.json` 位于应用私有目录，不是针对同 UID/adb/root 的密码学防篡改机制；它防止的是正常升级、损坏、半成品和普通文件变化。内容完整性最终仍由 pins 决定。
4. 应用身份读取失败会按失败关闭处理，Node 准备报错而不是带着不确定身份复用缓存。
5. 状态提交失败被设计为不阻断加载，代价是下一进程重新完整校验；解压失败仍会阻断该次准备。
6. 只做了 JVM/Android jar 轻量编译和纯文件测试；真实设备上的首次安装、覆盖安装、bridge-only 更新、三进程并发、Android 文件属性/原子替换行为需主助手真机复核。
