## 2. 背景：两条识别路径

```
旧路径（生产回退）：tools/recognize-board.js → src/vision/recognizer.js（定位/几何/阵营采样/FEN）
新路径（流水线）：  vision-pipeline.js → piece-detector → piece-cropper → OCR 字形 → 像素颜色
                                        → evidence-fusion（多帧投票）→ board-validator（规则门）
```

底座关系（**这点两份评审都理解错了，我按要求纠正了**）：

- `recognize-board.js` / `recognizer.js` **不只是旧路径**，它同时是**检测 + 几何（`pickGrid` / `calibrateGrid`）的唯一实现**，
  而新流水线的检测宿主正是调用它（`recognizeScreen().native.list`）。
- 因此「让 `recognize-board` 调 `board-service → vision-pipeline`」会形成**循环依赖**，并让流水线不可信时失去回退路径。
- 正确切法：检测/几何下沉为底座，两个上层都用它；**收口发生在 `services/board-service.js`**（选哪条 + 回退策略 + 快照）。

## 3. 本轮实际改动（按重要性）

### 3.1 修复：空位被当成未知格（代码评审 P0-1）
- 位置：面板 `recognizeViaPipeline()` 里的 `unknownCells`。
- 原因：字符串层**空格是 `null`**（见 `src/vision/cells.js`），写成 `!ch || ch === "?"` 会把 60 个空位算成未知；
  稳定帧闸门「未知 > 6 丢帧」⇒ **每一帧都被丢掉**。
- 修法：抽出可测函数 `board-scan.countUnknownCells(chars)`（只数 `"?"`），面板与自检共用。
- 真机证据（修复前后）：
  ```
  修复前：稳定帧：未知格 60 个（> 6），丢弃这一帧   ← 每帧都丢
  修复后：稳定帧：这一帧不送识别（还缺一帧（稳定帧要两帧比像素差））      ← 首帧预热
          视觉流水线：规则门 通过｜确认 29／未定 0｜OCR 成功 25／缓存 0／兜底 6／补全 2
          稳定帧：未知格 27 个（> 6），丢弃这一帧                        ← 只丢「尚未确认」的那一帧
          视觉流水线：规则门 通过｜确认 29／未定 0｜…                    ← 随后正常观察
  ```
- 备注：评审建议改用 `result.fusion.unknown`，效果等价；这里选择「数公开字段 `chars` 里的 `?`」，
  因为它是**对外契约**（`chars` = 规则补全后的盘面），不依赖融合层内部计数。

### 3.2 修复：校验器未知格双倍计数（P1）
`board-validator.validate()` 原来写 `const unknown = red.unknown + black.unknown;`，
而 `countSide()` 不管查哪一方都会把整盘的 `?` 数进去 ⇒ 同一个未知格算两遍
（真机症状：30 个 `?` 打印成「未知 60」）。
现改为**单独一趟遍历**只数一次。

### 3.3 修复：融合阈值/权重完全不生效（P1）
`evidence-fusion.pieceOf(entry)` 里用固定 `DEFAULTS.minFinalScore` 且 `finalScore({...})` 不透传 opts
⇒ `createFuser({minFinalScore, weightDetect, weightOcr, weightColor})` 四个参数全部无效（只有 `frames` 生效）。
现改为 `pieceOf(entry, options)` 并把 `opts` 从 `createFuser` 一路传下去。

### 3.4 修复：`board` 与 `chars` 两套盘面（P1）
`vision-pipeline.recognize()` 原来返回 `chars: fused.chars`（**未补全帅/将**）与 `board`（补全后）两个不一致字段。
现统一：**`chars` = 唯一权威字段（补全后）**，新增 `rawChars` = 融合层原样输出（诊断用），`board` 与其保持一致。
面板同步改为只读 `chars`。

### 3.5 修复：检测框「先截断后排序」（P1）
`piece-detector.detect()` 原来 `slice(0, maxDetections)` 在 `sort(score 降序)` **之前**。
现改为先排序再截断（默认上限 40，一局面最多 32 子，现实中很少触发）。

### 3.6 修复：稳定帧闸门接入面板（方案 §12 #5 的功能缺口）
- 面板新增 `boardRegionSamples()`（棋盘区域灰度采样，**数字数组**）+ `frameGate.check()` 前置判定：
  不稳定帧直接不送识别（返回 `null`，驱动计一次「未识别」但不会乱推轮次）；
- 识别完再走 `acceptResult(未知格)`（>6 直接丢）；
- 「把游戏带回前台」后调用 `gate.onFocusChange()` 让下一帧只预热；
- **顺带修了 `frame-gate` 自身的洞**：`diff == null` 对 NaN 为 false、`NaN > maxMeanDiff` 也为 false
  ⇒ 采样格式不对时会被判成「**稳定**」（真机日志里那句「稳定（平均差 NaN）」就是这么来的）。
  现改为 `diff == null || !isFinite(diff)` 即判「无法比较」。

### 3.7 修复：镜像 bug —— 已知事实表把黑方当红方
（上一轮发现、本轮复现并定位到根因）
- 现象（真机日志）：`全盘 OCR 改正 26 格：(0,0)空→R(OCR 車)；(1,0)空→N(OCR 馬) …` —— 上方棋子全被补成**红方**。
- 根因：面板 `ocrBoard()` 返回**只带兵种**的 `cls`（全大写），驱动「模型漏检、OCR 看到字 ⇒ 补上」直接
  `chars[i] = theirs`，并把错颜色 `registerPatch` + `fixBaseline` 写进**已知事实与可靠基准**。
- 修法：新增 `src/vision/board-scan.js` —— 字形→兵种、**颜色只从像素来**（`piece-cropper.sampleColors` + `piece-color`），
  **判不出颜色就留 `null`（不猜）**；面板 `ocrBoard()` 改用它。
- 真机复查（同一批格子）：
  ```
  修后：[driver] 全盘 OCR 改正 28 格：(0,0)空→r(OCR 車)；(1,0)空→n(OCR 馬)；(2,0)空→b(OCR 象)；
                              (3,0)空→a(OCR 士)；(5,0)空→a(OCR 士)；(6,0)空→b(OCR 象) …
  ```

### 3.8 修复：颜色分类器的「恒 false」死代码（更早发现，一并记录）
`piece-color` 把自带选项对象传给 `piece-side.isRedPixel/isDarkPixel`，而后者的键名是 `redMin/redDominance/darkMax`
⇒ `r > undefined`、`max3 < undefined` **恒为 false** ⇒ 红/暗像素计数从未生效（黑方棋子永远判 UNKNOWN）。
修法：显式合并 `pieceSide.DEFAULTS`（`sideOptions`），并把自检样本从纯色改成「木纹底 + 笔画」的真实分布。

### 3.9 兼容层收口（结构评审第二批，已做）
- `piece-fusion.js`：标注 **@deprecated**，写明与 `evidence-fusion` 的分工（当前**无任何生产调用**）；
- `piece-side.js`：**不是重复实现** —— 它是**像素级判定**的底座（`piece-color` 与旧路径 `recognizer` 都依赖它）
  ⇒ 固定边界并写进文件头，而不是合并；
- `onnx-ocr-adapter.js`：标注「非公开入口 / 当前无生产调用」，将来接 ONNX 分类模型应作为 `ocr-runtime` 内部后端。

### 3.10 修复：检测入口收口 —— 抽共享底座 + 常驻 detect-only 会话（P0-2）

**问题**：新流水线的 `detect` 宿主调 `recognize-board.recognizeScreen()`，只为了取 `native.list`，
却顺带跑完了旧识别器的格点分配、颜色采样、棋规修复与 FEN 生成 —— 新旧架构没有真正分离，且每帧双份计算。

**修法**（另一个 agent 完成主体，本轮核验并接入工具链）：
- 新增 `src/vision/detection-stage.js`：只做「选检测区域（整屏 / 按目标宽高比 `fitAspect`）→ 调宿主检测器 → 坐标归一」，
  明确写明**矩形 160×320 模型不能直接拿方形棋盘调 `adapter.detect`**（会触发 OpenCV reshape 断言）；
- `recognizer.js` 改为使用该底座（删掉自己那份区域/宽高比逻辑），并保留 `normalize` 等旧导出；
- `tools/recognize-board.js` 新增 **`createDetectionSession()`（常驻，模型只加载一次）** 与 **`detectOnly()`**；
- 面板 `ensureVisionPipeline()` 改用常驻会话（退出时 `close()`）；`board-replay-test.js` / `ocr-benchmark.js` 也改为同一底座。

**真机证据**（本轮）：
```
视觉流水线已启用（常驻 detect-only YOLO + PP-OCRv6 + 双中心/多尺度 OCR + 逐格变化缓存）
稳定帧：这一帧不送识别（还缺一帧…）
视觉流水线：规则门 通过｜确认 0／未定 29｜OCR 成功 30／缓存 0／兜底 0／补全 2
本轮观察：未知格 0，耗时 4633ms    ← 首帧（含模型加载）
本轮观察：未知格 0，耗时 2866ms    ← 稳态
启动错误行: 0
```
基准工具改用底座后：`检测框 30 个 ⇒ 映射 29 格`、`与参考一致 29／不一致 0`、`稳定帧：稳定（平均差 0.00）`。

### 3.11 新增 5 条「生产组合」自检
自检 **176 → 181**，新增：

| 用例 | 守什么 |
|---|---|
| 未知格账目：空位不算未知 | 60 空位 + 30 子 ⇒ 未知必须 0（写 `!ch` 就会 60） |
| 校验器：未知只统计一次 | 1 个 `?` ⇒ `stats.unknown === 1`（不是 2） |
| 融合阈值/权重必须生效 | `minFinalScore=2` 时同一格不得确认 |
| 检测框排序/截断 | 45 个乱序框 ⇒ 保留分数最高的 40 个 |
| 流水线整盘：未知必须为 0 | 30 子 + 60 空位 ⇒ `?` 0 个、空位保持 `null` |
| 稳定帧闸门采样格式 | 传 `[r,g,b]` 必须报「无法比较」，不得被判成稳定 |

> 注：融合器**需要两票一致**（方案 §3.8），写测试时传 `frames: 1` 会永远只有一票 ⇒ 用例里已写明这个坑。

### 3.12 入口收口：悬浮窗与主界面都走 `board-service`（P2 第一步）

**问题（评审 P2）**：`services/board-service.js` 早就存在，但**只有自检在用** —— 悬浮窗面板、主界面、
各个探针各自拼「抓帧 → 定位 → 识别 → 回退」这条链，于是「稳定帧判定」「未知格统计」「几何回写」
这类事每处都得记得写一遍，漏一处就是一个难查的现场 bug（本轮真机就撞到两次）。

**做法**：把「编排」全部收进 `board-service`，入口只注入平台能力。

- `board-service.recognizeSmart(options)`：稳定帧 → 流水线 → 规则门 → **不可信自动回退旧路径**；
  帧不稳时返回 `{ok:false, unstable:true}`（不观察，也不拿脏帧推轮次）。返回值带
  `fusion` / `validation` / `pipelineStats`，供入口打一行限频诊断。`recognizeLegacy()` 兼容旧调用方。
- 新增可选注入：`calibrate(image, located)`（几何精校准，主界面原先写在入口里）、
  `vision = {pipeline, gate, samples, countUnknown, log}`（面板的流水线 + 稳定帧闸门）。
  `recognize()` 现在透传驱动的 `regionRatio` / `timeoutMs`（漏传会让主界面填的「棋盘范围」静默失效）。
- `resetFrameBaseline()`：切前台后丢掉上帧采样（否则会拿切窗前的采样去配新画面，白丢一帧）。
- 悬浮窗：删掉面板里那份重复实现 `recognizeViaPipeline`（~110 行），驱动钩子只剩
  `boardService.recognizeSmart(...)` 一行 + 画结果。流水线开关仍然是 `autorun.visionPipeline`。
- 主界面：`main.js` 的驱动钩子改为 `boardService.recognizeSmart()` / `boardService.locate()`，
  原先内联的定位+校准代码（~40 行）换成注入的 `calibrate`。

**自检**：`board-service` 用例扩到 6 个子场景（流水线可信 / 规则门否决回退 / 帧不稳不观察 /
`mode:'legacy'` / `regionRatio`+`timeoutMs` 透传 / 注入校准后 `locate()` 用校准几何）⇒ **182 项全绿**。

**真机（K40，2026-09-20）**：


## 7. 给复核者的两个「反直觉」提醒

1. **`node --check` 抓不到 QuickJS 的 `SyntaxError: invalid redefinition of lexical identifier`**：
   本轮就因为一个重复的 `const rawChars`（块内 + 函数内）让**整个面板脚本无法启动**，
   而 Node 侧语法检查全绿。⇒ 大文件改完必须在设备上确认脚本能启动。
2. **`node --check` 只能查语法**：像「红/暗像素计数恒 false」「融合配置不透传」这类问题，
   只能靠**带真实分布的样本**（木纹底 + 笔画）和**生产组合**用例兜住 —— 这也正是本轮补的 5 条自检的意义。
