# 象棋自动走棋项目文件结构评审

评审日期：2026-09-20  
项目位置：`apps/app/src/main/assets/sample/QuickJS 新引擎/项目与打包/象棋自动走棋`  
验证结果：`SELF_CHECK OK passed=175 failed=0`

## 1. 结论

当前项目已经形成较完整的分层骨架，象棋规则、搜索引擎、自动化状态机、AI.js Pro运行时适配、视觉识别和界面代码均已分目录管理。新视觉流水线也已经接入悬浮窗。

当前主要问题不是缺少模块，而是处于新旧架构并存阶段：主界面、悬浮窗、工具脚本没有完全统一到同一条调用链，部分职责存在重复实现，大量阶段性探针仍留在正式工具目录。下一阶段应优先完成架构收口，再继续优化模型和识别算法。

总体评价：结构方向正确，可维护性中等，尚未达到稳定发布结构。

## 3. 各目录职责评审

### 3.1 `src/app`

当前文件：

```text
bootstrap.js
config.js
controller.js
owner-channel.js
panel-bus.js
session-store.js
view-model.js
```

优点：

- 已开始建立正式应用层；
- 配置、控制器、会话、界面状态与通信总线已经分开；
- 具备统一主界面和悬浮窗运行逻辑的基础。

问题：

- `bootstrap.js`尚未成为所有生产入口的统一启动点；
- 主界面和悬浮窗仍有直接引用底层工具或模块的情况；
- 当前应用层主要在自检中被覆盖，生产调用链尚未完全迁移。

建议：

```text
main.js ─────────────┐
                    ├─→ app/bootstrap.js → controller
悬浮窗运行与测试.js ─┘
```

两个入口只负责创建界面和绑定事件，业务行为统一交给控制器。

### 3.2 `src/services`

当前文件：

```text
board-service.js
game-session.js
```

方向正确。服务层应成为应用层访问视觉、状态机和引擎的唯一入口。

建议明确：

- `board-service.js`：截图、定位、识别、稳定帧、局面验证；
- `game-session.js`：开始、停止、新会话、轮次、自动走棋生命周期；
- UI不得直接调用`recognizer.js`、`vision-pipeline.js`或`auto-driver.js`。

优点：

- 已具备YOLO定位、OCR、颜色判断、证据融合、棋盘验证和多帧融合所需模块；
- `vision-pipeline.js`已经承担新流水线编排；
- 悬浮窗已加载新流水线；
- 视觉职责比旧版更清晰。

主要问题：

1. `recognizer.js`与`vision-pipeline.js`并存；
2. `piece-fusion.js`与`evidence-fusion.js`职责接近；
3. `piece-side.js`与`piece-color.js`均涉及阵营判断；
4. `onnx-ocr-adapter.js`与`ocr-runtime.js`均承担OCR后端适配；
5. `board-scan.js`与完整流水线之间的边界还需要固定。

建议收口关系：

```text
vision-pipeline.js
├─ frame-gate.js
├─ piece-detector.js
├─ grid-tracker.js
├─ piece-cropper.js
├─ ocr-runtime.js
│  ├─ PP-OCR
│  └─ ONNX分类模型
├─ piece-color.js
├─ evidence-fusion.js
├─ temporal-fusion.js
└─ board-validator.js
```

兼容策略：

- `recognizer.js`暂时作为旧接口适配层，内部调用`vision-pipeline.js`；
- `piece-fusion.js`暂时转发到`evidence-fusion.js`；
- `piece-side.js`只保留兼容函数，新代码统一调用`piece-color.js`；
- `onnx-ocr-adapter.js`变成`ocr-runtime.js`内部后端，不再由业务层直接引用；
- `board-scan.js`只负责全盘OCR扫描，不直接管理状态机或点击。

## 7. 推荐迁移顺序

### 第一阶段：统一视觉入口

1. `board-service.js`内部统一调用`vision-pipeline.js`；
2. `tools/recognize-board.js`改为调用`board-service.js`；
3. `main.js`改为通过控制器访问棋盘服务；
4. 悬浮窗继续使用同一个服务；
5. 对同一张回放截图比较所有入口输出，必须完全一致。

### 第二阶段：兼容模块收口

1. 将`recognizer.js`改为兼容代理；
2. 合并`piece-fusion.js`和`evidence-fusion.js`；
3. 统一`piece-side.js`与`piece-color.js`；
4. 将ONNX OCR后端并入`ocr-runtime.js`；
5. 明确`board-scan.js`只用于OCR全盘扫描。

### 第三阶段：拆分大型文件

1. 拆分`auto-driver.js`；
2. 拆分`aijs-adapter.js`；
3. 将悬浮窗内的OCR、前台维护、抓帧和日志逻辑迁入服务层；
4. 入口文件只保留界面创建与事件绑定。

### 第四阶段：整理工具与测试

1. 工具分为active、legacy和fixtures；
2. 建立`tests/unit`、`tests/replay`、`tests/device`；
3. 历史探针不参与发布打包；
4. README只展示仍受支持的运行入口。

## 8. 验收条件

结构收口完成后必须满足：

- 主界面、悬浮窗、实机探针对同一截图输出完全相同的局面；
- 生产代码只有一个视觉流水线入口；
- OCR后端只有一个公开运行时接口；
- 红黑颜色只有一个公开分类接口；
- 合法着法只有一个权威生成与校验实现；
- UI不直接调用YOLO、OCR或点击实现；
- 旧兼容模块有明确弃用说明；
- `tools`中的正式工具不超过10个；
- Node自检全部通过；
- K40实机探针、悬浮窗和自动走棋均使用同一版本文件；
- 打包目录不包含历史探针和回放数据。

## 9. 风险提示

当前工作区存在较多未提交修改和新增文件。整理目录前必须保留现有改动，禁止直接重置或批量删除。移动文件应分阶段进行，每一步都修正引用并运行自检。

本次评审只检查结构和引用关系，没有删除、移动或覆盖现有项目文件。
