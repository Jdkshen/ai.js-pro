## 二、`apk_workspace_gc` 回收不了临时快照（真实故障，已修）

### 现象

K40 上 **10 个临时 APK 快照累计 1.0 GiB**；`apk_workspace_gc` 无论怎么传 `includeTemporary+includeUnknownOwner+minAgeMinutes=0+allowUnknownAge` 都是 `wouldDelete=0`，而 `apk_workspace_inventory` 一直报 `activeJobs=2`、并警告「旧任务记录不含 workspaceId，GC 会保守跳过所有临时工作区」。

### 根因（两处叠加）

1. **任务重启恢复只改内存、不回写元数据**：`ToolkitJobs` 恢复时把内存状态标成 `INTERRUPTED`，但元数据文件里的 `state` 仍是 `RUNNING/QUEUED`；而工作区清单的 `scanActiveJobs()` 是**读元数据文件**的 → 永远认为有 activeJobs。
2. **墓碑分支完全不清理陈旧元数据**：任务没有结果文件时走 `addTombstone`，只加墓碑、不删/不改元数据 → 上述陈旧状态永久保留。
3. 叠加 `ToolkitWorkspaceInventory.kt:173` 的**一刀切保护** `if (activeJobs > 0) reasons.add("active_jobs_workspace_unknown")` → 一个死任务挡住**全部**临时工作区的回收。

### 修复

- 恢复分支：标终态后 `persist(job)` 写回元数据（幂等）。
- 墓碑分支：`metadataFile(id).delete()`（墓碑已记录丢失原因，元数据可安全删除）。
- `scanActiveJobs()` 加 **mtime 兜底**：active 状态但超过「最长超时 2 倍（3600s）」未更新 → 视为陈旧，不再阻断（真实活跃任务会在状态迁移时 `persist()` 刷新 mtime）。

### K40 实测（dev-1376）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `apk_workspace_inventory.activeJobs` | 2 | **0** |
| GC `wouldDeleteCount` / `wouldReclaimBytes` | 0 / 0 | **10 / 1,015,061,349** |
| 实际执行 | — | **deleted=10、reclaimed=1,015,061,349 字节（≈968 MiB）、failed=0** |
| `quotaRemaining` | 6 | **16** |

## 三、`apk_dex_search_members` 提示语义拆分

- `stopReason=limit` → **`limitHint`**：「本次是按调用方传入的 limit=1 截断，**不是预算用尽**；要更多结果请加大 limit 或缩小 prefix/查询范围」，**不再**给 `budgetHint`/`nextActions`。
- `stopReason=scan_budget`/`time_budget` → 仍给 `budgetHint` + `nextActions`。
- `budgetUsed` 两种都保留（纯诊断）。实测：`limit=1` → `stopReason=limit`+`limitHint`；`limit=500` → 不截断、无提示。

## 五、仍未做 / 边界

1. **#17（jadx 不完整）仍未用真实超限方法复测**——手头没有那份 `.shop` APK，`McpToolsKt.<clinit>` 也未能触发（工作区当时被 1 GiB 撑爆，现已清空可再试）。

3. 工作区**自动**回收仍未做（只有显式 `apk_workspace_gc`）。
4. `file_search` 的内容/正则预算仍无法从文件中间续扫（只有目录遍历可续），已在返回里如实写明。
5. `apk_workspace_inventory` 的 `byState.temporary` 与 `totalCount` 在删空后一致为 0，但**没有**对「dangling 目录」做自动清理（设计如此：orphan/dangling 永不自动删除）。
