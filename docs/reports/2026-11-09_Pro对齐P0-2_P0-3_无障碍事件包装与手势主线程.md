# Pro 对齐 P0-2 / P0-3：无障碍事件包装与手势主线程约束（task-60）

- 任务：task-60（W2），来源 = Pro 真缺口复核终表 P0 前两条（automator 域）
- 约束：不跑构建/装机/发布/git（本条用了 gradle 单测）；写作用域 = modules/automator/src/{main,test}/** + docs/reports/**
- 结论一句话：**P0-2 不需要新的脚本 API**（我们早就能拿到事件对象，证据见 §1），真正缺的是「脚本可见形状」的唯一可测映射 → 已实现；**P0-3 主线程不是模糊错误**（是「能跑但卡 UI」），但「回调线程自调阻塞手势」是必然死锁且无任何提示 → 已给具名异常。

## 1. 取证①：脚本现在能不能拿到无障碍事件对象？什么形态？

**能，字段已经覆盖 Pro 包装类的核心面。** 通路与形态：

| 环节 | 位置 | 事实 |
| --- | --- | --- |
| 主进程事件 → JSON | modules/automator/src/main/java/com/stardust/view/accessibility/AccessibilityEventForwarder.kt:51（delegate）、:162-181（forward→sendBroadcast） | 订阅开启时把事件序列化成 JSON：kind/eventType/packageName/className/windowId/eventTime/text（window_content_changed 另带 contentChangeTypes、window_state_changed 另带 windowChangeTypes） |
| :script 进程收事件 | modules/engine/src/main/java/com/stardust/autojs/runtime/api/Events.java:142-194 | 首次订阅时经 RemoteAutomationBridge 注册；收到 JSON 后 emit("accessibility_event", event)，并按 kind 追加 emit（view_clicked/window_state_changed/toast/…） |
| 脚本拿到的对象 | modules/engine/src/main/java/com/stardust/autojs/runtime/api/remote/RemoteAccessibilityEvent.java:50-67 | Java Bean：getKind/getEventType/getPackageName/getClassName/getText/getWindowId/getEventTime/getContentChangeTypes/getWindowChangeTypes + toJson() + 可读 toString() |
| Node 引擎 | modules/engine/src/main/assets/node24/prelude.js:4696、4713-4745 | 自己的 accessibility.on(...) 形态（kind/pkg/class 的 toString + 逐 kind 派发） |
| Pro 参照 | .artifacts/AutoJsPro源码树-2026-11-09/源码树/business/com/stardust/automator/AccessibilityEventWrapper.java | 包装类含 packageName/eventType/className/text/… 与 toString；**我们的 Bean 已覆盖同一批核心字段**（我们另有 toJson 与 kind 通道） |

**判定**：再现造一个脚本 API（或第二套字段命名）没有价值，只会造出第二条事件源/第二份契约。
真正的缺口是**那份「事件 JSON 快照」的映射逻辑内联在 AccessibilityEventForwarder.forward() 里**（Android-only、无单测，脚本可见形状没有唯一、可测的定义）→ 这是本轮实现的 P0-2 部分，**接在既有事件回调路径上**（未新增事件源）。

## 2. 取证②：主线程调手势现在到底是什么行为？

| 事实 | 位置 |
| --- | --- |
| 阻塞路径 = VolatileDispose.blockedGet()（**无超时** wait） | modules/automator/src/main/java/com/stardust/automator/GlobalActionAutomator.kt:113-134；modules/common/src/main/java/com/stardust/concurrent/VolatileDispose.java:11-23 |
| 回调投递线程 = servant looper 线程（**自己的 Thread**，不是主线程） | modules/engine/src/main/java/com/stardust/autojs/core/accessibility/SimpleActionAutomator.kt:227（Handler(loopers.servantLooper)）；modules/engine/src/main/java/com/stardust/autojs/core/looper/Loopers.java:124-148（initServantThread：Looper.prepare/loop） |
| Pro 的做法 | 源码树 GestureOnMainThreadException.java（RuntimeException + 文案）；Pro GlobalActionAutomator.java:91 在主线程直接抛 |

**结论（两种情况分开）**：
1. **主线程调阻塞手势**：回调由 servant 线程投递 → 不会死锁、**能跑**；但调用线程（UI 线程）被阻塞到手势结束（长按/慢滑可达数百 ms 到数秒）→ ANR 观感，且**没有任何提示**。这不是「模糊错误」，是「静默卡 UI」。
2. **在回调投递线程（servant looper 线程）上再调阻塞手势**：该线程自己 wait()，而唤醒它的回调只能由它自己投递 → **必然死锁，且不抛任何异常**（脚本表现为卡死）。这是唯一「必然坏且无提示」的路径。

**判定**：给 2 加**具名异常**（本轮实现）；给 1 只加 **warning 日志**（不改既有行为——现状能跑，直接抛会误伤现在可用的脚本；且我们与 Pro 的线程模型不同：Pro 在主线程直接拒绝，我们的回调线程本就不是主线程，所以约束点应落在「谁要投递回调」而不是「是不是主线程」）。

## 3. 改动清单

1. **新增** modules/automator/src/main/java/com/stardust/automator/AccessibilityEventWrapper.kt（纯 JVM，不依赖 android.* / org.json）
   - 字段：kind/eventType/packageName/className/text/windowId/eventTime/contentChangeTypes/windowChangeTypes（@JvmOverloads 构造）；
   - toString() 可读；toJson() 产出与改造前**逐键逐序相同**的 JSON（含两个条件键规则）；escape() 自带（org.json 在 JVM 单测里是 stub）；kindOf(eventType, className) 与改造前同一套判定（含 Toast 特判，@JvmStatic）。
2. **改** modules/automator/src/main/java/com/stardust/view/accessibility/AccessibilityEventForwarder.kt
   - forward() 改为 wrapperOf(event) 抽字段 + wrapper.toJson()（去掉内联 JSONObject；键不变）；原私有 kindOf 并入 wrapper。
3. **新增** modules/automator/src/main/java/com/stardust/automator/GestureOnMainThreadException.kt
   - GestureOnMainThreadException(reason) : RuntimeException（具名、自研文案）；
   - GestureThreadGuard：refusesBlockingGesture(callerThreadName, callerOwnsCallbackLooper)（纯判定 + 可执行改法）、mainThreadWarning(...)（不抛的 warning 文案），均 @JvmStatic。
4. **改** modules/automator/src/main/java/com/stardust/automator/GlobalActionAutomator.kt（阻塞路径手势前）
   - 先判「调用线程是否为回调投递线程」→ 是则抛 GestureOnMainThreadException；主线程则 Log.w(GESTURE_TAG, …)；**gesturesAsync 不动**（它不等待回调）。
5. **新增测试** modules/automator/src/test/java/com/stardust/automator/AccessibilityEventWrapperTest.java、GestureThreadGuardTest.java（纯 JVM）。

## 4. 验证方式

- gradle 单测（本模块）：`gradlew :automator:testDebugUnitTest --tests "com.stardust.automator.*"` → **BUILD SUCCESSFUL**（21s）；共 **24 项 / 0 失败**：本轮新增 AccessibilityEventWrapperTest 5 项 + GestureThreadGuardTest 4 项；既有 ExampleUnitTest 1、DfsFilterTest 1、NodeActionArgumentsTest 11、ScrollActionTest 1、UiObjectCollectionArgumentsTest 1 全绿（无回归）。
- **本轮单测真抓到一个错**：把 forwarder 的符号常量搬进纯包装类时，TYPE_NOTIFICATION_STATE_CHANGED 被写成 0x00100000（真实值 = 64）→ notification/toast 会被误判成 accessibility_event；`kindOfMatchesTheFrameworkEventTypesAndKeepsTheToastSpecialCase` 当场红（expected notification / was accessibility_event），用 `javap -constants android-35/android.jar` 复核后修正为 0x00000040。这正是「唯一可测映射」的价值：原实现内联在 Android-only 对象里，这条路没人测过。
- 测试覆盖：
  - 事件映射：JSON 键集与顺序逐字钉住（含条件键只在自己 kind 出现）、字符串转义（引号/反斜杠/换行/制表/控制字符）、kindOf 与 android.view.accessibility.AccessibilityEvent 常量对齐（含 Toast 特判）、toString 可读；
  - 线程守卫：回调线程 → 具名异常文案（含线程名、卡死说明、改法）；非回调线程 → 不拒绝；主线程 → warning 文案；异常是 RuntimeException 且 reason == message；**源码级断言**：守卫只出现在阻塞路径一处、gesturesAsync 体内无 blockedGet/守卫（防止以后把异步路径也拦掉）。
- 真机（Lead 用脚本在 K40 上验）：见交付消息里的「脚本侧可观察」口径。

## 5. 脚本侧可观察

- **事件（不变）**：`events.on('accessibility_event', e => ...)` 以及 `events.on('view_clicked'|'window_state_changed'|'toast'|...)`，`e` 仍是那个 Bean：`e.kind / e.eventType / e.packageName / e.className / e.text / e.windowId / e.eventTime / e.contentChangeTypes / e.windowChangeTypes / e.toJson() / e.toString()`；本轮只把映射实现搬到可测的包装类，**键与值逐字不变**（有断言钉住）。
- **手势（新增可观察）**：
  - 在回调投递线程上调阻塞手势（click/press/longClick/swipe/gesture）→ `GestureOnMainThreadException`，`e.message` 含线程名与「改用 gesturesAsync/clickAsync 或换线程」的改法；
  - 主线程上调阻塞手势 → 行为不变，logcat `DshGesture` 多一条 warning（`adb logcat -s DshGesture:V`）。

## 6. 未验证边界

1. **真机未跑**（本轮只到 JVM 单测）：主线程 warning 是否真在 logcat 出现、回调线程死锁路径能否在真机构造（需要在 servant looper 线程里调阻塞手势，现实触发点罕见，例如截图回调链），都由 Lead 真机/脚本验。
2. 「回调投递线程 == 传入 Handler 的 looper」这一判据基于 SimpleActionAutomator 的构造方式（Handler(servantLooper)）；**若以后有人给 GlobalActionAutomator 传主线程 handler**，主线程就会命中具名异常而不是 warning（方向正确，但属行为变化，需要那时的改动者显式确认）。
3. 事件包装类**只覆盖 forwarder 这一条通路**（Node 的 prelude 与 Rhino 的 RemoteAccessibilityEvent 各仍有自己的形态）；本轮没有统一三引擎的事件对象（那要动 engine/node24，超出写作用域）。
4. text 仍是「多片段按空格连接」的字符串（与改造前一致）；Pro 包装类有 String[] 形态，我们没有加——保持脚本可见形状不变优先。
5. **notification / toast 的真机归类未验**：单测按 AOSP 常量对齐（并抓到过一个字面量错误），但 forwarder→广播→:script 这条链在真机上没跑过；脚本侧可这样看：`events.on('toast', e => ...)` / `events.on('notification', e => ...)` 是否收到、`e.kind` 是否正确。
