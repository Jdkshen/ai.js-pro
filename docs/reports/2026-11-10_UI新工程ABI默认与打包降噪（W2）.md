# UI 新工程 ABI 默认值取证 + 打包降噪（W2 / task-85）

## 1. 取证：v7a 从哪来（flutter-ui/lib/project_page.dart）
| 位置 | 事实 |
| --- | --- |
| project_page.dart:12 | static const allAbis = ['arm64-v8a', 'armeabi-v7a'] |
| project_page.dart:13-14 | abiChoices = { 'all': allAbis, ... }（下拉的「全部」就是这两个） |
| project_page.dart:76 | List<String> abis = List<String>.from(allAbis) ← 页面状态默认 = 双 ABI |
| project_page.dart:273-276 | 读回工程时 config['abis'] 不是 List（新工程没存过）→ 仍然回落到 allAbis |
| project_page.dart:144 | values() 里 'abis': List<String>.from(abis) → 保存即写进 project.json |
| project_page.dart:1466 | 用户切下拉 → abis = List<String>.from(abiChoices[choice]!) |
结论：新工程的 abis 默认值来自 Flutter 页面自己的 allAbis 常量（双 ABI），不是回填模板默认；因此每次从 UI 打包都会带 v7a，AbiPolicy 也就每次给出「declared armeabi-v7a 未产出」的 warning（设计内的诚实警告，不失败）。

## 2. 方案（二选一 + 建议）
(a) 新工程默认 abis=[arm64-v8a]
- 收益：消除每次的 v7a warning；新工程体积略小、打包更快。
- 代价/冲突：① 与 AbiPolicy「不静默」的冲突点在于——默认收紧后用户不会再被提醒「这个包 32 位装不上」，除非 UI 同时显式写明「仅 64 位」，即把「不静默」从打包日志搬到表单默认值的呈现才算等价；② 32 位设备直接装不上（v7a 真机本就没验过）；③ 要动 Dart（:76/:276 + 文案）→ 归 W4，且需先协调。

(b) 保留双 ABI 默认，在打包侧/日志侧降噪（推荐，本任务已实现）
- 做法：AbiPolicy.signature(resolution) + warningLevel(previousSignature, resolution)：同一进程里同一条结论只 W 一次（完整 warning + 可抄修法），重复出现降为 INFO 短行（missing/produced），结论变化（声明/产出集合变了）重新 W；事实不消失——打包报告里 abisDeclared/abisProduced/abisMissing 每次都写，getPackagingReport().abisProduced 始终含「可用 ABI」。
- 代价：warning 仍是「每个新进程的第一条」，不是彻底静默。

建议：采用 (b)（零 UI 改动、不牺牲可发现性）；(a) 只在用户明确要求「新工程默认只要 64 位」时再做，且必须由 W4 在表单上显式画出「仅 arm64-v8a」。UI 文案/Dart 一律归 W4，本任务未动 Dart。
