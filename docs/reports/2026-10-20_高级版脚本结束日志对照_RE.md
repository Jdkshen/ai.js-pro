# 2026-10-20 高级版脚本「结束」日志对照 RE（Pro 9.3.11-0 vs 我们 dev-1133）

> 任务：task-187。用户想知道高级版 AutoJs Pro 脚本结束时控制台/日志是什么样，和我们「脚本运行失败 / 脚本已停止」等输出对照。
> 样本：output/auma-base.apk（com.boyai.auma，Pro 9.3.11-0，versionCode 9131100，Node 16.14.0）；反编译源码 .artifacts/pro-apk/auma-src/sources；真机 MI8 ce4d2bdb 上 com.boyai.auma 已安装。
> 方法：jadx 源码定位结束路径 + aapt2 dump resources 提取中文原文（resource ID 对照）+ MI8 真机跑三个脚本（正常、抛错、UI 关闭）并拉取 Pro 外部日志文件 /sdcard/Android/data/com.boyai.auma/files/logs/log.txt + logcat + 截图。

## 0. TL;DR（用户最关心的样子）

1. 正常结束/UI 关闭时，Pro 在**全局控制台日志**里打印（不是 toast）：

       2026-10-20 00:39:46.329/TRACE: 
       ------------
       [/sdcard/脚本/pro_end_test.js]运行结束，用时1.336000秒

   实际耗时是**秒 + 6 位小数**（C 格式 %f），前面固定有换行和一条 12 个短横线；级别是 **TRACE**（Console verbose）。资源原文（zh）：`\n------------\n[%s]运行结束，用时%f秒`；英文：`Execution finished，%f sec.`。
2. 开始运行时对应打印：`HH:mm:ss.SSS/TRACE: 开始运行[<脚本路径>]`（资源 text_start_running）。console.log 是 DEBUG。
3. **正常结束和用户关闭 UI 都不弹 toast、不输出 ERROR**；只打印上面的结束行。关闭 UI（Rhino ScriptExecuteActivity 返回）实际日志：`运行结束，用时2.787000秒`，随后 Activity 关闭，无异常/toast。
4. **异常结束**：先打印结束行（耗时），再打印 ERROR 堆栈（一行 Error + 一行 at 脚本:行号），并弹一个短 Toast：`错误: Error: PRO_THROW_TEST (/sdcard/脚本/pro_throw_test.js#4)`。logcat 另有 W/RunnableJSExecution 的 onException 和完整堆栈。
5. **用户停止（非 UI 关闭，forceStop/停止全部）**：属于 ScriptInterruptedException，走 onException 分支但**不打印 error、不发错误 toast**，只打印结束行；任务/通知行移除。没有单独的「脚本已停止」控制台行。停止全部时另有一个 toast：`已停止%d个正在运行的脚本`。
6. **Pro 的结束行不在 logcat 里**（GlobalConsole 只写 log4j 文件/控制台 UI；logcat 只有异常时的 W/RunnableJSExecution），所以抓 logcat 看不到正常结束；我们目前相反——我们的 GlobalConsole 会 `Log.d` 到 logcat，且格式/小数位不同（详见 §4）。
7. Pro Node UI（V8ScriptExecuteActivity）默认返回只 finish Activity，onDestroy 不 destroy engine，所以返回后脚本可能继续；结束时仍走同一 bc4 onSuccess/onException 打印结束行。不是「返回即结束」。

## 1. Pro 结束路径（源码证据）

### 1.1 监听器：bc4.C1003（ScriptEngineService 的全局 listener）

文件：okhttp3/internal/io/bc4.java（Pro 的 ScriptEngineService 等价物），静态字段 f3404；构造函数里 `scriptExecutionObserver.registerScriptExecutionListener(f3404)`。

- onStart（120-131 行）：设置 console title；source 不以 no-log## 开头时发 EventBus C1006(1001)；engine.setTag(autojs.script_start_time, now)；广播 autojs.pro.action.execution.started。
- onSuccess（134-141 行）：调用 m2414(scriptExecution) 打印结束行；发 C1006(1002)；广播 execution.finished（带 ScriptExecutionInfo）。
- onException（71-117 行）：**先 m2414 打印结束行**；若 ScriptInterruptedException.causedByInterrupted 则 message=null（用户停止），否则 message=th.getMessage() 并且 `engine.getConsole().error(th)`（打印完整堆栈）；有 uncaughtException 再打印并覆盖 message；message!=null 时发 C1006(1003)（触发错误 toast）；广播 finished success=false + message + Rhino 行列号。
- m2414（144-155 行）：从 engine tag `autojs.script_start_time` 取开始时间，`(System.currentTimeMillis()-start)/1000.0` 得 double 秒；source 以 no-log## 开头则跳过；否则 `f3408.verbose(text_execution_finished, source, seconds)`。f3408 是全局 Console（GlobalConsole）。

### 1.2 开始/错误/停止全部的事件消费：bc4.onScriptExecution

文件 bc4.java 234-248 行（@Subscribe EventBus）：

    1001 start  -> console.verbose(开始运行[%s])
    1003 error  -> UiHandler.toast(R.string.text_error + ": " + message)

即错误 Toast 的原文是 `错误: <message>`（资源 text_error=错误，级别是短 Toast；UiHandler.toast 用 js1.m6040(...,0)，0=LENGTH_SHORT 语义）。

停止全部：bc4.m2413（318-325 行）先 ScriptEngineManager.stopAll()，count>0 时 toast `已停止%d个正在运行的脚本`（资源 text_already_stop_n_scripts）。

### 1.3 执行包装：RunnableScriptExecution / Activity

- RunnableScriptExecution.execute（Pro 20-48 行）：doExecution 成功且无 uncaughtException → notifySuccess(engineResult) → engine.destroy()；异常 → onException（内部 Log.w(TAG="RunnableJSExecution", "onException: engine = ...", th) 完整堆栈）→ engine.destroy()。
- UI 模式 ScriptExecuteActivity.finish（442-462 行）：notifySuccess(this.mResult) → super.finish；onDestroy（639-682 行）notifySuccessIfNotFinished() + scriptEngine.destroy()。因此 Rhino UI 按返回/关闭 Activity 走 **success 路径**：只打印结束行，无 ERROR/toast。
- Node UI V8ScriptExecuteActivity.onBackPressed（1932-1934 行）只走 JS delegate；默认 C6971.call=super.onBackPressed（450-460 行）→ finish；onDestroy（2079-2081 行）默认 C6991=super.onDestroy（744-754 行），**没有 engine destroy/stop**。Node 执行结束仍由 bc4 listener 打结束行；返回本身不保证结束。

## 2. 资源原文（aapt2 dump resources 提取）

| resource | 英文 | 中文（zh） |
| --- | --- | --- |
| text_execution_finished (0x7f1102fd) | `\n------------\n[%s]Execution finished，%f sec.` | `\n------------\n[%s]运行结束，用时%f秒` |
| text_start_running (0x7f1103c7) | Start running | 开始运行 |
| text_error (0x7f1102f7) | Error | 错误 |
| text_already_stop_n_scripts (0x7f11028f) | %d running scripts have been stopped | 已停止%d个正在运行的脚本 |
| text_stop (0x7f1103c8) | Stop | 停止 |

注意 `%f` 是 6 位小数；实际日志 `1.336000秒`、`2.787000秒`、`0.513000秒` 已验证。控制台浮窗/LogActivity 的显示会包含这个多行文本；日志文件格式为 `yyyy-MM-dd HH:mm:ss.SSS/LEVEL: message`（多行 message 的后续行不带前缀）。

### 3.4 用户停止（forceStop/停止全部，源码 + 代码路径）

- ScriptRuntime.exit → engines.myEngine().forceStop() → ScriptExecution 异常（ScriptInterruptedException）；bc4.C1003.onException 中 causedByInterrupted 为 true：m2414 仍打印结束行，但 **不 console.error、不 message、不发 C1006(1003)**；UiHandler 不会弹错误 Toast。
- 广播 execution.finished success=false + message=null；任务列表行移除；没有「脚本已停止」的控制台行（仅在 UI 操作菜单里有「停止」资源，不是日志）。
- 与 UI 关闭的区别：UI 关闭是 notifySuccess（真正 success，广播无 success=false）；用户停止是 finished success=false/message=null；两者都不报错、不弹错误 toast，都只有结束行。

### 3.5 Pro Node UI 关闭（源码结论）

V8ScriptExecuteActivity 返回默认只 finish Activity；onDestroy 不 destroy engine；因此 Pro 的 Node UI 返回 ≠ 立即结束脚本；真正的结束行要等 Node 引擎结束（onSuccess）或异常。实测用 Pro 跑 `/sdcard/脚本/Node.js使用Android原生界面/main.js` 时，受 MI8 上其它应用/浮窗干扰，Node UI Activity 未出现在 top，未能取到干净的 Node UI 返回实测；源码结论足够明确，实际日志格式与 Rhino 的 m2414 相同（同一 bc4 listener）。

### 3.6 任务/通知状态（Pro）

- 每次开始/结束都发广播（源码 bc4）：started=autojs.pro.action.execution.started；success/finished=autojs.pro.action.execution.finished，携带 ScriptExecutionInfo；异常结束额外 success=false、message、Rhino 行列号。FlutterScriptsChannel 收到 started/finished 后推送 Flutter 任务列表事件（FlutterScriptsChannel 235-268 行），任务行据此增加/移除；这不是控制台日志。
- Pro 没有「每个脚本结束」的系统通知：ScriptNotification 是脚本主动调 `$notify` 才创建的（ScriptNotification.java）；ScriptService 的前台通知只有一条通用的「%s保持运行中」（foreground_notification_title），脚本结束后服务是否退出取决于是否还有脚本，不是每条脚本一个通知。
- 异常时只有 1 个短 Toast（错误: message）；success/UI close/用户停止都没有结束 Toast。

### 3.7 我方任务/通知状态（对照）

- :script / :native 宿主每个 RUN 有 token，结束时 ScriptHostService reply 101 FINISHED / 102 ERROR(message=脚本已停止 或 describeError)，PocScriptHost/PocNativeRunner 从 TASKS 移除；主进程 ForegroundService 按 execution lease 释放。任务页行移除逻辑与 Pro 类似，但没有 Pro 的 `execution.started/finished` 全局广播给 Flutter（我们的 Flutter 任务页走 PocRuntime 查询/PocScriptHost 静态列表）。
- 错误时：引擎侧 `错误: message` Toast + host `脚本运行失败：message` Toast（多一个）；用户停止时 STOP_MESSAGE=脚本已停止 被 PocScriptHost.onError 识别并吞掉，不弹错误 Toast；没有单独的结束通知。
- 我校 :script 的 ScriptExecutionGlobalListener 结束行写 :script GlobalConsole（logcat D/GlobalConsole），主进程日志页通过 103 只收到脚本 ConsoleImpl 的行，开始/结束行不会出现在主日志页（K40 实测只转发 OUR_END_OK start/end）；这一点和 Pro 的全局 log.txt 一处可见不同。

结论：我们的结束行**在错误堆栈之后**，Pro 是结束行**在错误堆栈之前**（Pro m2414 先于 console.error；我们的 app 级 ScriptExecutionGlobalListener 与引擎 listener 顺序相反/在 finally 之后）。我们的 host 还会多一个 `脚本运行失败：...` 的主进程 Toast（Pro 只有 `错误: ...`）。

### 4.3 我们 :script 结束日志为什么可能没出现在主日志页

- 我们 :script 启动时由 AutoJs 注册 ScriptExecutionGlobalListener，结束行写的是**:script 进程的 GlobalConsole**；主进程日志页/统一环通过 PocScriptHost 的 103 console 转发接收的是**脚本自己的 ConsoleImpl**，开始/结束行不在其中。K40 实测主进程 GlobalConsole 只看到 OUR_END_OK start/end，没看到结束行；而 Pro 的全局日志文件是 :script 进程写的同一个 GlobalConsole 文件/控制台，用户在同一处能看到。
- 我们的 per-run ScriptRunLog 另有一份落盘（正常结束 / 被停止 / 异常退出 + 堆栈 + 本次运行的 console），这是 Pro 没有的；但它也不会自动进主进程统一日志页。

## 5. 对齐建议（按优先级）

1. P0 格式：把 strings.xml 的 `%2$.3f` 改成 `%2$.6f`（或 Pro 的 `%f`），与 Pro 显示一致；若产品更想要友好 3 位，应在文档明确这是有意差异，不要同一功能出现两种精度。
2. P0 位置：把开始/结束行也转发到主进程统一日志/日志页（HostConsoleSink 或 103 增加 global 事件），否则用户在主机日志里看不到脚本开始/结束，只能去 :script logcat/运行日志文件找。
3. P1 异常顺序与去重：确保结束行在错误堆栈之前（对齐 Pro m2414 先于 console.error）；抑制 host 额外 Toast「脚本运行失败：...」，只保留引擎侧「错误: <message>」；或把 host toast 改成与 Pro 一致。
4. P1 用户停止：保持 Pro 语义（只结束行、无 error/toast、无「脚本已停止」控制台行）；我们 host 的 `脚本已停止` 只用于任务列表/内部协议，不要再额外 toast；ScriptRunLog 的「被停止」footer 可作为诊断保留但不进用户控制台。
5. P2 清理日志噪音：移除或降级 `D/RunnableJSExecution: Engine destroy`（Pro 没有），避免结束日志被额外行打断；异常 logcat 保留 W/RunnableJSExecution 堆栈（与 Pro 一致）。
6. P2 Node UI：Pro Node UI 默认返回不结束脚本；若我们的 NodeUiActivity 返回现在会结束（task-178），需在文档/验收里明确是有意产品差异，不能声称与 Pro Node UI 完全一致；结束日志仍应走同一结束行格式。

4. 我方 K40 当前是 debug assemble 的测试包（versionCode 465 / 1.0.2，覆盖了原 dev 通道版本），不是 dev-1133 的发布包；日志代码与 dev-1133 相同，但证据严格说是 dev-1126+taks178 的 debug 构建；如需严格 dev-1133 证据，应装 dev 通道包重跑。
