## 0. 一句话现状

在「天天象棋」上做**自动走棋**：截图 → 识别 90 格盘面 → 生成合法着法 → 用 Shizuku/无障碍注入点击 → 截图确认落子。
识别侧目前用 160×160 的 7 类 YOLO（只判兵种、不判颜色；颜色另用像素采样判）。
**盘面级准确率：皮肤 9 帧/810 格 = 97.2%（未知格 0.6）；域内 10 帧/320 格 = 97.5%。**
两次「微调提升精度」的尝试**都失败了**（详见 §4），本文最想请评审的就是 §7 的那些问题。

## 1. 名词与口径（很重要，之前踩过「口径自欺」）

- **盘面级准确率**：把 90 格逐格比对真值（FEN），算 `对格 / 总格`。**严格区分大小写**（大写=红、小写=黑）。
  曾一度做了大小写归一，结果「颜色判错」被算成对，81.9% 被报成 88.5% —— 现在必须分开统计：
  `严格（含阵营）` / `只看兵种+位置` / `纯颜色错格数` / `平均未知格数` / `跳过格数`。
- **未知格**：识别器对某格既不敢判空也不敢判兵种（候选置信度太低）→ 记 `?`。它会被一致性修复吞掉，所以要单独看。
- **两个数据集**（都不参与训练，只用于验收）：
  - **皮肤集**：K40 + 这一套棋局皮肤的 9 帧真实截图 / **810 格**。其中 3 帧是人工逐格读的，6 帧是「模型草稿 × 像素机械判读」交叉验证得到的（冲突格记 `?` 不参与计分）。
  - **域内集**：另外 10 帧照片域截图 / **320 格**（有真值）。
- 每次评测都开**会话级几何校准**（见 §3.1）+ 一致性修复，保证所有模型用同一条流水线。

## 3. 已经踩掉并修好的坑（真机实测，全部有日志）

### 3.1 校准的「静默失败」
`locateBoardOnScreen()` 返回的是 `{frameObject}`，**没有 `imageObject`**（只有 `locateBoardInImage` 有）。
`calibrateGrid(image, located, ...)` 原来只读 `imageObject` → 直接 `return {ok:false}`，而调用方没检查返回值 →
**继续用未校准的几何识别**（表现为「颜色整片判错、未知格一堆」）。
修：`calibrateGrid` 两个字段都认，并允许调用方直接传图。

### 3.2 一致性修复会把成对子力错配掉
黑士被误判成红仕 → 同时触发「仕/士不在九宫（硬违规）」和「红仕出现 3 个（数量违规）」→ 修复逻辑把**真子删掉**了。
修：两个修复分支都**先试「翻色」**再降级；**未知格 6 → 0**。

### 3.3 校准代价函数（踩了两次，同一类错误）
```js
// 错误版本：只算「违规数 × 1000 + 未知格数」
// 加翻色后，几乎每个偏移都能做到「0 未知格」→ 搜索直接停在未对齐的 (0,0)，
// 颜色正确性反而崩塌（纯颜色错 0 → 18 格）
cost = fixes * 1000 + unknown;
// 正确版本：把「修复动作次数」也算进去
```
同一类错误在 `pickGrid` 上又出现两次：
1. 只算「违规 + 未知格」→ **全空/挂在棋盘外的网格代价为 0**，被选成最优（实测选到偏移 -54，识别出「90 格全有子」）；
2. **FEN 解析失败被当成 0 违规** → 瞎网格又被选成最优（实测「子 88 未知 2」）。
最终代价函数见 §3.6。

### 3.4 截图通道（MediaProjection 很脆）
MIUI 会把投屏会话移除 → 之后每帧截图都超时。Shizuku 的 `screencap -p <path>` + `images.read` 稳定、免授权、不会被失效。
已实现 `capture()` 自动回落（实测 `capture ok=true 用时=1419ms 实际通道=shizuku`，帧 1080×2400 非全黑）。
⚠️ 另外：`locateBoardOnScreen` 内部用 MediaProjection 截图，**会话死掉后它会无限等**（脚本卡 4 分钟无输出无异常）。

### 3.5 线定位器在本皮肤下不可靠
`locateBoardInImage()` 要求**9 条竖线全命中**，实测经常只有 7~8 条：
```
定位失败：垂直线：格点阵与给定棋盘范围对不齐（步长 114.6，命中 7/9 条）；请把范围调到紧贴棋盘，或改人工校准
```
显式给 `region`（试了 6 组，含紧贴棋盘的）最好也只到 8/9。它同时卡住采集器与评测工具（多帧被跳过、草稿 0 帧）。

### 3.6 现在用 `pickGrid`（两套已知基准 + 子力数先验）
关键：**棋盘几何会随游戏 UI 变**（同一台 K40、同一个游戏，实测到两套：`origin(81,666)/step(115,114)` 与 `origin(72,660)/step(114.8,114.3)`），所以不能硬编码。

```js
function scoreGrid(image, grid, opts) {
  const r = run(image, {ok:true, grid, imageObject:image, frameObject:image}, {...}, null);
  const pieces = r.chars.filter(c => c !== '.' && c !== '?').length;
  let violations = 0;
  const parsed = fen.parseFen(r.layout + " w");
  if (!parsed.ok) violations = 9;                       // ← 解析失败必须惩罚，不能算 0
  else violations = fen.validateBoard(parsed.board).errors.length;
  return {
    cost: violations * 1000 + r.unknownCells * 10 +
          Math.max(0, 28 - pieces) * 100 + Math.max(0, pieces - 32) * 100,  // ← 子力数先验
    pieces, unknown: r.unknownCells, violations, result: r
  };
}
// 搜索：两套种子各自 ±30px、步长 6px 粗搜（早停：代价 0）→ 最优点附近 ±5px、步长 1px 细搜
// 接受条件：pieces ≥ 24 && violations === 0 && unknown ≤ 4
```
实测：**171 次推理/帧 ≈ 19.8 秒/帧**，单帧验证通过（未知格 0）。

### 3.7 采集器的坑（也一并记下）
- 早期版本要求「游戏接受这一步」才收帧 → 大部分时间在等对手/动画，3 分钟只收 9 帧；
- 每帧抓两次图（`waitStable` 里一次 + 落盘一次）→ 改直接抓到目标路径；
- 随机走子会把棋局走死（进结算页），之后连按返回键会**彻底离开棋盘** → 后续全部识别失败、`连续 21 次失败放弃`。需要三级自救：返回键 → 重拉游戏+点屏幕中间 → 重新校准网格；
- ⚠️ 重跑前脚本里的 `rm -f /sdcard/xiangqi-p4/realframes2/*.png` **把已收的 13 帧删了** —— 现在规定：重跑前先备份到别的目录。

### 3.8 库缺 require（评审时同样要警惕的「看着成功其实没落地」）
`recognize-board.js` 里新增 `pickGrid` 用到的 `geometry`/`fen` **没被 require 进来**（一次批量编辑报告成功、实际没写入），
表现为 `pickGrid 抛异常：cannot read property 'createGrid' of undefined` → **评测工具每帧空手返回、草稿 0 帧**。
教训：改了库函数后要**实测一次**，不能只看编辑工具的成功回执。

### 4.4 两次「真实帧微调」都失败了

**实验 A（用 9 帧真实帧，2026-09-13）**
- 数据：9 帧 × (1 原图 + 40 几何/光度抖动) = 369 + 通用域 800 = **1169 张**
- 配方：从 v3n 热启动，AdamW / lr 1e-4 / 12 轮 / imgsz 160 / mosaic 0 / batch 16 / CPU
- 结果：**皮肤 611/810 = 75.4%（基线 97.2%）；域内 183/320 = 57.2%（基线 97.5%）；通用 val mAP50 0.335（基线 0.530）**
- 直接原因（已定位）：**标签毒化**。标签流水线是「模型草稿 × 像素机械判读交叉验证」，但机械判读只能独立校验**颜色/有无**，
  **兵种仍取自单个模型草稿** → 草稿里 ~3% 的兵种错（如 車↔炮）被当成真值，再经 ×41 抖动放大 ⇒ 训练集里约 **1/4 的框是错的**。
- 推论：**不能拿模型输出当训练标签的兵种来源**。要么标签由构造精确得出（如合成），要么人工逐格核对。

**实验 B（合成 900 张，标签精确）**：皮肤 94.4% / 域内 98.1% ⇒ 少量数据（<30 帧等效）微调 160 模型，
即便标签干净也会**破坏通用先验且补不回来**（域内微涨、皮肤反降）。

## 5. 正在做的改进（准备跑第三次）

1. **标签可信度**（针对 §4.4 的根因）
   - `chess-consensus-label.py`：每个格子要过三道闸才算真值
     - 机械判读（像素）：空 / 有子偏红 / 有子偏暗
     - **多模型投票**：票源取实测最好的 4 个（仓内 97.2% / v4 95.8% / v2 94.4% / ft 94.4%），
       **至少 3 票一致、且「仓内的那一票必须在多数里」**；否则记 `?`
     - 机械判读的颜色/有无必须与兵种一致（大写=红、小写=黑、`.`=空）
   - 整帧再过**棋规硬校验**（各类子力上限 + 双方各一个帅/将）；不通过则**整帧丢弃**（同源错误的典型信号）
   - `?` 格**不是留空**，而是用**同帧最近空格**的贴片盖掉 —— 格子里真有子却不给标签 = 教模型「检出它就是假阳性」

2. **保守微调**：`--freeze 10`（冻结主干）+ `lr 1e-5` + 3 轮 + mosaic 0，验收只看 §1 的两个盘面级指标，
   且**必须 ≥ 97.2% 且未知格 ≤ 0.6** 才考虑替换。
3. **几何**：评测/标注工具优先用 `pickGrid`（§3.6），线定位器只当兜底。

## 7. 请评审的问题（按优先级）

1. **标签**：我们的「多模型投票（仓内那票必须在多数里）+ 像素机械判读 + 棋规硬校验」是否足以把**兵种**错误压到
   可训练的水平？有没有更便宜/更强的替代？（例如：用游戏自带的「棋谱/残局」拿到**已知盘面**再截图；
   用对局记录 + 合法着法链反推盘面；或对少量帧做「人眼逐格」全量标注）
2. **训练配方**：在**只有 10~100 帧**真实盘面的前提下，要让 160×160 的检测模型在这套皮肤上「不变差、略有提升」，
   正确做法是什么？（冻结主干 / 只调检测头 / LoRA-ish / 对比学习 / 蒸馏 / 域随机化合成 / 只做 logit 校准 /
   几乎不动权重的「last-layer finetune」？）为什么我们的两次都出现灾难性遗忘（通用 mAP50 0.530 → 0.335）？
3. **是否该放弃微调**：把力气改到**推理侧消错**（可疑格逐格枚举 + 合法着法全票）是否更划算？
   注意识别器已经会输出「未知格」和逐格候选（我们目前只用了 top-1）。
4. **采集**：除了「随机走子」，还有哪些可靠方式批量获得**真实盘面截图**？（棋谱回放、残局关卡批量打开、
   用引擎自己走棋（③ 模式）录制、或用同一盘面人为制造光照/压缩差异）
5. **评估的统计功效**：810 格 / 9 帧（每帧 90 格高度相关）是否足以判断 1~2 个百分点的差异？
   给出建议：需要多少帧、该用什么检验（配对 McNemar？按帧 bootstrap 置信区间？），以及帧级/格级聚合的正确姿势。
6. **几何与速度**：`pickGrid` 每帧 171 次推理 / 19.8 秒。有没有更稳更快的做法？
   （霍夫变换/模板匹配/边缘投影；用检出框中心之间**等距**约束直接解 9×10 格点；先用小模型粗定位再精修）
7. **类别不平衡与召回**：域内短板是红方子力召回（馬 .30 等）。针对性的手段有哪些值得试？——
   class-balanced loss / per-class anchor / CopyPaste 增强 / 难例挖掘 / 提高输入分辨率（160 → 320，代价 21ms → 22ms？实测见下）？
   参考实测：K40 上 160 方形 pre+inf ≈ 7.4ms（131 FPS），160×320 矩形 ≈ 12.4ms，320 方形 ≈ 21.3ms，640 ≈ 80ms。
8. **颜色判定**：现在用中心区像素统计（`max(r,g,b) < 170` 判有子；`r > b + 40` 判红）。
   在木纹背景 + 高光/阴影下有无更鲁棒且同样便宜的做法？（HSV 阈值？红黑双通道投影？用 7 类模型 + 一个微小颜色头？）
9. **标定阈值**：识别器的「未知格」阈值（候选置信度）怎么定才能兼顾「不漏判」与「少未知」？
   是否应该输出**逐格概率分布**并交给下游（合法着法全票）而不是在识别器里拍板？
10. **工程细节**：上面 §3 那些 bug 有没有同类风险我们还没发现的？（尤其「静默失败」模式：
    函数返回 `{ok:false}` 但调用方不检查；代价函数把「不可解析/退化输入」评为最优；编辑工具报成功但没写盘）
