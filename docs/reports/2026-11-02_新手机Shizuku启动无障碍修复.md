# 新手机 Shizuku 已授权却无法启动无障碍（dev-1311 候选）

## 实机定位

用户新手机：型号 `2602BRT18C`，Android 17 / SDK 37，系统 `OS4.0.3.0.XPLCNXM`；MCP `192.168.10.4:8765`。初始应用 dev-1309，Shizuku 管理器 `13.6.0-a17.1 / 1087`。

初始探测结果：Shizuku Binder 存活、授权为 true、后端 UID 2000；应用没有 WRITE_SECURE_SETTINGS，无障碍设置为空、服务未连接。普通 Shizuku `id` 查询也在启动执行服务阶段超时，原无障碍入口复测约 5 秒返回 false。

无线调试恢复后抓到执行服务进程的明确异常：

```text
ShizukuServiceStarter: unable to start service ...ShizukuUserService
Caused by: java.lang.NullPointerException
  at android.app.LoadedApk.makeApplicationInner(LoadedApk.java:1780)
  at android.app.LoadedApk.makeApplication(LoadedApk.java:1668)
System.exit called, status: 1
```

服务在框架创建 Application 的阶段退出，尚未进入本应用 UserService 的命令执行逻辑，随后客户端等待连接超时。不是 Shizuku 授权未通过。

独立对照：使用已授权的 ADB 写入本应用无障碍组件后，服务正常连接，`AutomationConnectionState.isReady=true`，系统 `dumpsys accessibility` 也出现 AI.js Pro Bound service。因此本机无障碍实现可以运行，阻断点是原来的 Shizuku UserService 启动路径。

证据保存在 `.artifacts/shizuku-accessibility-20261102/`；`probe-initial.log`、`more-probes.log`、`user-service-pid9932.log`、`adb-control.log`、`adb-control-dumpsys.txt`。USB 曾短暂出现后断开，本轮经已受信任的无线调试 `192.168.10.4:42117` 连接，没有操作旧测试机或 K40。

## 修改

- 无障碍启用优先经已授权 Shizuku 的 Binder 转发，直接对系统 settings 服务发出参数化请求，不创建本应用 UserService、不启动 app_process。
- 写入当前应用所属 Android 用户的设置，合并已有组件，识别完整/缩写两种组件名；保留其他无障碍服务和顺序，避免子串误判和重复。
- 保留旧系统的 UserService 兼容回退，整个设置/连接流程共享预算；Binder 调用由有界后台工作线程执行，超时和中断不阻塞界面，临时输出限制 32 KiB 并清理。
- 成功以真实无障碍服务连接为准，去掉“设置中有组件就算成功”的兜底；修复入口同样使用真实连接状态。
- 页面保留具体错误（未运行、未授权、系统写入失败、已写但未连接），不再把所有失败都提示为“请确认已授权”。移除失败说明中会直接覆盖其他服务列表的 ADB 写入示例。

协议依据：[Shizuku 官方 Binder 转发](https://github.com/RikkaApps/Shizuku-API#remote-binder-call)、[Android Binder shellCommand 实现](https://github.com/aosp-mirror/platform_frameworks_base/blob/master/core/java/android/os/Binder.java)。没有修改手机 Shizuku 安装包，也没有因这次故障更改应用权限默认值。
