# 红黑判色改用引擎「找色」（2026-09-20，K40 真机）

> 触发：用户在真机排查颜色判错时提出「新引擎不是有找色的案例吗」——
> 引擎自带 `images.findColor / findMultiColors / findAllPointsForColor`（**原生实现**），
> 象棋脚本却一直在用「逐点 `images.pixel` + 平均饱和度/Lab a*」自己算颜色。

## 1. 引擎里的找色是什么

| 接口 | 语义 | 实现 |
|---|---|---|
| `images.findColor(img, color, {region, threshold})` | 区域内第一个命中点 | `native_frame_store.cpp` → `findColor`（C++ 扫） |
| `images.findColorInRegion / findColorEquals` | 同上（带坐标 / 精确匹配） | 同上（`threshold=0`） |
| `images.findAllPointsForColor(img, color, {region, threshold})` | **区域内所有命中点**（本任务用它计数） | `findAllPointsForColor`（上限 2 万点） |
| `images.findMultiColors(img, first, [[dx,dy,c],…], {region})` | 多点形状匹配 | `findMultiColors` |
| `images.detectsColor(img, color, x, y, threshold)` | 单点相似判定 | `colors.isSimilar(images.pixel(...))` |

容差语义：**逐通道** `|Δr|≤T && |Δg|≤T && |Δb|≤T`（`threshold` 0~255）。
示例脚本：`sample/QuickJS 新引擎/图色处理/02-截图找色与多点找色.js`、`01-图色 API 自动回归.js`、
`10-图色查找补充接口.js`。

## 3. 真机实测（32 格同一帧，`tools/ink-lookup-probe.js`）

| 格子类型 | 红命中（密度） | 黑命中（密度） | 判定 |
|---|---|---|---|
| 红方棋子（9 格） | 881 ~ 1227（0.215 ~ 0.300） | **0** | RED |
| 黑方棋子（16 格） | **0** | 493 ~ 769（0.120 ~ 0.188） | BLACK |
| 空位（8 格） | 0 | 0 | UNKNOWN |

耗时：**找色判色 22 ms / 32 格**（≈0.7 ms/格）｜老「逐点采样 484 点 + 分类器」**137 ms**（≈4.3 ms/格）⇒ 快 6 倍。

## 4. 真机暴露的两个连带问题（本次一并修）

1. **颜色会被永久钉死**：投票器原来的「单帧翻面保留上一帧」没有次数上限 ——
   只要某格被读反一次（落子动画/高亮环那一瞬），之后每帧的正确读数都被当成「翻面」而丢弃。
   真机症状：驱动反复 `轮次推不出来（UNKNOWN）`，原始读数里 (2,3) 红炮一直是 `c`、(4,6) 黑炮一直是 `C`，
   而面板全盘 OCR（同样走找色）每轮都在把它改回来 → 两套读数互相打架。
   ⇒ 现在连续 `flipFrames=3` 帧读反就采纳新颜色（并记 `stats().flips`）。
2. **autorun 的「声明轮到我」只试一次**：碰上「局面还有未知格」被拒后标记就清掉了，
   之后没有基准 ⇒ 状态机一路 `RECOVERING` 空转到 `stopAfterMs`。⇒ 被拒时保留标记、下一轮干净帧重试。

## 5. 已知残留（下一步）

- 面板全盘 OCR 的**兵种**仍会漏/串（例：整行 `兵` 里的 (6,6) 读不到；`士` 偶尔读成 `H`）——
  属于 OCR 侧问题，与颜色无关（颜色已用真值截图逐格核对： (4,6) 黑炮、 (2,3) 红炮 均判对）。
- 几何：`locateBoard` 这次给出 `origin.y = 697`（真实棋盘约 666）却没有触发校准失败。
  颜色因为锚在 YOLO 框上不受影响，但**兵种映射**在边界格上会受影响。
