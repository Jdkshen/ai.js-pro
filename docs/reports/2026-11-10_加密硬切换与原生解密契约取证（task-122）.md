## 二、③ 原生解密契约取证（**只读，未改**；等你确认）

- Java 侧把**参数**（不是结果）交给原生：`AssetsProjectLauncher.kt:380 EncryptedScripts.setHardenedParams(packageName, salt, fingerprint)`；`modules/engine/src/main/java/com/stardust/autojs/script/EncryptedScripts.kt:27-44` 存这三个值，`:126-127` 取出来用。
- 另一条路（旧/原生库不可用）走 JVM：`ScriptEncryption` 的 `mKey`/`mInitVector` 由运行端**反射**塞进去（`AssetsProjectLauncher.kt:388-394`），这条是**吃 Java 派生的 key/vector** 的。

### 对「硬化成真 256 位」的含义（未做，等你确认）

| 路径 | 谁派生 | 硬化要改哪 | 风险 |
|---|---|---|---|
| 打包产物 + 原生库（`setHardenedParams` 后） | **原生**（与 Java 同公式、同截断） | **必须同时改** `ScriptKeyDerivation.deriveKey` **和** `script_crypto.c:316` 的派生/截断；两处必须逐字一致 | 只改一侧 ⇒ 解不开（表现为解密/padding 失败，**不是**点名错误） |
| 无原生库 / 旧路径（JVM `ScriptEncryption`） | Java（反射塞 `mKey`） | 只改 Java | 低 |

- 现状「32 个 hex 字符当 32 字节用」⇒ 有效熵 ≈ 128 位（hex 每字符 4 位），但 AES 仍按 32 字节展开（`aes256_expand_key(key[32])`）。要成真 256 位，两条路都要改成「派生 **32 原始字节**（或 64 hex 解码）」，且**旧产物必须重新打包**。
- **建议落地顺序（等你拍板）**：⑴ 先改 Java + C 两处并写**跨端一致性**单测（用固定 (pkg,salt,fp) 断言同一 key 值，C 侧可用 `javah`/测试进程比对或由打包端校核）；⑵ 再改 `randomSaltHex` 之外的 key 长度口径与 project.json 字段（若加版本标记，运行端应能对「新 key 长度 + 旧版本标记」点名拒绝）；⑶ 真机用**新打的包**验一次。**在此之前不要动**。
