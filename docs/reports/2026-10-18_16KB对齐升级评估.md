# 16 KB 页对齐升级评估（Flutter / OpenCV / ML Kit / androidx）

- 日期：2026-10-18
- 评估对象：`apps/app`（Miuix + Flutter 玻璃 POC）、`modules/engine`（QuickJS / PP-OCR / OpenCV / ML Kit 原生）
- 结论一句话：**19 个 arm64 库中只有 `libflutter.so` 的 PT_LOAD 未对齐（0x1000）**；OpenCV / ML Kit / androidx.graphics 早已达标，**不需要升级**。真正要动的只有 **Flutter 引擎线（3.3.4 → 3.47.7）** 与 **自有 native 的 RELRO 末尾对齐**（严格口径）。
- 本文所有对齐数据均为本次实测（非引用），测量对象就是 K40 上正在运行的 `dev-1002` 包（sha256 与本地构建产物逐字节一致）。

## 1. 判定口径：什么叫"符合 16 KB 对齐"

Android 15 起支持 16 KB 页；Android 16 对不符合的应用弹"Android 应用兼容性"对话框（release 包在 16 KB 设备上则会走 page-size-compat 兼容模式甚至加载失败）。Google 官方要求（[page-sizes](https://developer.android.com/guide/practices/page-sizes)）可拆成三条独立判定：

| # | 判定 | 检查方法 | 本次是否硬门 |
| --- | --- | --- | --- |
| 1 | **ELF PT_LOAD `p_align` ≥ 0x4000** | `llvm-readelf --program-headers`，看每个 `LOAD` 行末列 | ✅ 硬门（系统弹窗里唯一给出确切结论的项） |
| 2 | **APK 内未压缩 .so 的 zip data offset 16 KB 对齐** | 解析本地 zip 头 `header_offset+30+fnlen+extralen`，%16384 | ✅ 硬门（AGP ≥ 8.5.1 自动做） |
| 3 | **PT_GNU_RELRO 末尾 16 KB 对齐** | `(RELRO.vaddr + RELRO.memsz) % 0x4000` | ⚠️ 严格口径/推荐项：AOSP 与 Flutter 都把这条写进检查（见 [flutter#193545](https://github.com/flutter/flutter/issues/193545)、[PR#193930](https://github.com/flutter/flutter/pull/193930)），但**本次弹窗没有把它单独报出来** |

补充事实（本次实测）：

- K40（`cccc62c7`，LineageOS / Android 16，SDK 36）的 `getconf PAGE_SIZE` = **4096**。也就是说**这台机器是 4 KB 页**，弹窗属于"debuggable 应用 + 4 KB 设备"的**警告**路径（框架字符串 `page_size_compat_*_warning_4kb`），并不会真的崩；16 KB 真机/模拟器上才会变成加载问题。
- 弹窗文案里明确写着"由于当前正在测试的是**可调试**应用，因此系统会显示此警告"——**release 包不会弹这个窗，但也不会有警告兜底**，这是最容易漏掉的风险点。
- 官方检查脚本：[check_elf_alignment.sh](https://cs.android.com/android/platform/superproject/main/+/main:system/extras/tools/check_elf_alignment.sh)。

### 2.3 K40 上弹窗的实测内容（关键，且与直觉相反）

在 K40 上冷启动 `dev-1002`（force-stop 后拉起 `SplashActivity`），弹窗真实内容为：

- 标题"Android 应用兼容性"；正文"此应用不符合 16 KB 对齐要求。**ELF 文件对齐检查失败**。"
- "以下库未进行 16 KB 对齐："共列出 **19 个库（APK 里全部 arm64 库）**，其中：
  - `libflutter.so`：**"LOAD 区段未对齐"**（与实测一致，唯一确切结论）
  - 其余 18 个（含实测 LOAD 全 0x4000 的 OpenCV / ML Kit / quickjs / libapp / **libc++_shared** / graphics-path）：**"未知错误"**
- 框架侧字符串可佐证这是"未知错误"兜底：`page_size_compat_unknown`（设备 `/system/framework/framework-res.apk` 里的 `page_size_compat_*` 资源族：`apk_not_aligned` / `elf_not_aligned` / `apk_and_elf_not_aligned` / `unknown` / `title` / `never_show`，另有 `_4kb` 变体）。

**怎么解读**：系统弹窗的逐库结论目前只有"LOAD"这一类被真正实现；对已经对齐的库它给的是兜底文案"未知错误"，**不是**"这个库有问题"的证据。因此：

1. 静态实测（§2.2）才是可信的逐库判定；
2. 但"改完 libflutter.so 弹窗就会消失"**不能仅凭静态推断**——必须把"弹窗是否消失"作为 P1 的出口实测项（见 §8），并准备"仍有'未知错误'条目、但不再有 LOAD 条目"这种中间态的解释口径。

## 3. 剩余未对齐清单与根因

### 3.1 硬缺口：libflutter.so（必须解决）

- **根因**：payload 里的 `libflutter.so` 是 **Flutter 3.3.4（2022-09）** 的预编译引擎，链接期只用了 4 KB 页对齐（`p_align=0x1000`），4 个 LOAD 段全是 0x1000。`build-aot.ps1` 只重编 AOT（`libapp.so`），**从不动引擎**；`libapp.so` 由 3.3.4 的 gen_snapshot 产出，本身已是 0x4000。
- **为什么不能"就地修"**：ELF 的 `p_align` 与段间偏移在链接期决定，事后 patch `libflutter.so` 会破坏段映射（真要 patch 还得重排整个文件），不可行也不可维护。
- **结论**：只能换引擎版本 → 即 §4 的 Flutter 3.47.7。

### 3.2 严格口径缺口：RELRO 末尾（建议解决，非阻塞）

- **根因**：链接时只传 `-Wl,-z,max-page-size=16384`，没有同时传 `-Wl,-z,common-page-size=16384`，LLD 只把 **LOAD 段**按 16 KB 对齐，**PT_GNU_RELRO 末尾**仍按 4 KB 圆整。
  - 自有库：`CMakeLists.txt` 三处 `target_link_options` 都只写了 `max-page-size`；NDK 侧 `build-quickjs.ps1` 已带 `-DANDROID_SUPPORT_FLEXIBLE_PAGE_SIZES=ON`（r27c 下等价于只设 max-page-size），所以 `libquickjs` / `libquickjs_jni` / `libppocr` 依然落在 12288 / 8192。
  - 第三方预编译（OpenCV / ML Kit / graphics / pikafish / libc++_shared）：**我们无法重链**，只能等上游或换版本。
- **上游同样没修完**：Flutter 直到 **3.47.7（2026-10-08 发布）** 的官方 `libflutter.so` 仍然是 LOAD 0x10000、RELRO 末尾 12288 —— 本次直接下载 `io.flutter:arm64_v8a_release:1.0.0-deb2874…` 实测确认，对应 issue [#193545](https://github.com/flutter/flutter/issues/193545)（open）与修复 PR [#193930](https://github.com/flutter/flutter/pull/193930)（open，未合入）。

### 3.3 已经不是问题的（澄清历史弹窗文案）

POC 验收文档（`docs/reports/2026-10-17_Flutter玻璃界面POC验收.md` §6.1）里写的"列出 libapp.so 以及既有 libopencv_*、libquickjs*、libmlkit_* 等"，按本次实测应更正为：**这些库的 LOAD 早已对齐，弹窗里给的是"未知错误"兜底文案**。它们不需要升级，避免把工作量估到 OpenCV / ML Kit 上。

## 5. 升级步骤（分阶段，含影响面）

### P0 — 基线固化与守卫（1 人日）

**做什么**

1. 归档当前基线：`output/flutter-poc/payload` → `output/flutter-poc/payload-3.3.4-baseline/`（回退用，git 忽略目录，不入库）；把 §2.2 的表另存为 `docs/reports/2026-10-18_16KB对齐升级评估_基线.csv`（可选）。
2. 新增 `tools/check-16kb.py`（或 .ps1）：解包 APK → 对 `lib/arm64-v8a/*.so` 输出三列（LOAD p_align / RELRO 末尾 %16K / zip data offset %16K），任一项低于阈值即非零退出。解析逻辑本次已跑通（见 §9 附录）。
3. 把该脚本挂到 `tools/publish.ps1` 的前置校验（与现有 versionCode / SHA 校验并列），**发布前 fail-fast**。

**影响面**：只新增工具与发布校验，不动构建产物、不动 payload、不动业务代码。
**风险**：脚本依赖 `llvm-readelf` 路径，建议参数化（`-Readelf`，默认 NDK r27c/r26d 的 `llvm-readelf.exe`）。

### P1 — Flutter 引擎线切换（5–8 人日，主战场）

**做什么**

1. 安装 Flutter **3.47.7** 到独立目录（如 `C:\Android\flutter-3.47.7`），保留 3.3.4 不动；补装 `platforms;android-36`（当前只有 28 / 35）。
2. 重建 payload（改 `output/flutter-poc/build-aot.ps1` + `prepare_payload.py`）：
   - `flutter_embedding_3.3.4.jar` → `flutter_embedding_release-1.0.0-<engineHash>.jar`（从 `https://storage.googleapis.com/download.flutter.io/io/flutter/…` 拉，hash 与引擎一致）；
   - `libflutter.so` → 从 `io.flutter:arm64_v8a_release:1.0.0-<engineHash>` 取。注意：Maven 里是**未 strip** 的 165 MB 版本，打包时由 AGP 的 strip 任务压到 10 MB 量级——本仓库 debug 构建不 strip，**必须在 payload 生成阶段自己 `llvm-strip`**，否则 debug APK 会暴涨约 150 MB；
   - `libapp.so` → 新 SDK 的 `flutter assemble android_aot_bundle_release_android-arm64` 产物（**该 target 名在 3.47.7 仍然存在**，已核对 `flutter_tools/lib/src/build_system/targets/android.dart`）。
3. `apps/app/build.gradle`：`debugImplementation files(payload/flutter_embedding_3.3.4.jar)` → 新 jar 路径；补齐 §4.2 的传递依赖（或放开对应 `force`）。
4. 处理 `flutter pub get --offline`：3.3.4 时代业务工程已缓存依赖，3.47.7 需要重新解析一次（首次联网），之后可继续离线。
5. 回归 Impeller：3.47 在 Android 上默认 Impeller / Vulkan，玻璃折射 shader、模糊、首帧快照重试逻辑都要重测；必要时用 meta-data `io.flutter.embedding.android.EnableImpeller=false` 兜底。

**影响面**

| 维度 | 影响 |
| --- | --- |
| 构建脚本 | `build-aot.ps1`（SDK 路径、assemble 参数、新增 strip 步骤）、`prepare_payload.py`（新增 jar/so 校验）、`payload-report.json`（SHA 全变） |
| payload | 3 个文件全换：embedding jar 609 KB → 1.58 MB、libflutter.so 9.9 MB →（strip 后待测）、libapp.so 5.5 MB →（待测）；`flutter_assets` 由新 SDK 重新生成（Material 资源路径可能变化） |
| 示例矩阵 | Flutter 侧只有 3 条桥（bootstrap / list / theme），但**玻璃首页 + 抽屉降级项**要全点一遍；Dart 3.13 + Material 拆包（3.47 把 Material / Cupertino 拆成独立包）可能要求业务工程改 import |
| 发布流程 | payload 生成从"手工可重跑"变成"必须锁 engine hash"；建议把 hash 写进 `payload-report.json` 并在发布会话里打印 |
| 包体 | 预计 +2~5 MB（新引擎 + 对齐填充），需实测记录（现状 253 MB） |

**出口门**：新 APK 里 `libflutter.so` 的 4 个 LOAD 全 ≥ 0x4000（预期 0x10000）；K40 上冷启动不再出现 LOAD 类弹窗条目；玻璃首页截图与旧版对比无结构性差异。

### P2 — 自有 native 的 RELRO 补齐（1–2 人日，可与 P1 并行）

**做什么**（二选一，推荐 A + B 都做）

- **A（最小改动）**：`modules/engine/src/main/cpp/CMakeLists.txt` 三处 `target_link_options` 增加 `"-Wl,-z,common-page-size=16384"`（保留现有 `max-page-size`），重跑 `build-quickjs.ps1`（3 个 ABI）。
- **B（跟官方）**：NDK r27c → **r28 / r29**，保留 `-DANDROID_SUPPORT_FLEXIBLE_PAGE_SIZES=ON`（r28 起该开关同时设 max / common page size），重跑 `build-quickjs.ps1`。

**影响面**：`modules/engine/src/main/jniLibs/<abi>/*.so` 全部重编（`libquickjs` / `libquickjs_jni` / `libaijscrypto` / `libppocr`）；`:app:verifyQuickJsNativeLibrariesFresh` 的 mtime 守卫按现有流程走（`build-quickjs.ps1` 末尾已统一刷新 mtime）；包体因对齐填充略增（< 1%）。
**注意**：第三方预编译（OpenCV / ML Kit / graphics / pikafish）**不在本阶段范围内**，它们的 RELRO 末尾仍是 12288 / 8192，需要 P3 决定是否接受。

### P3 — OpenCV / ML Kit / androidx 复核（0.5–1 人日）

**做什么**：不是"升级"，而是"取证 + 决策"。

1. 复核 §2.2 的 9 个 OpenCV 库 + ML Kit + graphics：LOAD 全 0x4000、zip 对齐 0 —— 结论是**当前版本已满足硬门**，不需要换。
2. 只有当 P1 / P2 的实测证明"系统弹窗确实按 RELRO 判定"时，才启动真正的换版：
   - OpenCV：等官方 4.11+ / 5.x 的下一版 16 KB 资产（自建 aar 流程见 `docs/guides/SIFT特征匹配示例.md` 的 `--output-aar` 段落）；
   - ML Kit：16.0.1 已是 Maven 最新，**无版本可升**，只能向 Google 报 issue（同类：[googlesamples/mlkit#987](https://github.com/googlesamples/mlkit/issues/987)、[#975](https://github.com/googlesamples/mlkit/issues/975)）；
   - graphics-path：1.1.0 可试，但不保证 RELRO 变化。
3. 产出：一张"换版能否改善 RELRO"的结论表，避免无谓改动。

**影响面**：若维持现状 → 零改动；若换 OpenCV 官方 aar → 其 Java 层是 Java 17 字节码（当初正因 AGP/JDK 限制才自编 Java 8 版），需要重新评估 `minSdk 26` 下的 desugar 与 `libopencv_java5` 的 JNI 注册路径。

### P4 — 全量回归与发布（2–3 人日）

**做什么**

1. 设备矩阵：K40（Android 16 / 4 KB，主验弹窗与玻璃首页）、小米 8（Android 10，兼容性回归）、**16 KB 模拟器**（Android 15/16 的 16 KB 页镜像，唯一能证明"真 16 KB 环境可加载"的环境）。
2. 功能矩阵：Miuix 主界面、抽屉、文件 / 工作区、QuickJS 运行、OCR（ML Kit 与 PP-OCR 各一次）、YOLO（OpenCV DNN）、SIFT、截图 / 悬浮窗、打包页出包、象棋插件加载。
3. 发布：`tools/publish.ps1` 前置校验加上 P0 的 16 KB 门；正式发一版并验证手机自更新链路。

**影响面**：发布脚本、更新源产物、`.artifacts/publish-*.log` 记录格式；无代码风险。

## 7. 风险与回退

| # | 风险 | 触发概率 | 影响 | 缓解 / 回退 |
| --- | --- | --- | --- | --- |
| R1 | **3.47.7 的 libflutter.so RELRO 末尾仍非 16 KB**（实测 12288；上游 #193545 open、PR #193930 未合） | 100%（已实测） | 若系统 / Play 把 RELRO 纳入硬判定，则"完全合规"无法达成 | 以 LOAD 为硬门、RELRO 记为已知偏差；跟踪 PR，等 3.48+ |
| R2 | **弹窗逐库口径不明**：18 个已对齐库也显示"未知错误" | 高 | 修完 libflutter 后弹窗可能仍出现（但不再有 LOAD 条目），"弹窗消失"这一验收项可能不达成 | P1 出口用干净安装复测并截图留证；验收拆成"无 LOAD 条目"（硬）+ "无弹窗"（目标）；必要时向 ROM / Google 反馈 |
| R3 | **embedding 依赖冲突**：仓库 `force` 了 fragment 1.6.2 / annotation 1.7.1，新 embedding 要 1.7.1 / 1.8.1 | 高 | 运行时 `NoSuchMethodError` / `ClassNotFoundException`，且只在跑到 Flutter 页面时炸 | 放开 / 上调 force；用 `gradlew :app:dependencies` 核对；先在 `-PflutterPoc=true` 的 debug 变体验证（不影响发布包） |
| R4 | **Impeller 默认渲染器变化**（3.47 安卓默认 Impeller / Vulkan） | 中 | 玻璃折射 / 模糊效果偏差、首帧慢、低端机回退 | 保留 `EnableImpeller=false` 逃生开关；对比截图；必要时锁 OpenGL |
| R5 | **compileSdk 35 → 36**（platform 36 未安装）与 AGP 版本联动 | 中 | 构建直接失败 | 先装 platform 36；AGP 保持 8.6.1 试，失败再升 8.7.x（Gradle 8.9 可满足 AGP 8.7） |
| R6 | **debug 包体积暴涨**：Maven 的 libflutter.so 未 strip（165 MB） | 高（若不处理） | 253 MB → 400 MB+，装机 / 发布链路变慢 | payload 生成阶段用 `llvm-strip`（NDK 自带）；把 strip 后尺寸写进 `payload-report.json` |
| R7 | **release 包无弹窗兜底**：release 在 16 KB 设备上不弹窗，直接走兼容模式或加载失败 | 中 | 用户侧"静默不可用" | P4 必须在 16 KB 模拟器上跑 **release** 构建，而不只是 debug |
| R8 | **AOT 管线脆弱**：`build-aot.ps1` 依赖外部工程目录 `AutoJsPro-*`、`--offline` pub get、`C:\Python314` 硬编码 | 中 | 换机器 / 换 SDK 后脚本直接失败 | 本阶段顺手参数化（`-FlutterSdk` / `-SourceProject` / `-Python`），结果写进 `payload-report.json` |
| R9 | **包体 16 KB 对齐填充** | 低 | +1~2% | 记录即可 |

**回退方案（三层，按代价从小到大）**

1. **构建开关级**：POC 全部挂在 `-PflutterPoc=true` 下，不带该参数即回到无 Flutter 的构建；发布包默认不带（`apps/app/build.gradle` 的 `if (flutterPocEnabled)`）。→ 出问题直接不带参数构建。
2. **payload 级**：P0 已归档 `payload-3.3.4-baseline/`；把 `flutterPocPayload` 指回基线目录 + 旧 jar 依赖，即可在 5 分钟内回到 3.3.4 引擎（可继续验证业务，只是 16 KB 未解决）。
3. **分支级**：整条升级在独立分支 `feature/16kb-flutter`，P1–P2 的提交按阶段拆（引擎切换 / 依赖调整 / native 链接参数 / compileSdk），任一阶段失败可单独 revert，不牵扯业务代码。

## 8. 验收标准（可直接当 DoD 用）

### 8.1 静态（机器判定，进发布门禁）

- [ ] APK 内 **所有** `lib/arm64-v8a/*.so`：**每个 PT_LOAD 的 `p_align` ≥ 0x4000**（当前只有 `libflutter.so` 不满足）。
- [ ] APK 内所有未压缩 `.so` 的 **zip data offset % 16384 == 0**（当前 19/19 已满足，防回归）。
- [ ] （推荐项）自有库 `libquickjs.so` / `libquickjs_jni.so` / `libppocr.so` / `libaijscrypto.so` 的 **RELRO 末尾 % 16384 == 0**。
- [ ] `libflutter.so` 的 engine hash 与 embedding jar 的 hash **一致**（写进 `payload-report.json`）。
- [ ] `tools/check-16kb.*` 在 `tools/publish.ps1` 前置校验里返回 0。

### 8.2 设备（人判）

- [ ] **K40（Android 16 / 4 KB）**：清数据后冷启动 `SplashActivity`，兼容性弹窗中**不再出现任何 "LOAD 区段未对齐" 条目**；目标（非硬门）是完全不弹窗。
- [ ] **16 KB 模拟器（Android 15/16，16 KB 页镜像）**：安装 + 启动 + 玻璃首页渲染 + 3 条桥（bootstrap / list / theme）全部正常，无 `dlopen` 失败、无 SIGSEGV。
- [ ] **小米 8（Android 10）**：Miuix 主界面、抽屉、示例运行无回归。
- [ ] **release 构建**在 16 KB 模拟器上同样可启动（验证 R7）。

### 8.3 功能冒烟（现有示例矩阵）

- [ ] Rhino / QuickJS / Node 三棵示例各抽 3 个可运行。
- [ ] OCR：ML Kit 路径 + PP-OCR 路径各 1 次（`libmlkit_google_ocr_pipeline` / `libppocr` 都被 dlopen）。
- [ ] OpenCV 路径：YOLO(DNN) 1 次 + SIFT 1 次（覆盖 `libopencv_dnn` / `features` / `flann` / `geometry`）。
- [ ] 打包页出 1 个 APK；象棋插件加载 1 次（覆盖 `libpikafish`）。
- [ ] 截图 / 悬浮窗 / 任务列表等 Miuix 老路径不回退。

### 8.4 发布流程

- [ ] `tools/publish.ps1 -DryRun` 通过（版本号计算、校验链）。
- [ ] 正式发一版，手机自更新链路验证（历史要求：发布后校验 versionCode、SHA-256、手机端 curl 清单）。
- [ ] `docs/reports/` 补一份"升级完成"验收记录，并把本文件的结论表更新为"已达成"。

```powershell
$re = "C:\Android\ndk-r26d\toolchains\llvm\prebuilt\windows-x86_64\bin\llvm-readelf.exe"
& $re --program-headers libflutter.so | Select-String "LOAD|GNU_RELRO"

# 2) APK 内所有 arm64 库（解包后逐个跑；目录 .artifacts/16kb-eval/apk-libs/*.so）
Get-ChildItem .artifacts/16kb-eval/apk-libs -Filter *.so | ForEach-Object {
  $lines = & $re --program-headers $_.FullName
  $loads = $lines | Where-Object { $_ -match '^\s+LOAD\s' } | ForEach-Object { ($_.Trim() -split '\s+')[-1] }
  "{0}  {1}" -f $_.Name, ($loads -join ",")
}

# 3) zip 内 data offset 是否 16 KB 对齐（Python）
python .artifacts/16kb-eval/zipalign2.py apps/app/build/outputs/apk/miuixCompat/debug/app-miuix-compat-arm64-v8a-debug.apk
```
