### 已识别的结构性问题（不是「文件大」那么简单）
1. **God class**：`QuickJsHostBridge`（9,173 行）单类覆盖十几种关注点 ✗ —— 它的方法名被 JS 侧按名调用（`Java.type('…QuickJsHostBridge')`）⇒ **类名必须保留** ⇒ 可行做法是**抽出静态 helper 类**、原类只留薄转发 ✓；
2. **多套 UI 栈并存**：`src/miuix`（Kotlin/XML）+ `flutter-ui`（Flutter）✗ —— 这是**产品决策**层面的成本（不是 bug）⇒ 只在「新功能只往一边加」这类纪律上收敛 ✓；
3. **多源集**：`src/main` / `src/miuix` / `src/flutterpoc` / `src/inrt` / `modules/*` ⇒ 同名的类散在不同源集（本轮队友已两次因此定位错文件 ✗）⇒ 需要**索引文档**或命名前缀纪律 ✓；
4. **重复实现漂移**：已由 W3 专项列出 15 条 ✓（其中「插件包名 8+ 副本」✗ 已建议加钉子 ✓）；
5. **可观测性债**：本轮已补 24 处静默失败日志 ✓、`printStackTrace` 还剩 `apps/app` 51 处 / `modules/common` 4 处 ✓。

## 二、流程（按用户口径：**一个修改 / 一个审查 / 一个验证 / 审完验完再统一改**）

```
Phase 0  体检基线（Lead，本文档）                          ← 已完成
Phase 1  只读调研：每个子系统产出一份「编号优化建议」        ← 本轮派发
         每条必须给：目标 / 证据(指标或 file:line) / 影响面 / 风险 / 预估 / 建议验证方式
Phase 2  Lead 汇总成总清单 + 排优先级 → 交用户拍板
Phase 3  逐条执行，**三角色分离**：
         作者(author) 写 → 审查(reviewer, 另一人, 只读 diff) → 验证(verifier, 另一人或 Lead: 编译+单测+真机)
         · 同一文件**同时只有一个写者** ✓
         · 审查不通过 ⇒ 退回作者，**不进验证** ✓
         · 验证不通过 ⇒ 退回作者 + 审查记录 ✓
Phase 4  本批全部通过后**统一提交**（不与未验证改动混在一起）✓
```

### 硬约束（避免「重构反而引入事故」）
- **不做大爆炸重写** ✗：每批 ≤ 3 个条目、每条独立可回退 ✓；
- **行为不变优先**：纯搬移/改名/抽 helper 类 ⇒ 必须**逐字节等价**或由测试钉住 ✓（本项目的血泪：模板截断、桥名单漂移、BOM 丢失都是「看起来无害的编辑」✗）；
- **改完必须跑**：`:engine:testDebugUnitTest` / `:app` 编译 / `flutter test` / 相关真机验收 ✓（**编译通过只是及格线** ✓ —— 本轮 W2 的三次迭代正说明这一点 ✓）；
- **`.ps1` 改动后必须核 BOM + 解析 0 错** ✓（已有门禁 `check-ps1-encoding` ✓）；
- **不删 `.artifacts/updates/**`、不删 `src/test/**`** ✓（目录规范红线 ✓）。
