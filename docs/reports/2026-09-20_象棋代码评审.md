# 象棋自动走棋代码评审

评审日期：2026-09-20  
评审范围：象棋项目生产入口、新视觉流水线、OCR/颜色融合、棋盘校验与相关测试  
基础验证：全部JavaScript文件通过`node --check`；`SELF_CHECK OK passed=176 failed=0`

## 结论

代码目前可以通过现有自检，但新视觉流水线仍存在会影响真机运行的逻辑缺陷。最严重的问题是悬浮窗把所有正常空棋位也统计成未知格，导致新流水线在正常棋盘上几乎必然被稳定帧安全门拒绝，然后回退旧识别路径。这与真机日志中出现的“未知格44/45”“不断RECOVERING”一致。

本轮共发现2个高优先级问题、4个中优先级问题和3个结构/测试问题。建议先修复P0和P1，再继续调模型阈值或点击方式。

## P0：正常空棋位被统计为未知格，新流水线几乎必然被拒绝

位置：`悬浮窗运行与测试.js:2070`

当前代码：

```js
const unknownCells = chars
    ? chars.filter(function (ch) { return !ch || ch === "?"; }).length
    : 90;
```

`evidence-fusion.js`使用`null`表示正常空棋位，使用`?`表示存在检测证据但尚未确认的棋子格。上述代码把两者一起统计，因此一盘有30枚棋子时，约60个正常空位也会被算作未知格。

随后代码调用：

```js
boardFrameGate.acceptResult(unknownCells)
```

闸门阈值是未知格大于6就拒绝，所以新流水线即使识别完全正确，也会被判定失败。

影响：

- 新视觉流水线无法稳定进入自动走棋；
- 日志出现未知格44、45或更高；
- 状态机反复进入`RECOVERING`；
- 系统不断回退旧`recognizer.js`路径；
- 调整YOLO、OCR或颜色阈值无法解决该问题。

建议修复：

```js
const unknownCells = result.fusion
    ? Number(result.fusion.unknown || 0)
    : chars.filter(function (ch) { return ch === "?"; }).length;
```

必须增加测试：包含30枚棋子、60个空位、0个`?`的盘面，未知格必须为0。

## P0：新YOLO检测入口实际执行了整套旧识别流程

位置：`悬浮窗运行与测试.js:1955`

新视觉流水线的`host.detect()`当前调用：

```js
recognizeBoard.recognizeScreen({ ... })
```

然后只从返回值中提取：

```js
recognized.native.list
```

`recognizeScreen()`并不是纯检测接口，它还会执行旧棋盘识别、阵营采样、FEN生成以及模型加载/释放逻辑。结果是新流水线每一帧先完整跑一次旧流水线，再拿旧流水线的原始框继续跑OCR、颜色和融合。

影响：

- 新旧视觉架构并未真正分离；
- 每帧重复进行无用计算；
- 旧识别异常会连带让新流水线拿不到检测框；
- 模型可能被重复加载；
- 真机耗时和资源占用明显增加；
- 无法独立验证新流水线。

建议修复：

由`board-service`或专门的`detector-service`长期持有检测器，直接调用：

```js
adapter.detect(detector, image, options)
```

生产链路不应通过`tools/recognize-board.js`获取YOLO原始框。

## P1：棋盘校验器把未知格数量计算了两次

位置：`src/vision/board-validator.js:83`

当前代码：

```js
const red = countSide(board, "w");
const black = countSide(board, "b");
const unknown = red.unknown + black.unknown;
```

`countSide()`无论检查红方还是黑方，都会遍历整盘并统计所有`?`。因此同一个未知格会分别进入`red.unknown`和`black.unknown`，最后被加两次。

影响：

- 日志中的未知数量翻倍；
- `allowUnknown:false`时错误原因不准确；
- 上层若依据`validation.stats.unknown`做阈值判断，会提前拒绝正常结果。

建议修复：

未知格应单独遍历一次：

```js
const unknown = board.filter(function (ch) { return ch === "?"; }).length;
```

`countSide()`不应返回全盘未知格，或只由一个公共统计函数返回。

## P1：证据融合配置没有真正生效

位置：

- `src/vision/evidence-fusion.js:47`
- `src/vision/evidence-fusion.js:51`
- `src/vision/evidence-fusion.js:56`
- `src/vision/evidence-fusion.js:77`

`createFuser(options)`合并了自定义配置，但`pieceOf()`内部调用`finalScore()`时没有传入配置，并且使用固定的`DEFAULTS.minFinalScore`：

```js
const score = finalScore({ ... });
const ok = score >= DEFAULTS.minFinalScore;
```

因此以下配置实际无效：

- `minFinalScore`
- `weightDetect`
- `weightOcr`
- `weightColor`

只有`frames`在`createFuser()`内部真正被使用。

影响：

- 调试时修改融合阈值没有效果；
- 不同皮肤或模型无法调整证据权重；
- 日志看似使用了配置，实际仍使用默认值。

建议修复：

```js
function pieceOf(entry, options) {
    const opts = Object.assign({}, DEFAULTS, options || {});
    const score = finalScore({...}, opts);
    const ok = score >= opts.minFinalScore;
}
```

`createFuser()`调用`pieceOf(one, opts)`。

## P1：规则补全后的`board`与返回的`chars`不一致

位置：

- `src/vision/vision-pipeline.js:436`
- `src/vision/vision-pipeline.js:461`

代码先复制融合结果：

```js
const board = fused.chars.slice();
```

随后`inferKings()`可能在`board`中补全帅/将。但是返回值同时包含：

```js
board: board,
chars: fused.chars
```

这两个字段可能不同。悬浮窗当前优先取`board`，其他调用者可能读取`chars`，从而得到没有补全帅/将的旧结果。

影响：

- 不同入口对同一帧输出不同局面；
- 校验通过的`board`与日志/绘制所用`chars`可能不一致；
- 旧兼容接口可能再次报告缺少帅/将。

建议修复：

确定唯一权威字段。推荐：

```js
chars: board,
rawChars: fused.chars
```

所有生产代码只读取`chars`。

## P1：检测框在排序前被截断

位置：`src/vision/piece-detector.js:113-115`

当前顺序：

```js
if (boxes.length > opts.maxDetections) {
    boxes = boxes.slice(0, opts.maxDetections);
}
boxes.sort(function (a, b) { return b.score - a.score; });
```

如果原生检测器返回超过40个框且未按置信度排序，高分框可能先被截掉。

建议改为：

```js
boxes.sort(function (a, b) { return b.score - a.score; });
if (boxes.length > opts.maxDetections) {
    boxes = boxes.slice(0, opts.maxDetections);
}
```

## P2：`ocr-runtime.js`没有进入生产流水线

项目已经新增统一OCR运行时，但`vision-pipeline.js`仍直接调用`h.ocrSession.detect()`，悬浮窗也直接创建并传入会话。

影响：

- OCR阈值、错误处理和资源释放存在两套实现；
- `ocr-runtime.js`通过自检并不代表生产代码使用了它；
- 后续ONNX OCR与PP-OCR切换仍要修改业务代码。

建议：`vision-pipeline.js`只依赖统一接口：

```js
ocrRuntime.recognizeGlyph(image, region)
```

会话创建、后端选择和释放全部留在`ocr-runtime.js`。

## P2：应用层和服务层尚未成为生产入口

`src/app/bootstrap.js`、`controller.js`、`board-service.js`结构已经建立，但主界面和悬浮窗仍直接访问`tools/recognize-board.js`、视觉模块和自动化驱动。

影响：

- 同一业务逻辑在多个入口重复；
- 修复容易只作用于某一个入口；
- 测试中的应用层与真机实际调用链不一致。

建议所有入口统一为：

```text
UI → controller → board-service → vision-pipeline
```

## P2：现有自检没有覆盖关键生产组合

现有176项自检全部通过，但仍未发现上述问题，说明测试覆盖更偏向单模块契约，缺少生产组合测试。

至少补充以下测试：

1. 60个正常空位不能算未知格；
2. 一个`?`在校验器中只能统计一次；
3. 自定义融合阈值与权重必须改变输出；
4. `inferKings()`后`board`与公开`chars`一致；
5. 45个无序检测框必须保留置信度最高的40个；
6. 新流水线的检测阶段不得执行旧`recognizer.js`；
7. 主界面、悬浮窗、回放工具对同一输入输出完全一致；
8. 检测器和OCR会话在连续帧之间只创建一次。

## 建议整改顺序

第一批，立即修复：

1. 空位误算未知格；
2. 未知格双倍计数；
3. 检测器直接接口，移除新流水线对旧识别流程的依赖。

第二批，统一数据契约：

1. 修复融合参数传递；
2. 统一`board/chars/rawChars`；
3. 修复检测框排序与截断顺序；
4. 统一OCR运行时。

第三批，结构收口：

1. 让`board-service`成为唯一识别入口；
2. 主界面与悬浮窗改用控制器；
3. 将旧`recognizer.js`降级为兼容代理；
4. 整理历史探针与工具目录。
