## 0. 结论摘要

1. **独立 APK 里的 engine dex 与 assets/modules/*.js 来自 template.apk 的预置副本，不是当前安装的 AI.js Pro 动态复制/合并的。**
   - 宿主 app 只在打包时补两类东西：瘦身模板缺少的 lib/arm64-v8a/*.so（来自宿主 APK），以及 Node 工程的 assets/node24/**、assets/source-engine-upgrade/node24/arm64-v8a/**（来自宿主 APK）。
   - 引擎 classes*.dex 与 assets/modules 下的 __ui__.js/__console__.js/__plugins__.js 等没有从宿主复制。
2. 打包器实际选择哪份 template.apk 取决于设备上的来源优先级（见 §2）；当前 K40 还有一份最高优先级的 /sdcard/template.apk（79,098,976B，2026-10-18），会覆盖仓库里的两份模板。
3. 仓库里两份模板都**不是当前版**：
   - apps/app/src/main/assets/template.apk（20,418,813B，2026-11-03）：引擎 dex 缺 dev-1380 的 AijsNativeJavaClass；7 个 assets/modules 文件与仓库不同。
   - plugins/apkbuilder-plugin/src/main/assets/template.apk（88,424,956B，2026-11-06）：引擎 dex 同样缺 AijsNativeJavaClass；2 个 assets/modules 文件不同。
   - K40 的 /sdcard/template.apk（79,098,976B，2026-10-18）更老，__ui__.js 只有 20,651B（当前是 79,231B）。
4. 当前装上的 dev-1382 主 APK 里 assets/template.apk 仍是旧模板：raw=20,418,813，sha256=08838a9d83b89ed8d183305c418c1f13be6ff57879117c7592f31070ffb4b434，与仓库文件完全相同。
5. **用户要彻底修好这个 bug：必须重新打包；升级 app 不会让旧独立 APK 自动变好。** 而且必须先重建模板（并处理 /sdcard/template.apk 覆盖），否则新打包出来的 APK 仍会带旧 engine dex；只升级 app 或只重新打包用户工程都不够。

## 1. 证据：打包时模板怎么进入独立 APK

### 1.1 打包入口先把模板整包解压到工作区

- ApkBuilder 构造函数接收模板 InputStream/File，并创建 ApkPackager：
  - apps/app/src/main/java/com/jdkshen/aijspro/autojs/build/ApkBuilder.java:137-145
- build() 调用 mApkPackager.unzip()：
  - ApkBuilder.java:406
- ApkPackager.unzip 是 wholesale 解压所有非目录 entry 到工作区，没有按来源替换：
  - third-party/ApkBuilder/apkbuilder/src/main/java/com/stardust/autojs/apkbuilder/ApkPackager.java:51-65

所以工作区里的 classes*.dex、assets/modules/*.js 默认就来自模板；后续打包只会覆盖项目文件、manifest、res/图标、lib 子集等。

### 1.2 宿主来源只有两类补充

- lib 补充：ApkBuilder.ensureTemplateLibs（ApkBuilder.java:183-255）从宿主 APK 的 lib/arm64-v8a 补瘦身模板缺的 so；清单来自模板/宿主 assets 的 excluded-zip-files.json（:157-172）。
- Node 运行时补充：ApkBuilder 在 Node 工程路径调用 Node24PackagingAssets.copyFromHost（ApkBuilder.java:588-602）；它只复制：
  - assets/node24/**
  - assets/source-engine-upgrade/node24/arm64-v8a/**
  - 见 Node24PackagingAssets.java:14-19,46-77
- 没有代码从宿主复制 classes*.dex 或 assets/modules/*.js 到工作区。搜索 ApkBuilder.java 的 assets/modules/classes 引用为空；Node24PackagingAssets 的 MODULES 只指向 assets/node24。

结论：用户这个 Rhino 打包包里的 engine dex 和 __ui__.js 来自模板；宿主 app 升级只会更新宿主自己的 classes/assets，不会改写已经生成或正在生成的包里的这些文件。

## 2. 实际选中的是哪份模板（代码优先级）

ApkBuilderPluginHelper.openTemplateApk 的顺序（apps/app/src/main/java/com/jdkshen/aijspro/build/ApkBuilderPluginHelper.java:74-103）：

1. /sdcard/template.apk（manualTemplateFile，第 75-79 行）— 手动覆盖，优先级最高。
2. 宿主 assets/template.apk + 宿主 lib 合并（mergedBundledTemplate，第 81-86 行；实现 :189-245）— 这是当前主 APK 自带的瘦身模板。
3. 宿主私有缓存 files/apk-builder/<hostVersionCode>/template.apk（cachedTemplateFile，第 87-90 行）。
4. 已安装打包插件 com.jdkshen.apkbuilder.plugin 的 ensureTemplate（第 91-94 行；实现 :296-331）。
5. 宿主 assets/template.apk 流式兜底（第 95-101 行）。

**重要现场风险**：K40 上这份 /sdcard/template.apk 是最高优先级；若今天在 K40 上直接打包，会选它，而不是仓库里的 20.4MB 模板。它日期是 2026-10-18，__ui__.js 只有 20,651B，明显是更老的模板。

用户报告的崩溃行是 __ui__.js:408 的 view.getClass().getName()；这个调用在 79,231B 的 __ui__.js 中（见 §4），不在 20,651B 的旧 manual 模板中。因此用户实际打包很可能用的是 host/plugin 模板（或手工模板是在那次打包之后才放入的，或在另一台设备上打的）。要复现/修复必须明确实际来源；修复动作应把 manual 覆盖也处理掉。

## 6. 回答用户问题

### 6.1 包里的 engine dex/JS 来自哪里？

- 对 Rhino 打包包：**来自 template.apk 的预置 classes*.dex + assets/modules/*.js**，不是当前安装 app 的 dex/JS；
- 若用的是宿主瘦身模板：lib/arm64-v8a 由宿主 APK 补齐（这一部分是混合），但 engine dex 与 modules 仍来自模板；
- 若用的是插件/全量模板：所有 engine 内容都来自模板；
- 若用户工程是 Node 工程：assets/node24/** 与 Node runtime 由宿主 APK 覆盖，这属于 (a)/(c) 的 Node 特例，不影响本 bug 的 Rhino __ui__.js/engine dex；
- 不存在“从当前 app 动态复制 classes*.dex/assets/modules 到打包产物”的路径。

### 6.2 模板什么时候重建？

- 插件模板：:inrt:buildApkPlugin（apps/inrt/build.gradle:74-103），输出 plugins/apkbuilder-plugin/src/main/assets/template.apk + template-manifest.json；assembleRelease 或插件 mergeAssets 可触发。
- 宿主瘦身模板：tools/build-slim-template.ps1（输出 apps/app/src/main/assets/template.apk + excluded-zip-files.json），不是 Gradle 自动任务。
- 全量 inrt APK 中间产物：apps/inrt/build/outputs/apk/release/inrt-arm64-v8a-release-unsigned.apk。

### 6.3 模板是否过期？

- host 模板：不是当前版（7 个 modules 不同；engine dex 缺 dev-1380；落后 4 个 modules 提交）。
- plugin 模板：不是当前版（2 个 modules 不同；engine dex 缺 dev-1380；落后 1 个 modules 提交）。
- K40 manual 模板：最老（2026-10-18，__ui__.js 20KB），绝对不能用于当前修复验证。

### 6.4 要不要重新打包？

**要重新打包；升级 app 不会自动修旧包。** 理由：

1. 独立 APK 的 classes*.dex 与 assets/modules 是从模板整包解压进去的，安装/升级宿主 app 不会修改已生成的独立 APK；
2. 当前装上的 dev-1382 主 APK 自带模板仍是旧 hash（20,418,813 / 08838a9d...），所以即使“用当前 app 打包”，只要走宿主 slim 模板，仍复制旧 engine；
3. 仓库里 host/plugin 模板都缺 dev-1380 的 AijsNativeJavaClass，必须先从修复后的 :inrt 源码重建模板；
4. K40 上 /sdcard/template.apk 优先级最高且更老，必须删除或替换，否则会覆盖新模板；
5. 修复顺序应为：修引擎（已完成）→ 重建 :inrt 模板（宿主 slim + 插件按需）→ 更新/移除 manual 模板 → 重新打包用户工程 → 再验证 view.getClass().getName() 与旧用户路径。

仅升级 app 并重新打包但如果模板不重建：还是会坏；仅升级 app 不重新打包：旧包永远坏。
