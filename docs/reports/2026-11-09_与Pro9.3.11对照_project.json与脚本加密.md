# 与 AutoJs Pro 9.3.11 脱壳源码的两处逐字段对照：`project.json` 与脚本加密链

> 输入：`.artifacts/AutoJsPro源码树-2026-11-09/源码树/`（Pro 侧）；`modules/`、`apps/`（我们侧）。
> 方法：**两边都把 JSON 键/类型从源码里抠出来逐条比**，Pro 侧键名取自 JADX 反编译保留的 `@SerializedName`（混淆成 `@xk4("…")`）。
> 结论都标注了「代码推导」与「未做端到端验证」的边界。

## 一、`project.json` 字段对照

### 1.1 顶层键

**Pro 9.3.11（21）**：`abis` `androidResources` `assets` `build` `encryptLevel` `features` `icon` `launchConfig` `main` `name` `optimization` `packageName` `permissionConfig` `plugins` `publish` `scripts` `signingConfig` `type` `useFeatures` `versionCode` `versionName`

**我们（`modules/engine/.../project/ProjectConfig.java`，22 个字段）**：`name` `versionName` `versionCode` `packageName` `main` `assets` `launchConfig` `build` `icon` `scripts` `useFeatures` `engine` `type` `androidResources` `permissionConfig` `encryptLevel` `scriptStorage` `scriptSalt` `signatureFingerprint`

| 类别 | 键 | 说明 |
|---|---|---|
| **共有（15）** | name, versionName, versionCode, packageName, main, assets, launchConfig, build, icon, scripts, useFeatures, type, androidResources, permissionConfig, encryptLevel | 形状基本一致 |
| **Pro 有、我们 Java 模型没有（6）** | `abis` `features` `optimization` `plugins` `publish` `signingConfig` | ⚠️ **但我们的 Flutter 打包页在读写它们**：`flutter-ui/lib/project_page.dart:146/157/163/166/268/296/327` 处理 `encryptLevel`/`signingConfig`/`permissionConfig.requestListOnStartup`/`launchConfig.displaySplash` —— 即**同一产品里 Dart 与 Java 是两套字段视图** |
| **我们独有（6）** | `engine` `scriptStorage` `scriptSalt` `signatureFingerprint` `androidResources.*` `permissionConfig.*` 的扩展 | 前 4 个是我们的脚本保护/引擎选择扩展；后两个是**嵌套类**（与 Pro 形状一致，已核对 `ProjectConfig.AndroidResources`/`PermissionConfig`） |

### 1.2 同名但**语义/类型不同**（这才是真正的不兼容）

| 键 | Pro | 我们 | 后果 |
|---|---|---|---|
| **`scripts`** | `Map<String,String>`：**构建钩子**（Pro 常量里有 8 个名字：`build-apk-pre/build/prepare/package/optimize/post-*`；样例 `"build-apk-pre-prepare": "sh build.sh"`） | `Map<String,ScriptConfig>`：**以脚本路径为键的运行配置** `{useFeatures,uiMode,engine}`（`ProjectLauncher` 用它 `setScriptConfig`） | 读 Pro 工程时 Gson 会因 `Expected BEGIN_OBJECT but was STRING` 抛 `JsonSyntaxException`；`fromFile/fromAssets` **catch(Exception) → 返回 null** → **整个工程被判无效**（不是崩溃，是静默失败） |
| **`launchConfig.displaySplash`** | Pro 的键 | Java 侧用 **`showSplash`**（`MiuixBuildActivity.kt`），Dart 侧用 `displaySplash`（`project_page.dart:327`） | 一方写的启动图开关另一方读不到 |
| `launchConfig` 其余 | `splashIcon` `splashLayoutXml` `stableMode` | 我们只有 `hideLogs` `splashText`，另有 `logBridge` `requestPermissions` | 丢字段 |
| `permissionConfig.requestListOnStartup` | 有 | Java 模型没有（Dart 有） | 丢字段 |
| **`encryptLevel` 取值域** | `0` 无 / `1` offline / `2` offline-dex / `3` offline-snapshot / `100` online | `0` 无 / `1` AES+CBC+8 字节头 / `2` 编译再加密（`ScriptProtection.MAX_LEVEL=2`），UI 档位另有 3=加密 so / 4=快照 so | **同值不同义**（Pro 的 1 是「离线加密」、我们的 1 也是加密，但 2/3/100 语义分叉）→ 跨包迁移会误解保护等级 |
| `build` | `build_id` `build_number` `build_time` | 同 3 键 ✓ | 一致 |

### 1.3 可操作结论（①）

1. 若要**读 Pro 工程**：至少要把 `scripts` 做成「**先按 String 试、再按对象试**」的容错解析（或分成 `scripts`（钩子）与 `scriptConfigs`（运行配置）两个字段），否则 Pro 工程在我们这边直接 `null`。
2. `launchConfig` 需要**同时认 `displaySplash` 与 `showSplash`**（写哪一个也统一），并把 `splashIcon`/`splashLayoutXml`/`stableMode`/`requestListOnStartup` 补进 Java 模型（Dart 已经在管这些键）。
3. `abis`/`features`/`optimization`/`plugins`/`publish`/`signingConfig` 要么补进 Java 模型（至少「读进来不丢、原样写回」），要么明确记录「仅打包页使用、运行端忽略」。
4. `encryptLevel` 建议把 Pro 的 0/1/2/3/100 映射表写进 `ScriptProtection` 的注释与校验（现在是 0/1/2 + UI 3/4，语义没对齐）。

## 二、脚本加密链对照（`ScriptEncryption`）

### 2.1 Pro 9.3.11 的做法（`engine/encryption/ScriptEncryption.java`，159 行）

```
key0 = MD5(packageName + versionName + mainScriptFile + versionCode)     // 32 个 hex 字符 → 当 ASCII 字节用 → AES-256 密钥
iv   = MD5(buildId + name).substring(0, 16)                              // 16 个 ASCII 字符
mKey = AES/CBC/PKCS7Padding(key = key0.getBytes(), iv = iv.getBytes())
        .encrypt("seBmfdYSRu2ysWEl")                                     // 硬编码 16 字节常量 → 输出 16 字节
脚本 = AES/CBC/PKCS7Padding(key = mKey /* 16 字节 → AES-128 */, iv = iv.getBytes())
```

- `initFingerprint(config)` 里还有一条**自校验**：用 `mKey`/`mInitVector` 对常量跑一次 AES（反编译尾部截断，但形态是「加密常量来验证派生是否成功」）。
- 没有文件头、没有 HMAC、没有完整性校验 —— 密文就是裸的 CBC 输出。

### 2.2 我们的做法

- `engine/encryption/ScriptEncryption.kt`（**14 行**）：只做解密，委托 `AdvancedEncryptionStandard(mKey.toByteArray(), mInitVector)`；算法 **AES/CBC/PKCS5Padding**（16 字节块下与 PKCS7 等价）。
- `project/ScriptKeyDerivation.java`（92 行）：
  - **新方案**：`key = SHA-256("aijspro-script-key|" + packageName + "|" + saltHex + "|" + certFingerprint)` 取前 32 个 hex → AES-256；`iv = SHA-256("aijspro-script-vec|" + saltHex + "|" + certFingerprint)` 取前 16 hex；盐 16 字节随机、写进 `project.json` 的 `scriptSalt`；`signatureFingerprint` 把密钥绑到签名身份（换证书重签就解不开）。
  - **旧方案（兼容老产物）**：`legacyKey = MD5(packageName + versionName + mainScriptFile)`、`legacyVector = MD5(buildId + name).substring(0,16)`。
- 我们**多出来**的（Pro 没有）：`EncryptedScriptFileHeader`（8 字节文件头）、`scripts.pack`（非入口脚本整体加密的容器）、`NativeScriptCrypto` + `libaijscrypto.so`（密文嵌进原生库）。

### 2.3 逐项差异 → 兼容性缺口

| # | 差异 | 影响 |
|---|---|---|
| 1 | **我们的 `legacyKey` 少了 `versionCode`**：Pro 是 `MD5(pkg + versionName + main + versionCode)`，我们是 `MD5(pkg + versionName + main)` | 对 Pro 产物必然派生出不同的 `key0` |
| 2 | **缺 Pro 的「常量再加密」一步**：Pro 最终 AES 密钥 = `AES(key0, iv).encrypt("seBmfdYSRu2ysWEl")`（16B → **AES-128**）；我们直接拿 `MD5` 的 32 个 ASCII 字符当 **AES-256** 密钥。**在我们的仓库里搜 `seBmfdYSRu2ysWEl` = 0 命中** | 即使 key0 对了，最终密钥也不同 |
| 3 | padding 名不同（`PKCS7Padding` vs `PKCS5Padding`） | **等价**（16 字节块），不构成缺口 |
| 4 | 我们多了 8 字节文件头 / `scripts.pack` 容器 / 原生库存储 | **格式层不兼容**：Pro 的密文没有文件头，我们解不带头的裸密文需要专门容忍 |

**结论（②，代码推导，未做端到端验证）**：**我们解不开 Pro 9.3.11 加密的脚本，Pro 也读不了我们的**。差异最小集合是两条：① `versionCode` 进 `key0`；② 常量再加密那一步 + AES-128。

**要兼容的最小改动**（若决定做）：在 `ScriptKeyDerivation` 加一条 **Pro 兼容派生**（`key0 = MD5(pkg+versionName+main+versionCode)` → `mKey = AES-CBC(key0, iv).encrypt("seBmfdYSRu2ysWEl")`、`iv = MD5(buildId+name).substring(0,16)`），并在解密入口按「有无 8 字节文件头」区分我们的新格式与 Pro 的裸密文。
**验证方式**（本轮没做）：拿一份 Pro 加密产物（`assets/project/main.js` 或 `scripts.pack`）在我们运行端解一次；或写一条 JVM 对拍：用 Pro 的派生算出 `mKey`，再用它解开我们自己造的密文。

### 2.4 边界与未验证

1. 本对照**只读源码**：Pro 侧是反编译产物（JADX，Dex2C 的 native 方法看不到），尾部 `initFingerprint` 的自校验段被截断；我们侧是当前工作树（`HEAD` 附近）。
2. 我们仓库源自 **Auto.js 开源线**，旧方案可能本来就是对齐开源版而不是 Pro；**「不兼容」是相对于 Pro 9.3.11 的事实陈述**，不等于缺陷。
3. 未跑任何端到端解密测试；§2.3 的结论是「按代码推导」。
