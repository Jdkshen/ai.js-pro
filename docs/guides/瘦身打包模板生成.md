# 瘦身打包模板生成（:inrt → 宿主内置 template.apk）

> 脚本：[tools/build-slim-template.ps1](../../tools/build-slim-template.ps1)
> 产物：apps/app/src/main/assets/template.apk + apps/app/src/main/assets/excluded-zip-files.json
> 校验：:app:verifySlimPackagingTemplate

## 1. 为什么需要瘦身模板

打包脚本 APK 时，主程序会以 :inrt 运行时 APK 为模板，替换脚本/工程资源后再签名。
如果直接把 :inrt 的完整 release APK 当模板，所有用户都要为 lib/*（约 54MB 未压缩）、
Node24 的 97MB libnode.so 和 6.5MB new_api_database.ser 付体积。

因此入库的是「瘦身模板」：

- 模板里不包含任何 lib/*；
- 模板里不含 assets/source-engine-upgrade/node24/arm64-v8a/libnode.so
  与 resources/new_api_database.ser；
- 打包时从已安装的宿主 APK 按 excluded-zip-files.json 的
  general/opencv/v8 清单补齐 lib/*；
- 插件目录 plugins/apkbuilder-plugin/src/main/assets/template.apk 的 70MB 旧模板
  不由本脚本生成/覆盖，单独发插件版本时才处理。

## 2. 生成步骤

`powershell
# 完整流程：:inrt:packageRelease → 去 lib/ → 写 assets/template.apk + excluded json → 自动校验
.\tools\build-slim-template.ps1

# 复用已有 inrt release APK（只重新切片/写清单）
.\tools\build-slim-template.ps1 -NoBuild

# 只调脚本时跳过 gradle 校验（不推荐）
.\tools\build-slim-template.ps1 -NoBuild -NoVerify
`

脚本内部使用 :inrt:packageRelease，不是 :inrt:assembleRelease；
后者会 finalizedBy buildApkPlugin，把新模板复制到插件目录。本脚本只写
apps/app/src/main/assets/，不会动插件模板。

生成物：

| 文件 | 说明 |
|---|---|
| apps/app/src/main/assets/template.apk | 无 lib/* 的瘦身模板（约 16–17MB，arm64-v8a） |
| apps/app/src/main/assets/excluded-zip-files.json | 本次剔除的全部 lib/*，分 general/opencv/v8 |

## 3. lib 匹配要求（关键）

1. 一一对应：inrt APK 中每个 lib/ entry 必须恰好出现在
   excluded-zip-files.json 的某个数组里，不能漏、不能多；
   脚本会按排序严格比对，不一致直接失败。
2. 分类规则：
   - opencv：libopencv_*.so 与 libtbb.so；
   - v8：libv8*.so / libnode*.so（当前为 0 个，保留字段兼容未来 Node/V8）；
   - general：其余 lib/*（crypto、c++_shared、MLKit OCR、pikafish、ppocr、quickjs 等）。
3. 宿主必须真的有这些 entry：打包时按清单从
   context.getPackageCodePath()（宿主已安装 APK）逐条补；任何一个不存在都会
   导致打包失败。因此模板和 excluded 清单必须与当前宿主 APK 的原生库集合同批生成。
4. 模板不能含 lib/：verifySlimPackagingTemplate 会硬失败；体积必须
   6–20MB（当前约 16.4MB）。
5. 不要手工编辑 excluded-zip-files.json：改 :inrt 依赖或宿主 ABI 后重新跑脚本。

## 4. 校验与排错

脚本最后自动执行：

`powershell
.\gradlew.bat :app:verifySlimPackagingTemplate --console=plain
`

校验内容：模板存在、6–20MB、无 lib/、含 AndroidManifest.xml / classes.dex / resources.arsc、
excluded 三字段齐全且 general/opencv 不同时为空、AXML 包名探测。

常见失败：

- 尺寸 >20MB：漏跳过了 libnode.so 或 new_api_database.ser（检查脚本里的
  excludedAssetNames 与本次 inrt 产物）。
- excluded 缺少 lib / 打包补全失败：宿主 APK 与模板不是同批构建；以当前
  :app:assembleMiuixCompatDebug 产物重新生成模板和清单。
- 模板仍含 lib/：不要用 assembleRelease 产物原地改名；必须走本脚本的过滤逻辑。

## 5. 真机冒烟（可选）

模板/清单生成后，可按打包链路做一次 K40 冒烟：

1. 构建并安装含新 assets 的宿主 APK；
2. 打包页选一个小工程，生成脚本 APK；
3. 安装生成 APK 并启动，确认脚本能运行、原生库/OpenCV/QuickJS 与模板匹配。

> 插件模板（70MB）不参与本流程；需要更新插件时单独用新 :inrt release 重建插件。
## 6. ⚠️ 设备侧到底用了哪个模板（优先级链 + 判据 + 本轮真机坑）

> **为什么单列一节**：本轮真机踩过一次「**在 PC 上重建了 `assets/template.apk`，但设备打的包行为完全没变**」——原因不在模板本身，而在**设备侧选模板的链**。
> **标注约定**：§6.1/§6.2 是**读码**（行号给在正文）；§6.3/§6.4 里的现象是**真机实测**（Lead，K40）。

### 6.1 实际选模板的顺序（读码：`ApkBuilderPluginHelper.openTemplateSelection()`，`apps/app/src/main/java/com/jdkshen/aijspro/build/ApkBuilderPluginHelper.java:96-140`）

| 优先级 | 来源 | 判据 |
|---|---|---|
| ① | `/sdcard/template.apk`（手动覆盖） | `isUsableTemplate`（存在 + 是文件 + **≥ 20 MiB**，`:368-369`） |
| ② | **宿主缓存** `files/apk-builder/<宿主 versionCode>/template.apk` | 同上（`:103-107`） |
| ③ | **内置瘦身模板 + 宿主 lib 合成**（`mergedBundledTemplate()`） | 合成结果**写回 ② 的同一个路径**（`:270-271`），再按 ② 判 |
| ④ | **插件模板**（`extractTemplateFromPlugin()` 反射调插件 `ensureTemplate(cacheDir)`） | 插件在位且落地产物可用；**也落在 ② 的同一个路径**，并写 `cacheVersionMarker = 插件版本`（`:377-407`，marker 在 `:405`） |
| ⑤ | 原始内置 `assets/template.apk` | 直接读资产（`:123-139`）；前三/四档都不成立才会走到 |

**⇒ 两个关键事实**：
1. **②③④ 共用同一个缓存文件**：谁先成功谁就「占坑」，之后**同一 versionCode** 会一直命中 ② ⇒ 只重建 PC 侧 `assets/template.apk`（对应 ③/⑤）**不一定生效**；
2. **缓存目录按宿主 versionCode 分目录**（`:268-269`）⇒ **升 versionCode 会自然换目录**、重新走 ③。

### 6.2 页面/日志里那条是「**状态**」，不是「**实际来源**」（读码：`templateStatus()`，同文件 `:184-209`）

- `templateStatus()` 的顺序是：① `/sdcard` → ② 宿存缓存 → **③ 装了插件就直接报「最后手段：插件模板（仅当内置模板损坏时才会用到）」**（`:196-198`）→ ④ 内置 assets。
- 它**没有「merged 内置」这一档** ⇒ **装了插件时，状态可能报「插件模板」，而实际选择会走 ③ 内置合成**（两者顺序不同）；反之插件卸载后状态落 ②，文案才会变成「宿主缓存（内置模板与宿主 lib 合成）」（`:193-194`）。
- **权威证据 = 缓存里的来源标记**（`cacheVersionMarker`）：文案「宿主缓存（**模板来源：<插件版本>**）」⇒ 这份缓存是**插件**产的；「宿主缓存（**内置模板与宿主 lib 合成**）」⇒ marker 为空，是**内置**产的。

### 6.3 一条判据（logcat；**实测**）

~~~text
# 装了插件时（K40 dev-1518 宿主）：
C-PKG: template available=true source=APK 打包插件 (1.0.0 (1)) detail=最后手段：插件模板（仅当内置模板损坏时才会用到） size=-1
# 卸载插件后重打（用上 dev-1520 内置模板）：
C-PKG: template available=true source=/data/user/0/com.jdkshen.aijspro/files/apk-builder/1520/template.apk detail=宿主缓存（内置模板与宿主 lib 合成） size=31332339
~~~

> ⚠️ **grep 注意**：logcat 会把 tag 渲染成 `C-PKG   :`（冒号前有空格）⇒ **搜正文**（`template available` / `apk-builder` / `template extracted from plugin`），**不要**搜 `C-PKG:`。
> 另外：`template extracted from plugin <版本> -> <路径>` 这条（`:406`）是**插件确实落过模板**的直接日志。

### 6.4 操作结论（本轮真机坑的正解）

1. **改了 `apps/inrt` / 引擎后，想让「设备打的包」带上改动**：只重建 PC 侧 `assets/template.apk` **不够** ✗ —— 必须让设备**不落在 ②/④**：
   - **卸载插件**（或确认缓存不是插件产的：看上面 6.2 的 marker 文案）；
   - **清 `files/apk-builder/`**（或该 `<versionCode>` 子目录）；
   - **升宿主 versionCode**（`:268-269` 分目录机制 ⇒ 自然重走 ③）。
2. **若链路依赖插件路径** ⇒ **必须重建并更新插件** ✓（插件模板是**插件自己的资产**，PC 侧重建内置模板对它无效）。这就是本轮「改了模板但产物行为不变」的根因。
3. 排查顺序建议：**先看缓存来源标记 + `<versionCode>` 目录** → 再看 6.3 的 logcat → 最后才怀疑模板本身。

### 6.5 本节证据边界（**别当全都验过**）
- **实测（Lead，K40，dev-1518→1520）**：装插件时产物**没有** PC 侧刚重建的修复；卸载插件后重打，logcat 的 `source`/`detail` 变成「宿主缓存（内置模板与宿主 lib 合成）」且**三通道提示立刻可见** ✓。
- **读码（本节 6.1/6.2 的顺序、共享缓存路径、状态链与选择链不同、marker 语义）**：逐行读 `ApkBuilderPluginHelper.java`（行号已给）；**没有**逐条真机复验——例如「装插件但缓存为空时实际会走 ③ 内置合成」属**读码推断**，未实测。
- **未覆盖**：插件自身模板的来源与重建（见文末原注：插件模板需用新的 `:inrt` release 单独重建）。
